## BTRFS (evo-x2)

**Subvolume layout:** `/` mounts `@` (root). `/home` lives INSIDE `@` (intentionally snapshotted) — EXCEPT `/home/hermes`, its own `@home-hermes` toplevel subvolume since 2026-09-15 (plain fstab mount while hermes is enabled, deliberately NOT the `@cache-home` automount style — tmpfiles rules under `/home/hermes` + automount is the shadow-dir class; btrbk-covered with its own BOUNDED pool retention `target_preserve 14d 4w` vs `@`'s forever — the motivating problem was every deleted agent-workspace byte being hoarded pool-side forever; migration runbook `docs/services/hermes.md` + `scripts/migrate-hermes-subvol.sh`; first pool receives landed 2026-09-18 (full Sep-16 send + incremental chain, verify gate OK on both prefixes; the 09-16/17 nightly sends were Zone-6 guard-killed, healed by manual `btrbk clean` of the mid-receive garble + re-run)). **`/nix` is a separate FILESYSTEM since the 2026-09-05/07 Samsung flip** (by-label `tlc`, BTRFS zstd on the Samsung; kernel nvme0/nvme1 enumeration FLIPS across boots — live 2026-09-14: nvme0n1p2; the old QLC `@nix` subvol at `/mnt/btrfs-root/@nix` was DELETED 2026-09-20 — pre-flight green (every boot entry's `init` path resolves on the live Samsung store, every ESP initrd present, rollback ladder 3/3 live), ~129G freed as the cleaner drained extents across `commit=300` transactions); the pre-flip claim "`/nix` lives inside `@`" is STALE. `/data` is a separate BTRFS partition (subvolid=5, toplevel). Only `@cache-home` (`~/.cache`) remains a separate top-level cache subvolume with automount (2026-08-17): `@go`/`@npm`/`@cargo` were retired — their contents moved to `/mnt/buildcache` (`GOMODCACHE`, `npm_config_cache`, `CARGO_HOME`) or were stale, and the leftover `~/go`/`~/.npm`/`~/.cargo` plain dirs hold nothing churning. `@cache-home` stays because it carries ~16 GB of LIVE app caches with no buildcache home (nix eval cache 6G, browser caches, gopls) — its exclusion from btrbk `@` snapshots is its entire job. Rust `target/` dirs symlink to `/mnt/buildcache/rust/<project>` (USB SSD) to avoid COW fragmentation; sccache (`/mnt/buildcache/sccache`) content-addresses the compile artifacts.

**Snapshots:** Root (`@`) daily via btrbk at 23:00, `/data` (toplevel) daily at 23:30. Local root retention = `snapshot_preserve_min 2d` (keep-all floor) + `snapshot_preserve 3d 1w` (first-of-day / first-of-week) — so the live set is ~2 weeklies + ~3 dailies, NOT "3d+1w" flat. The prune phase runs AFTER the sends, so guard-killed runs DEFER it: the 2026-09-26..29 zone-6 kill streak (4 consecutive 23:00 runs SIGTERM'd, the last mid-catch-up at trip #1441) held 12 expired subvols live past their windows until the first successful run prunes the whole backlog in one pass (tracked in docs/todo/storage.md). /data unchanged at 14d+4w. Staggered BEFORE nix-gc (00:00) so expired snapshots free extents before GC runs. Snapshot freshness verified daily (alerts if >3 days old). `/mnt/btrfs-root` (subvolid=5) automounted for btrbk access.

**Snapshot-pinning doctrine (2026-09-25 sweep):** BTRFS CoW means `rm` of a large tree frees its extents only when the LAST local snapshot referencing them expires — btrbk pool receives are separate extents on the pool and never pin NVMe/Samsung bytes. Worst-case local pin windows from `snapshots.nix` retention (root window RECONCILED 2026-09-25 against btrbk 0.32.7 `schedule()` source + live `.snapshots` inventory): root `@` (3d 1w, min 2d) = **2w sharp**; `/data` (14d 4w, min 7d) ≈ 4-5w; pool `services/*` (7d 4w) ≈ 4w (16T headroom, rarely binding); `hot/forgejo` (3d) ≈ 3d. **btrbk retention buckets are CALENDAR-anchored, not age-based**: `3d` = all snapshots from the last 3 day-buckets (days start 00:00), `1w` = the FIRST snapshot of each of the TWO calendar weeks covered (current + previous; weeks start Sunday per btrbk's `preserve_day_of_week` default, matching the observed Sunday-dated weeklies) — the live root set is ~4-6 snapshots (4 dailies + 2 weeklies), and the "12-day-old weekly" seen 2026-09-25 was IN-SPEC, not a prune gap: a weekly landing at a week start (Sunday 23:00) survives until the first run after its second Sunday boundary, i.e. exactly 14 days. /data's 25d-oldest weekly (vs 28d 4w nominal) is the same calendar math within its budget. A file created AND deleted between two nightly snapshots may never be pinned at all. The large intentionally-deletable trees — budget the pin window before deleting "for space":

**Rescue snapshot tier + snapshot canary (2026-09-12 glob-delete incident):** `sudo btrfs subvolume delete /mnt/btrfs-root/.snapshots/@.20260*` — typed where `du` was meant — glob-deleted ALL six local snapshots at 02:20 (sudo is PASSWORDLESS here; `btrfs subvolume delete` has no confirmation). Protections shipped same day: (1) **`services.btrfs-rescue`** (`platforms/nixos/system/btrfs-rescue.nix`, VM-tested) keeps `keep` (2) read-only snapshots of `@` in `/mnt/btrfs-root/.rescue/` — outside btrbk's snapshot_dir so `.snapshots/*` globs cannot reach it, dir pinned `chattr +a` (append-only blocks subvol-delete even for root) with a per-run SELF-TEST stamping `btrfs_rescue_append_only` (a kernel that stops enforcing +a flips the Gatus check red — no phantom protection); (2) **fish guard** (`platforms/common/programs/fish.nix` `btrfsGuardHook`, interactiveShellInit only) — `sudo/btrfs … subvolume delete` (incl. `sub del` abbreviations) and `rm`/`mv`/`trash` on `.snapshots`/`.rescue` paths print the post-glob-expansion target list and require typing `delete`; scripts/bash/non-interactive fish unaffected; (3) **metrics + Gatus** — `btrfs_root_snapshots` / `btrfs_rescue_snapshots` ("BTRFS Snapshot Canary" / "BTRFS Rescue Snapshots" checks, anchored pat). Deliberately NOT `chattr +a` on `.snapshots` itself — btrbk prunes there nightly. **Incremental-chain doctrine (research-verified against btrbk source):** with zero local snapshots exactly ONE full non-incremental send is unavoidable — that is btrbk's designed self-heal (uuid-based source↔target matching; received subvols get fresh uuids and cannot be re-matched; receive-back is space-infeasible). NEVER configure `incremental strict` for these instances — it converts self-heal into no-backup. Rules: never hand destructive one-liners with globs to an operator without a confirmation layer; the rescue tier doubles as a preserved incremental-send parent (uuid-matched against the pool target) if `.snapshots` is ever wiped again.

**Backups:** btrbk sends every nightly root+data snapshot to the BTRFS RAID1 HDD pool (`/mnt/pool/backups`) since 2026-08-16/17. Root receives are kept FOREVER (`target_preserve_min = "all"`, user decision 2026-08-21 — CoW extent sharing makes snapshot count ~free; every deleted NVMe byte is pinned pool-side, which is the point; revisit at ~50% pool usage). /data keeps 30d 12w (Docker/DB churn would grow unboundedly otherwise), plus pool-side snapshot instances. The NVMe is no longer a single point of failure for snapshots. Remaining exposure: the pool is same-chassis (survives NVMe death, not the house); offsite leg IMPLEMENTED 2026-09-11 decision → 2026-09-22 build: Hetzner StorageBox BX11 + BorgBackup (client-side repokey-blake2, port 23; rationale + implementation blueprint in `docs/research/hetzner-storagebox-borgbackup.md`) — deployed DORMANT (`services.offsite-borg.enable = false`, system-796); go-live is owner-gated (StorageBox hostname/username + `ssh-keyscan -p 23` host-key pin), runbook `docs/services/offsite-borg.md`. **Per-service subvolume doctrine (2026-09-15):** each service's state belongs to exactly ONE snapshot set — A (plain dir under `@`, default), B (own subvol + own btrbk entry; pool `services/*` precedent), or C (unsnapshotted `chattr +C` subvol, dump-only RPO; the Samsung Phase-2 `hot` tier). Nested subvols are silently EXCLUDED from `@` snapshots (backup gap AND a silent rollback-semantics change), and `nodatacow` only sticks in never-snapshotted subvols — full analysis + decision triggers: `docs/planning/2026-09-15_per-service-btrfs-subvolumes-analysis.md`.

**Compression:** `compress=zstd` on `/` (filesystem-wide — covers all `@` subvolumes). `/data` uses `compress=zstd:3`. NOT `compress-force` (against upstream Btrfs guidelines). BTRFS compression is filesystem-wide: setting it on any mount applies to ALL subvolumes on that filesystem. Only `subvol`/`subvolid` and VFS options like `noatime` are per-mount-point. Beyond space savings, compression is a **flash-ENDURANCE lever on QLC** — fewer/larger compressed writes mean less write amplification and SLC-cache pressure (the LWN "Btrfs at Facebook" 824855 framing; full sweep: `docs/research/2026-09-05_btrfs-internet-sweep-vs-systemnix.md`). **Csum-error growth rate is the bounded-vs-progressing damage discriminator**: a static csum-error count (scrub delta ≈ 0 across runs) means old, bounded damage — repairable by deleting affected files; a GROWING count means active media/churn damage — hardware-first triage. Probe pair: `smartctl` media_errors + before/after scrub delta (2026-09-06 /data lesson: imported heuristics are claims; local operator history outranks them — the corruption traced to an operator-inflicted unsafe partition shrink, not failing hardware)

**Commit interval:** `commit=300` on `/`, `/data`, and (since 2026-08-27) the automounted subvol/toplevel mounts `~/.cache` + `/mnt/btrfs-root` — every BTRFS mount on the box now follows the doctrine (the two automounts silently defaulted to 30s before). Default 30s commits metadata every 30s; on QLC NAND this is ~10x write amplification for metadata alone. `commit=300` batches metadata commits to every 5 min, preserving SLC cache blocks for foreground I/O. Data loss window on crash: 5 min (acceptable with daily btrbk snapshots + CoW journaling consistency).

**Scrub:** `autoScrub` weekly on `/`, `/data`, `/mnt/pool` — all three scrub units' ExecStart is a DEFERRAL GUARD (`snapshots.nix` `scrubGuard`): skip cleanly (next weekly window retries) when IO PSI some avg10 ≥20%, zram ≥80%, or any btrbk/balance send is streaming. **The guard was DEAD CODE from 2026-08-31 until 2026-09-29** (found by the memory-guard scrub-stop-phantom investigation): the ExecStart override targeted the stray attrnames `btrfs-scrub--`/`btrfs-scrub-data`/`btrfs-scrub-mnt-pool` — unit FILES systemd never starts (the weekly timers pull the TEMPLATE instances `btrfs-scrub@-`/`@data`/`@mnt-pool`), so every scrub ran raw and the 2026-09-26..28 storm scrub read 5.9 TB straight through. The override now sits on the template (`"btrfs-scrub@".serviceConfig.ExecStart` with `%f` — systemd expands %f to the mountpoint, keeping the wrapper's argument contract). LESSON (the stray-attrname class): a `systemd.services.<name>` attr that doesn't match an upstream-defined unit CREATES a dormant unit file instead of erroring — an override that "evals green" can guard nothing; verify the overridden attrname is the unit the timers actually instantiate. Live lesson: the 2026-08-31 14:30 boot stacked Persistent scrub catch-up on `/` AND `/data` on top of the btrbk-data full re-send — three full-disk readers on one QLC NVMe (plus flm cold loads) = the 16:34 freeze (incident #3). A perpetually deferred scrub shows as never-finished in btrfs-health metrics (Gatus-visible), never phantom-green. Changed from monthly — frequent reboots (58 unsafe shutdowns) almost never let a monthly scrub complete before interruption. Scrub results collected as Prometheus metrics (`btrfs_scrub_errors_total`, `btrfs_scrub_status`, `btrfs_scrub_error_free`) via `btrfs-health-metrics` every 5 min. Gatus alerts on Discord when `btrfs_scrub_error_free` drops to 0 (errors found).

**TRIM:** `services.fstrim.enable = true` with daily schedule (`OnCalendar = lib.mkForce "daily"`). All BTRFS/ext4 mounts explicitly set `nodiscard` — QLC NAND causes 253ms discard latency → BTRFS commit stalls → WDT reset. Daily fstrim at idle I/O priority (`IOSchedulingClass=idle`, `Nice=10`) keeps the NVMe controller's FTL informed of freed blocks so the SLC cache stays healthy. BTRFS CoW churn (every write = new block + unreported free block) re-exhausts the SLC cache within 22-47h on weekly TRIM — daily runs only trim ~24h of churn (~50-100 GiB, ~10-15 min) vs the initial 446 GiB backlog (1h14m). Monitored via Gatus (`system_fstrim_duration_over_threshold`) when trim takes >30 min.

**bees dedup:** NOT recommended on this hardware. bees does random 4KB reads across the entire filesystem to hash blocks — QLC NAND random IO sensitivity makes this counterproductive. `auto-optimise-store` (whole-file hardlink dedup) captures the biggest win with zero extra IO.

**BTRFS quotas (qgroups):** NOT enabled. `btrfs quota enable` adds metadata overhead to every transaction for qgroup accounting. On QLC NAND, this I/O tax is not worth per-subvolume usage tracking. If the NVMe is upgraded to TLC/MLC, enable quotas and re-add the qgroup metrics (removed from `btrfs-health.nix` — search git history for `btrfs_qgroup_referenced_bytes`).

**Scrub monitoring:** `btrfs-health-metrics` (every 5 min) collects `btrfs_scrub_errors_total`, `btrfs_scrub_status`, `btrfs_scrub_duration_seconds`, and `btrfs_scrub_error_free` via `btrfs scrub status`. Requires `CAP_SYS_ADMIN` (the kernel's `btrfs_ioctl_scrub_progress` checks `capable(CAP_SYS_ADMIN)`). The service overrides `harden {}`'s empty `CapabilityBoundingSet` with `CAP_SYS_ADMIN`. Gatus "BTRFS Scrub Errors" alerts on Discord when `btrfs_scrub_errors_present` is 1; the incomplete leg moved to "BTRFS Scrub Incomplete" (`btrfs_scrub_incomplete_unexplained` 1) and stays green while the guard's churn window holds `btrfs_scrub_deferred_by_guard` 1 — the old single "BTRFS Scrub Health" check (on the `btrfs_scrub_error_free` composite, still emitted) falsely red on every RUNNING or guard-deferred scrub. **Space-pressure monitoring (2026-08-18):** the same collector also emits `btrfs_health_critical` / `btrfs_health_warning` composites from `classify_btrfs_health()` (single source of truth with the state log; CRITICAL = unalloc<5% or meta>90% — the 2026-06-26 ENOSPC crash precursor) and Gatus "BTRFS Chunk Health" alerts on `btrfs_health_critical 0`. Before this, the check only asserted the raw metrics EXISTED — a phantom green while `/` sat at live CRITICAL unalloc=4%. Note: csum failures during `btrfs send`/reads do NOT feed scrub counters — only an actual scrub detects them; the 2026-08-18 01:50 btrbk EIO (root 256 ino 1331118, /data) was invisible to scrub metrics until the next weekly scrub (tracked in docs/todo/storage.md P0).

**Balance (chunk consolidation):** Weekly automated balance in `btrfs-health.nix` prevents the 2026-06-26 metadata ENOSPC crash mode. Metadata balance (`-musage=50`) runs Mon 04:00, data balance (`-dusage=50 -dlimit=10`) runs Mon 05:00 — staggered after metadata (which is fast) and before nix-gc (00:00 next day). Both are guarded by `btrfs-chunk-check`: skip if a balance is already running, skip if device-unallocated < 5 GiB (metadata) or < 10 GiB (data) bounce room. Data balance is bounded (`-dlimit=10` = max 10 chunks per run, ~10 GiB) to prevent runaway IO. Both use `ProtectSystem = false` (balance ioctl needs raw filesystem access) + `CAP_SYS_ADMIN`.

**GC guard — NEVER gate reclamation on a % of device-unallocated (fixed 2026-08-21):** `btrfs-gc-guard` (ExecStartPre on `nix-gc` + `nix-build-cleanup`) originally blocked GC when `UNALLOC_PCT < 10` — on a 723 GiB device that demands 72 GiB of chunk-level unalloc, a level GC itself can NEVER restore (deleting files frees extents WITHIN allocated chunks; only balance returns chunks). Result: a 5-night deadlock (2026-08-17..21, root 96%, GC failing nightly while ~20 GiB sat idle, 44 generations accumulating). Correct gates (current): absolute `UNALLOC_BYTES < 5 GiB` floor (same figure the balance jobs use) + `META_PCT > 90` hard block (the real crash precursor). General rule: space-recovery automation must be gated on the resource it actually consumes (a few GiB of metadata churn room), never on a threshold the recovery action cannot itself satisfy.

**Manual `btrfs balance` at 0% unalloc froze the box (2026-08-24 crash #3):** root sat at 0% chunk-unalloc (gc-guard warned; both scheduled balance jobs correctly self-skipped), then a manual `sudo btrfs balance start -dusage=10 -musage=10` with zram 85% full + ClickHouse at 100% CPU drove IO PSI to 99% and froze the kernel DEAD in 2.5 min (journal stops mid-entry 06:20:52, no panic, WDT never fired — the scheduler-livelock class). Chunk-headroom recovery runbook (now embedded in gc-guard + both balance skip messages): (1) `rm /btrfs-emergency-reserve` to free extents FIRST, (2) wait for QUIET (zram <80%, low IO PSI), (3) `sudo ionice -c 3 btrfs balance start -dusage=5 -dlimit=2 /`, (4) re-provision the reserve. Both balance services carry Guard 0 since 2026-08-24: skip when IO PSI some avg10 ≥20% or zram ≥80%. The DAS was ALSO absent the whole 2-day boot (all USB disks missing since before the 2026-08-22 05:55 boot — physical reseat needed, `scripts/das-link-recovery-check.sh`) — an aggravator, not the freeze cause. Related: after crash reboots VERIFY `/run/booted-system` == `/run/current-system` — the 06:31 boot loaded an Aug 16 rollback generation (no XFS mount, no guards) and ClickHouse wrote telemetry to the ROOT fs for 13 min until the 06:42 deploy re-mounted XFS over it ("Directory to mount over is not empty") — shadowed data under the mount needs manual cleanup.

**Emergency reserve:** A 10 GiB `fallocate`d file at `/btrfs-emergency-reserve`, created on boot by `btrfs-emergency-reserve.service`. Delete it (`rm /btrfs-emergency-reserve`) for instant 10 GiB free space when you need to run balance, repair, or survive metadata ENOSPC. The file is NOT auto-recreated after deletion — manually re-provision with `sudo systemctl start btrfs-emergency-reserve` after recovery. Tracked via Prometheus metrics (`btrfs_emergency_reserve_present`, `btrfs_emergency_reserve_bytes`) and Gatus alerts on Discord if the reserve goes missing. **Snapshot-pinning caveat (T14, 2026-09-11):** the reserve's extents are PINNED by daily btrbk root snapshots — `rm`'ing it frees its 10 GiB only as the pinning snapshots expire (root pin window = 2w sharp — calendar-anchored, see the Snapshot-pinning doctrine above), not instantly, so "instant 10 GiB" holds only when the newest snapshots don't yet reference the file's extents (true at cold provision, weaker at steady state). A periodic rewrite timer was evaluated and NOT adopted: extra CoW churn for near-zero benefit while chunk-unalloc (~222 GiB as of 2026-09-02) is the real headroom — the `unalloc >10G` re-check stays the safety gate before any space-hungry op, and the reserve is the last-ditch margin, not the first. ## BTRFS & Filesystems

- **All mounts set `nodiscard`** — QLC NAND (`discard=async`) causes 253ms discard latency → BTRFS commit stalls → WDT reset. Daily `fstrim.timer` (idle priority) handles TRIM.
- **SLC cache exhaustion is the root crash cause** — QLC NAND uses an SLC write cache that BTRFS CoW churn exhausts within 22-47h when fstrim is weekly. With cache gone, every write hits QLC directly (~253ms), building an exponential I/O queue that freezes the kernel → WDT reset. Daily fstrim + `commit=300` mitigates this. See `docs/gotchas-archive.md` for full incident narrative.
- **`commit=300` on all BTRFS mounts** — Reduces metadata write frequency ~10x vs default 30s, preserving SLC cache blocks. Data loss window: 5 min (acceptable with daily snapshots + CoW journaling).
- **ext4 uses bare `discard`** — `discard=async` on ext4 → mount fails → emergency shell.
- **Non-`nofail` mounts = boot hazard** — Any non-root mount without `nofail` that fails brings down `local-fs.target`.
- **Compression is filesystem-wide** — `compress=zstd` on any mount applies to ALL subvolumes. Only `subvol`/`subvolid` and VFS options are per-mount.
- **`/nix` on its own `@nix` subvolume (migrated 2026-08-17)** — Was a plain dir inside `@`, so btrbk snapshots AND pool sends carried the ~47 GiB nix store (CoW-pinned up to 30d/12w). Store is rebuildable — needs no snapshots. Sibling subvolumes are never part of a snapshot of `@`. Migration: `scripts/migrate-nix-subvol.sh` (reflink bulk copy via `cp -a --reflink=always` — rsync has NO `--reflink` flag, that is cp syntax; recurred 2026-09-16 in migrate-hermes-subvol.sh v1); old `@/nix` deleted post-verification, space frees as snapshots expire. `/home` still lives inside `@` (intentionally snapshotted).
- **`rm` doesn't free space when snapshots reference data** — Reclamation happens as btrbk snapshots expire (14d retention).
- **`findmnt -o MAJ:MIN` on btrfs returns the ANONYMOUS superblock devt (`0:48`), never a member's devt** — btrfs superblocks get anon device numbers; comparing them against `lsblk` member devts can NEVER match (would misclassify every healthy mount as stale; caught by `tests/test-pool-recovery.nix`). For mount identity on btrfs use the fs **UUID** (`findmnt -no UUID` vs `lsblk -nrno UUID <member>`) or a real-I/O probe.
- **`compsite` is memory-intensive** — Needs `MemoryMax=2G` minimum on a 47 GiB nix store. Runs every 6h (not 5min).
- **`/tmp` tmpfs capped at 48 GiB** — Via `systemd.mounts` (static `tmp.mount`). NEVER use `fileSystems."/tmp"` — generates runtime fstab entry → unmount failure.
