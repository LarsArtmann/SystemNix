## Systemd

- **`chmod` on a freshly chown'd (no-longer-root-owned) path needs CAP_FOWNER — CAP_DAC_OVERRIDE does NOT cover chmod** (2026-09-20, hot-user-caches + forgejo-subvol-bootstrap): a root bootstrap that creates a subvol, `chown`s it to the service user, then `chmod`s it EPERMs at the chmod under `harden{}`'s listed caps unless `CAP_FOWNER` rides along (chown succeeds via CAP_CHOWN, making the path non-root-owned; the kernel gates chmod on ownership/CAP_FOWNER specifically — the textfile-collector FOWNER class in a bootstrap shape). Live: `chmod: changing permissions of '/mnt/hot/users/lars/cache/nix': Operation not permitted` → unit failed → exit-4 on every activation.
- **Sandbox setattr with the SETGID bit EPERMs even with the cap in the bounding set — reorder or drop the bit, do not chase caps** (2026-09-22, discordsync attachments bring-up): `chmod 2770` on a dir whose group is outside the unit's groups EPERM'd with CAP_CHOWN+CAP_FOWNER+CAP_DAC_OVERRIDE+CAP_FSETID ALL in the bounding set (NoNewPrivileges=true), and `rsync -a` mode-preservation hit the same class on every foreign-group dir — while the identical `chmod 2770` succeeds as a plain user on the SAME filesystem outside the sandbox (measured live; mechanism unresolved — suspect NNP/capability effective-set handling at exec under the systemd sandbox). Robust patterns that sidestep the class entirely: (1) `chown root:root` → `chmod 0770` (NO setgid bit — it is decorative when the writer runs as the dir's owner) → `chown user:group`; (2) rsync with `--no-perms` + tolerance for perm-only stderr (any non-"failed to set permissions" line still fails the copy) + content-only verify (`grep -E '^[><ch]'` on itemized output). Root-context repro of the mechanism is queued (P0, docs/status/2026-09-22_14-35).
- **AmbientCapabilities (NOT CapabilityBoundingSet) is what GRANTS a cap to a non-root `User=` — the bounding set only LIMITS** (2026-10-07, geometrikks zero-ingestion; lesson first learned 2026-09-06 mail-relay, never landed here until the class repeated): a `CapabilityBoundingSet = "CAP_DAC_READ_SEARCH"` on a non-root unit RENDERS into the unit file yet the process runs with an EMPTY effective set — every foreign-owned path read EACCESes. Root processes DO acquire bounding-set caps, which is exactly why root-unit precedents (cv-backup, backup collectors) mislead when copied onto user units. Pair every cap grant under a non-root `User=` with `AmbientCapabilities = <same caps>` (`NoNewPrivileges=true` is fine — ambient caps survive execve on kernel ≥4.14; caddy binding 80/443 as user caddy is the standing live precedent). The failure mode is NEAR-silent at the app level — v0.19.0 geometrikks DID log every unreadable file at ERROR, but mislabeled EACCES as `Log file does not exist … waiting for it to appear` (upstream #302), so a diagnosis grep for read-errors finds nothing while an existence-grep finds the whole story; `Total processed: 0` while `/health` stays 200 for 8+ days. Probe with `systemctl show -p AmbientCapabilities <unit>`, `/proc/<pid>/status` `CapEff` (decode: `python3 -c "v=int('0x4',16); print([n for b,n in {0:'CHOWN',1:'DAC_OVERRIDE',2:'DAC_READ_SEARCH',3:'FOWNER',4:'FSETID'}.items() if v>>b&1])"` — CapEff must contain the granted caps; an empty CapEff with a non-empty rendered BoundingSet IS this bug), and when diagnosing ingestion: grep the journal for the app's ACTUAL message vocabulary (`does not exist`), not just the phrases your hypothesis predicts (`processed`, `error`). Full narrative: `docs/status/2026-10-07_13-11_geometrikks-zero-ingestion-ambient-cap-status.md` + the 12-35/17-03 addenda (the "silent swallow" reading was falsified 2026-10-07 — grep artifact).
- **A oneshot that must precede a mount: `unitConfig.DefaultDependencies = false` AND pull it from the on-demand `.mount` — NEVER from a fstab `.automount`** (2026-09-20 + 2026-09-25, hot-user-caches; two cycles, two fixes): (1) ACTIVATION cycle — default service deps add `After=sysinit.target`, but sysinit is After=local-fs.target and the automount the bootstrap must precede sits in the local-fs transaction → local-fs → automount → bootstrap → sysinit → local-fs ordering CYCLE ("Transaction order is cyclic"; at boot this class can wedge local-fs outright). `DefaultDependencies = false` removes it; the real dependency (the toplevel mount) must be the explicit `after`/`wants`/`RequiresMountsFor` — the default chain contributes nothing but the cycle. (2) BOOT cycle — survives (1): NEVER wire `wantedBy=`/`before=` against a fstab `.automount` unit from a unit that must precede the mount. At boot the automount sits inside the local-fs/sysinit transaction together with `systemd-tmpfiles-setup.service`, and the closing edge makes systemd's cycle breaker DELETE THE TMPFILES START JOB ("Job systemd-tmpfiles-setup.service/start deleted to break ordering cycle") — the main tmpfiles pass then NEVER RUNS, silently: `/run/binfmt` (nix sandbox `extra-sandbox-paths`) missing → EVERY sandboxed build dies `getting attributes of path "/run/binfmt"` at "setting up the build environment"; `/run/systemnix/sev1` missing → sev1-bridge 226/NAMESPACE ×2900; `/run/lock/systemnix-heavy`, `/run/lvm`, `/run/emeet-pixyd` too. Live 2026-09-24 22:35 — the FIRST boot after the hot-user-caches deploy (no reboot between deploy and boot = the cycle sat latent for 2 days). Detection traps: the journal shows tmpfiles-setup "Finished" from the INITRD instance (looks like it ran); `/run/systemd/units/invocation:` has entries only for the -dev passes; `stat -c %y /run` dates the loss but not the actor. The fix: pull the bootstrap from the on-demand `.mount` (`wantedBy`/`before` on `<escaped-path>.mount`) — the subvol only needs to exist before the FIRST REAL MOUNT, and the bootstrap then never enters the boot transaction at all. Regression-pinned by `tests/test-hot-user-caches.nix` (asserts tmpfiles-setup active + a probe tmpfiles rule applied after boot — only an actual BOOT catches transaction cycles). Belt: deploy.sh runs `systemd-tmpfiles --create --remove --exclude-prefix=/dev` after every switch (NO `--boot` — boot-only `D! /tmp` must stay boot-only or every deploy wipes /tmp); manual heal: `sudo systemd-tmpfiles --create --remove --exclude-prefix=/dev`. Follow-up worth doing: `boot.binfmt.preferStaticEmulators = true` (F-flag static qemu) drops `/run/binfmt` from extra-sandbox-paths entirely, making builds immune to this whole class.
- **NEVER declare a `fileSystems` mountPoint that is an HM `mkOutOfStoreSymlink` — systemd CANONICALIZES mount units through symlinks** (2026-09-20, hot-user-caches go-build): `~/.cache/go-build → /mnt/buildcache/go-build` turned the hot-disk subvol mount into `mnt-buildcache-go\x2dbuild.automount` — an autofs NESTED INSIDE the `/mnt/buildcache` autofs — failing at unit load (exit-4 every activation). A proper integration needs the HM symlink gated off AND a boot ordering that never loads the automount while the symlink exists (HM activates AFTER early-boot automounts); the go-build hot-cache relocation is parked in hot-user-caches.nix until that design exists.
- **`harden {}` ExecStart trap** — NEVER put `ExecStart`/`Type`/`RemainAfterExit` inside `harden {}`. Merge outside via `mkMerge`. Eval-enforced since 2026-09-14: `lib/systemd.nix` THROWS on any lifecycle key (Exec*/Type/RemainAfterExit/Restart) passed into `harden`/`hardenUser` — the illegal shape aborts evaluation with the fix in the message.
- **`runuser` + `harden {}` = PAM failure** — PAM can't complete session init. Run as `User` directly, add shell `runuser()` passthrough function.
- **Root → user-manager bus requires `--machine=<user>@.host --user` (systemd ≥254)** — sd-bus IGNORES a foreign `$XDG_RUNTIME_DIR` for `--user`: a root system unit calling `XDG_RUNTIME_DIR=/run/user/1000 systemctl --user …` dies "Failed to connect to user scope bus … Operation not permitted" (activitywatch-data-to-pool crash-looped every deploy on this until 2026-08-19). Use `systemctl --machine=lars@.host --user …` (machined proxies the connection from the host; verified live) and only treat stop-failure as fatal when the target process (pgrep) is actually still running.
- **`serviceOneshotDefaults` for oneshots** — `serviceDefaults` defaults to `Restart=always` which is INVALID for `Type=oneshot`. Use `serviceOneshotDefaults`.
- **`%h` not `$HOME` in ExecStart** — Hardened user services may NOT expand `$HOME`. Use `%h` (systemd specifier). Eval-enforced: `systemd-shape-audit.nix` class 4 flags a literal `$HOME` in system-declared user-unit Exec lines (HM-internal units are evaluated in the HM closure, not covered)
- **`switch-to-configuration` exit code 4** — Service in `start-limit-hit` blocks activation. `deploy.sh` runs `systemctl reset-failed` first. **nh wraps this exit 4 as its OWN exit 1** — deploy.sh greps the output for `Exited(4)` to keep the recovery path (post-switch restarts incl. `buildcache-usb-recovery`) reachable; the exit code alone cannot distinguish "activated with failed units" from "aborted".
- **A chronically-FAILING unit whose unit FILE changes exit-4s every activation that touches it (2026-09-09, root cause of the un-anchored-generation saga)** — stc RESTARTS units whose generated file changed; a timer-only oneshot in a permanent FAIL state (an owner-decided "keep alerting" stance) therefore exit-4s the FIRST deploy after ANY churn to its defining module — activation advances `/run/current-system` but skips the profile bump, and a reboot reverts (the Sep-8/Sep-9 `btrfs-verify-pool-backups` + snapshots.nix case: deploy was "green", generation never landed). Doctrine: never leave a unit in permanent FAIL that any deploy can restart — downgrade the chronic branch to WARN (`fatal=no` pattern, snapshots.nix verify) while REAL regressions (mount loss, device errors, root-backup staleness) stay hard-FAIL, and keep the chronic gap's visibility in layers activation never runs (OnFailure alerting, backup-coordination, Gatus). Diagnosis: `readlink /run/current-system` vs `readlink /nix/var/nix/profiles/system` after EVERY deploy that says "activation completed with failed units".

- **A doomed-but-restarting unit exit-4s activations WITHOUT any unit-file change (2026-09-09 16:20 flm class)** — the complement of the bullet above: with the flm EADDRINUSE corpse pinning :52626, every :52625 client connection (PMA/enricher, ~4-5 min cadence) re-requests a backend start ("restart immediately on client request") that dies in <1s; one landing INSIDE a switch transaction makes stc report `warning: the following units failed: fastflowlm.service` → exit 4 → profile bump skipped. Unit files were byte-identical across generations — stc never restarted it, the churn did. Worse: **stc's target cascade re-arms stopped-but-enabled sockets mid-transaction** (observed 2026-09-09 17:19:33 — "Listening on FastFlowLM … (public socket)" seconds into activation with no operator start, no mem-guard restore), so a manual `systemctl stop fastflowlm.socket` does NOT survive a deploy. Mitigation (deploy.sh, 2026-09-09): a pre-switch guard stops socket+service when the unit journal shows recent `bind: Address already in use`, and a post-switch guard re-stops them after the switch re-arms; consumers fail fast (ECONNREFUSED; PMA heuristic-commit fallback) until the reboot clears the corpse. Residual risk until reboot: a client connection in the seconds-scale window between stc's socket re-arm and its report — on exit-4 just re-run the deploy. Both guards fired as designed in the 2026-09-09 18:35 deploy (→ system-764, clean activation, profile bumped, 0 failed units at settle). SECOND re-armer found the same evening: the **memory-emergency-guard's restore branch** re-arms the socket BETWEEN deploys — it sees the stopped socket, assumes its own past sacrifice, and restores it within minutes while memory is healthy (live 17:56:24 + 18:44:55, "sacrifice sockets restored", 2 of maxRestoresPerDay=3, ~10 min restore cooldown); doomed-start churn then resumes and self-extinguishes only at the daily restore cap. Guard journal filter gotcha: its script output logs under syslog id `memory-emergency-guard-check` — `journalctl -u memory-emergency-guard` NEVER shows it (this artifact caused the original wrong rule-out). Post-reboot the whole interaction is gone (the deploy guards only fire on EADDRINUSE journals); a corpse-aware restore skip is a P1 candidate (docs/todo/stability.md).
- **`switch-to-configuration` ignores `restartTriggers` on oneshot+RemainAfterExit** — `deploy.sh` explicitly restarts the provisioner/storage-dir oneshots after `nh os switch`. EVERY new `*-storage-dir`/provisioner oneshot MUST be added to that restart list in `scripts/deploy.sh` or its fixes never re-run until reboot (bank-sync-storage-dir sat failed for 6 deploys before being added, 2026-08-19). Eval-enforced since 2026-09-14: `deploy-restart-audit.nix` cross-references every converger-pattern oneshot AND every oneshot+RemainAfterExit+restartTriggers unit (inert by construction) against the deploy.sh text — INDIRECTLY-enabled bridges (wantedBy=<service>) need a dedicated is-active-gated block because the loop's `is-enabled` gate skips them (cv-oidc-env, found by the audit 2026-09-14, is the reference block).
- **Secret-bridge oneshots need BOTH units restarted — and the provisioner loop CANNOT do it (2026-08-22 dnsblockd SSO outage)** — a provisioner-rotated Pocket ID secret reaches a consumer through a two-unit chain: `dnsblockd-oidc-secret` (oneshot, `RemainAfterExit=true`, rewrites the env file) → `dnsblockd.service` (reads `EnvironmentFile` at process start only). Neither restarts on deploy: the bridge is `wantedBy = dnsblockd.service` → **`is-enabled` returns rc=1 for indirect units, so the deploy.sh provisioner loop silently skips it**, and switch-to-configuration never restarts the daemon for a runtime-file change. deploy.sh has a dedicated block (is-active-gated) restarting bridge + daemon in order. The same shape applies to ANY consumer bridging provisioner secrets via env files (browser-history does the same pattern with `browser-history.service`). Symptom of a stale link: `invalid_client` on token exchange while the authorize step works. Full narrative: `docs/status/archived/2026-08-22_02-46_dnsblockd-oidc-secret-desync-diagnosis.md`
- **Pocket ID client rows can VANISH after a SQLITE_BUSY crash — "Client does not exist" ≠ secret desync (2026-08-22)** — under machine-wide IO pressure (crash-recovery night: btrbk sends + data-to-pool + zram refaults) Pocket ID's SQLite hit a fatal `database is locked` chain (health-check failure → exit 1 → restart), and after the 02:42 restart the `dnsblockd` OIDC client row was GONE from the DB (authorize → `The requested OAuth 2.0 Client does not exist`, `error=invalid_client` on `/authorize`). This is a DIFFERENT failure than secret desync (which 401s only at token exchange). The provisioner self-heals it on next run (client-missing → POST create + secret); manual probe to distinguish: `GET /authorize?client_id=...` → 302 `/interaction?...` = client OK, error redirect = client missing. Secret files surviving a DB recreation while the client is recreated = the desync class; DB losing the client row entirely = this class. Both healed by one provisioner run + the restart chain above. Full narrative: `docs/status/archived/2026-08-22_03-49_dnsblockd-oidc-outage-fixed-self-review.md`
- **`PathChanged` not `PathExists`** — `PathExists` fires immediately if file exists at unit start → re-fire loop → start-limit-hit. Use `PathChanged`. Eval-enforced: `systemd-shape-audit.nix` class 3 rejects PathExists/PathExistsGlob path-unit triggers (ConditionPathExists on services is the correct gate and is not flagged)
- **`WorkingDirectory` runs BEFORE `ExecStartPre`** — If ExecStartPre creates the dir, service fails with `status=200/CHDIR`. Set WorkingDirectory to a parent that exists.
- **`ReadWritePaths` entries must exist BEFORE the unit starts** — systemd builds the mount namespace before ANY ExecStartPre; a missing path aborts with `status=226/NAMESPACE` (an in-unit ExecStartPre mkdir can NEVER create its own ReadWritePaths). Create pool/data dirs via a mount-gated oneshot ordered `before` the service (atticd-storage-dir / google-sync-dirs pattern). Eval-enforced since 2026-09-14: `mount-gating-audit.nix` requires every ReadWritePaths entry under `/mnt/` to be gated by `RequiresMountsFor` (ancestor OR descendant form) or `ConditionPathIsMountPoint` — its first live catch: bank-sync-canary + immich-db-backup both wrote to /mnt/pool ungated (now fixed with RequiresMountsFor); ConditionPathIsDirectory deliberately does NOT count (the shadow-dir masking bug)
- **CPUQuota=200% default in `harden()`** — All services get a 2-core cap. Override per-service (AI services: 300-400%).
- **Docker services use `multi-user.target`** — NOT `graphical.target`.
- **`harden` vs `hardenUser`** — User services (systemd --user) MUST use `hardenUser`.
- **`findmnt`/`/home` probes are BLIND inside `harden{}` units (`ProtectHome = true` default)** — the unit's mount namespace replaces `/home` with an empty inaccessible tmpfs, so `findmnt -n /home/hermes` (or any /home path test) always fails with stderr suppressed — the `btrfs-verify-pool-backups` hermes gate sat as dead code and phantom-greened through the 2026-09-17 00:46 run while `@home-hermes` had ZERO pool receives (its first send had been guard-killed). Probe mount state via `systemctl is-active --quiet <name>.mount` instead (PID-1 truth, immune to ProtectHome); fixed in snapshots.nix same day.
- **`TimeoutStartSec` for ExecStartPre-heavy services** — systemd default is 90s. Services with slow pre-start (DB heal, DNS wait, state migration) exceed this during system switches (I/O contention). Set `TimeoutStartSec = "3min"` explicitly for discordsync (DB heal + DNS wait) and hermes (535 MB state migration). Without it, `nh os switch` reports "Failed to start" even though the service succeeds on retry.
- **`StartLimitBurst`/`StartLimitIntervalSec` in `serviceConfig` = SILENTLY IGNORED (CRITICAL)** — In systemd 261+, these directives are ONLY valid in the `[Unit]` section. Placing them in `serviceConfig` (which maps to `[Service]`) causes systemd to silently ignore them with a warning: `Unknown key 'StartLimitIntervalSec' in section [Service], ignoring`. Services with `Restart=on-failure` then restart INFINITELY with no limit. **Correct placement:** NixOS top-level options `systemd.services.<name>.startLimitBurst` / `.startLimitIntervalSec` (camelCase, outside `serviceConfig`), or `unitConfig.StartLimitBurst`. The `service-defaults.nix` helper documents this (lines 21-27); eval-enforced by `start-limit-audit.nix`.
- **`ExecStartPre = "+…"` is the escape hatch for privileged setup inside hardened units** — the `+` prefix runs that one command with FULL privileges (bypasses `User=`, `CapabilityBoundingSet`, `SystemCallFilter`, namespaces). Use it for ownership migration / chown-style preStart in units that are otherwise sandboxed: `crush-daily`'s in-sandbox `chown -R` SIGSYS'd at every boot (`~@privileged` blocks `fchownat`) AND would have EPERM'd anyway as the service User (2026-08-18; same pattern as browser-history's `+wait-server` gate). Alternative for the syscall part: `SystemCallFilter = lib.mkAfter [ "@chown" ]` (last rule wins) — but `+` is simpler and actually works as root. **`!` is the NARROWER sibling (systemd.service(5), verified 2026-09-10 against the local man page)**: it ONLY bypasses `User=`/`Group=`/`SupplementaryGroups=` — sandboxing (namespaces, `CapabilityBoundingSet`, syscall filter) STAYS applied. Prefer `!` when root identity alone suffices and the sandbox is compatible (dots' mkService uses it for dir chown preStart); `+` remains REQUIRED when the command needs capabilities outside the bounding set (the CAP_DAC_OVERRIDE textfile-collector class)
- **A `+`-privileged readiness gate MASKS the permission denial it gates against (2026-09-09 overview/daemon socket)** — overview's `+wait-daemon` ExecStartPre probed `/run/project-discovery/daemon.sock` as ROOT (root bypasses DAC), passed green, then the overview process itself (User=overview) got EACCES dialing the 0600 `lars:users` socket → exit 69 → start-limit-hit → exit-4'd activations. Two stacked causes: the LOCKED project-discovery-daemon rev `4f6e3c8` predated `PROJECT_DISCOVERY_SOCKET_MODE` (the env var was set to 0666 but the binary created the socket 0600), and the gate's `+` hid it. Rules: (1) when a locked input ignores a config env var, check whether the PINNED REV implements it before blaming the config (git grep at the locked rev); (2) readiness gates that assert the SERVICE USER can reach a resource must probe AS that user — a root-probe gate is a phantom green for exactly the DAC class it exists to catch. Socket now 0666 (configuration.nix `socketMode`), daemon ≥ `1a31c1a` honors it.
- **Timer-driven oneshots must NOT also carry `Restart=on-failure` with `RestartSec` ≈ the timer cadence** — the restart-retry and the next timer fire land as two start requests in one window; the rejected one counts against the rate limit and ONE failed run cascades into a self-re-arming `start-limit-hit` that blocks runs for hours (browser-history-agent 2026-08-18: `RestartSec=5min` + 5-min timer + `burst=2/1800s` → alternating blocked/success fires all day). The timer IS the retry mechanism: `Restart=no` + a generous short-window burst (`5/300s`). Eval-enforced since 2026-09-14: `systemd-shape-audit.nix` class 2 rejects ANY matching-timer unit with `Restart != no`; deliberate bounded-retry exceptions (rapid retries that self-extinguish long before the next timer fire, e.g. forgejo-ensure-repos 3×5s vs daily timer) go in `services.systemd-shape-audit.allowTimerRestart` with a justification comment
- **NEVER grant service access via home-dir ACLs — bind-mount instead; NEVER `chown -R`/recursive-chmod across a unit that has Bind*Paths** — (1) any later `chmod` on an ACL'd home dir rewrites the ACL _mask_ and silently kills every named entry while `getfacl` still lists them (`mask::---`, hermes 2026-08-20); (2) systemd builds the mount namespace BEFORE ExecStartPre, so a recursive ownership walk EROFS-es into the read-only bind and crash-loops the unit (hermes down 09:18→09:35, 2026-08-20) — and `find -xdev` does NOT protect (same-filesystem binds share st_dev); prune the exact bind path. Eval-time WARNING guard: `chown-vs-bind-audit`; regression test: `tests/test-hermes.nix`
- **A perms-heal fast path must probe EXACTLY the predicate set the heal repairs — ownership AND write bits, across the whole tree, not just the root** (2026-09-20 cv-state-perms incident): the probe checked only ownership, went phantom-green while cv-owned-but-readonly dirs (store-mode copies: nix store trees are 0555 and plain `cp -r` propagates that into the state dir) made the upstream `rm -rf assets` EPERM → cv-server start-limit-hit → exit-4 deploy. Rules: (1) fast-path predicate == heal repair set (`! -user u -o ! -group g -o ! -perm -u+w`, all three, whole tree); (2) find's `-perm`/`-user` test the symlink ITSELF (mode 0777) — safe against read-only store targets — but split heal chmods by `-type d`/`-type f` so nothing chmods THROUGH a symlink; (3) `chmod` on a freshly `chown`'d non-root-owned path needs CAP_FOWNER even when CAP_DAC_OVERRIDE is present (see the 2026-09-20 FOWNER rule); (4) journal a heal summary (count + sample + convergence check) so a RECURRING writer stays visible instead of an anonymous green. Sibling audited same day: hermes-perms' fast path now walks child ownership too (mode drift deliberately unprobed — the exec-preserving `X` chmod semantics have no find predicate).
- **Wedged `switch-to-configuration` blocks ALL deploys (exit 11 "Could not acquire lock")** — nixpkgs' Rust switch-to-configuration can complete every activation step, print its final report, and then hang forever (suspected missed dbus `JobRemoved` signal) while holding an flock on `/run/nixos/switch-to-configuration.lock`. Every later deploy then fails `Could not acquire lock` until the zombie PID is killed or the machine reboots (live incident 2026-08-18 13:44+: all work done at 13:44:08, process still wedged an hour later, next deploy exit 11). deploy.sh detects a >30-min-old stc holding the lock, prints the recovery command, and aborts; opt-in auto-kill via `DEPLOY_KILL_WEDGED_STC=1 nix run .#deploy`. Never auto-kill on age alone — a legit activation restarting a unit with a long `TimeoutStartSec` (btrbk-pool-seed: 6h) looks identical from the outside.

- **systemd-oomd kills nix-daemon during builds** — nix-daemon is the top memory consumer under `/system.slice` during builds (4-8G peak). Because it is **socket-activated**, an oomd kill triggers rapid restarts → `start-limit-hit` → daemon permanently dead → ALL nix operations fail. Fix: `ManagedOOMPreference = "omit"` + `OOMScoreAdjust = -1000` (`networking.nix`). Recovery: `sudo systemctl reset-failed nix-daemon.service && sudo systemctl start nix-daemon.service`. Pressure threshold is 60%/30s — tolerates transient spikes from nix builds, AI model loads, and Docker restarts while still catching genuine exhaustion; per-slice `ManagedOOMMemoryPressureLimit` matches (60%). Re-evaluate if kills recur

- **NEVER let any /tmp cleaner touch `systemd-private-*` — they are live service infrastructure, not stale tmp (forgejo 12-day mirror outage, 2026-08-18..30)** — systemd's PrivateTmp backs every service's `/tmp` with a host-side dir `/tmp/systemd-private-<boot-id>-<unit>-<rand>/` bind-mounted into the unit's namespace. The `tmp-cleanup` timer globbed `/tmp/*` and `rm -rf`d entries stale >4h WITHOUT excluding them (they are NOT dotfiles — the "dotfiles are protected" comment didn't cover this class; systemd's own tmpfiles-clean excludes them, custom cleaners must too). Forgejo's mirror-sync credential helper (`os.CreateTemp("/tmp/forgejo-clone-credentials-N")`, new in forgejo 15.0.x, enabled by the Aug 18 nixpkgs bump) then failed ENOENT on EVERY credentialed pull mirror for 12 days (~2,400 error lines/day; each failed sync aborts BEFORE the fetch — so all ~100 mirrors silently missed 12 days of upstream commits, while `updated_unix` kept advancing and the syncs LOOKED fresh). Self-perpetuating: a broken service writes nothing into its private tmp, so the dir always profiles as stale and cleanup keeps it deleted. Diagnosis traps that cost the investigation: the version-bump correlation was WRONG (the errored process ran the SAME `forgejo-lts-15.0.7` binary that runs clean today — diff 15.0.6→15.0.7 touches nothing in the mirror path), the "PrivateTmp checked, not on the main unit" note was WRONG (it is, via the nixpkgs module), and "mirrors still complete" was WRONG (runSync returns false before fetching). Fix: `systemd-private-*` exclusion in the tmp-cleanup loop (`scheduled-tasks.nix`), behavior-tested. - **Every new converger oneshot breaks EVERY host's eval until `scripts/deploy.sh` knows its name (deploy-restart-audit, fleet-wide 2026-09-19 hot-user-caches)** — `deploy-restart-audit.nix` cross-references the unit tree against the deploy.sh text at EVAL time: any `Type=oneshot` matching a converger pattern (`-storage-dir/-backup-dir/-dirs/-provision/-setup/-bootstrap/-oidc-secret/-oidc-env/-migrate`), or oneshot+RemainAfterExit with `restartTriggers`, MUST appear by name in `scripts/deploy.sh` — else `nix eval .#nixosConfigurations.evo-x2.config.system.build.toplevel` (and every deploy) dies on the assertion, on every host importing the module. Wiring procedure, in preference order: (1) provisioner restart loop (directly enabled units — `wantedBy` on ANY unit type, automounts included, generates the `[Install]` symlink `is-enabled` finds; re-run cost of an idempotent bootstrap is one existence check); (2) dedicated is-active-gated restart block for INDIRECT units the `is-enabled` gate skips (dnsblockd-oidc-secret / cv-oidc-env pattern); (3) `services.deploy-restart-audit.allowUnits` ONLY for upstream plumbing converged by its own module, with a justification comment where set. ## Boot critical-path discipline

Every unit `wantedBy = [ "multi-user.target" ]` GATES the login screen (`graphical.target` waits for multi-user). Rules learned 2026-10-06 (boot-speed deep research; boot was 3min 8s, userspace 115.3s of which ~97s was hermes' ExecStartPre):

- **NEVER put full-scan IO (recursive tree walks, `sqlite PRAGMA integrity_check` on GB-scale dbs, whole-disk scrubs) into the ExecStartPre of a multi-user-gated unit.** With `Type=simple` the ENTIRE ExecStartPre window gates multi-user: hermes' converged-tree `find` probe walk + unconditional 1.4 GB integrity_check cost ~96s per boot under a storm (the 2026-08-31 "full 3min" and the 2026-10-06 boot -1 "6min timeout + restart + orphans" were the same class). The fix shape: move probe+heal TOGETHER (never probe alone — phantom-green, cv-state-perms lesson 2026-09-20) into a post-start oneshot pulled by `<daemon>.wants` + `after = <daemon>.service` — same every-start convergence cadence, off the critical path (`hermes-perms-heal` is the reference).
- **Condition full-scan health checks on the failure signal, not the calendar.** sqlite deletes `state.db-wal` on the last clean close → a PRESENT `-wal` file is the unclean-shutdown signal; only then pay the integrity scan (the WAL-gate in hermes-migrate-state).
- **Boot-time convergence oneshots belong in `OnBootSec` timers (~2min), not `wantedBy = multi-user`** — `btrfs-rescue-snapshot` (36s) and `crush-hot-db-migrate` (37.5s) both gated login for convergence work no login needs. Watch the interactions: a timer-pulled service becomes STATIC (`is-enabled` rc=1) so deploy.sh's provisioner loop skips it — convergers whose name must stay deploy-covered need an explicit restart block there (deploy-restart-audit only needs the NAME in deploy.sh; the crush-hot-db-migrate block is the reference). `RemainAfterExit=true` + timer = the boot fire is the one effective run per boot.
- **Boot fsck on non-root data/cache disks is passno-driven and ON by default** (NixOS writes 2 for every non-root fs; there is NO `fsckPass` option in this nixpkgs — `fileSystems.<mp>.noCheck = true` is the knob). The buildcache cache SSD burned 49.9s per boot on fsck until 2026-10-06.
- **Boot-window IO-priority demotion for timer-fired oneshots** (OnBootSec 30s-2min): merge `ioTier.background` (or lower) so first fires yield to the desktop settle; BFQ only reorders under contention.
- Measure with `systemd-analyze time / critical-chain / blame` on a CALM boot — a boot measured under an IO storm (the freeze-19 recovery boot) conflates structure with storm amplification.

## D-state-safe job timeouts for boot-critical oneshots (2026-09-29)

**Never order a runtime service between an automount and its mount.** systemd's sandbox namespace builder `umount2(..., MNT_DETACH)`es autofs mounts in every forked child; the umount's path LOOKUP blocks on a _pending_ direct autofs (`/proc/<pid>/stack`: `umount2 → autofs_mount_wait → autofs_wait`), and the pending mount can only be satisfied by the mount job queued _behind that same service_ — kernel-level self-deadlock. SIGKILL is undeliverable (D-state) and `TimeoutStartSec` cannot complete the job (it only settles once the process does). Live 2026-09-29: `hot-user-caches-nix-bootstrap` (mount: `/home/lars/.cache/nix`) hung this way **on 4 consecutive boots (Sep 24, Sep 27 ×2, Sep 29) — it never completed successfully once**; the cache relocation never worked, and every nix invocation on the host (all agents' `flake check`/`build`/`print-dev-env`, direnv) parked in `autofs_wait` D-state — 84 processes, load 86, boot transaction stuck 3+h. **Fix (final): the bootstrap is DELETED** — subvolumes are provisioning state (`disko/samsung-tlc.nix` declares them; flake geometryGuards assert), fstab mounts directly (`x-systemd.mount-timeout=90s` bounds even a pathological mount). Pattern precedent: `snapshots.nix` cacheSubvolumes (`@cache-home`) — provisioning-owned subvol + automount, nothing runtime in between. **If a service MUST gate a mount** (forgejo-subvol-bootstrap: runtime-created subvol, deliberately not disko): `JobTimeoutSec` + `JobRunningTimeoutSec` (unitConfig) cancel the JOB and free the mount even though the wedged process survives until reboot. Emergency no-root mitigation for a live wedge: `XDG_CACHE_HOME=/tmp/x nix …` bypasses the automounted cache dir entirely.

## BFQ I/O Priority Tiers (evo-x2)

The evo-x2 has a 2TB QLC NVMe (Lexar NQ790) with an SLC write cache that BTRFS CoW churn exhausts within 22-47h. BFQ I/O scheduling prevents build storms from freezing SSH sessions and the desktop compositor.

**Tier system** (lower BE priority = higher I/O precedence):

| Tier              | Helper               | BFQ Class/Pri  | Services                                            | Purpose                                 |
| ----------------- | -------------------- | -------------- | --------------------------------------------------- | --------------------------------------- |
| Interactive       | `ioTier.interactive` | BE/1           | sshd                                                | SSH must always respond                 |
| Desktop           | `ioTier.desktop`     | BE/3           | niri, dms, pipewire, crush (wrapper)                | Compositor/audio must stay responsive   |
| Service (default) | `ioTier.service`     | BE/4           | Most services                                       | Default for unclassified services       |
| Heavy DB          | `ioTier.heavyDB`     | BE/5           | clickhouse, monitor365-server                       | Latency-sensitive databases             |
| Background        | `ioTier.background`  | BE/6           | signoz, discordsync, browser-history, ollama, attic | Standard daemons tolerating I/O latency |
| Build             | `ioTier.build`       | BE/7 + Nice=10 | nix-daemon, forgejo-runner, PMA                     | Batch builds and CI — lowest BE         |
| Maintenance       | `ioTier.maintenance` | idle + Nice=10 | fstrim, clamav                                      | Only runs when nothing else needs I/O   |

**Usage:** Import `ioTier` from `lib/default.nix`, merge with `harden {}` via `mkMerge`:

```nix
inherit (import ../../../lib/default.nix lib) harden ioTier;
# ...
serviceConfig = lib.mkMerge [
  (harden { MemoryMax = "1G"; })
  ioTier.background
];
```

**Crush wrapper:** The `crush` binary is wrapped with `ionice -c 2 -n 3 nice -n 5` (BE/3) via `writeShellApplication` in `base.nix`. Works in all contexts (interactive, scripts, MCP) — not just interactive shells like the old alias. Scheduled tasks (`crush-update-providers`) use the raw binary directly via `lib.getExe'`.

**DB-heal oneshot:** DiscordSync's 11 GB SQLite integrity check runs as `discordsync-db-heal.service` (Type=oneshot, RemainAfterExit=true) with its own 10-min timeout — extracted from ExecStartPre so deploy activation isn't blocked by DB recovery during build storms.

## Boot mirror (Samsung 2nd boot disk)

**Samsung 2nd boot disk (2026-09-18, `platforms/nixos/system/boot-mirror.nix`)**: `/boot-mirror` mounts the Samsung p1 ESP (`SAMSUNG-EFI`, 4G, nofail — mirror is additive, QLC chain stays primary-managed) and `boot-mirror-sync.service` (oneshot, deploy.sh provisioner-restarted + multi-user-pulled) keeps it a VERIFIED byte-mirror of the QLC `/boot`: `bootctl --esp-path=/boot-mirror --variables=no install` (loader binary + EFI/BOOT fallback + per-ESP random seed; NEVER touches NVRAM) + rsync `--delete` (`/loader/random-seed` stays per-ESP — receiver-side exclude protects it) + a `diff -r` gate that FAILS the unit on any tree drift. `/nix` already lives on the Samsung, so after `nix run .#boot-mirror-activate` (idempotent: creates the `Linux Boot Manager (Samsung)` EFI entry and orders it FIRST; QLC entries stay fallback) the firmware boots loader+kernel+initrd+store entirely off the QLC — only root `@` remains on it. pre-reboot-check §11 grades mirror issues FAIL once the mirror is first in BootOrder, WARN before activation. Rollback: firmware boot menu (F8/F11/F12) or `efibootmgr -o` with the QLC `Linux Boot Manager` id first. The seconds-wide window between a switch and the post-switch sync restart can boot the PREVIOUS generation from the mirror — safe (its store paths live ≥3d). nixpkgs `mirroredBoots` is grub/extlinux-ONLY (verified 2026-09-18) — do not "simplify" the unit away. Stale mirror: `systemctl restart boot-mirror-sync`. **ACTIVATED 2026-09-30, first reboot pending:** `nix run .#boot-mirror-activate` applied NVRAM BootOrder → `000C` (Samsung) first with pre-reboot-check §11 green AT FAIL grade (tree identical); notable: the entry existed since the 09-19 era but NVRAM BootOrder still led with QLC `0001` until this run — cause unknown (firmware reset vs `-o` never previously executed). ## Docker & Containers

- **`oci-containers` backend defaults to Podman** — Set `backend = "docker"` when Docker is already enabled.
- **`Requires=docker.service` on compose units = permanent outage after any docker blip (fixed 2026-08-31)** — a Requires= dependency failure at boot (dockerd's containerd startup timed out ONCE under I/O storm, then self-healed via its own Restart) fails the compose unit's start JOB with result=dependency, and job failures NEVER re-trigger `Restart=always` (restarts only apply to executed processes) — manifest + twenty stayed down until a deploy. `mkDockerService` now uses `wants` so ExecStart failing against a not-yet-ready daemon feeds the normal Restart loop. Companion rule: EVERY compose service incl. DB sidecars MUST set `restart = "always"` — manifest's postgres lacked it, died exit-255 at the docker restart, and the app crash-looped against the dead DB for 15+ min (gatus red) until `docker start mnfst-postgres-1`. Runtime remediation for that class: restart the compose unit (needs root) or `docker start <db-container>` (works via docker group).
- **Docker 29.x `userland-proxy-path`** — `daemon.settings.userland-proxy = false`.
- **Attach-flavor compose units (dozzle) do NOT survive a docker daemon restart (found 2026-08-31 live test)** — `docker-dozzle.service` runs `docker compose up` ATTACHED (main process = compose); a `systemctl restart docker` kills the attached process → ExecStop/ExecStopPost run compose down (container REMOVED) → unit lands inactive(dead) with Result=success until next boot/deploy. Detached-flavor units (manifest, twenty) ride through fine. Verified in the 2026-08-31 convergence test: mnfst-postgres-1 self-healed via restart=always in ~17s, manifest/twenty stayed active, twenty-worker-1 came back via compose dependency gating (starts only after twenty-server-1 reports healthy — do NOT read a temporarily "Created" worker as a failure), but dozzle needed `sudo systemctl start docker-dozzle.service`. Consider converting dozzle to the detached flavor if daemon-restart resilience matters for it.
- **`docker system prune --filter until=N` is a false-green on docker 29.x — use granular prunes (fixed 2026-08-31)** — the weekly `docker-prune` unit logged `Total reclaimed space: 0B` while 2 dangling images (2-3 wk old) and a tagged zoo sat eligible; plain `system prune` NEVER removes tagged-but-unused images (old version tags like `twenty:v2.7.3` persist forever without `-a`) and skips volumes without `--volumes`. The unit now runs `container prune` + `network prune` + `image prune -af --filter until=168h` + `builder prune -f --filter until=168h` (`platforms/nixos/system/scheduled-tasks.nix`): `-a` + until collects unused tagged images OLDER than the 7-day bound while fresh builds survive (verified live: 34→9 images, 8.6→2.1 GB; website images built 3 h earlier kept); builder prune only takes cache records untouched ≥7 d — the 8 GB warm cache from this week's builds stays by design and ages out in later runs. Volumes deliberately never auto-pruned — docker's "reclaimable" column for volumes only means NO RUNNING CONTAINER currently mounts them, not disposability (4.75G across 225 volumes, 4 active, 2026-09-30 — real data).
- **containerd bbolt corruption** — Recovery: stop docker → `mv meta.db meta.db.bak` → remove `containers/`/`containerd/`/`network/` dirs → restart.
- **systemd-oomd kills Docker containers under system-slice pressure (Twenty worker)** — Docker containers run as `docker-<id>.scope` under `/system.slice`. systemd-oomd picks the largest memory consumer to kill when system-slice pressure exceeds 50% for 20s. The Twenty worker (~856MB, largest container) was SIGKILL'd (exitCode=137) every ~15s: oomd kills → `restart: always` restarts → Node.js init spike → more pressure → oomd kills again → infinite loop (136 restarts in 40 min). Docker reports `OOMKilled: false` because systemd-oomd kills via cgroup signal, not Docker's own OOM handler. Fix: `mem_limit: "2g"` + `memswap_limit: "2g"` + `NODE_OPTIONS="--max-old-space-size=1536"` in the compose file. `ManagedOOMPreference=omit` canNOT be set on Docker scopes from NixOS (transient units). The nix-daemon oomd exemption reduces cascade pressure events, which indirectly reduces worker kills.
