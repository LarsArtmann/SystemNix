## Quickshell (DankMaterialShell)

Quickshell is a QtQuick desktop shell replacing Waybar, Dunst, Wlogout, polkit_gnome, **and rofi** (launcher, clipboard, keybinds, emoji, calc). Configured via DankMaterialShell's upstream HM module.

- **Input:** `dankMaterialShell` (github:AvengeMedia/DankMaterialShell/stable) — brings `quickshell` transitively, no separate quickshell input
- **HM module:** `platforms/nixos/desktop/quickshell.nix` — imports DMS upstream, sets `programs.systemnix-quickshell.enable = true`, enables `systemd.enable = true` (defaults to false!)
- **DMS plugins:** `pkgs/dms-plugins/` — 13 SystemNix-native widgets + 2 community launcher plugins (dms-emoji-launcher, DankCalculator) declaratively installed via DMS's `plugins` option with port-templated settings from `lib/ports.nix`. Community plugins use `fetchFromGitHub`. Each uses `PluginComponent` + `plugin.json`
- **DevShell:** `nix develop .#quickshell` for hot-reload QML development with `qmlls` LSP
- **Wallpaper management:** DMS owns wallpapers natively. awww is RETIRED. `dms-wallpaper-init` service seeds a random wallpaper from `~/.local/share/wallpapers/` (installed from `wallpapers-src` flake input) at session start. DMS derives cycling directory from current wallpaper's parent dir. `Mod+W` = `dms ipc call wallpaper next`. Dynamic theming (`enableDynamicTheming = false`) is DISABLED — matugen overrides Catppuccin Mocha (our global theme). Re-enable if committing to Material You dynamic colors. **Dangling-pointer self-heal (2026-09-14):** DMS stores the wallpaper as a bare FILE path — a deleted file leaves `wallpaper get` exiting 0 with a dead path (blank screen; hit when the auto-commit daemon baked a `~/projects/wallpapers` deletion into `53fe554`). The init script now re-seeds from the collection when the current path is missing/unset (healthy path still exits untouched). Test point wallpaper OUTSIDE `~/projects` — the daemon commits deletions there
- **dms-wallpaper-init needs `dms` in runtimeInputs** — The service calls `dms ipc call wallpaper next` but `dms` is NOT on PATH by default in a systemd service context. Must add `dankMaterialShell.packages.${pkgs.system}.default` to the script's `runtimeInputs`. Side effect: runtimeInputs dirs sit FIRST in the script PATH — a stubbed `dms` for testing must be sed-injected into the script text, PATH-shadowing cannot win
- **Waybar RETIRED:** Completely removed (import, package, service, scripts). DMS is the sole shell
- **Rofi migrated to DMS (2026-06-30):** niri's 5 rofi keybindings rewired to DMS IPC (`spotlight toggle`, `clipboard toggle`, `keybinds toggle niri`, `spotlight toggleQuery ":e"`, `spotlight toggleQuery "="`). Rofi leaked 7 GB and OOM-killed niri. Rofi config (`rofi.nix`) remains for Sway backup WM only. DMS service has `MemoryMax=4G` as defense-in-depth. Emoji via dms-emoji-launcher plugin (trigger `:e`), calculator via DankCalculator plugin (trigger `=`)
- **Runtime verified:** DMS owns `org.freedesktop.Notifications`, `org.gnome.ScreenSaver`, `org.kde.StatusNotifierWatcher` DBus names
- **DMS niri module:** Import `dankMaterialShell.homeModules.niri` for niri-specific integration (workspace IPC via `$NIRI_SOCKET`)
- **`inputs.nixpkgs.follows`** on the DMS input is MANDATORY — mismatched Qt causes runtime crashes
- **Shutdown countdown overlay (2026-08-14):** `modules/nixos/desktop/shutdown-overlay.nix` runs a SECOND Quickshell instance (`services.shutdown-overlay`, user service) that shows a fullscreen overlay on ALL monitors when `/run/systemd/shutdown/scheduled` has ≤60s left — `WlrLayer.Overlay` + `ExclusionMode.Ignore` + click-through `mask: Region {}` (DMS FrameWindow pattern). It reads the µs timestamp from line 1; `shutdown -c` removes the file and the overlay hides within 200ms. niri's built-in hotkey overlay ("Important hotkeys", compositor-drawn while a keybind chord is pending) renders above the ENTIRE layer-shell Overlay layer (`Niri::render_inner` pushes it before `Layer::Overlay`) — no client can top it; only session-lock/exit-dialog do. A standalone quickshell run from SSH needs `DISPLAY` set or it dies silently after a Gtk warning (session user services get both DISPLAY and WAYLAND_DISPLAY imported, so the unit is unaffected)

## Focus-New-Windows (launch follow)

**Module:** `modules/nixos/desktop/focus-new-windows.nix` (`services.focus-new-windows.enable`) — user systemd service watching `niri msg --json event-stream` (smart-audio pattern), deployed live 2026-08-16

- **Purpose:** niri never moves focus to a window opening on another output (the `open-on-workspace` → `chat`/`media` on DP-2 case). The daemon calls `focus-window --id` on newly opened unfocused windows so spotlight launches take you there
- **`WindowOpenedOrChanged` fires for opens AND updates** — the daemon tracks known window IDs (seeded from the `WindowsChanged` snapshot, pruned by `WindowClosed`) so a title change on a background window never steals focus
- **`is_focused` gate:** niri-unstable already focuses same-output opens itself (verified live). The daemon only acts on cross-workspace/cross-output opens — same-workspace launches stay zero-touch
- **`startupGraceSeconds`** (default 10): windows opening right after session start are NOT followed (login autostart would otherwise drag focus across workspaces)
- **`skipAppIds`:** regex list (Python `re.search`) of app-ids that must never steal focus
- Cross-workspace `focus-window --id` verified live (switches active workspace). The true cross-OUTPUT case (DP-2 connected) is untestable from SSH — verify after DP-2 reconnect

## Smart-Audio (focus-following HDMI audio router)

**Module:** `modules/nixos/desktop/smart-audio.nix` (`services.smart-audio.enable`) — user systemd service, deployed live

- Python stdlib daemon watching `niri msg --json event-stream`; maps focused workspace → output → Radeon HDMI profile; switches via `wpctl set-profile` + `wpctl set-default`. HDMI audio profiles on the Radeon card are MUTUALLY EXCLUSIVE — profile switching (not just sink switching) is required
- **Device discovery is DYNAMIC (2026-08-31)**: `deviceName = "auto"` resolves the ALSA card offering HDMI profiles (the GPU audio function) from `pw-dump` at startup, retrying up to 120s; sink names use a `{card}` placeholder substituted with the resolved token (e.g. `pci-0000_c6_00.1`). The old hardcoded `pci-0000_c5_00.1` died to start-limit-hit after the post-crash PCI renumber (c5→c6, same class as the NIC-vanish / sd-letter traps) — never pin PCI addresses here again. Verified live: auto-resolved `pci-0000_c6_00.1`, routed DP-1
- **PipeWire OBJECT IDs DRIFT — resolve the device by NAME before every switch (2026-09-06 live incident: "audio doesn't follow to the TV")**: the daemon cached the device id at startup (Radeon=69); after device re-registrations id 69 became the RYZEN analog card, so every `wpctl set-profile 69 3` silently mutated the WRONG card (`check=False` swallowed it) — the HDMI profile never changed, the extra2 sink never appeared, and the daemon error-looped "sink not found" while ALSO flipping the Ryzen card's profile as collateral (killing the mic source on DP-1-bound switches). Fix: `resolve_device()` re-resolves by the stable `device.name` (with auto-scan fallback) before every profile switch, `wpctl` output is captured and logged on rc≠0, and sink-not-found logs the live hdmi node names. DP-1↔DP-2 both verified live post-fix. Class lesson: PipeWire numeric object ids are ephemeral; NAME is the stable handle — same doctrine as PCI addresses and sd-letters
- **Jack↔profile↔output mapping VERIFIED (2026-09-06, authoritative source `/proc/asound/card0/eld*`)**: DP-1 (LG HDR 4K monitor) = eld#0.1 = `output:hdmi-stereo-extra1`; DP-2 (LG TV SSCR2) = eld#0.2 = `output:hdmi-stereo-extra2` — the module defaults are correct. Diagnose jack wiring with `grep monitor_name /proc/asound/card*/eld*` (wpctl's `[monitor]` suffix on the sink description is cosmetic and can be missing on freshly flipped profiles); don't confuse it with a dead jack
- **niri `focus-workspace <number>` is ambiguous with named workspaces** — numeric refs resolve unexpectedly across outputs (verified: `focus-workspace 4` landed on an unnamed DP-2 workspace). Drive tests with workspace NAMES (`focus-workspace main` / `focus-workspace chat`)
- Supersedes the static WirePlumber profile-priority rules in `audio.nix` — RESOLVED 2026-09-19: the `51-hdmi-monitor-priority` block was REMOVED (it was doubly dead — its `alsa_card.pci-0000_c5_00.1` match pinned the pre-crash PCI address that renumbered to `c6` on 2026-08-31, so it matched nothing, and `device.restore-profile = false` would have re-applied priorities on every device event against the daemon's switches). smart-audio is the sole HDMI profile router; WirePlumber keeps its default `restore-profile` so device events re-apply the daemon's last choice
- **`pkgs.writers.writePython3Bin` runs a strict pyflakes/pycodestyle linter at build time** — use `pkgs.writeScriptBin` with a `python3.interpreter` shebang for daemon scripts (cost a full build+deploy cycle to learn)
- **Audio debugging tools (2026-08-22):** `alsa-utils` (speaker-test, aplay, amixer) and `pipewire` (pw-cat, pw-play, pw-cli) are in `linuxUtilities` in `base.nix` for audio routing verification. `speaker-test -c2 -twav` plays test tones on the default sink; `pw-cat -p /usr/share/sounds/...` pipes audio through PipeWire directly
- **TV HDMI input audio format: PCM, not Bitstream (2026-09-25)** — with the LG TV SSCR2 set to Bitstream, the PC's stereo-PCM stream audibly lost dialogue clarity (the TV routes plain PCM through a mismatched decode/DSP path); switching to PCM matched the sender and improved it. "DTV Audio Setting"/"Digital Sound Out" are tuner/ARC-scoped and INERT for PC-over-HDMI streams. Same-day diagnosis method for muffled dialogue: inspect the playing stream via `pw-dump | jq` (`media.class == "Stream/Output/Audio"` → `.info.params.Format[0].position`) — Helium negotiated proper FL/FR stereo on stereo YouTube, so a "muffled pirates" movie stream was the SITE serving a MONO re-encode, not the audio stack
- **Idle DPMS via swayidle (raised 2026-09-14):** swayidle has a 14400s (4h) timeout that calls `niri msg action power-off-monitors` (DPMS off) before the existing 43200s (12h) suspend timeout (was 1200s/20min until `af870305`; the deployed generation still carries 20min until the next `nix run .#deploy` — verify with `systemctl --user cat swayidle.service | grep ExecStart`). The user-reported "~5 min to black" predates the raise and is unexplained (deployed-generation drift or another timer — the post-deploy grep is the real check). `sway-audio-idle-inhibit` inhibits idle during audio playback, so the TV-as-audio-sink case is handled — DPMS won't fire while audio is playing. Any input (mouse/keyboard) turns monitors back on; no explicit `power-on-monitors` needed

## Desktop (DMS / Quickshell / Helium)

- **Never pull `graphical-session.target` into the user-manager boot transaction (2026-08-18 black-screen incident)** — any unit enabled via `default.target` that sets `Wants=graphical-session.target` starts the target at lingering boot (before SDDM exists), which starts `niri-session-manager` (`Requires=niri.service`) → a headless zombie niri with zero outputs. SDDM's `niri-session` then exits "A niri session is already running" → black screen, monitor sleeps. Amplifier: `niri-drm-healthcheck` restart-looped the zombie every 2 min. Fixed three ways: (1) `aw-watcher-window-wayland` no longer sets `Wants=` (its gate wrapper waits for the compositor socket instead — indefinitely, session may come hours after boot); (2) `niri.service` carries `ConditionEnvironment=XDG_SESSION_ID` (only present in the manager env after a real SDDM login ran import-environment) and `Restart=on-failure` (a clean exit is logout — `always` respawned a headless niri that blocked the NEXT login); (3) `niri-drm-healthcheck.sh` has the same login-screen guard as `display-watchdog.sh` (never restart niri when no user graphical session exists — a restarted headless niri is just as headless). Do not "fix" silent autostart units by adding `Wants=graphical-session.target`; wait on the compositor socket or use `After=` + a gate wrapper. Also: `writeShellApplication` scripts that shell-parse command output need every binary in `runtimeInputs` (display-watchdog shipped without `gawk` → its login-screen guard silently always said "no session").
  - **Machine-enforced since 2026-08-18:** `modules/nixos/desktop/session-boot-audit.nix` (`services.session-boot-audit`) fails `nix flake check` if ANY user unit reachable from `default.target` Wants/Requires/BindsTo `graphical-session.target` — it graphs NixOS-shape units, HM-shape units (`Unit`/`Install` sections), AND raw-text `systemd.user.units` (parsed), seeds the built-in `default→basic→{paths,sockets,timers}` chain, and reports the full offending chain. Exceptions go in `allowedUnits` with a reason. Negative-tested against the exact historical bug. `niri-drm-healthcheck` (user unit) also carries `ConditionEnvironment=XDG_SESSION_ID` (the healthcheck has nothing to heal pre-login), and the `niri_zombie` metric + Gatus "Niri Zombie Session" check (running niri + no graphical session, 2-check grace for the logout window) is the runtime tripwire. The `XDG_SESSION_ID` condition is fact-backed: `niri-session` imports the FULL login env (`systemctl --user import-environment`, no args) before starting `niri.service`, pam_systemd sets the var in every real session. Regression source: `6ea92969` (2026-08-15) added the fatal `Wants=` while "fixing" the watcher for real boots
  - **Qt6 never had a gtk2 theme — `qt.platformTheme/style.name = "gtk2"` kills Qt6 QQC2 apps** (2026-08-18): every unwrapped QtQuick.Controls app then aborts `module "gtk2" is not installed` (niri-flake-polkit crash-looped 49×, auth dialogs dead). Use `platformTheme.name = "adwaita"` (qadwaitadecorations — a Wayland-decorations plugin; note the HM-set `QT_QPA_PLATFORMTHEME=adwaita` itself resolves NO platformtheme plugin and is inert-by-design) + a built-in QQC2 style (`fusion`). Flagged as debt since the 2026-04-03 audit, ignored until it broke auth. **The adwaita/fusion switch was silently defeated 2026-04-28→09-02 by a stale `QT_STYLE_OVERRIDE = mkForce "kvantum"` session var (removed 2026-09-02): kvantum was NEVER deployed, so every QWidget app ran an unresolvable style override while the config claimed fusion. Qt style selection has exactly ONE owner — the `qt.platformTheme/style` block in home.nix; never hand-set QT_STYLE_OVERRIDE/QT_QUICK_CONTROLS_STYLE. post-deploy-check's "polkit dialog render sanity" fails on any deployed-but-unresolvable Qt style env var and on QQC2 `module ... is not installed` journal aborts.** The runtime polkit agent host is the DMS quickshell instance (QuickAuthDialog.qml)
- **niri-session-manager restore-storm (2026-08-31: 152 empty ghostty terminals per login)** — the manager saves EVERY niri window every 15 min to `~/.local/share/niri-session-manager/session.json` and re-spawns all of them at login. Ghostty is `gtk-single-instance`: one process, many surfaces, each surface saved as a separate window with `terminal_state: null` (content is not restorable) → restore spawns bare `ghostty` per saved window (~20/s, `MAX_SPAWN_CONCURRENCY=5`), every restored empty shell gets re-saved at the next 15-min tick, and the pile only GROWS (+2/login from spawn-at-startup). Fix: `com.mitchellh.ghostty` MUST stay in `single_instance_apps` — the app lists now live in **`platforms/nixos/users/niri-session-manager-apps.nix` (single source of truth since 2026-09-02)**: it feeds the generated config.toml in home.nix, carries `mkInvariantViolations` (asserted at HM eval time AND by `tests/test-niri-session-config.nix` with negative cases — every terminal app-id ∈ single_instance_apps; transient dialogs like `gcr-prompter`/`xdg-desktop-portal-gtk` ∈ skip_apps). ALL terminal app-ids are single-instance at restore time (one spawn per terminal, incl. multi-process ones — an empty shell has no state worth N copies); `emacs` pinned preemptively for the daemon class (dormant Mod+Shift+E keybind, not installed). A literal restartTriggers on the config is deliberately NOT wired: upstream restore re-runs on EVERY process start under `Restart=always`, so a mid-session restart replays the spawn storm — the `niri_session_manager_config_stale` metric (niri-health collector) makes the until-next-login window observable instead. Cleaning a poisoned session: kill the single-instance ghostty pid FIRST (else the next periodic save re-records every surface), then rewrite session.json — and `trash` the `session-*.bak` files too (a "corrupt" file makes the manager fall back to the newest valid BACKUP, resurrecting the storm). Upstream hazards (LarsArtmann/niri-session-manager v0.3.0): restore re-runs on EVERY process start (one crash = another full spawn storm), and save does not dedupe same-pid single-instance surfaces
- **Auto-discovered modules are FLAKE-PARTS wrappers, not bare NixOS modules** — files under `modules/nixos/{services,desktop}/` are imported into the flake-parts module set; they MUST declare `flake.nixosModules.<filename> = { config, lib, ... }: { ... };` (see `niri-config.nix` / `session-boot-audit.nix` for the shape). A bare NixOS module `{ config, lib, ... }` in those dirs evaluates WITHOUT error in the flake-parts namespace and silently contributes NOTHING to hosts — nothing imports it, no options appear, no assertions fire. Symptom: your new module's options "don't exist" on the host despite clean evals. **WORSE variant (signoz-coverage, 2026-08-31 19:35): a bare module whose `let` bindings force `config.systemd.services` (e.g. for eval-time assertions) does NOT evaluate silently — it HARD-fails every nix command with `attribute 'systemd' missing` until wrapped; a mid-flight session committing such a file blocks ALL deploys.** When un-wrapping a foreign bare module, also remember: `...` in the lambda pattern takes NO trailing comma, and the outer attrset needs its own closing brace
- **`nix eval …config.system.build.toplevel.drvPath` does NOT check NixOS assertions** — assertion checking is only forced by `nix flake check` (pre-commit + CI). An assertion-failing config evaluates cleanly to a drvPath; verifying a guard REQUIRES `nix flake check --no-build` (or an actual build). Also latent: forcing ALL assertion messages (e.g. `nix eval --json …config.assertions`) crashes on the sops templates module (`owner: ${cfg.owner}` with owner=null when a template sets only uid) — only failed assertions' messages are coerced in normal operation
- **`extendModules` probe overrides: hand-rolled override attrsets now need `content`, NOT `value`, and a PLAIN `enable = false` in configuration.nix forces probe overrides to priority ≤ 50 (2026-09-23, offsite-borg positive-render probe; both error shapes re-verified live against the locked nixpkgs 2026-09-24)** — two stacked traps for probe authors: (1) the module-system override wrapper's inner field is `content` (`mkOverride = priority: content: { _type = "override"; inherit priority content; }`), so the long-documented `{ _type = "override"; priority = 50; value = true; }` literal dies `error: attribute 'content' missing` at `lib/modules.nix:1458` (the `strip` function reads `def.value.content`) — never hand-roll the attrset, write `lib.mkOverride 50 true` (`mkForce` IS `mkOverride 50`); (2) plain values carry priority 100 (`defaultOverridePriority`), so the host's plain `enable = false` conflicts with a probe's plain `enable = true` — `has conflicting definition values … Use lib.mkForce value or lib.mkDefault value to change the priority` — probes must override at priority ≤ 50, and a probe that must beat an EXISTING `mkForce` needs priority < 50 (configuration.nix's plain `enable = false` is exactly why `offsite-borg-positive-render` uses `mkOverride 50 true`)
- **Eval-time `readFile`/`readDir` on a BUILT package output forces its realization — `error: path '<pkg>.drv' is not valid` after every nixpkgs bump (2026-09-06, niri)** — `niri-config.nix` read its user unit texts from `${niriPkg}/lib/systemd/user`, so EVERY `nix eval` / `nix flake check --no-build` required niri to be physically present in the store; each nixpkgs bump changes the drv, and the pre-deploy gate died at eval until niri happened to be rebuilt (deploy evals survived only because build-allowed evals realize niri mid-eval — the gate's dependence on store state was invisible while the store was warm). Fix: read unit texts from the niri SOURCE tree (`${niriPkg.src}/resources/` — pure, the fetch is always available at eval) and replicate niri-flake's single install substitution (`ExecStart=niri` → `ExecStart=$out/bin/niri`; its `replace-service-with-usr-bin` branch is the nixpkgs meson flavor, not niri-flake's). Generated units verified byte-identical to the packaged ones. General rule: eval-time code must never coerce a package OUTPUT (readFile/readDir/hashFile/`/. +`) — coerce `src`, `passthru`, or plain interpolations only
- **DMS `inputs.nixpkgs.follows` MANDATORY** — Mismatched Qt causes silent runtime crashes.
- **DMS modals already follow the focused monitor** — Spotlight/clipboard/emoji/keybinds modals open on niri's focused output (upstream fix #869, included since DMS 1.5.3). - **Hardened root units that `rm` foreign-owned trees need `CAP_DAC_OVERRIDE` in the `harden{}` call (2026-09-06, `nix-build-cleanup`)** — build sandboxes are `nixbld`-owned (0700 dirs + Go modcache trees made read-only), and `harden{}`'s default empty `CapabilityBoundingSet` strips root's DAC override, so every cleanup run died in a wall of `rm: Permission denied` (the same class was observed and never fixed since 2026-07-21). Fix: `CapabilityBoundingSet = "CAP_DAC_OVERRIDE"` inside the `harden {}` argument (niri-config precedent; first post-fix run freed 2.6 GB). Companion: deploy.sh STARTs `nix-build-cleanup.service` post-switch every deploy — stc never restarts inactive oneshots on unit-file change, so without a per-deploy run a broken unit sits unverified until the 4h timer (silent-failure history: 2026-07-18, 2026-08-16, 2026-09-06). - **Textfile collectors must write a UNIQUE tmp (`mktemp`), never `$OUT.tmp`, when the unit is hardened root (2026-09-05)** — the sticky 1777 textfile dir eventually collects a FOREIGN-owned leftover (one manual run as another user is enough), and `harden{}`'s empty CapabilityBoundingSet means root cannot `open(O_TRUNC)` a file it doesn't own: the collector fails every tick and the failing oneshot blocks EVERY deploy at test-activation (Exited(4)). Live class: a lars-owned `niri.prom.tmp` from a manual Sep-3 debugging run blocked `niri-health-metrics` for ~2 days and failed the 2026-09-04 deploy. Fix pattern (niri-config.nix): `TMP=$(mktemp "$DIR/<name>.XXXXXX")` + `chmod 644` (mktemp is 0600; DynamicUser node_exporter needs o+r) + `trap 'rm -f "$TMP"' EXIT` (no leak when a later step fails) + `CapabilityBoundingSet = "CAP_FOWNER CAP_DAC_OVERRIDE"` on the unit so the final `mv` over a foreign-owned target also can't wedge (memory-emergency-guard precedent). **Repo-wide enforcement (2026-09-06): `scripts/audit-textfile-tmp.sh` (pre-commit + CI) rejects fixed-tmp writes AND `/run/secrets-rendered` literals in every .nix file; all collectors were converted after mail-relay became the second live detonation (2026-09-02..06, see its section).**
