## Shell & DevTools

- **curl ≥8.2x advertises `Accept-Encoding` by default — body-parsing curls MUST pass `--compressed`** (2026-08-16 nixpkgs bump). Servers that honor it (crush-daily API middleware, node_exporter `/metrics`, anything behind Caddy `encode`) return `Content-Encoding: gzip`, which plain `curl -s` does NOT decode: greps match nothing, jq fails, and bash warns "ignored null byte in input" (gzip streams contain NULs). Status-code-only checks (`-o /dev/null -w %{http_code}`) are unaffected. Bit the smoke checks twice under different disguises: first DiscordSync `/api/stats` (misdiagnosed as "null bytes in JSON", "fixed" with `grep -a`), then Crush Daily `/api/reports` ("unexpected response" forever against a healthy API). `--compressed` is a no-op on identity responses — safe on every body-parsing curl
- **`rsync -a --files-from=<list>` does NOT recurse into listed directories — the `-a`-implied `-r` is silently DROPPED in files-from mode (2026-08-31)** — pass `--recursive` EXPLICITLY. Symptom: rsync exits 0, "succeeds", and has copied only empty dir skeletons + single files (four benchmark runs silently measured nothing before this was caught). Related trap the same evening: `du -sk --files0-from=-` needs NUL separators (`tr '\n' '\0'`), and `btrfs filesystem du` reports LOGICAL bytes — use `compsize` or a df-free-delta for physical/compressed usage.
- **python urllib AUTO-FOLLOWS redirects; curl does NOT (no `-L` by default)** — verifying an HTTP body check with python can LIE about curl semantics (2026-08-18): paperless `/` 302-redirects to `/accounts/login/?next=/`; python `urlopen` followed it and showed the login body, while the smoke's curl saw only the empty 302 body and failed. Always validate smoke-check patterns with the SAME tool the check uses (curl), or probe the FINAL URL directly. Same class: `test -e /etc/systemd/system/<unit>.service` is the correct enable-gate for smoke checks — `systemctl is-enabled` returns rc=1 for units pulled in via `requiredBy` only (paperless-web has no own [Install] symlink despite running), and `list-unit-files` matches unit files that exist but aren't deployed-enabled (bank-sync fired its vHost check while disabled). **EXCEPTION — fstab-generated `.mount` units NEVER exist at that path**: `fileSystems` entries render to `/etc/fstab` and systemd-fstab-generator creates their units AT RUNTIME in `/run/systemd/generator/` — a `[ -e /etc/systemd/system/var-lib-clickhouse.mount ]` gate is permanently false and its check block silently skips = phantom green (post-deploy-check XFS gate, caught 2026-08-22). Gate fstab mounts on the fstab entry itself (`awk '$2 == "/path"' /etc/fstab`) or `findmnt`; `systemctl` NAME-based actions still work on generated units. Related detector: `system_current_system_profiled` (system-health) alerts when `/run/current-system` matches no numbered profile — the manual-activation signature (deploy.sh post-switch steps + boot entries missing; reboot reverts)
- **`writeShellApplication` pipefail + `|| echo 0`** — Produces multi-line output under pipefail. Use `|| true` + `''${var:-0}`.
- **`writeShellApplication` pipefail + `| sort | head` SIGPIPE** — Append `|| true` to pipeline.
- **`set -o pipefail` + `echo "$body" | grep -q` on a >64KiB body = FALSE "body lacks" FAIL (2026-08-19)** — grep -q exits at its first match, the echo writer then dies on SIGPIPE (exit 141) while still writing the rest of the body into the 64KiB-capped pipe, and pipefail fails the whole pipeline even though grep SUCCEEDED. Hit when the bank-sync templ-components dashboard grew to ~106KiB: the smoke check claimed the body lacked a string that provably sat at byte ~100. Probe bodies via `grep -q "pat" <<<"$body"` (herestring, no pipe) or the `check()` helper's `curl -o /tmp/.smoke-body` + file grep — never an echo|grep -q pipeline on a large captured body. Diagnosis trick: dump the captured var with printf in the failure branch and grep THAT — if it matches, the pipeline is the bug, not the server
- **`grep -F` on arbitrary file content needs `-e` — lines starting with `-` are parsed as OPTIONS (2026-10-01 restructure)** — when grepping a line verbatim out of one file against another (`grep -F "$line" targets`), a line beginning with `-` (a `- [ ]` TODO row, a `---` fence) is consumed as a flag and the grep dies "invalid option" or silently mismatches. Always `grep -F -e "$line"` — the `-e` explicitly terminates option parsing and names the pattern.
- **Never read `$1` AFTER `shift` in shell helper functions — capture into a named variable BEFORE shifting (2026-10-01 restructure, 21-file misdirect)** — after `shift`, `$1` is a DIFFERENT argument (or empty), and a write path built from it silently lands in the wrong target: the restructure's append helper misdirected 21 runbook appendices into extensionless stray files via exactly this shape (recovered byte-exact). The reliable form is `target=$1; shift` — then use `$target`. Same family: quote every path built from positionals so an empty capture fails loudly instead of writing to a mangled name.
- **Store regexes in a variable for `[[ string =~ regex ]]` (2026-10-01 anchor validator)** — bash parses a QUOTED literal in `=~` as a plain string (metacharacters never match) while an unquoted literal invites word-split/glob surprises. The unambiguous form: `re='^[a-z0-9-]+$'; [[ $candidate =~ $re ]]` — the unquoted variable is parsed as ERE.
- **Verify mechanical steps with a CONTENT PROBE, never a line count (2026-10-01 restructure)** — `wc -l` on batch outputs proves nothing: banner-only output files passed the count check while their payload was missing. Grep a distinctive payload phrase per target (`grep -c "migrated from AGENTS.md" docs/services/*.md`) instead of counting lines. Same family as the degenerate-artifact rule: a verifier that cannot fail on empty/garbage output is not a verifier.

- **`comm` MUST share the collation of the sorts feeding it (2026-09-17 smoke baseline diff)** — the fail-set baseline compared `LC_ALL=C sort`ed files with a comm running under the ambient `en_US.UTF-8` locale: byte-order vs UTF-8 collation diverge on the multibyte fail names (em dashes), comm prints all three "not in sorted order" warnings (masked by `|| true`), and a genuinely NEW fail line can be silently mis-merged out of the regression signal. Fix: run comm itself under `LC_ALL=C` whenever either input was sorted under C. Same class as the head-SIGPIPE lesson: every byte-order tool in a chain must agree on collation
- **`find -L` for Nix store symlinks** — `find` does NOT follow starting-point symlinks by default.
- **Smart direnv library** — `~/.config/direnv/lib/zz-smart-nix.sh` overrides `_nix_add_gcroot` (5.1x speedup) + `use_go_env` (auto-detects GOEXPERIMENT/GOPRIVATE).
- **Fish per-prompt direnv caching** — mtime-gated; 0.7ms cache hit vs 43ms. Per-session sentinel includes `$fish_pid`.
- **`git insteadOf` flake.lock SSH pollution** — Global rule rewrites `https://github.com/` → `git@github.com:`. Workaround: `GIT_CONFIG_GLOBAL=/dev/null nix flake update <input>`.
- **statix `repeated_keys` disabled** — False positive for NixOS modules. `statix.toml` (non-dotted) has `disabled = ["repeated_keys"]`.
- **Pre-commit statix lints STAGED `.nix` files only** — Unstaged/pre-existing debt does NOT block commits (pathspec-scoped commits stay clean), so `statix check .` repo-wide (always exit 0 in practice) is NOT a gate predictor. Run `nix fmt` or stage the files to lint them.
- **zellij copy model: OSC52 is NATIVE; `copy_command` REPLACES it (2026-08-16)** — zellij always copies via OSC52 escape sequences, which tunnel through SSH to the client terminal's clipboard (works in iTerm2 and Ghostty). `copy_command = "wl-copy"` kills SSH copying dead (no Wayland session inside SSH) — that was the original iTerm2 bug. `copy_clipboard` selects the DESTINATION (`"system"`/`"primary"`), NOT the mechanism — `"osc52"` is an INVALID value that hard-fails config parse (deployed config verified via `zellij setup --check`). Current state: Linux sets NO copy_command (native OSC52), darwin keeps `pbcopy`; `mouse_mode = false` returns native selection/scrollback/Cmd+C to iTerm2 (pane focus keyboard-only Ctrl+j/k). iTerm2 prerequisite: Settings → General → Selection → "Applications in terminal may access clipboard".

- **btop can show STALE PER-PID STATS after PID reuse — the pane is NOT frozen (live 2026-09-16, user-corrected)** — a long-running btop displayed `celery … paperless … 31G, 20 threads` for 45+ min, updating every second, while the kernel proved that PID had Threads=1 and lifetime peak VmHWM 196MB (60d/174 unit-runs of cgroup peaks maxed at 0.82G under 1–2G MemoryMax caps, zero OOMs). Mechanism: this box is a PID-reuse machine (celery forks a fresh pool child every 10 min via max-tasks-per-child, nix builds fork thousands; pid_max 4.2M wraps in weeks) — btop's per-PID cache kept the PREVIOUS owner's stats (MEM/threads/CPU-graph) under the NEW owner's identity (name/user/exe refresh, stats don't). **Proof pattern: starting a SECOND btop instance builds a fresh cache — the bogus row corrects/vanishes there while everything else matches.** Before believing ANY per-process memory alarm from a long-running monitor: cross-check `/proc/<pid>/status` (VmRSS + VmHWM — VmHWM bounds the process's whole life, killing "transient spike" theories in one shot) against a fresh monitor instance. Related trap: `ps` truncates user names to 8 chars by default (`paperless` → `paperles`) — filter with `ps -o user:16`, not a bare awk equality on the user field

- **`~/go/bin` (GOBIN, PATH slot #2) silently SHADOWS every mkLarsPackages tool (2026-09-22)** — stray `go install` binaries there beat the system-managed, lock-pinned copies: `buildflow` resolved to `version dev` (a Sep-20 `go install`) while the system shipped `7e1fbfe` and an imperative `nix profile` copy sat at `557fe59` — three divergent versions, the stray winning. Cleanup: 6 shadows trashed from `~/go/bin` (buildflow, art-dupl, cqrs-lint, golangci-lint-auto-configure, meta, templ; golines kept — no system copy exists), profile emptied (buildflow/govalid were version-identical dupes, sshpass had 0 uses, typst moved to `base.nix`). Doctrine: the user `nix profile` stays EMPTY — LarsArtmann tools come from `mkLarsPackages`, nixpkgs tools from `platforms/common/packages/base.nix`; after any session `go install`s a fleet tool, trash the stray from `~/go/bin`.

- **The Crush tool shell's `kill` is an UNSUPPORTED BUILTIN STUB (2026-10-06 rust-cache window)** — `kill -9 <pids>` inside a bash-tool command prints "kill: unsupported builtin" and does NOTHING; with `2>/dev/null` on the call it fails SILENTLY and a later `ps` "verified nothing died" claim becomes FALSE evidence (the suspended migrate/rsync family survived a supposed SIGKILL until the real binary was used). Same trap class as the raw-`curl` ban: use the ABSOLUTE path `/run/current-system/sw/bin/kill` (or `nix shell nixpkgs#util-linux`) for any signal work in tool commands, and re-verify process state with `ps -p` BEFORE claiming a kill landed.

## qmd (Global RAG Search CLI + Crush MCP)

**Wiring (2026-08-20; MCP rescoped 2026-10-09):** flake input `qmd` (`github:tobi/qmd`, tag-pinned) → `environment.systemPackages` in `platforms/nixos/system/configuration.nix` (global CLI). The Crush MCP is project-scoped, NOT global: `mcps.qmd` was removed from `platforms/nixos/users/home.nix` and the MCP is declared ONLY in `~/projects/CV/.crushrc` (`mcp add qmd --command qmd --args mcp`) — every other Crush session spawns without it. NO service module, NO port, NO Gatus check — stdio MCP spawned per Crush session; the CLI is on PATH for everything else.

- **Why the upstream flake, not `pkgs/qmd.nix`:** the retired 2026-08-14 packaging (`fetchFromGitHub` + `pnpmConfigHook` + local pnpm lock copy) died of NAR-hash drift across nixpkgs bumps and a broken daemon wrapper. Upstream's own flake FODs the bun-installed node_modules (`bun install --frozen-lockfile --ignore-scripts`; only `better-sqlite3` gets node-gyp'd) and ships wrapper fixes we'd otherwise re-derive (MCP stdio llama-log quieting, upstream #723). Upstream owns the hashes; updates = bump the tag + re-verify `qmd --version` and an MCP initialize handshake
- **Do NOT add `inputs.nixpkgs.follows`** — the nodeModules FOD hash is validated against upstream's pinned bun; a different bun can install a different tree and break the FOD hash (same class as bank-sync's deliberately-unfollowed go-nix-helpers)
- **Runtime is `bun src/cli/qmd.ts`** through the wrapper (node never runs the CLI directly — the old "spawn node ENOENT" crash class is gone). GPU is auto-probed; CPU default is fine for the 300M-1.7B models. `QMD_FORCE_CPU=1` / `QMD_LLAMA_GPU` override
- **User-local state:** collections in `~/.config/qmd/index.yml`, index+models in `~/.cache/qmd` (3 GGUF models, ~2 GB total, auto-download on first semantic search; BM25 `qmd search` works model-free). Onboarding a corpus: `qmd collection add <dir> --name x && qmd update && qmd embed`
- **Crush picks up new MCP entries only on session restart** — after a deploy that changes crushrc, already-running sessions keep the old MCP set

- **Agent-sandbox shell quirks (2026-10-03, helium-history session)** — the Crush bash tool (mvdan/sh interpreter) blocks `systemctl` outright ("command is not allowed for security reasons"; `journalctl --user` WORKS, and repo source + built store paths are readable substitutes for `systemctl cat`); its `kill` prints "unsupported builtin" on some invocations while the kill may still take effect via an external binary, and `$!` expands to garbage ("g1") — so: never trust `kill` rc or `kill -0` liveness probes here, and discover background-test PIDs via `pgrep` instead. Also `exec -a <fake-argv0> sleep` dies (coreutils sniffs argv0) — use python3 as the payload for fake-cmdline process tests (e.g. testing the helium-launch main-only guard).
