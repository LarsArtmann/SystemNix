## IO-PSI Storm Attribution — live probe set (2026-11-03)

Codified from the 2026-10-15 85–96 % storm attribution (one pass named `crush -y` ≈ 407 MB/s + a `go test -race` trio ≈ 130 MB/s combined; source: `docs/status/2026-10-16_00-07_boot-failure-triage.md` §a.2/§f.9). Run these three probes in this order BEFORE any containment recommendation (the SIGSTOP doctrine above requires attribution first):

1. **Pressure context — `/proc/pressure/io` before/after** (bracket the whole attribution window so the numbers below are storm-anchored):

   ```bash
   cat /proc/pressure/io   # before
   # …run probes 2-3…
   cat /proc/pressure/io   # after
   ```

2. **Per-pid IO delta — two-snapshot `/proc/*/io` join KEYED ON PID (6 s window).** The join MUST be a fixed-key `join(1)` on the pid field, never `paste` (line-order join): the 2026-10-15 session's wrong-key join printed CUMULATIVE bytes as plausible-looking deltas and cost a round trip. Pids that appear in only one snapshot drop out silently instead of mispairing:

   ```bash
   snap() { for d in /proc/[0-9]*; do \
              b=$(awk '/^read_bytes|^write_bytes/{s+=$2} END{print s+0}' "$d/io" 2>/dev/null); \
              printf '%s %s\n' "${d#/proc/}" "$b"; done | sort -k1,1; }
   join <(snap) <(sleep 6; snap) -j 1 -o 0,2.2,1.2 \
     | awk '{d=$2-$3; if (d>1048576) printf "%8.1f MB/s  pid %-8s %s\n", d/6/1048576, $1, comm($1)} \
              function comm(p) { getline < ("/proc/" p "/comm"); close("/proc/" p "/comm"); return $0 }' \
     | sort -rn | head -25
   ```

   Name a suspect pid's full argv via `pgrep -af` PIPED THROUGH `scripts/redact-argv.sh` (secrets ride argv — the monitor365 `--jwt-secret` and crm `-api-token` were both seen live).

3. **Per-cgroup IO ranking — `io.stat` rbytes/wbytes.** Fields are `KEY=VALUE` pairs per device line; parse by key, never by column index (column-parsing produced all-zeros on 2026-10-15):

   ```bash
   for f in /sys/fs/cgroup/system.slice/*/*.io.stat /sys/fs/cgroup/system.slice/*/io.stat \
            /sys/fs/cgroup/user.slice/user-*.slice/user-@1000.service/*.scope/io.stat \
            /sys/fs/cgroup/user.slice/user-*.slice/user-@1000.service/app.slice/*/io.stat; do \
     [ -r "$f" ] || continue; \
     awk -v c="${f#/sys/fs/cgroup/}" '{for(i=2;i<=NF;i++){split($i,kv,"="); \
        if(kv[1]=="rbytes")r+=kv[2]; if(kv[1]=="wbytes")w+=kv[2]}} \
       END{if(r+w>1048576) printf "%9.1f MiB R %9.1f MiB W  %s\n", r/1048576, w/1048576, c}' "$f"; \
   done | sort -rn | head -15
   ```

   (`cancelled_write_bytes` is ignored deliberately: it nets out FS-level reclaim, not demand.) Cross-check per-pid deltas against the diskstats-throughput trap from the SIGSTOP doctrine: a wedged device (~4 MB/s) can hold some-avg10 at 30–45 at NEAR-ZERO throughput — if probe 1 shows high PSI but probe 2/3 show no writer, suspect device-level wedging (BTRFS metadata, fsync storms), not a process.

## ZRAM & Memory Reclaim

- **bun-memory-watchdog (2026-10-10)** — `bun test` (the qmd-mcp toolchain agent sessions spawn as plain user processes — no systemd unit to cap) hit ~70 GB RSS with no natural ceiling; a 30 s /proc sweep now SIGKILLs any bun whose VmRSS ≥ 16 GiB (exact resolved-exe match + PID-reuse re-verify, dry-run drill mode). Module `modules/nixos/services/bun-memory-watchdog.nix`, runbook `docs/services/bun-memory-watchdog.md`, fixture-tested by `checks.bun-memory-watchdog-selftest`
- **`vm.swappiness=150` for zram-only swap** — With zram as the ONLY swap, low swappiness tells the kernel to prefer page-cache reclaim (disk I/O on BTRFS/QLC NAND) over zram swap (in RAM) — this fed the recurring BTRFS I/O storms (`kworker/inode_switch_wbs` at 100% CPU, I/O PSI `full avg10=79%`). Correct range for zram-only: 100-200 (kernel docs: "for zram, use 100+")
- **ZRAM fill is monitored** — `system-health` emits `system_zram_swap_fill_percent` (orig_data_size/disksize from `/sys/block/zram0/mm_stat`) + `system_zram_fill_over_threshold` (≥90%); the Gatus "ZRAM Fill" check alerts Discord. Metrics are emitted ONLY when `/sys` is readable — absence fails the check fail-closed (no phantom greens)
- **ZRAM sizing for zram-only swap** — live zram0 = **~47 GiB (`memoryPercent = 50`) on ~94 GiB visible RAM** (MemTotal after the 18 GiB GPU VRAM carveout — the config's old ~33/~110 figures predated the carveout). A too-small zram (was 17%/16 GiB, then 30%/28.2 GiB) fills under normal load, and with no disk-swap fallback the kernel falls back to aggressive page-cache eviction = BTRFS disk I/O storms. **2026-09-02 sizing lesson:** the 28.2 GiB device sat at **97% fill (27.4 GiB swapped, 10.7 GiB physical at 2.6x) as STEADY STATE — 53% MemAvailable, 0.26% PSI, a perfectly healthy machine whose swap gauge read "critical"** (that reading fed the same-day sev1 alert-spam incident). Fill-% is only a meaningful cliff signal with headroom: at 50% the same load reads ~58% and the unevictable-shmem cliff moves ~19 GiB further out. Physical cost is bounded by compression (~18 GiB at full 47 GiB) and idle cost is ZERO (pages allocated only when stored) — sizing zram generously is free. Takes effect on REBOOT (zram is sized at boot). The 1 GiB VRAM carveout (the BIOS FLOOR — 512 MiB is not settable on this board; live since 2026-09-05 boot 13:16, GTT-first) grew visible RAM to ~124.3 GiB — the percent-based device auto-scaled to 62.2 GiB at 50% (verified live)
- **`vm.watermark_scale_factor=100`** — At 10 the kernel waits until memory is very low, then does aggressive synchronous "panic reclaim" I/O bursts. 100 (the default) starts reclaim earlier and gradually, avoiding sudden BTRFS writeback storms
- **`vm.dirty_ratio=5`, `vm.dirty_background_ratio=1` for QLC NAND** — 10% of ~94 GiB = 9.4 GiB of dirty pages before forced writeback = huge writeback bursts on QLC NAND. 5%/1% spreads writes more evenly
- **`vm.vfs_cache_pressure=150`** — Prefers reclaiming dentry/inode cache (cheap, no disk I/O) over page cache (expensive, requires disk reads/writes)
- **`vm.page-cluster=0` + `vm.watermark_boost_factor=0` (2026-09-05)** — every mainstream zram deployment (Fedora, Pop!_OS, ChromeOS) ships both; we sat at kernel defaults (3/15000) despite zram-only swap since forever. page-cluster=0 kills readahead-window amplification on swap-in (a clustered swap-in reads 8 pages to fault 1); watermark_boost=0 stops kswapd boosting off swap faults (pointless feedback on zram)
- **zram compression ratio is ~3.2x live** — Measured via `/sys/block/zram0/mm_stat`. zstd level=1 is optimal (level 3 gains 1.7% ratio for 11.5% less speed)
