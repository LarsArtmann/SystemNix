## Gatus Health Check Design Patterns

> **Where checks are DECLARED:** per-service checks live in the owning module's `services.integration.<name>.checks` entry — see [integration-registry.md](./integration-registry.md) step 9. `gatus-config.nix` keeps only the infra/meta core; never hand-add service rows there.

- **Alert `description` fields must NEVER contain `"` or `\`** — gatus 5.36.0 validates the description charset at startup and a violation PANICS the whole config (`alert description must not have " or \`, `invalid endpoint <key>`), crash-looping gatus while every restart fires `notify-failure@` (2026-09-29 storm: a `mount_point="/"` inside a description, ~5s popup cycle). `conditions` are exempt (validated as globs, quotes legal there). `checks.gatus-config-parse` runs the real `gatus validate` against the rendered evo-x2 yaml on every flake check — the only layer that sees descriptions composed across registry modules (source-level lints cannot). Note: `gatus validate` also attempts its sqlite open AFTER validation; that sandbox panic is expected and deliberately ignored by the check (pass = "Validated N endpoints" line present + no "error parsing config"). Do NOT set GATUS_LOG_LEVEL=WARN in that check — the endpoint-count line is INFO.
- `pat(*metric_name*)` = presence check (metric exists in `/metrics` output)
- `pat(*metric_name 0*)` = value check (metric exists AND equals 0 — e.g. "no errors")
- `pat(*<html*)` = HTML body check (web UI is serving HTML)
- **Liveness vs health**: liveness = "process alive" (`[STATUS] == 200`), health = "functional" (`[BODY] == pat(*metric*)`). Always include BOTH conditions — liveness alone gives false greens
- **"Intentionally headless" vs "desktop died"**: `niri-health-metrics` emits `niri_graphical_session` (1 if user has a wayland/x11 session via `loginctl`), `niri_desktop_died` (1 if graphical session active but niri not running), and `niri_crash_loop` (1 if `niri_restarts_10m >= 3`). Gatus alerts on `niri_desktop_died 0` and `niri_crash_loop 0` — NOT on `niri_running 0`. This avoids false alerts when the user is SSH-only and hasn't logged in via SDDM. `niri_desktop_died` uses a 60s grace period (2 consecutive checks) to avoid flapping during niri's 2s auto-restart window. **Freshness-composite contract (2026-09-19): the "Niri Compositor" check owns collector-death alerting for ALL niri checks** — node_exporter serves a frozen textfile forever, so a dead collector leaves every sibling check (Desktop Died/Crash Loop/Zombie/AW Watcher) blind at its last values; only the Compositor check's `system_niri_metrics_fresh` conditions can see that, and new niri metric checks must NOT grow their own freshness condition (they ride the Compositor contract). The four sibling VALUE-0 checks are line-anchored (`pat(*\n<metric> 0\n*)`, 2026-09-19) so a future HELP/TYPE comment in niri.prom cannot phantom-green them, and the collector's journalctl greps carry `timeout 10` per the journal-stall doctrine
- **Phantom metrics**: Rust `metrics` crate lazily serializes — a metric that's never incremented never appears in `/metrics`. Always verify the metric exists at runtime via pre-deploy-check.sh section 10
- **Escape layers are the real failure class**: a pat() pattern crosses THREE layers — Nix string → YAML → Go glob. gatus 5.36.0 `pattern.Match` = `filepath.Match` with `/` stripped; `\` is an ESCAPE, so a literal backslash-n matches only the letter 'n'. Write `\n` (single backslash) in double-quoted Nix strings; verify with `tests/test-gatus-patterns.nix` and the mutation method from `docs/status/2026-08-22_03-58_gatus-anchored-pattern-escape-bug-quick-wins.md`
- **Monitoring the monitor — read gatus's sqlite, never its API** (`system-health.nix`): the gatus HTTP API sits behind OIDC and 401s unauthenticated curl — the original curl-based self-check always fell back to a phantom 0 (permanently green). The collector reads `/var/lib/private/gatus/gatus.db` (DynamicUser hides `/var/lib/gatus` on the host) with `sqlite3 -readonly` (WAL readonly is fine as root): sustained failure = endpoints with results but ZERO successes in the whole table (gatus self-prunes retention); staleness = db+wal mtime >15 min (gatus wedged/dead). Emits `system_gatus_meta_scrape_errors` (1 = check itself failed), and the value metrics ONLY on success — absence fails the Gatus pat() conditions fail-closed. Post-fix, the metric reports TRUE sustained-failure counts (6 during the monitor365/browser-history outage era) instead of phantom zeros

## ClickHouse (SigNoz backend) traps

- **ClickHouse `background_pool_size` sanity check trap** — Reducing `background_pool_size` below the default (16) triggers cascading `Code: 36 BAD_ARGUMENTS` startup sanity checks: every `number_of_free_entries_in_pool_*` merge_tree setting (defaults 20/8/25) must be less than `background_pool_size * background_merges_mutations_concurrency_ratio` (default 2), and each fails one-at-a-time (whack-a-mole through deploys). Keep `background_pool_size` at default. The other 4 pool reductions (`background_schedule_pool_size=8`, `background_buffer_flush_schedule_pool_size=4`, `background_move_pool_size=2`, `background_fetches_pool_size=1`) are safe — no sanity-checked dependents (~145 threads saved). An eval-time assertion in `signoz.nix` catches `background_pool_size=2`
- **ClickHouse `Type=notify` without sd_notify** — Upstream sets `Type=notify` but the binary never calls `sd_notify`. SystemNix overrides `Type=exec`. Remove when upstream adds sd_notify
- **ClickHouse internal self-logs are unbounded + 1 Hz samplers (fixed 2026-08-17)** — the `system` db held 52 GiB / 9.13B rows (90% of the data dir): log tables had no TTLs, and `metric_log` (`collect_interval_milliseconds=1000`) + `asynchronous_metric_log` (`asynchronous_metrics_update_period_s=1`) sampled at 1 Hz (async alone: ~750 rows/s, 56M rows/day). Fixed in `signoz.nix`: 14d TTLs for all log families (config XML covers fresh tables) + `signoz-clickhouse-log-ttl.service` converging existing tables incl. zombie `<log>_N` copies from unclean restarts (stale, ~30 GiB, decay via TTL) + daily 04:20 timer. **`flush_interval_milliseconds` is the WRONG knob for volume** — it only batches rows into parts; row rate scales with the collect/update interval (verified live: flush 2000ms left the rate at 1 Hz). `metric_log` is WIDE (~274 KB column metadata): `MODIFY TTL` exceeds `max_query_size` (QUERY_IS_TOO_LARGE) → the script falls back to monthly partition drops, and its config block carries only the collect-interval halving. 13 permanently READ-ONLY zombies (TABLE_IS_PERMANENTLY_READ_ONLY: trace_log_14..18, query_metric_log_4..6, etc.) cannot be ALTERed via SQL — the script reports them for a human `DROP TABLE` decision (~10 GiB reclaim available)

## Shared monitoring modules

- **`backup-coordination` module** — Generic backup monitoring via Prometheus textfile. Add backups to `services.backup-coordination.backups.<name>` in `configuration.nix`.
- **`system-health` module** — Textfile collector for systemd state, memory, GPUActive, CPU%. Pre-computes boolean flags for Gatus (Gatus `pat()` can't do numeric comparison). **User-manager monitoring (2026-08-31):** `monitoredUserManagers` (default: the host's `users.primaryUser`) adds `system_user_units_failed{user}` / `system_user_manager_reachable{user}` / `system_user_units_scrape_errors{user}` via the machined bus proxy (`systemctl --machine=<u>@.host --user`, `timeout 10`-bounded) + the Gatus "User Unit Failures" check — catches USER-unit deaths the system-level checks can't see (smart-audio sat in start-limit-hit the whole 16:38 boot, nothing alerted). Logout ≠ wedge: `/run/user/<uid>` absent → reachable 0, failed 0 (legitimate logout, no alert); present-but-query-failed → scrape_errors 1 (the dnsblockd-:9090 wedge class, alerts).
- **Secret rotation monitoring** — `pocket-id-secret-rotation` checks client secret freshness (90d threshold). Does NOT auto-rotate.
- **Gatus `[BODY].jsonpath.X` unreliable in v5.36.0** — Use `[STATUS]` + `[BODY] == pat(*)` instead.

## SigNoz

- **SigNoz alert `target=0` + `above_or_equal` = always true** — `mkRule` has eval-time `validateTarget` assertion. Use `target=1` for "at least one" semantics.
- **SigNoz `up{job="..."}` rules NEVER match — the phantom-green `job`-label class (fixed 2026-08-27)** — the OTel prometheus receiver stores the scrape job as the resource attribute `service.name` (and `server.port` etc.); NO series ever carries a `job` label, and PromQL label matchers CANNOT reference dotted keys (`up{service.name="x"}` → 400 parser error; `up{service_name="x"}` → empty because that label only exists on series where the scraped binary self-reports it). Six rules sat permanently phantom-green (DNS Blocker Down, Docker Daemon Down, ClickHouse Down, Telemetry Collector Down, EMEET PIXY Daemon Down, GPU Thermal) while "Niri Compositor Down" (`niri_running < 1`) false-fired CRITICAL on every headless/SSH-only period. Fixes, all live-verified against the query API: (1) process liveness → `node_systemd_unit_state{name="<unit>.service",state="active"}` below 1 (the ollama pattern — the repo had already learned this once and only converted one rule); (2) endpoint-reachability (process alive but stats API wedged, the 2026-08-27 dnsblockd :9090 case) → `count(up{service_name="<svc>"}) or vector(0)` below 1 — works ONLY for binaries whose OTel bridge self-reports `service_name` (dnsblockd, pocket-id); note the up-series label FLIP: scrape success carries the self-reported labels, scrape failure emits a bare-label up=0 series, so a plain selector goes stale mid-outage (count+vector(0) turns absence into a fireable 0); (3) graphical-session services → the session-aware gates (`niri_desktop_died`, `system_emeet_pixyd_expected_down`) mirroring the Gatus design — never raw `niri_running`; (4) GPU temp → no `node_amdgpu_*_temp` metric exists; use `max(node_hwmon_temp_celsius{chip=~".*c5:00_0"} or ClickHouseAsyncMetrics_Temperature_amdgpu_edge)` — hwmon chip labels are PCI-address-keyed (fragile to this box's post-crash bus renumbering), the ClickHouse async metric name is stable but CH-dependent; the OR covers both blind spots. **Histogram suffix metrics are DOTTED in SigNoz** (`dnsblockd_dns_resolve_duration_ms.sum`, `caddy_http_response_duration_seconds.sum` — NOT `metric_sum`): query them via the `{__name__="metric.suffix"}` selector form or the panel/rule matches nothing (the `{__name__=~...}` regex form in Telemetry Export Failures is the established pattern). Meta-limitation: `system_signoz_alert_rules_healthy` only counts rules (>15) — it can NEVER catch this class; the generic detector is comparing each rule's PromQL against the metrics store, which needs per-rule expectations (absence-based rules legitimately return empty when healthy). **The `signoz-query-lint` flake check (2026-08-27 evening) now rejects the STATIC classes at eval time** — `job=` label matchers, underscore histogram suffixes (`metric_sum`), bare `up{service_name=` selectors without the `count(...) or vector(0)` wrapper, and a maintainable dead-metric blocklist (`node_amdgpu_gpu_temp_celsius`) — over `_signoz-alerts.nix` (comments stripped) AND `dashboards/*.json`. Rule-query verification workflow: `fetch http://localhost:8080/api/v1/rules` for states, `api/v1/query?query=...` for live selector checks, ClickHouse `signoz_metrics.distributed_time_series_v4` (`SELECT count() WHERE metric_name='X'`) for phantom-metric sweeps
- **SigNoz dashboards: removing a panel requires removing its layout item too** — panel JSON lives in `spec.panboards.<uuid>`, but `spec.layouts[0].spec.items[]` references panels by `$ref` path; deleting only the panel makes the v2 API reject the whole dashboard (`references unknown panel "<uuid>"`, HTTP 400) and the provisioner HARD-FAILS the deploy (by design). The 2026-08-27 GPU dashboard panel removal hit exactly this — second deploy caught it
- **SigNoz dashboard LAYOUT OVERLAP is the sibling validator failure (2026-09-17)** — a hand-added panel at `x=2,y=19` while two 6-wide panels already occupied the row made the v2 API reject the update with `spec.layouts[0].spec.items[12] and items[13] overlap` (HTTP 400) and the provisioner unit HARD-FAILED; the script's convergence verifier still printed "OK 7 dashboards" because it checks the name SET, not per-panel success — read the FAILED lines, never the final count alone. Recovery without a deploy: the provisioner's update is just `PUT /api/v2/dashboards/<id>` with the whole file, so fixing the JSON in-repo and PUTting it directly converges the live dashboard and the next provisioner run becomes "Unchanged: skipping". The `signoz-query-lint` flake check now rejects ANY pairwise grid-rectangle intersection across all `dashboards/*.json` (heredoc'd python trap; NOTE: heredoc terminators inside a runCommand `''` string must sit at the block's MINIMAL nix-indent level — nix strips the common indent and an indented terminator never matches, eating the rest of the script with bash "unexpected EOF"); negative-tested via `scripts/negative-test-lints.sh` case `signoz/dashboard-overlap`
- **SigNoz journald logs pipeline (2026-08-16 overhaul)** — the OTel journald receiver (`all=true`, `priority=info`, `start_at=end` — NEVER "beginning", no persistent cursor = full-journal re-ingestion on restart) ingests the WHOLE journal; the `transform/journald` OTTL processor extracts `body=MESSAGE`, `severity_*` from `PRIORITY` (string "0".."7"), and `resource.service.name` (precedence: SYSLOG_IDENTIFIER < `_SYSTEMD_UNIT` < `CONTAINER_NAME` — docker's journald log-driver makes container logs flow with the container name as service). All statements guard on `IsMap(body) and body["PRIORITY"] != nil` so OTLP logs pass untouched; `set(body, body["MESSAGE"])` MUST be the last statement (after it, field accesses return nil). One OTTL statement per list element — the parser does NOT split embedded newlines. The 2026-08 info-level CPU burn (96% CPU, monitor365-server at 900 entries/s) is gone — journal volume is ~5 MB/h (~6 entries/s, 500x below the burn era); journald's per-unit rate limiting (10k/30s) bounds recurrence. Docker's default log driver is `journald` (`default-services.nix`) — existing containers keep json-file until recreated
- **SigNoz's Services page is TRACE-driven — and the signoz-coverage module is the rail that keeps registration honest (2026-08-31)** — a service appears at `/services` ONLY if its binary actively pushes OTLP spans; logs (80+ journald service names) and the 9 prometheus scrape jobs are invisible there. For a month only 6 services ever sent spans (cv-application, crush-daily, browser-history, discordsync, file-and-image-renamer, gotenberg) while overview/PMA initialized a TracerProvider with ZERO span sites ("OTel tracing enabled" in the journal, then silence), papdashboard has OTel metrics but no trace SDK, and fastflowlm carried a pure-noop env var (removed). `modules/nixos/services/signoz-coverage.nix` closes the class: (1) a registry (`services.signoz-coverage.expected`, keyed by systemd unit, `wiring = "env" | "config" | "upstream"`) with eval-time assertions BOTH ways — wiring="env" entries must carry `OTEL_EXPORTER_OTLP_ENDPOINT` on their unit, and ANY unit setting that var must be a registry key (`untrackedOtelUnits` escape hatch); (2) a 5-min textfile collector reading ClickHouse DIRECTLY (`signoz_traces.distributed_signoz_index_v3` for last-seen spans — `serviceName` column, `toUnixTimestamp64Milli(timestamp)`; logs_v2's `timestamp` is UInt64 NANOSECONDS, `intDiv(max(ts),1e6)`, NOT DateTime64) emitting `signoz_traces_reporting/_missing/_upstream_gaps`, `signoz_logs_pipeline_stale`, `signoz_coverage_scrape_errors`; (3) Gatus "SigNoz Traces Coverage"/"Logs Pipeline Fresh" + three SigNoz self-watch rules. Fail-closed: query failure writes `scrape_errors 1` + `missing = enforced_total` (an `exit` inside the `{ } > "$TMP"` redirect block SKIPS the trailing mv — the file never lands). Upstream gaps stay visible via `signoz_traces_upstream_gaps` without paging; flip wiring "upstream"→enforced when instrumentation lands. **First catch within minutes of shipping**: enabling dnsblockd's `otlp_endpoint` (config key added in dns-blocker.nix) exposed a LATENT upstream bug — its exporter omitted `WithInsecure()`, so every export died `https://localhost:4318 … server gave HTTP response to HTTPS client` (the Go SDK defaults to TLS; the feature had never been enabled by anyone before). Scheme-aware fix RESOLVED 2026-09-13 (task queue): shipped upstream (dnsblockd `70ca2ea`, 2026-09-01, pushed via `8aa005f`), the lock carried it from `94c9cb93` (2026-09-06), the deployed `dnsblockd-94c9cb9` emits spans (live-verified `signoz_traces_reporting{service="dnsblockd"} 1`), and the registry flipped to wiring `"config"` with `maxUpstreamGaps` ratcheted 5→4; bank-sync had already been flipped to `"env"` 2026-08-31 (upstream `901978e`). Remaining gaps (overview, projects-management-automation, papdashboard, hermes) were re-verified never-emitted (`last_span_age -1`) and need real upstream instrumentation first (TODO_LIST tracks them). Event-driven emitters (renamer, gotenberg) get `maxAgeHours = 720` — their spans only exist when work happens; a 26h budget would page on quiet weeks. The `-health` sister unit shares the main unit's serviceName (same binary). **`wiring = "event"` added 2026-09-17 (gotenberg)**: a fourth wiring value for env-wired emitters whose work cadence is UNPREDICTABLE — gotenberg had 0 spans ALL-TIME in the retention window (ClickHouse-verified) purely because no office/email conversion ran in 30d+, and `last_span_age -1` counts as missing REGARDLESS of budget, so any finite budget is a standing false page for a never-seen event-driven service. Event entries keep the registry + reverse-assertion contract (still key members, expected/reporting gauges still emitted), are EXCLUDED from `signoz_traces_missing`, and do NOT inflate `signoz_traces_upstream_gaps` (that count now selects `wiring == "upstream"` explicitly); availability stays owned by the service's own Gatus health check. Flip back to `env` only when the workload cadence becomes regular.
- **SigNoz provisioners must CONVERGE, never delete+recreate** (`_signoz-scripts.nix` v7 pattern) — recreating a rule mints a fresh ruleId, and SigNoz emits a fake RESOLVED (old id) + FIRING (new id) pair per rule per deploy; an `|| true` on DELETE additionally let zombie duplicates accumulate (3 live at diagnosis). The provisioner compares a canonical projection (jq filter normalizing away API-injected fields like `disabled`/`stats`/`legend` in query specs) of desired vs live: unchanged → skip; changed → `PUT /api/v1/rules/{id}` (preserves ruleId — the v1 API supports PUT even though the UI uses v2); duplicates → delete ALL copies by name then create one; removed-from-nix → delete. Every state mutation checks its HTTP status; a final convergence assertion (exact name set, zero dupes, counts match — diff on failure) must pass or the unit fails. Same pattern for the notification channel via `PUT /api/v1/channels/{id}` (create-only-if-absent is not enough when templates change) and for ROUTE POLICIES (see next bullet): one policy per desired ruleId (create-if-absent), delete orphans+duplicates FILTERED BY the `systemnix` tag (never touch untagged — they may be user-created), assert exactly-one-per-rule. DASHBOARDS converge the same way via `/api/v2/dashboards`: native v2 (Perses `schemaVersion: "v6"`) JSONs with a stable slug in `.name` + tag `owner=systemnix`; the v2 GET returns the spec byte-identical to the file (verified), so `jq -S .spec` comparison detects drift exactly; zombie copies = same `spec.display.name` but different slug (the pre-v2 provisioner POSTed a fresh copy per deploy — **251 accumulated** and the new API's strict `DisallowUnknownFields` rejected the old format with HTTP 400 "unknown field title" on EVERY deploy, silently, because dashboard failures were warnings). Dashboard failures are now HARD failures
- **SigNoz Discord alert rendering** — Default alertmanager templates (`discord.default.title`/`.message`, referenced when channel `discord_configs[]` omit `title`/`message`) are label dumps — that is where `prometheusreceiver dev Unspecified…` spam came from. Custom inline Go templates on the channel config are supported and are what we ship. Fired alerts carry labels `alertname`, `ruleId`, `ruleSource` (= GeneratorURL) + rule labels (`severity`); annotations come ONLY from the rule payload's `annotations` field (the top-level `description` is UI-only) — `mkRule` in `_signoz-alerts.nix` sets `annotations.description` with `{{$value}}` (prometheus-style, expanded at rule-eval time). **`{{$value}}`/`{{$threshold}}` MUST be written with ZERO spaces inside the braces**: SigNoz's `preprocessTemplate` (`pkg/types/ruletypes/templates.go`) only special-cases the EXACT strings `{{$value}}`/`{{$threshold}}` — `{{ $value }}` gets rewritten to `{{index .Labels "value"}}` → renders empty. Successful Discord notifies are JOURNAL-SILENT (only warnings log); the cheapest positive delivery probe is a >256-rune alertname, which makes the notifier log a `Truncated title` WARN carrying `receiver` + `ruleId`.
- **SigNoz routes alerts EXCLUSIVELY via route policies — and API-created policies do NOT survive signoz restarts** (2026-08-16 regression: every alert silently dropped for ~30 min) — the custom dispatcher (`pkg/alertmanager/alertmanagerserver/dispatcher.go` → `nfmanager/rulebasednotification/provider.go Match()` → `GetAllByName(orgID, ruleId)`) resolves receivers ONLY through route policies whose NAME equals the ruleId, evaluating an expr-lang expression over alert labels. `preferredChannels` on a rule is NOT a route (it only feeds legacy startup-built matchers keyed to the ruleId AT PROVISION TIME — rule recreation breaks them); `receivers: ["default-receiver"]` in `/api/v1/alerts` is display-only. v1-API rules NEVER get policies auto-created (that path only runs for rules carrying `notificationSettings` from the UI), and — proven live 2026-08-16 — a plain signoz RESTART silently wipes all API-created policies (2026-04:47 deploy recreated 20/20 within 13s via the v6 provisioner). Policy API: `POST /api/v1/route_policies {expression: 'ruleId == "<uuid>"', kind: "policy", channels: ["Discord Alerts"], name: <ruleId>, tags: ["systemnix","auto-provisioned"]}` → 201; `GET /api/v1/route_policies` → `{data: [...]}` (list includes API-created); `DELETE /api/v1/route_policies/{id}` → 204. Rule DELETE does NOT clean name-matched policies (orphans accumulate — the provisioner's tag-filtered orphan pass handles this).
- **SigNoz alertmanager external URL** — `alertmanager.signoz.external_url` in signoz.yaml (factory section `alertmanager:` → `signoz:` → squashed `external_url`). Default is hardcoded `http://localhost:8080` — without this key every ruleSource link Discord shows is localhost. The rules engine bakes external_url into every rule object AT CONSTRUCTION (startup), so the key is useless without a restart: `systemd.services.signoz` carries `restartTriggers = [ signoz.yaml source, web dist source ]`. ## Collector & journal hygiene

- **`journalctl | grep -c` is an IO trap** — Serializes every journal entry through a pipe. Use `journalctl --grep "pattern" --output cat | wc -l` instead — filters inside journalctl. Add `-n N` for early termination once N matches are found. Affected: monitor365-server-watchdog, niri-health-metrics (every 30s!), niri-health.sh, niri-drm-healthcheck.sh.
- **`journalctl --grep` WITHOUT `--since` is STILL an IO trap under a small MemoryMax (2026-08-31 sev1 page)** — `system-health-metrics`' oomd counter ran `journalctl -u systemd-oomd --grep "Marked.*for killing" --output cat | wc -l` with NO time bound: it walked the ENTIRE 7.2G journal with page cache charged to the unit's 128M cgroup — reclaim thrash made one run take 11-28 MIN against a 2min timer, the textfile went stale most of the time, and sev1 paged "system_health metrics missing/stale" on the desktop all afternoon. EVERY journal counting query needs BOTH: a `--since` window sized to its semantics (24h ≈ 10s here) AND `timeout N` as the hard ceiling (fail closed via a `*_scrape_errors` gauge, totals held at last-known — `system_oomd_kills_scrape_errors` is the pattern, Gatus asserts it 0). **`--since` WITHOUT `timeout` is the same trap (2026-08-31 evening recurrence, 23:23-23:40):** the forgejo mirror-error scan HAD `-30 min` but NO timeout — under I/O pressure (movie playback off the same DAS USB link) four consecutive collector runs hit the 3min unit timeout, wrote NO textfile, and the sev1 bridge fullscreen-paged SYSTEM MONITORING STALE on every flap cycle mid-movie. Now `timeout 30` + fail-visible scrape_errors; the docker block (`docker info/ps/inspect` can hang on a wedged daemon) got `timeout 15`/`timeout 10` the same way. When a bounded-section collector still hits its unit TimeoutStartSec, the WHOLE textfile write is lost — every IO-capable section's timeout must sum comfortably under the unit ceiling. Same lesson in `btrfs-health.nix`: `btrfs scrub status /` hung 1h+ on a kernel-side ioctl wedge right after boot — ALL btrfs ioctls (`filesystem usage`, `scrub status`, chunk-check) are `timeout 30`-wrapped now, and the gc-guard timeout fails CLOSED (UNALLOC defaults to 0 → abort GC). **journalctl exit-code trap (same incident):** journalctl exits **1 when NO entries match the filter** (0 when entries shown, ≥2 real error) — under `set -o pipefail` that 1 propagates through `… | wc -l` and reads as a scrape failure. Treat 0 AND 1 as valid counts, only ≥2/timeout as failure: `out=$(timeout 60 journalctl … | wc -l) || status=$?` then `[ "$status" -le 1 ]`. Also: `| sort -rn | head -8` needs `|| true` — head's early close SIGPIPEs sort (exit 2, "fflush failed") and pipefail+errexit kills the whole collector unit into OnFailure (census section, live 17:13).
- **`psql` exits 0 on SQL errors — `|| fail=1` gates are vacuous without `-v ON_ERROR_STOP=1` (2026-10-03 paperless_tasks class)** — the collector's `psql … || fail=1` never fired when the query hit a schema break: psql printed the error, exited 0, and the run "succeeded" with an EMPTY interpolated metric — `collector_success 1` while the whole `.prom` was rejected by the exporter parser and paperless failed-task alerting went dark. EVERY textfile collector invoking psql must pass `-v ON_ERROR_STOP=1` (nonzero exit on first SQL error) so a fail-closed gate means anything. Sibling trap from the same incident: **paperless ≥3.1 Tag is a TreeNodeModel with NO `slug` column** — inbox membership is `is_inbox_tag` (bool), not a slug lookup. Both bugs were deploy-catchable (fixture test queued).
- **gawk treats an unopenable input file as a FATAL error — `awk '… END {…}' /proc/[0-9]*/stat` dies SILENTLY and emits NOTHING when a pid vanishes between glob expansion and open (2026-09-11 phantom-metric deploy block)** — END never runs, stdout stays EMPTY (not 0), exit 2, and the trailing `2>/dev/null || true` hides the evidence completely. The system-health `STUCK_DSTATE` scan hit exactly this: whenever a process exited mid-scan, `system_stuck_dstate_processes` went ABSENT for that 2-min collector cycle (the `[ -n "$VAR" ]` fail-closed emission gate suppresses the line), and pre-deploy §10 failed intermittently — the 05:41 gate probe saw absence, the 05:43 collector run saw `0`. gawk-verified: `fatal: cannot open file` aborts before END (nixpkgs awk = gawk 5.4.1). Fix: feed the glob through `cat … 2>/dev/null | awk …` — cat absorbs vanished entries as warnings and awk always reaches END, making the emission deterministic. Regression: `tests/test-scripts.nix` `awk-vanished-input` (dangling-symlink fixture reproduces the race deterministically + a static tripwire on the module source). Rule: NEVER pass a shell glob over churn-prone paths (`/proc/*`, `/sys/*`, `/tmp/*`) directly to awk as file arguments.
- **Every `systemctl --machine=<u>@.host --user` call opens a `login` PAM session + a logind session scope — keep such calls BATCHED in collectors (2026-10-06 gkr-pam burst)** — systemctl's machined proxy shells out to `systemd-run -M.host -pUser=<u> -pPAMName=login systemd-stdio-bridge`; `pam_gnome_keyring auto_start` (only `/etc/pam.d/login` carries it; sddm substacks it) fails promptless ("couldn't unlock the login keyring") once per call with no authtok. `system-health-metrics`' per-unit is-active/show/is-enabled probing over ~28 enabled user services meant ~28 journal lines + ~28 throwaway logind sessions EVERY 2-min tick (~20k lines/day). Root-causeable in one `journalctl -o verbose` step: the spam lines carry `_SYSTEMD_UNIT=run-p<pid>-i<seq>.service` + `_EXE=…systemd-executor`. Fix shape: one batched `systemctl … show -p Id -p ActiveState -p Type unit1 unit2 …` for all candidates (+ one for sockets) = 2-3 bridges per scan. The direct user bus is NOT an option from hardened root units: `CAP_DAC_READ_SEARCH`/`CAP_FOWNER` don't cover socket-connect write checks nor setuid drops to the 0660 `/run/user/<uid>/bus`. Residual 1-2 lines per tick are the machined floor — acceptable; the desync-related line at real SDDM login is separate (desktop.md keyring lore).

## Telemetry hardware keys

- **nvme-cli 2.16 JSON key names** — `nvme smart-log -o json` emits `avail_spare`/`spare_thresh`/`percent_used`/`temperature` (Kelvin!) — NOT `available_spare`/`percentage_used`. The string `available_spare` appears in the binary only as a bit-name inside the `critical_warning` sub-object. A `jq '.[$key] // 0'` fallback turned this rename into weeks of phantom `0` values feeding a false "Spare Blocks Low" alert; collectors must error+skip on missing keys (see `node_nvme_collector_keys_missing` + the Gatus "NVMe Collector Key Integrity" check).
- **Hardcoded `/dev/nvme0n1` in smartd + nvme-health-monitor ENUMERATION-SHIFT trap (fixed 2026-08-31)** — inserting the Samsung 970 EVO Plus internally made IT nvme0 and slid the Lexar system disk to nvme1; `services.smartd.devices = [{ device = "/dev/nvme0n1"; }]` and `services.nvme-health-monitor.device` (default `/dev/nvme0n1`) then silently monitored the BRAND-NEW disk while the QLC system disk (root of everything) lost ALL SMART/nvme telemetry. Both now use `/dev/disk/by-id/nvme-<model>_<serial>` (slot-independent; smartd 7.5 parses by-id for nvme — onecheck-verified). Same class as the sd-letter udev trap: NEVER reference nvme/sd devices by kernel-enumerated names in configs.
