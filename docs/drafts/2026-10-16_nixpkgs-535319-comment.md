Ran this module in production (nixpkgs 7fd4004d, crowdsec 1.8.1, PrivateUsers rendered) and hit two of these for real:

1. `machines add` is non-idempotent: it writes the DB row first, the credentials file second. When the file write EACCES'd (the state root materialized root:root — `/var/lib/crowdsec` itself is still not in the new `dirs` list here, only `data_dir` below it), every later start fails with `user already exist` because the guard only checks the file. We delete the orphan before the add:

```
if [ ! -s "$creds" ]; then
  cscli machines delete "<name>" --ignore-missing || true
fi
```

`--file` alone doesn't fix the DB-first ordering. Checked v1.8.1 `climachine/delete.go`: no confirmation prompt, missing row returns nil, so this is a no-op on healthy boots.

2. Same deployment, for the PrivateUsers story: `AmbientCapabilities = [ "CAP_DAC_READ_SEARCH" ]` read nothing — caps held inside the userns don't apply to host inodes, the file acquisition globbed zero files with no hint why. Supplementary groups DO map through the userns (journal source reads fine via `systemd-journal`, and adding the crowdsec user to the log dir's owning group fixed those reads). So the `extraGroups` option here is the right shape; the capability route is a trap.
