# SigNoz Web UI: 404 Root-Cause Fix — Built, Deployed, Serving

**Session:** 2026-08-16 ~19:40–21:25 · **Host:** evo-x2 · **Outcome:** ✅ `https://signoz.home.lan/` serves the SigNoz SPA shell (was: bare `404 page not found` from the Go API router)

## Problem

From the MacBook on LAN, `https://signoz.home.lan/` returned a plain-text `404 page not found`. Caddy's `protectedVHost` LAN bypass proxies straight to the query service on `:8080`, and the deployment ran SigNoz **headless**: `web.enabled = false` in `signoz.nix` and no frontend dist anywhere. Only the `/api/v1/...` surface existed (which provisioner, alerting, and Gatus use). Discord alert links rendered 404 for the same reason — a known deliberate gap, tracked as the "signoz vHost 404 warning" in the smoke test.

## Root Cause Chain (upstream source, pinned rev `c40ebb02`)

- `pkg/web/config.go`: `web.directory` defaults to `/etc/signoz/web`, `web.index` to `index.html`; `web.enabled=false` swaps in the `noop` provider → every non-API route falls through to gorilla/mux 404.
- `pkg/web/routerweb/provider.go`: at startup the Go binary `os.Stat`s the directory, reads `index.html`, templates `[[.BaseHref]]` + `[[.Settings]]` into it, caches the result, and serves SPA fallbacks itself (missing file → index.html). So the ONLY missing piece is a static dist at the configured path.
- Upstream builds it via `make js-build` = `cd frontend && CI=1 pnpm install && pnpm build` (vite → `frontend/build/`).

## d) TOTALLY FUCKED UP (own goals, honestly)

1. **Phantom metric self-inflicted deploy block.** My first Gatus needle `pat(*data-react-helmet*)` made the pre-deploy-check `pat()` extractor read `data` as a Prometheus metric → "Metric 'data' ABSENT" → **DEPLOY BLOCKED**. I knew that extractor exists (it's documented) and still tripped it; fixed by anchoring on `<title data-react-helmet`. Should have grepped the extractor BEFORE writing the pattern.
2. **Deploy lock collision, badly handled.** First deploy failed with `Could not acquire lock` because the auto-git daemon's own `nh os switch` was mid-activation (same generation!). My abort-on-failure semantics then skipped the entire post-switch section — provisioner restarts, `buildcache-usb-recovery`, smoke tests. The system converged anyway *because the daemon's run did that work*, not because my pipeline did. Deploy tooling should wait-and-retry on lock contention, not abort.
3. **First FOD attempt burned a build cycle** by shipping a placeholder hash before checking `fetchPnpmDeps`' requirements in the pinned nixpkgs (it demands explicit `fetcherVersion`). Minor, textbook, avoidable by reading the builder first — I *did* read it, just after writing the attrset instead of before.
4. **Unrelated breakage fixed under time pressure without pre-verification of its blast radius**: the daemon's flake.lock bump (nixpkgs → `e5bdc4a`) broke eval via the stale `wf-recorder` ffmpeg override (`called with unexpected argument 'ffmpeg'`). I confirmed upstream wf-recorder now builds against ffmpeg_8 from cache and removed the overlay — correct, but it was a parallel-session change interacting with mine, and I touched it only because it blocked MY deploy.
