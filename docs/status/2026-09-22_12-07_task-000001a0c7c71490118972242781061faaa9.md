## d) TOTALLY FUCKED UP

Radical honesty. Two real findings; neither is currently causing damage — both were found and fixed during THIS run's self-review, which is itself the criticism: they should have been caught before the item was closed.

### D1 — `borg.yaml` was never git-tracked (latent go-live blocker) — FIXED `1c7e85bc`

- **What was broken:** `platforms/nixos/secrets/borg.yaml` — the encrypted passphrase, dedicated SSH private key, known-hosts pin, and repo target — existed ONLY in this working tree. `.gitignore:144` (`secrets*`) swallowed it; every other file in that directory is force-added, this one wasn't (the prior session skipped the `git add -f` step that is IN the AGENTS.md sops recipe).
- **Severity:** latent, not user-facing — but for a backup leg whose entire purpose is surviving this machine's death, the secret being untracked is exactly the wrong failure mode. A fresh clone (or CI, or the owner's second machine) would lack the secret at go-live, and NOTHING catches it: the sops declarations are `enable`-gated, so `sops-key-audit` never even looks until the flip — the audit protects only shapes that are on.
- **Root cause:** prior session forgot `-f`; **my failure** is that the audit checked module, sops wiring, deploy.sh, docs, and both eval shapes — but never ran the one-command `git ls-files` check on the secrets dir. It was one command away.
- **Mitigation:** fixed (`git add -f`, verified encrypted blobs in HEAD). See F23 for the structural guard.

### D2 — Git index write failure during the D1 fix (live incident, repaired in-session)

- **What happened:** `git commit` of the D1 fix pre-commit-validated fine, then died with `fatal: repository has been updated, but unable to write new index file. Check that disk is not full…`. The commit itself **did** land (`1c7e85bc`, content verified), but the post-commit index write-back failed — leaving a **phantom staged deletion** of `borg.yaml` (index lagging HEAD) on a disk with 123 G free, i.e. the "disk full" diagnosis was false. Most probable cause: index contention with the auto-commit daemon racing the same `.git/index`, on the QLC root during today's io-storm conditions.
- **Severity:** transient corruption of git metadata only; content never at risk.
- **Mitigation:** repaired in-session with `git add -f` (re-staging the file clears the phantom deletion; deliberately avoided `git reset`/`git restore` per house safety rules), then verified `git show HEAD:` blob content + clean status. No fsck-level damage observed; not run (heavy) since the tree is consistent.

### D3 — What is NOT fucked up (checked, for the record)

Repo green at HEAD: `nix flake check --no-build` passes, evo-x2 eval green, both eval shapes assertion-clean, formatter clean, pre-commit hooks (incl. gitleaks on the staged sops file) passed.
