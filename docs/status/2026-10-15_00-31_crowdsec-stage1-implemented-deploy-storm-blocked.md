## b. The live-fire bug the first deploy hit (upstream module gap, root-caused + fixed)

First activation (parallel session's deploy, 22:19): `crowdsec-setup` → `cscli machines add: user 'evo-x2': user already exist`, start-fail loop, then start-limit hit. Root cause chain (all source/live verified):
1. Upstream `crowdsec.nix` tmpfiles list creates `state/`+`confDir` but **NOT `/var/lib/crowdsec` itself** — the parent materialized `root:root 0755` (boot-time side effect of the bouncer module's register oneshot `StateDirectory = … crowdsec`, which also auto-activates because ITS enable defaults to crowdsec.enable).
2. `cscli machines add --auto` writes the **DB row first, credentials file second** → DB write succeeded, creds-file write EACCES'd → orphan machine in SQLite → every retry fails permanently.
3. Fix (c41a21ad): tmpfiles `20-crowdsec-root` chowns `/var/lib/crowdsec` → `crowdsec:crowdsec 0750` (`d` entries re-chown existing dirs — heals the live dir at next activation); `registerBouncer.enable = false` for stage 1 (kills the StateDirectory ownership hazard; stage 3 re-enables deliberately); `crowdsec-machine-repair` ExecStartPre (runs BEFORE setup): creds file missing → `cscli machines delete <host> --ignore-missing` — flag verified against `cmd/crowdsec-cli/climachine/delete.go` v1.8.1 raw source (no `--force` on delete, no confirmation prompt, `--ignore-missing` returns nil on absence).
