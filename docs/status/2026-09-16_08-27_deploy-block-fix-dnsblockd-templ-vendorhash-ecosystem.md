## e) WHAT WE SHOULD IMPROVE

1. **Upstream gate: "go.mod changed without vendorHash refresh"** — a tiny pre-commit hook (or extension of go-taskqueue's existing `vendor-hash` drift check) that fails when go.mod/go.sum changed but the flake's vendorHash line did not. Would have prevented 3 of 3 Go failures this session. Impact: kills the recurring multi-repo deploy-block class. Fix: add `check-vendorhash-drift` (grep-shaped, seconds to run) to go-standard's check set in go-nix-helpers so every consumer inherits it.
2. **Upstream gate: templ artifact provenance** — dnsblockd's byte-equality gate caught the drift at BUILD time (good, fail-closed), but the daemon committed the poison silently. A pre-commit running `scripts/check-ui-artifacts.sh` (already exists in dnsblockd!) would fail the daemon's commit instead of the next deploy. Fix: wire check-ui-artifacts.sh into dnsblockd's .githooks/pre-commit.
3. **The identical-got-hash diagnostic deserves codification** — when a go-modules FOD hash-mismatches, compare `got:` across two revs: identical → local-replace-only bump or stable proxy (safe to refresh hash); different → re-tag poisoning suspect (do NOT bless; investigate upstream tag). This is a new, cheap discriminator that saved this session from a wrong "re-tag" rabbit hole. Fix: AGENTS.md Private-Go-Repos section.
4. **Daemon race discipline needs to be mechanical, not remembered** — I knew the doctrine and still lost two commit races. Improvement: always run `git status --short && git show --stat HEAD` as part of the commit command itself (`git status --short && git add <paths> && git commit …`), never as a prior step.
5. **Deploy-hold decision under parallel sessions needs a crisp rule** — this session I held the deploy on "parallel WIP in tree"; the tree then went clean via daemon sweep, making the hold judgment call ambiguous. Suggestion: deploy.sh gains a WARNING (not block) listing `~/projects/*` repos whose master is ahead of origin AND that SystemNix pins via `github:?ref=master` — the exact drift that made this session's tq fix unreachable from the lock.
6. **vendorHash-measurement hygiene**: I measured go-taskqueue's first got-hash (`sFltv49…`) against a PRE-tidy tree and then had to recompute (`dtC0Y6…`) after the tidy changed the module set. Lesson: when the fix involves BOTH source (go.mod) and hash changes, do the source fix FIRST, then one hash measurement — never interleave. Cost: one extra FOD build cycle under elevated IO.
7. **`--autostash` rebase under a live parallel session worked but was a gamble.** The safe sequence I should default to: `git status --short` (note foreign unstaged files) → announce → rebase. It worked because the bot commit touched disjoint files; next time might not.
