1. **`.crush/live-verify-404.py` follows redirects (known gap, still unfixed):** its alerts probes report FAIL because urllib lands on dash's 200. Fix = install the NoRedirect opener (the script's own docstring says so). Deliberately NOT fixed this session: it lives in `.crush/` alongside the locked-tree session's files and the raw-probe evidence supersedes it; queued as a one-liner.
2. **Search-domain interplay (behaviour note, not a bug):** with `search home.lan` in resolv.conf, glibc/python retry ANY failing lookup as `<name>.home.lan` — which now hits the wildcard. A public-typo name (`foo.larsartmann.cloud` unknown locally) lands on the Caddy 404 page instead of NXDOMAIN (this is also why live-verify probe 6 "passed": it exercised the home.lan wildcard via search expansion, not the cloud catch-all). Same behaviour an Unbound local-zone wildcard would produce; documented in dns-blocker-config.nix + gotchas.
3. **Cloud catch-all remains untested end-to-end BY DESIGN:** the cloud zone is explicit-record-only, so only an explicit cloud name WITHOUT a vHost reaches the cloud catch-all; its config is unchanged since the 2026-10-07 render verification.
4. **dnsblockd gate flakes under load (upstream, pre-existing, NOT this diff):** `TestProxy_WebSocketUpgradePinned` (15s loopback WS i/o timeout) and `TestHealthHandler_AfterDNSCrash` (ephemeral-port bind race) failed intermittently in the sandbox under load 50–136 and passed every solo retry; a vendored-sdns global (`cache.SetCacheSizeMetrics` vs the otel sdns bridge collector) data-race wave (55 tests) fired once under -race at load ~100 — server code is byte-identical to a fully-green full-gate run.
