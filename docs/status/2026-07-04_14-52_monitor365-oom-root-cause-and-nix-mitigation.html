07The One Question I Can't Answer

Why does the Monitor365 agent allocate 12 GB of virtual memory?

The agent's RSS is only ~217 MB, but its total-vm is consistently 10-12 GB. This is what makes oom_score so high (827) — the kernel sees 12 GB virtual and ranks it as the most memory-reclaimable process on the system, even though it's only touching 217 MB.

Possible causes:

  • Rust/tokio default thread stack reservations (each thread reserves a large virtual stack guard)
  • mmap with MAP_ANONYMOUS for arena allocators that never touch most pages
  • SQLite WAL mode pre-allocating large virtual address ranges
  • Something in the collector pipeline (fs_event watcher?) mapping large buffers

I can see total-vm:12,604,256kB in the OOM kill log, and VSZ: 6,899,628 (6.6 GB) in ps aux for the current agent PID. The discrepancy suggests the virtual size grows over time. Understanding this would tell us whether 512M MemoryMax is sufficient or whether the agent needs upstream memory profiling. Without being able to run valgrind --tool=massif or strace -e mmap (blocked by security policy), I can only hypothesize.
