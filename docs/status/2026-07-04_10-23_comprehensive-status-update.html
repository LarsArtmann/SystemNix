The last deploy failed with ExitStatus(Exited(4)) because a service was in start-limit-hit; the fix (systemctl reset-failed) is now load-bearing. 04Totally Fucked Up

Critical

GPUActive memory crisis

evo-x2, amdgpu, /proc/meminfo GPUActive

128 GiB physical RAM → ~94 GiB visible → 51+ GiB consumed by GPUActive (unreclaimable, GPUReclaim=0). Standard tools (free, htop) do not show this breakdown, so the system appears to have "mysterious" usage. The TTM pool is configured with a 112 GiB limit, exceeding visible RAM.

Why it matters This is the root cause of the chronic OOM pressure, oomd kills, service crash-loops, and deploy failures. Until GPUActive is understood and bounded, every other mitigation is a band-aid.
Critical

MemoryMax overcommit

systemd service definitions

Sum of service MemoryMax quotas exceeds the ~43 GiB actually available after GPUActive. The quotas were designed for a system with ~94 GiB free, not one where the GPU already owns half.

Mitigation Right-size every quota. Start with a scripts/memory-audit.sh that sums quotas against MemTotal - GPUActive and flags overcommit.
Critical

reset-failed is load-bearing

deploy.sh

The deploy script now runs systemctl reset-failed (system + user) before every switch because services chronically crash-loop into start-limit-hit. This masks the real instability.

Risk If a service is legitimately broken, reset-failed allows the deploy to proceed anyway, potentially leaving the system in a worse state.
Critical

No off-site backup

BTRFS /data, source code, secrets

A single disk failure, ransomware event, or catastrophic BTRFS corruption would wipe the homelab. No BorgBackup, rsync.net, or cloud DR exists.

Critical

Pocket ID provisioning cascade

pocket-id-provision.service

Slow Pocket ID startup causes many downstream services to start simultaneously, spiking memory during boot and contributing to the OOM chain. Ordering and resource constraints need review.

05What We Should Improve

1. Make GPUActive impossible to ignore

Add a DMS widget, a Gatus check, and a SigNoz metric that surfaces GPUActive from /proc/meminfo with a clear alert when it crosses a threshold (e.g., 40 GiB).

2. Right-size memory quotas

Write a memory-audit script and adjust every MemoryMax/MemoryHigh to fit the real available pool. Add RestartSec=5 and RestartSteps=3 to serviceDefaults to reduce crash-loop thundering herds.

3. Replace reset-failed with health-gated deploy

Instead of blindly resetting failed units, only reset specific units that the pre-deploy check has verified are safe to reset. Log any unexpected failures and abort the deploy.

4. Stagger service startup

Add After= / RequiresMountsFor= and memory-ordered targets so heavy services (SigNoz, Immich, ClickHouse) do not all start at once after Pocket ID.

5. Off-site backup now

Provision a Hetzner StorageBox (or similar), set up BorgBackup via sops-managed SSH key, and back up /data, ~, and critical state dirs nightly. This is higher priority than most feature work.

6. Fix the real agent crash

Restoring visibility is good, but the Monitor365 agent still has an upstream Rust panic. Either fix the Axum 0.7 route issue, downgrade the dependency, or replace the agent's metrics path with a simpler health check until upstream is stable.

7. Stop building from source on Darwin

The 256 GB SSD is 90%+ full. Audit every Darwin package and avoid any source build. Cache heavy packages on the NixOS host where possible.

8. Split the largest modules

signoz.nix and forgejo.nix are too large. Extract helpers, OIDC setup scripts, and service definitions into separate files to reduce merge conflict risk and review burden.

07Top #1 Question I Cannot Figure Out Myself

Is the 51+ GiB GPUActive on Strix Halo a driver/firmware bug we can fix with a kernel or amdgpu update, or is it an inherent architectural behavior of unified-memory APUs that we must design around forever?

Everything in the codebase treats GPUActive as an observed fact: we read it from /proc/meminfo, we cap other services around it, and we warn about it. But the codebase cannot answer whether this memory is actually in use by the GPU, leaked by the driver, or reserved by firmware. A definitive answer requires:

  • Testing on a newer kernel (linuxPackages_latest) or amdgpu firmware,
  • Comparing with Windows behavior on the same hardware,
  • Reading TTM/TTM pool debugfs counters, and
  • Possibly checking AMD errata or Mesa bug trackers.

Until this is known, every memory decision is a bet. If it is a bug, we patch or upgrade. If it is architecture, we must permanently reserve ~50 GiB from service planning and document it as non-negotiable.
