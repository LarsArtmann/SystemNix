## TL;DR (16:59)

1. **The span was noise.** 2,613 of bank-sync's 2,643 error spans in the 10 days to 2026-11-28 (98.9%) are `context canceled`, all of them dashboard reads whose HTTP client had already left. The pasted span is the second of 13 error spans produced by one aborted page load on 2026-11-24 22:53:56.888. Nothing failed in the sync path.
2. **Three fixes are applied.** go-cqrs-lite: a cancellation no longer sets the span status to Error. bank-sync: an aborted page load stops at the first canceled loop iteration, is not cached, and logs at Debug. SystemNix: journald log `service.name` is now per record and named like the trace (`bank-sync`, not `bank-sync.service`).
3. **The SystemNix fix is LIVE and measured:** another session's deploy restarted the collector at 16:25:25 with the new config; the next 10 minutes held 15,420 journald rows from 133 units with 0 rows under a wrong service name (before: 340 of 430, 79%, wrong in a throwaway run of the old statements).
4. **The two Go fixes are NOT live.** go-cqrs-lite's change sits uncommitted in its working tree; bank-sync's is committed by the daemon but unpushed. The go-cqrs-lite fix reaches bank-sync only through a new `otel/v4` tag, a `go.mod` bump and a vendorHash update. Until then production still shows 13 error spans and one WARN per aborted page load.
5. **The trace-to-log correlation was not applied.** It needs a design decision (three options), not an edit: filed as the row "Trace-to-log correlation" in bank-sync's `TODO_LIST.md`.

## e) What we should improve

1. **Signal quality of bank-sync traces.** After the `otel/v4` bump a canceled query is no longer an error; go further and give each request a root span, so one page load is one trace with its queries as children instead of N root traces, and so a trace can be opened to the page that caused it.
2. **Error families that lie.** A static `WrapTransient` around a DB call turns "the client left" into `[transient:db.query]`. Either the storage wrap sites become cancellation-aware in bank-sync, or go-error-family's `Wrap*` constructors demote a `context.Canceled` cause to Rejection fleet-wide. The second is the root-cause fix and a library behavior change; it needs a decision.
3. **Log ingestion is three defects deep for every stdout app, not only bank-sync:** severity is DEBUG for every line (PRIORITY 6), multi-line error trees arrive as unrelated records, and until 16:25 today three quarters of all rows carried another unit's service name. The first two are still open and they decide whether "filter logs by severity" is usable at all.
4. **Trace-to-log correlation needs a decision, not more investigation** (row "Trace-to-log correlation").
5. **The trigger of the aborts is still unknown.** A client that leaves about 30 ms after the first query, up to four times within one second, is navigation churn or automation, not an impatient human. Until the access log is read, every fix here treats the symptom.
6. **Volume.** 4.4 M `query.handle` spans in 10 days (about 5 per second) for a single-user dashboard is a cost question nobody has asked yet.
7. **Process, for me:** run the session-start probe; verify structural claims before putting them into a subagent brief; read the component source that is already on disk before configuring it; re-check live state right before writing "not live yet"; check for a running deploy before any heavy command; write the memory entries when the lesson is learned.
8. **Process, for the fleet:** the daemon commits with heuristic messages and possibly without the pre-commit legs; work that depends on gates (a shared library's API surface, a fleet-wide collector config) should get its full gate run in the session, not "before the push, some other time".
