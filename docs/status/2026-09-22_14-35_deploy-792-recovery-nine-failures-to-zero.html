Browser History SQLITE_READONLY crash-loop: uid drift + a symlink that ate the heal

modules/nixos/services/browser-history.nix

The 13:04 mass-restart handed the DynamicUser unit a different dynamic uid (files in the state dir stayed owned by 65293, the deterministic uid in use since Aug 9) — the main DB became unwritable → exit-69 loop. The binary (1c8f967) was exonerated: it had run healthy for 1.5 days. The first heal attempt was a silent no-op because /var/lib/browser-history is a symlink into private/ and chown/chmod -R never follow a symlink top-level argument.

Fix +-privileged ExecStartPre heal operating on /var/lib/private/browser-history: journals ls -lan (evidence), chown -R --reference to the directory's owner, and chmod -R u+rwX. The nightly backup's root-sqlite open also became -readonly (WAL sidecar poisoning class). Server healthy (200) since.

05e) What We Should Improve

+
New-service bring-up checklist wantedBy + enable symlink + one verified unit start + smoke gate on the .wants symlink BEFORE the first deploy carries the module. Health Hub shipped all UI/monitoring surfaces but the one line that starts it.
+
DynamicUser + persistent state is a mass-restart hazard The deterministic-uid assumption holds until a mass activation shuffles allocation. The ownership-heal ExecStartPre pattern (evidence + chown --reference + chmod u+rwX on the REAL private/ path) should be considered for every DynamicUser service with pre-existing state files.
+
Probe mounts with timed, permission-aware writes "WRITE HANG/FAIL" conflated EACCES with hangs and sent the diagnosis down a wrong path (wedged DAS theory). Timed probes on user-writable paths per mount separated the two in seconds.
+
Concurrency discipline during guard-active windows The storm was ~20+ live agent sessions doing latency-bound fsync churn on the QLC root (PSI 40-70% at 4-8% disk busy). The gates and guard contained it, but the box spent the morning sacrificing flm for it.

07g) The One Question I Cannot Answer Myself

Why does setattr with the setgid bit EPERM inside the hardened sandbox even with CAP_FSETID in the bounding set?

Facts: root process, caps CHOWN/FOWNER/DAC_OVERRIDE/(+FSETID) bounding, NoNewPrivileges=true, chmod 2770 fails on a foreign-group dir and rsync mode-sets fail with every cap present — while the identical operations succeed as an unprivileged user outside the sandbox on the same filesystem. Something in the systemd sandbox (NNP cap handling at exec? an idmapped/flags-adjusted ReadWritePaths bind?) strips effective capability use for setattr.
