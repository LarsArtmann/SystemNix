04Totally Fucked Up

Critical

Strix Halo GPUActive Memory Crisis

/proc/meminfo — GPUActive field — boot.nix TTM config

evo-x2 has 128 GiB physical RAM but only ~94 GiB visible to Linux (34 GiB BIOS VRAM carveout). Of that 94 GiB, GPUActive (GTT buffer objects) consumes 51+ GiB (55%) with only desktop workloads (Helium browser, Quickshell, niri). GPUReclaim=0 means these pages CANNOT be reclaimed under pressure. The TTM pool is configured with pages_limit = page_pool_size = 112 GiB — exceeds the 94 GiB visible! Combined with zram swap at 100% full, the system runs in chronic memory pressure.

Why it's fucked up: The TTM pool config was set to "fix" GPU OOM but overshot into consuming all available RAM. free -h and htop do NOT show GPUActive — only /proc/meminfo exposes it. This is invisible to the entire monitoring stack. Every OOM crash, every journald starvation, every watchdog reset traces back to this.

Impact: Every Helium crash, every display hotplug stall, every near-OOM event is amplified by this. The system has ~30 GiB of usable RAM for all user processes despite having 128 GiB physical.
Critical

Helium Crashes on Every Display Hotplug

platforms/common/packages/base.nix:34-43 — MESA_VK_WSI_PRESENT_MODE in amd-gpu.nix:27

Chromium's GPU watchdog kills the GPU process when it stalls during display pipeline reconfiguration (monitor unplug → TV plug). On Strix Halo DCN 3.5.1, surface recreation takes longer than the ~10s watchdog timeout due to the GPUActive memory pressure above. Amplified by --enable-zero-copy (DMA-BUFs invalidated on connector change, no software fallback) and MESA_VK_WSI_PRESENT_MODE=immediate (narrowest possible race window for Vulkan swapchain recreation).

Fix Applied: --disable-gpu-watchdog added to Helium wrapper. Flake check passes. Pending deploy. Secondary risk: MESA_VK_WSI_PRESENT_MODE=immediate remains in amd-gpu.nix — consider removing if other apps stutter during hotplug.
Critical

Jan llama-server Respawner Leak

Jan AI app — not a systemd service

Jan spawns a new llama-server process every 1-3 minutes (~1.2 GB each). Not managed by systemd, no cgroup limits. Accumulates until OOM or manual kill. Needs investigation — either cgroup wrapping or Jan configuration fix.

Critical

Swap Permanently at 100%

zram swap configuration

zram swap is at 100% utilization. With ~30 GiB effective RAM for user processes, swap is constantly exhausted. This causes: journald starvation under pressure, OOM cascade chains (Helium → Electron → dbus-broker → niri loses DRM master), and slow display pipeline reconfiguration. The root cause is the GPUActive crisis above — treating the symptom (swap) without treating the cause (TTM pool) is futile.

07The #1 Question I Cannot Answer

Should we cap the TTM pool to ~40 GiB, or is the 34 GiB BIOS VRAM carveout itself the problem?

The entire memory crisis chain traces back to one architectural decision: the BIOS carves out 34 GiB for VRAM on this Strix Halo APU, leaving only ~94 GiB visible to Linux. Then the TTM pool config (pages_limit = page_pool_size = 112 GiB) allows the GPU driver to consume more than all visible RAM via GPUActive (GTT buffer objects), currently eating 51+ GiB.

Option A: Cap the TTM pool to ~40 GiB. This frees ~54 GiB for the OS. But will Helium, Ollama, and Quickshell GPU OOM? We don't know the actual working set — GPUActive grew to 51 GiB organically, suggesting the GPU driver needs that much for current workloads. Capping too low may just move the crashes from "GPU watchdog kill" to "GPU out-of-memory."

Option B: Reduce the BIOS VRAM carveout. The GMKtec EVO-X2 BIOS (v1.11) exposes a VRAM allocation setting. Reducing from 34 GiB to e.g. 16 GiB would give Linux ~112 GiB visible. But the carveout exists because Strix Halo has unified memory — the GPU physically shares system RAM. Reducing VRAM may starve the GPU of dedicated memory for compute workloads (Ollama, video decode). The BIOS setting may also not be linear — it could be a minimum guarantee, not a hard cap.

Option C: Leave the TTM pool as-is but set GPUReclaim=1 (currently 0). This would let the kernel reclaim GPUActive pages under pressure. But GPUReclaim is a relatively new amdgpu feature and its behavior on GFX1151 (gfx1151) with unified memory is undocumented. It may cause GPU hangs or data corruption if it reclaims pages still in use by the GPU command stream.

Why I can't figure this out: There is no documentation on the correct TTM pool size for Strix Halo desktop workloads. The AMD upstream guidance for unified-memory APUs is "let the driver manage it" — but the driver default was insufficient (causing GPU OOM in Ollama), which is why the pool was increased in the first place. Each option has a plausible failure mode that I cannot evaluate without destructive testing on a production machine. The correct answer likely requires either AMD engineer input or a controlled experiment matrix that I cannot run remotely.
