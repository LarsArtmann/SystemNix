03Boot chain: QLC stays the boot disk

The ESP and systemd-boot stay on the Lexar, untouched. Boot I/O fails the TLC test: read once per boot, sequential, nobody waiting interactively. Root @ stays on QLC regardless, so moving the ESP buys zero failure-domain improvement, and keeping the boot path byte-identical is what keeps Phase 1 rollback simple.

UEFI → ESP (Lexar, ~1 G) · stays → systemd-boot → kernel + initrd (on ESP) · stays → initrd mounts root @ (Lexar) + /nix (Samsung, neededForBoot)
switch-root → stage 2 → systemd activates every unit from /nix on the Samsung · root fs, /home, /data remain on the Lexar

Both disks are boot-required

Samsung dead: initrd drops to emergency shell, cannot mount /nix. QLC dead: no bootloader, no root. The failure modes are symmetric; rescue runbooks for both are in the risks section.

Why this is still the right call

Post-Phase-1 the boot's heavy reads (systemd units, binaries) already come from the Samsung via /nix. The QLC's pathology is write/GC-side; a quiet boot's sequential read is exactly what it does fine.

06Supporting tiers

RAM: 128 G

Go caches ~96 G (go-build 65 + go-mod 13 + aux 18). Phase 4 moves the 78 G of GOCACHE+GOMODCACHE to Samsung; rust, pnpm and playwright stay (cold, big). No TRIM through the JMS567 bridge.

Backups, media, archive. Unchanged by the plan. Nightly DB dumps keep landing here after Phase 2 (dump-style backups are location-agnostic, which is what makes the XFS move free of backup-topology constraints).

08Migration phases (each gated, review amendments baked in)

0

Prerequisites (no hardware)

Deploy the staged balance fix (gawk/class runtimeInputs, chunk-unalloc ~6.4 G CRITICAL) and fix the /data EIO inode (P0) so nightly btrbk stops walking 86 G into an abort. Both reduce QLC pressure before any migration writes.

1

/nix → Samsung p2 (the big one)

Partition + mkfs.btrfs -L nix + subvol nix + live rsync -aH --delete. Quiesce builds AND auto-optimise-store AND nix-gc timers (the optimiser rewrites hardlinks on every store add), final delta sync. Add fileSystems."/nix" (by-label, neededForBoot = true, nofail OFF) and deploy. CRITICAL ordering: the deploy itself realizes new store paths onto the QLC AFTER your sync, so run a delta rsync AGAIN after deploy and BEFORE reboot, or the new generation's closure is incomplete on the Samsung. Reboot. Verify: readlink /run/current-system, nixos-rebuild, fio sanity, shell-exec latency during a build storm (the acceptance test). Soak 3 days, then delete @nix: 129 G freed immediately.

2

Hot DBs → Samsung p1 XFS, one service at a time

pocket-id → postgres → forgejo: stop, rsync dataDir (or bind-mount the XFS dir at the existing path), restart, gatus green. Consider extending the candidate list by the same classifier: dnsblockd (hottest write DB on root), gatus, papdashboard sqlite. Honest RPO note: these DBs leave btrbk snapshot coverage, so nightly dumps become the sole recovery path (equivalent cadence, weaker mechanism); postgres WAL archiving is a sensible Phase 2.5.

3

/home decision (trigger-based)

Stays on QLC by default. Trigger: if post-P1/P2 the QLC still feels slow for git status / editor opens during IO storms. Fits on Samsung (~431 G cumulative). Cost: btrbk root-snapshot scope change + HM symlink re-point + one offline window.

4

Go caches → Samsung p2 (optional)

Move GOCACHE + GOMODCACHE only (~78 G); rust/pnpm/playwright stay on USB. Compile-iteration cache-hit reads go 2.2 ms → 27 µs.

10Open decisions

User ratification

1. Layout: 64 G XFS + ~860 G BTRFS

Recommended over single-BTRFS-with-noCoW-dirs: nodatacow drops data checksums, and you want checksumming under /nix (nix does not verify on read); the XFS hot-DB partition follows the clickhouse precedent cleanly.

User ratification

2. Phase ordering: 0 → 1 → 2, then decide 3/4 from data

Phase 0 (balance fix + EIO inode) is the gate; Phase 1 delivers most of the value; Phases 3/4 are trigger- and data-driven.

Resolved in review

3. Boot disk: QLC (ESP + systemd-boot untouched)

Settled 2026-08-31: boot I/O fails the TLC classifier, root stays on QLC either way, and an untouched boot path keeps Phase 1 rollback trivial.

Scheduling

4. Reboot window for Phase 1

Single reboot, after the post-deploy delta rsync. Expect a full store re-warm of the page cache afterwards (first execs pull from TLC, fast).
