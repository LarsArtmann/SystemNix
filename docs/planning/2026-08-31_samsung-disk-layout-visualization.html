The hot subvol: one mount, per-service boundaries

Mounted once at /var/lib/hot with -o nodatacow; the per-service subvol boundaries exist in the fs tree regardless of mount points, so snapshots and deletes stay surgical with zero extra mount units. chattr +C is set explicitly per subvol root by the storage-dir oneshot. Attribute granularity is per-directory, so a service that values integrity over latency (gatus's tiny sqlite) simply lives without +C and keeps checksums.

Boundary FS attr Size Phase Why

hot/gatus (candidate) no +C tiny candidate Monitoring store: write volume trivial, so integrity detection (csums) beats fsync latency.
Layout doctrine
  • Partition starts NEVER move; BTRFS shrinks only from its end; XFS never shrinks. Therefore: fixed things front, ONE elastic BTRFS pool behind, future XFS carved fresh from p2's tail at the moment of need (online btrfs resize -X → parted resizepart end → mkfs.xfs). The rejected 64 G mid-disk XFS would have been permanently un-growable.
  • nodatacow = XFS-like data path (in-place writes, no csums, no compression) riding on BTRFS CoW metadata: still no journal, crash consistency unchanged. fsync lands ~1–2 ms vs raw 0.78 ms vs ~200 ms today.
  • Snapshot landmine: nodatacow holds only for extents not shared with a snapshot; one scheduled snapshot silently reverts touched extents to CoW. Policy: no scheduled snapshots of hot, one-shot checkpoints deleted after the migration, eval-time assertion keyed on the hot prefix.
  • qgroups stay OFF (per-write metadata tax) but this is TLC: the doctrine's own clause permits enabling here later for per-service accounting (the removed btrfs_qgroup_referenced_bytes collector is in git history for re-adding).
  • VDO is dead upstream (removed in RHEL 9) and redundant: compression is BTRFS-native; dedupe (bees) stays declined on this hardware.

03Boot chain: QLC stays the boot disk

The ESP and systemd-boot stay on the Lexar (p7, 4 G vfat, lsblk-confirmed), untouched. Boot I/O fails the TLC test: read once per boot, sequential, nobody waiting interactively. Root @ stays on QLC regardless, so moving the ESP buys zero failure-domain improvement, and keeping the boot path byte-identical is what keeps Phase 1 rollback simple. Samsung p1 reserves exactly 4 G for a future ESP, mirroring the Lexar's own ESP size, so a boot-migration one day is zero-repartition.

UEFI → ESP (Lexar p7, 4 G vfat /boot) · stays → systemd-boot → kernel + initrd (on ESP) · stays → initrd mounts root @ (Lexar) + /nix (Samsung p2 subvol nix, neededForBoot)
switch-root → stage 2 → systemd activates every unit from /nix on the Samsung · root fs, /home, /data remain on the Lexar

Both disks are boot-required

Samsung dead: initrd drops to emergency shell, cannot mount /nix. QLC dead: no bootloader, no root. The failure modes are symmetric; rescue runbooks for both are in the risks section. The reserved Samsung p1 is empty until boot-migration day, so until then it changes nothing about the boot path.

Why this is still the right call

Post-Phase-1 the boot's heavy reads (systemd units, binaries) already come from the Samsung via /nix. The QLC's pathology is write/GC-side; a quiet boot's sequential read is exactly what it does fine.

08Migration phases (each gated, review amendments baked in)

0

Prerequisites (no hardware)

Deploy the staged balance fix (chunk-unalloc ~6.4 G CRITICAL) and fix the /data EIO inode (P0) so nightly btrbk stops walking 86 G into an abort. Both reduce QLC pressure before any migration writes.

1

Partitions + /nix → Samsung p2 subvol nix (the big one)

sgdisk: p1 ef00 +4 G, p2 8300 rest. mkfs.fat -F32 -n SAMSUNG-EFI p1 (formatted, UNMOUNTED, reserved). mkfs.btrfs -L tlc p2 + subvol create nix. Live rsync -aH --delete of the store. Quiesce builds AND auto-optimise-store AND nix-gc timers (the optimiser rewrites hardlinks on every store add), final delta sync. Add fileSystems."/nix" (by-label tlc, subvol = "nix", neededForBoot = true REQUIRED: stage-2 init lives in /nix/store; nofail OFF) and deploy. CRITICAL ordering: the deploy itself realizes new store paths onto the QLC AFTER your sync, so run a delta rsync AGAIN after deploy and BEFORE reboot, or the new generation's closure is incomplete on the Samsung. Reboot. Verify: readlink /run/current-system, nixos-rebuild, fio sanity, shell-exec latency during a build storm (the acceptance test). Soak 3 days, then delete @nix: 129 G freed immediately.

2

Hot DBs → hot subvol (nodatacow), one service at a time

Mount-gated oneshot creates hot plus nested per-service subvol boundaries (pocket-id, postgres, forgejo), sets chattr +C per subvol root; mount /var/lib/hot with -o nodatacow. Per service: stop → rsync → dataDir re-point → restart → gatus green. Checkpoints are ONE-SHOT btrfs snapshots, deleted after the migration (scheduled snapshots would silently revert touched extents to CoW); an eval-time assertion keyed on the hot prefix enforces the policy. Candidates by the same classifier: dnsblockd (hottest write DB on root), papdashboard; gatus joins WITHOUT +C (integrity over latency for a monitoring store). Honest RPO note: these DBs leave btrbk snapshot coverage, so nightly dumps become the sole recovery path; postgres WAL archiving is a sensible Phase 2.5.

3

/home → subvol home (trigger-based)

Stays on QLC by default. Trigger: if post-P1/P2 the QLC still feels slow for git status / editor opens during IO storms. subvol create home, no partition work. Cost: btrbk root-snapshot scope change + HM symlink re-point + one offline window.

4

Go caches → subvol caches (optional)

Move GOCACHE + GOMODCACHE only (78 G); rust/pnpm/playwright stay on USB. Compile-iteration cache-hit reads go 2.2 ms → 27 µs. subvol create caches, no partition work.

10Decisions

Ratified in review

1. Partition layout: ESP 4 G + ONE BTRFS pool, hot DBs on a nodatacow subvol

supersedes the decision doc's "XFS remains the choice for the hot-DB partition" and the Rev 1 64 G XFS p1

Partition starts never move; BTRFS shrinks only from its end; XFS never shrinks. A mid-disk XFS (Rev 1's 64 G, 14 G headroom on ≤50 G of DBs) could NEVER grow. Hence: p1 = 4 G ESP (ef00, FAT32 SAMSUNG-EFI, formatted now, unmounted, mirroring the Lexar's own 4 G ESP), p2 = ~927.5 G BTRFS tlc holding every role as subvols; future XFS is carved fresh from the tail at the moment of need. Hot DBs ride a hot subvol with -o nodatacow: fsync ~1–2 ms vs XFS ~1 ms (noise for these workloads) in exchange for full pool elasticity.

Resolved (benchmarked)

2. Filesystem for /nix: BTRFS + compress=zstd

scripts/bench-nix-fs.sh · recorded in the decision doc 2026-08-31

Performance a wash across ext4/XFS/BTRFS under live load; compression is the separator at a measured 1.89× (129 G → ~68 G). noatime,compress=zstd, NOT compress-force.

Resolved in review

3. Boot disk: QLC (ESP + systemd-boot untouched)

Boot I/O fails the TLC classifier, root stays on QLC either way, and an untouched boot path keeps Phase 1 rollback trivial. The reserved Samsung p1 makes any future migration zero-repartition.

User ratification

4. Phase ordering: 0 → 1 → 2, then decide 3/4 from data

Phase 0 (balance fix + EIO inode) is the gate; Phase 1 delivers most of the value; Phases 3/4 are trigger- and data-driven.

Optional, decide at P2

5. Enable qgroups on the Samsung pool?

TLC exempts it from the QLC doctrine; per-service subvols + qgroups give true per-service capacity accounting (collector available in git history). Default OFF until a concrete need.

Scheduling

6. Reboot window for Phase 1

Single reboot, after the post-deploy delta rsync. Expect a full store re-warm of the page cache afterwards (first execs pull from TLC, fast).
