01Incident Truth (why the existing stack missed)

Both freezes were scheduler LIVELOCKS, not lockups

kernel.softlockup_panic=1, hung_task_panic=1, and the 30s hardware watchdog are all armed — none fired. A livelock (all CPUs burning in zram refault/reclaim with IRQs enabled, RCU progressing) pets the WDT "eventually", never trips the soft-lockup detector, and starves khungtaskd of CPU. No panic → no evidence, no auto-recovery. Detection must act before the cliff; recovery layers can only bound the blast radius after.

Feedback loop (fixed 06:23)

Guard alerts → PapDashboard enricher → flm cold load → re-trip. Socket-first stop + auto-restore deployed.

PSI blind spot (fixed 06:23)

Zone 3 (PSI≥40 + zram≥80) added. But nothing watches the middle: PSI 20–40% sustained = storm forming, alert-only.

No aggregate demand cap

Builds run in system.slice/nix-daemon.service — oomd-EXEMPT, MemoryHigh-free. 10 concurrent builds × 4–8 GB exhaust RAM with nothing throttling them. VM tests land in the 90 GB-capped user slice whose memory.swap.max is unbounded → they fill zram instead of failing.

Warnings nobody saw

Discord fired 43 min before freeze #1 and 17 s before freeze #2. Phone delivery + an unmissable desktop overlay are part of the alert path, not decoration.
