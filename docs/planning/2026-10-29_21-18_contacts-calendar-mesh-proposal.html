01Summary & verdict

What you asked for: contacts and calendar currently live in two Google accounts; you want bidirectional sync, a real data owner you control, and a data-mesh shape.

What is true today: the mesh already exists on paper and half-exists in code. The contact half has a ratified constitution, a working Google import adapter (multi-account, per-account state and actors) and a working CardDAV out-mirror verified against the deployed Stalwart. The calendar half has nothing anywhere. Google is, in practice, the only store that holds the real bytes.

The blocker is not engineering, it is doctrine. Three ownership documents written in three repos disagree about who should own personal contacts and calendar. Two of them are dated today. Until one answer wins, every line of sync code is a bet on an unresolved question.

The bottom line Bidirectional sync is buildable, but it is constitutional: it amends the CRM mesh's rule that Google never receives a write, and it obliges us to build the conflict machinery the 2026-10-19 owner decision explicitly declined to build. Two coherent end-states are on the table (Mesh A / Mesh B, §04). I recommend Mesh B — one store owns both entity types (Stalwart), Kith demotes to relations — because it is the shape the document you pointed me at argues for, and the only one where a phone can eventually drop Google entirely. Decide D1, and the rest of this document becomes executable.

05Target architecture

The shape is "one owner, edges on both sides". Google is an edge, not a hub: it stays the app surface your devices already use, while the store you control holds the truth, the lineage and the restore point.

Stalwart (owner: contacts + calendar)
├── sync adapter · spoke A ─── Google account A (bidirectional, field-scoped)
├── sync adapter · spoke B ─── Google account B (bidirectional, field-scoped)
├── DAV devices ─── phones/tablets (CardDAV + CalDAV, phase P7)
├── Kith CRM ─── relations only; reads contact facts, never owns them
└── nightly archive ─── whole-store backup + restore drill

The adapter is a cache, not an owner: its state is the same disposable 0600 JSON the mesh already uses (delete it and the next run is a harmless full resync). It owns no entity, holds no truth, and can be redeployed from git — which is precisely the mesh constitution's test for "not the owner".

06Bidirectional sync semantics

This is the part that decides whether the mesh leaks. "Bidirectional" is not a flag; it is five rules and a control surface.

1. Merge against a base, not against each other

Keep the last-synced snapshot per item. A change is "theirs" only if it differs from the base; that is what distinguishes a remote edit from our own write. Two-way without a base is last-write-wins, and last-write-wins silently eats edits made on a phone.

2. Field-level provenance, ambiguous → queue

When both sides changed the same field since the base, do not pick a winner. Materialise a conflict item and show it. The journal's own rule already points this way: machine writes are low-trust, humans own overwrites.

3. Tombstones, never auto-delete

A remote deletion creates a review item, not a deletion. The existing adapters already behave this way ("deleted in Google …" as a note, exactly once; the CRM contact is never deleted). A sync engine that deletes on a tombstone is how a bad API day becomes data loss.

4. Loop suppression by recorded writes

Every write we make records its resulting version (etag/hash/updated timestamp) in adapter state, so the next pull recognises it as ours. The CardDAV mirror already proves the pattern: uid → etag+hash state, and a rerun with no changes performs zero writes.

Important · Silent-loss class

5. Unknown fields must round-trip opaquely

Google X-GOOGLE-* / extended properties · unknown vCard properties · timezone objects

A two-way sync that re-writes an object it did not fully understand deletes the parts it did not model. Contacts and events both carry vendor-specific and structural fields (Google extended properties, contact groups, photos as separate resources, iCal X- properties, attachments). Rule: store the unmodelled remainder opaquely and put it back byte-for-byte, and prove it with a fixture that round-trips a deliberately weird object. This single rule is the difference between a sync and a slow-motion data loss.

The control surface (all of it is required)

Per-spoke pause

One switch per account/collection, independent of the others.

Dry-run mode

Report the would-write / would-delete set; touch nothing (already implemented downstream).

Canary subset

Enable writes for N items first, and un-create them if the run goes wrong.

Idempotence is the safety net, not the feature Rerun = zero writes. Delete state = safe full resync. Every rule on this page exists so that a crashed or mis-deployed sync can never corrupt truth — which is exactly what the constitution's principle 5 already demands of every spoke.

07Calendar specifics

Calendar is where naive syncs die. These are the hazards I know of before touching the API; §11 lists what still needs verification.

Hazard Why it bites Rule we adopt
Recurrence + single-instance overrides A recurring event plus "this occurrence only" edits are modelled as a recurrence id / original-start relationship. A sync that flattens them duplicates or loses occurrences. Model recurrence explicitly; never expand-and-store; test an override fixture
Attendees and invitations Writing an event with attendees can email real guests — a sync can spam a meeting. Invitation state is also shared: you are not the only writer. Suppress notifications on every sync-side write; treat attendee-bearing events as read-mostly and queue conflicts
Read-only collections Birthdays, holidays and subscribed calendars exist inside the account and are not writable; they also duplicate contact facts. Explicit calendar-id whitelist; everything else is skipped and counted
Timezones and DST Floating vs UTC vs TZID-anchored times change meaning across a sync boundary. Preserve the original representation; never normalise to UTC on write
Reminders, sequence, etag Reminders are a child collection; sequence and etag drive optimistic concurrency. Conditional writes (If-Match-class); no blind overwrite
Incremental sync tokens Token expiry forces a full resync; deletions only appear when asked for explicitly. Handle token-expiry as a first-class path (the contacts adapter already auto-resyncs on EXPIRED_SYNC_TOKEN)
Devices: DAV vs the Google app CalDAV from a phone writes straight into the owner; the Google app writes into Google. Phase 1 keeps devices on Google. DAV cutover is a separate, reversible phase (P7) after CalDAV is probe-verified
The calendar owner has a verification debt CardDAV's dialect in this fleet is probe-pinned and reproducible. CalDAV's is not — nothing in nix-email's feature table claims it, and no transcript exists. Verifying it is step one of §11, because the whole calendar half of this proposal rests on that surface behaving.

08Phased execution

Same ladder that has worked for every other cutover in this fleet: read-only first, canary second, wide third, and a kill switch at every rung. Nothing in this plan writes to Google before P3.

0

P0 — Inventory and escape hatch (read-only)

Enumerate both accounts: collections, item counts, overlap, duplicate clusters, group/label vocabulary. Produce full exports (API dump + Takeout) before any write exists. Gate: you have seen the numbers and the duplicate list. Kill switch: none needed — nothing writes.

1

P1 — Ratify D1/D2 and declare the owner's collections

Record the topology decision and the write-authority amendment in the constitutions (this repo's ownership doc, the CRM mesh doc, the pbx doctrine). Then declare the addressbook and calendar objects in the mail plan instead of leaving them as runtime state — after verifying the plan dialect accepts those types. Gate: both documents say the same thing; the collections are declarative and redeployable.

2

P2 — Import Google → owner (dark, read-only outbound)

Both accounts' contacts and the whitelisted calendars land in the owner. Dedup runs hub-side. Reruns must be no-ops. Gate: counts reconcile per collection; a rerun performs zero writes; you have reviewed the merge report.

3

P3 — Owner → Google write path, ONE account, canary first

Dry-run, then 10 canary items, then a 7-day soak with the conflict queue empty. Scopes must be widened (write scopes replace today's read-only consent) and the GCP app must leave testing mode for tokens that survive a week. Gate: zero unexpected mutations over 7 days. Kill switch: pause the spoke; un-create the canary set.

4

P4 — Account A goes fully bidirectional

Phone edits, web edits and owner edits now converge on the owner. Gate: an edit made in Google appears in the owner and in the other spoke's view within two cycles, with one journal event and the right actor.

5

P5 — Account B joins; the two accounts converge through the owner

This is the actual answer to "my contacts are in two Google accounts": the hub is the only place both copies meet, so the accounts stop needing to know about each other. Gate: cross-account duplicates are gone by policy, not by accident; per-account links never collide.

6

P6 — Calendar repeats the ladder

Same P2–P5 sequence for events, after the CalDAV surface is verified and the calendar whitelist + attendee policy are settled. Gate: a recurring event with one overridden occurrence survives a full round trip untouched.

7

P7 — Optional: point devices at the owner (DAV)

Add the owner as a second account on one phone, read-only usage first, then decide whether it becomes primary. Reversible by removing the account.

8

P8 — Steady state and governance close-out

Decide Google's final posture: keep it bidirectional as a convenience edge, or dial it to one-way out (owner → Google) once the owner is the edit surface. Ship the four artifacts per spoke, wire the metrics and alerts, and run the restore drill.

09Risks & kill switches

Ordered by what it costs when it happens. Every row has a switch that stops it without a rebuild.

Mass deletion propagates (a bad token resync or an API oddity reads as "everything deleted") Critical Tombstones never auto-delete; delete ceiling per run (abort above N% deletions); pause spoke

10Verification & governance

The mesh's fourth principle (federated governance) is the part most projects skip. In this fleet it means: metrics exist, alerts fire, the restore drill runs, and every spoke ships its four artifacts.

Metrics to emit

Per spoke × collection: items, writes per direction, conflicts pending, tombstones held, deletions refused, sync lag seconds, last success timestamp. Promote the existing sharded sync counters rather than inventing a parallel scheme.

Alerts and surfaces

A Gatus check per spoke; a SigNoz panel for lag/conflicts; the conflict queue in the UI you actually open. Alert on: lag above two intervals, any pending conflict older than a day, and any run whose deletion count exceeds the ceiling.

Four artifacts per spoke

Contract doc, probe transcripts, ops runbook, decided boot posture. This is the constitution's own rule, and it is how the CardDAV mirror earned trust before it ever ran live.

Restore drill

Restore the owner from its nightly archive into a scratch path, verify counts and a sample of items, then prove the spokes re-converge. An untested restore is not an owner's backup leg.

How we will know it worked

+
One edit, three places, one event An edit in Google account A appears in the owner and in account B within two cycles, attributed to bot:google-sync:a — no phantom second write.
+
Deletes are reviewable, never silent A remote deletion produces a queue item and zero deletions on the first pass, always.
+
Reruns are free No-change rerun performs zero writes; deleting adapter state triggers a full resync that creates no duplicates.
+
Weird objects survive The opacity fixture (unknown properties, an override occurrence, a photo reference) round-trips byte-for-byte.

12Decisions needed

Six answers. D1 and D2 are commitments; the rest are scoping. Nothing else in this document should be built before the first two land.

D1 · Blocks everything

Which end-state: Mesh A (journal hub) or Mesh B (PII hub)?

A: Kith keeps contacts, Stalwart owns calendar. B: Stalwart owns both, Kith becomes relations-only.
My recommendation: B. It matches the document you sent me, gives one store and one restore drill for personal PII, and is the only topology that can eventually take a phone off Google. Choose A if you want contact truth to stay where it already is and accept two owners and two restore paths.

D2 · Constitutional

Do we amend "no write-back" and how wide is the write authority?

(i) Amend to field-scoped low-trust writes with a conflict queue — the sync may fill and add, never silently overwrite a human edit (recommended); (ii) amend to full authority, sync wins; (iii) do not amend — then bidirectional is off the table and the ask in this session cannot be met.

D3 · Blast radius

Which account is primary, and does the second stay symmetric?

Both bidirectional (recommended — it is the point of the request); personal bidirectional + work read-only (lower blast radius, less consent surface); or one account only. Also: do devices keep using Google in phase 1? Recommendation: yes, keep them — device cutover is P7 and reversible.

D4 · Scope

Contacts only, or calendar in the same project?

Calendar roughly doubles the surface (recurrence, attendees, timezones) and depends on verification #1. Options: contacts first and calendar as a second project (recommended); or both together if you want a single doctrine change and a single soak.

D5 · Data policy

Duplicate policy for the overlap, and what counts as "the" calendar set?

The two accounts almost certainly share people. Options: merge on email + name with a review list you approve (recommended); or keep per-account copies separate on purpose. Separately: name the calendar whitelist and the attendee-bearing-event policy (queue vs push). And note the 139 staged Twenty contacts — import them into the owner once, at P2, so they arrive through the same door as everything else.

D6 · Plumbing

Where does the adapter live, and how often does it run?

Recommendation: a timer on the fleet host beside the CRM (sops, deployment, monitoring and backups already exist there), polling on the order of minutes; push/webhook channels only if you want near-real-time and accept a public endpoint plus channel renewal.

13Alternatives dismissed

Alternative Why not
Bridge the two Google accounts to each other (no owner) Fails your requirement outright: no owner, nowhere to keep lineage, conflicts and tombstones, and a third-party-shaped dependency between two accounts that are supposed to stop needing each other.
A file-level DAV syncer between Google and a DAV store A second state store outside the journal, no lineage, and conflict handling limited to "keep both" — plus its Google backends are historically the weak spot. Verify before trusting; the mesh wants journal-attributed writes.
Stand up a fresh DAV server (Radicale/Baikal-class) as the owner A third store is a new backup leg, a new auth path and a new migration — exactly what the pbx doctrine argues against when an existing store already speaks the protocol.
Keep Google as the de-facto owner and mirror it locally That is today's state, and it fails the requirement: the bytes live on someone else's disks with no restore path you have run.
Periodic manual export/import (Takeout + CSV) Not bidirectional, no tombstones, no provenance, and it turns every merge into an afternoon of manual diffing.
