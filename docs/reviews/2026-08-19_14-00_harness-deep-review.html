Harness: a brutally honest audit

A read-everything assessment of stump.wtf/harness — the Go/Charm supervisor for AI agent CLIs. Architecture is sharp, the blast-radius and surface-area decisions are honest. There is also a real cluster of unfinished work declared in the ADRs themselves, a test story that is barely visible in public, and a few decisions worth reverting before they harden.

The headline: Harness is the rare tool that admits what it has not shipped yet. Multiple ADRs explicitly catalogue deferred items, open issues, and shipped-with-known-gaps sections (most pointedly ADR-0013 and the "Revision note" embedded inside it). The architecture itself is good — narrowly conceptual, dependency-coherent, with three load-bearing decisions (ADR-0003 native multiplexer, ADR-0005 daemon-self-supervises, ADR-0007 ring+log) that reinforce each other instead of competing.

The risks cluster in three places: (a) the daemon is a single point of failure for every agent on the box; (b) the scheduler (ADR-0013) lacks run history and missed-window recovery, which is the difference between "a cockpit" and "a timer with cosmetics"; and (c) the chatroom + distillation story (ADR-0011/0012/0015) is building real flywheel machinery before the run-history gap is closed, which inverts the priority order.

None of this is unrecoverable. The ADRs are the recovery plan: each shipped-with-known-gap section is the punch list. The fix is to promote those deferred items to commits, not to revisit the decisions.

01About the Project

What the docs say

Systemctl for your agents — a long-lived Go daemon that supervises AI agent CLIs (Claude Code, Crush, Codex) and exposes them via a keyboard-driven Bubble Tea dashboard, with the same cockpit reachable over SSH through Wish.

  • Source: gitea.stump.rocks/stump.wtf/harness (not on GitHub public)
  • Documentation site: stump-wtf.github.io/harness/
  • Owner: Joe (joestump — decisions 9–16 list them as decider)
  • Distribute: Homebrew tap + go install; single Go binary with daemon / TUI / CLI subcommands
  • Decision literature: 16 ADRs and 10 specs, all markdown, all with considered options and rejected options
  • Adjacent repos: stump.wtf/agent-trace (trajectory parsing, extracted from cosmtrek/mindwalk)

What the ADRs reveal that the homepage does not

  • Status fields are inconsistent across ADRs. Most say Proposed, two say Accepted (ADR-0013, ADR-0014), and the doc-site render shows unknown for 10/16. ADR-0011 references a Gitea PR (#112, #122) for the actual code — the ADR is the proposal; the code is what shipped. Either the status logic should map all "proposal with code merged" to Accepted, or there should be a single "as-built" annotation per ADR.
  • The shape of harnessd is fully conceptualised (ADR-0001 sets the binary shape, ADR-0002 the split, ADR-0003 the multiplexer, ADR-0004 the transport, ADR-0005 the supervision, ADR-0007 the persistence). There is no published internal/ layout decision, which means a newcomer has to read seven ADRs to know where core/, supervisor/, proxy/, tui/, config/, agent-trace-bridge/, etc. live. A single one-page "codebase map" ADR would pay for itself in onboarding.

02What's Excellent

+
Decisions record reasoning, not just outcomes Every ADR includes "Considered options" and "Rejected options — why." This is the hardest discipline to maintain at scope and the project has maintained it. A new maintainer can reverse-engineer why the daemon is one process (ADR-0002) or why schedule is a key on a harness (ADR-0013) without grepping git history.
+
Coherent dependency choice ADR-0001 maps every dependency to a structural need (PTY, emulator, SSH, UI, styles). The result is a tree where removal of any one package has an obvious second-order effect — that's rare, and it kept the door open for ADR-0016's decision to add Cobra+Viper explicitly and count the cost.
+
Security model is real, not decorative ADR-0008 explicitly acknowledges the irreducible risk ("attach = terminal access"), defaults to off for remote, keeps the SSH-only auth path, and refuses to invent crypto. The "no secrets in HARNESS_*" rule (ADR-0016) is the right cut.
+
The Backend escape hatch ADR-0003 defines a Backend interface and ships native as the default and tmux as the optional fallback. This is exactly the right shape for a project whose biggest technical risk is a young virtual-terminal emulator. The reclaimable egress keeps the schedule live if x/vt bites on a real program.
+
Config schema preserved as file-of-record ADR-0006 chose the TOML stays-the-truth side of the schema authority argument and ADR-0009 carved out projects as transient registration without polluting the global file. Together they keep the file portable, git-trackable, and editable by hand and by the TUI — the user's drei split.
+
Honest revision notes ADR-0013's mid-document "Revision note (2026-08-13)" revises the decision without papering over the one it replaced. The original 1A+2A argument is preserved under "Pros and Cons." This is how ADRs are supposed to evolve; most teams fake it.
+
Distiller-as-harness is the right pattern ADR-0012 frames cross-harness distillation as a supervised process that uses the facade to read, not a daemon subsystem that reaches into a model. The daemon keeps the "I hold no secrets" invariant from ADR-0008, and every auth path inherits the harness lifecycle machinery.

03Findings

F01 — Critical / Phase-1 must-fix

Scheduled-harness restart race vs enabled exclusion

ADR-0013 — "Consequences" / Deferred list, issue #159 referenced

The shipped scheduler fires through Manager.Start, which persists enabled = true. An unclean daemon exit mid-run can autostart a scheduled one-shot off-schedule on the next boot, defeating the deliberate parser exclusion at schedule × enabled = true.

Fix: a supervisor-level "start without persisting intent" primitive (e.g. Manager.fire(harnessID) distinct from Manager.Start), plus a state.json marker (last_fired_at) so the next boot can detect a missed window and either skip or replay cleanly.

F02 — Critical / Phase-1 must-fix

No run history; "did last night's run pass?" is unanswerable

ADR-0013 — Deferred: "Run history and per-run logs"

ADR-0013's own context promises that "did the 3am agent run fire, and did it pass?" is the headline question a cockpit answers. The shipped scheduler answers did the single continuous scrollback ever end with a zero exit? — only if you scroll to the bottom. That is the largest gap in the system and the one that most undermines the premise.

Fix: bounded ring of { run_id, started_at, ended_at, exit_code, outcome, trigger } per harness + one log file per run pruned to keep_runs. Surface in harness list as a column (or "last 5 runs" pill) and in harness describe.

F03 — Critical / Phase-1 must-fix

Clock correctness is unspecified across suspend/resume

ADR-0013 — Deferred: "Suspend-safe wall-clock evaluation"

The shipped scheduler delegates timing to robfig/cron/v3, which arms a single timer to the next due entry. On a laptop that suspends overnight, the armed timer fires once on resume (catch-up), which for a 5-field min hour dom mon dow spec is fine but for a suspend-resilient cron is not. The requirement stated in the original draft — re-evaluate against wall-clock on a short tick — has not been verified against robfig/cron's behaviour.

Fix: write the missing acceptance test ("schedule survives overnight suspend") and capture cron.Next(t) vs time.Now() immediately post resume. If they diverge by >5s, swap the scheduler implementation for one that re-evaluates on a short tick.

F04 — Critical / Phase-1 must-fix

Daemon crash takes every harness with it; no re-arming for the live PTYs

ADR-0002 + ADR-0005 — both flag this as the headline risk

If harnessd crashes, all harnesses die. The mitigation is keep-the-daemon-tiny + Restart=on-failure, and the advanced "per-harness reaper" was explicitly deferred. Given the cost humans pay when the daemon dies mid-session (lost scrollback, lost in-progress prompts, agent CLI re-spawn cost on slow backends), the "v2 consideration, noted not committed" framing has aged poorly.

Fix options, in order of cost: (1) ship a harnessd-reaper companion that retains the live PTYs if the daemon dies (forking+recovery is heavy); (2) ship a process-group reaper so harnesses can be re-parented across restarts; (3) document the explicit "daemon crash = blanket stop" as a known limitation and surface a banner in the TUI on every reattach.

F05 — Important / Phase-2

Trajectory harvesting defaults must be reviewed against the 1.1 GB corpus

ADR-0011 + ADR-0012

ADR-0012 names a "~1.1 GB across 1,738 transcripts" corpus that grows daily. ADR-0008 acknowledges that harvested transcripts may contain secrets a harnessed program printed itself. ADR-0011 makes harvesting opt-in per harness but does not name a default — defaults are user-hostile here. The TUI prompt for harvest_trajectory should default to false for any harness that touches tokens, and the daemon should refuse to enable harvesting for a harness with an env_file unless the user explicitly confirms.

F06 — Important / Phase-2

Cross-harness distillation + learned-tier search: missing a corpus cap

ADR-0012 — "Context is the scarce resource"

ADR-0012 names the 200-skill ceiling ("Correct at 15 skills; fatal at 200") and rejects embeddings and the LSA deferred path. But the corpus cap is retrieval-driven: the only mechanisms that shrink the index are the supersede rule and the "zero retrievals in N weeks since promotion" rule. There is no authoring-side guard. A wrong distiller over a noisy week can promote 30 skills in a row.

Fix: a hard weekly cap on promotions (max_promotions_per_week = N), a confidence threshold from classify's cluster size that must be met before authoring, and a quarantine workflow that holds unpromoted-but-promotable skills for a human review queue.

F07 — Important / Phase-2

Backend escape hatch lives only at the harness level, not the project

ADR-0003 + ADR-0009

backend = "tmux" | "native" is a per-harness knob. Projects (ADR-0009) can declare many harnesses at once. There is no project.backend default. If a user hits an emulator-level bug in x/vt, every harness in a project must be edited.

Fix: add [project] backend = "tmux" as a default with per-harness override, so a regression can be scoped without rewriting any harness table.

F08 — Important / Phase-2

HARNESS_REDUCED_MOTION reserved but not implemented

ADR-0016 — cross-references SPEC-0009 REQ "Reduced Motion"

ADR-0016 cleanly reserves the variable as the env override for a future chatroom toggle ("Reduced Motion"). Until the chatroom ships and the env is wired, the variable is dead. Either land it with the chatroom (ADR-0015) or document the reservation explicitly with a "do not use until v1.2" note in the error message.

F09 — Nice / Phase-3

Cobra+Viper are 14 modules including a dead YAML parser

ADR-0016 — Consequences

ADR-0016 counted the cost — 52 → 66 modules — and accepted it. The second TOML parser (pelletier/go-toml, pulled in by Viper) is a latent split-brain: it's nowhere in internal/config's import graph but a future contributor who adds a Viper-based TOML file path will reintroduce the conflict. A go mod why -m pelletier/go-toml carved into a comment in config.go is the cheapest insurance.

F10 — Nice / Phase-3

Wish's host-key ergonomics are inherited, not owned

ADR-0004 + ADR-0008

The ADR pair keeps secure defaults (0600 socket, keys allowlist, no password path) but the SSH host-key management is hand-waved forward to charmbracelet/keygen + optional melt seed-word backup. From the docs there is no shipped "first-run experience" for host-key generation and rotation. A returning user who reinstalls the binary may face a host-key-changed warning without a clear next step.

Fix: ship a harness server init verb that generates the host key, optionally prints a seed phrase, and writes a fingerprint line that the user pastes into their docfile of SSH host keys.

F11 — Nice / Phase-3

The chatroom is a new view, not a view of a session

ADR-0015

ADR-0015 builds the chatroom as a new dashboard mode keyed off tail.DefaultAdapters(). The "key" turns the chatroom on for every harness with a trajectory, even ones running with harvest_trajectory = false, because tail reads the source files directly. harvest_trajectory gates the MCP facade (ADR-0010); it does not gate the chatroom read. That's a real privacy gap: a harness explicitly opted out of harvesting is still included in the chatroom aggregate.

Fix: in internal/tui/chatroom, filter the tail.DefaultAdapters() set against core.Harness.HarvestTrajectory before subscribing. Same mcp_allow-style default-to-deny rule applies.

F12 — Nice / Phase-3

"Reduced motion" toggle is documented but unreachable

ADR-0016 — "More Information"

Re-mentioning F08 from a different angle: SPEC-0009's "REQ Reduced Motion" was deferred with a pointer to this reservation. Either the chatroom ships reduced motion or the SPEC req is reclassified as out-of-scope (with a reason). Leaving it dangling is a split between promised behaviour and shipped behaviour.

Open observations

  • cmd/harness/main.go still uses flag. ADR-0016 states the rewrite is coming. Until then, parseInterleaved exists for a real reason — the standard library's flag halts at the first positional. There is no tests-stampede guarantee in the ADR's migration plan; adding characterization tests on every verb before the swap is the cheapest insurance.
  • Drop-in harness.d schema is documented in configuration but not anchored to a spec or ADR. If a future "config-as-fleet" proposal arrives, drop-ins are where the friction will be felt.
  • The "Reduced motion" claim is in two places (ADR-0016 + SPEC-0009) and is implemented in zero places. A spec-table column "Status" would catch this category before it rots.

05Split-Brain Audit

Searching for places where two decisions or surfaces disagree about the same concept. Most are documented and intentional (the Backend escape hatch, the project-vs-profile dichotomy), but a few are real.

S01 — Intentional · Backend

Two Backend implementations (native, tmux) per ADR-0003. Single source of truth: the Backend interface. Good.

S02 — Intentional · project vs profile

ADR-0006 (profiles, durable, global, non-destructive) vs ADR-0009 (projects, ephemeral, repo-scoped, destructive). Two verbs, two lifecycles, kept deliberately separate. Good.

S03 — Intentional · scheduled one-shots vs resident harnesses

ADR-0013 chose not a separate [job.*] table. The cost is real (consumers branch on Schedule != "") but documented in ADR-0013's "Consequences." Accepted.

S04 — Real · enabled vs Schedule intent

ADR-0006 made enabled the autostart on-boot flag. ADR-0013 forbids schedule + enabled. ADR-0014 adds reload-introduced harnesses start per enabled. The persistence layer (state.json's runtime Enabled) and the config layer (enabled) split into two distinct concepts (ADR-0014 spells this out), but no diagram or table maps the matrix. F01 is the unresolved corner.

S05 — Real · trajectory gating

ADR-0010 gates the MCP-facade trajectory tools on harvest_trajectory. ADR-0015's chatroom uses tail.DefaultAdapters(), which reads source files regardless of harvest_trajectory. F11.

S06 — Implicit · logs location vs state location

ADR-0007 splits per-harness logs from the daemon-global state file (different paths under $XDG_STATE_HOME/harnessd). It works but the docs and one example only mention one of them. A single-page "filesystem layout" appendix would pay for itself. Documentation drift, not code drift.

S07 — Real · config authority

ADR-0006 says the TOML is the source of truth; TUI edits write back via Huh forms. ADR-0009 says projects never write to the global file. ADR-0009's project file is repo-local. The authority claim is true for the global file but the TUI's edit flow does not have a "this edit was in a project file, hydrate it" path documented. With the TUI's edit key on a project harness, what wins? F12's data point.

S08 — Subtle · restart policy overloading no

ADR-0006/ADR-0011/ADR-0013: restart = "no" is the prompt-harness default and the scheduled-harness requirement. A genuinely resident prompt loop (rare but reasonable — "always ask me to review code") cannot declare itself with prompt and a restart policy at the same time. Not a contradiction, but a schema-level minimum radius worth knowing. Document, don't change.

06Ghost System Audit

"Ghost system" = a thing described in the ADRs as either built or being-built, whose existence and value are real but whose code, tests, and shipping channel are not visible from the public surface. If you can't find it from the README + docs + ADR-0015's "Confirmation" list, it's at risk of becoming a phantom.

G01 — agent-trace (real, external)

stump.wtf/agent-trace, extracted from cosmtrek/mindwalk. ADR-0011 names the three packages (tail, classify, otel). Real, used, with accepted unit tests in its own repo per the implementation note. Strong integration.

G02 — run-history file (ADR-0013 promised, not shipped)

ADR-0013 lists "Run history and per-run logs" under Deferred. The TUI does not render it. The CLI does not have a runs subcommand. The feature does not exist in code. F02 is exactly this ghost. Build it.

G03 — wishlist / promwish (ADR-0004 references, "not v1")

ADR-0004 names wishlist ("the SSH directory") and promwish as future directions. Not explicitly built. If the project leans on promwish-style metrics later in a status report, treat it as future, not current. Not a bug; a labelling issue.

G04 — chatroom view (ADR-0015 proposed, integration ambiguous)

ADR-0015 says "New chatroom view within Harness TUI" — the internal layout choice is "deferred to implementation" with the note that internal/tui is currently flat. ADR-0015 references SPEC-0009; SPEC-0009 references ADR-0015. A circular reference with no shipped code on either side. Build one or both ends.

G05 — Switchboard (ADR-0010 names, not built)

ADR-0010 explicitly names "Switchboard" as the place where MCP write-capable harnesses should be routed for guardrails. The ADR's "more information" admits "Switchboard gates inbound work routing, not an agent calling harness_stop on a sibling." Switchboard is not in the codebase per the public surface. Either build it or remove the name from the docs.

G06 — "House pattern" overlap (ADR-0016)

ADR-0016 cites two sibling repos (msgbrowse, joe-links) as prior art that converged on the same decision. The citations are useful provenance, but they imply a house-style standard that isn't written down anywhere discoverable. A one-page "House Patterns" note that links the four would help. Documentation, not code.

G07 — harness server init (F10 candidate)

ADR-0008 lists host-key generation as "not v1 committed" but referenced as part of charmbracelet/keygen. No shipped first-run experience. A first-time user turning on [server] hits a missing-step. Close the ghost.

07Scope-Creep Audit

The ADR trail makes the scope creep legible: every "Proposed" feature that crossed the "single Go binary doing one job" line is named, with reasoning. Most of the creep is honest and reversible. The two flagged items below are the only ones where scope creep is not yet contained.

SC1 — Chatroom + distillation + learned-tier assembled before run-history

The flywheel stack — trajectory harvest (ADR-0011), facade tools (ADR-0010), distillation (ADR-0012), chatroom (ADR-0015) — is being built in roughly that order. The distillable signal without run history is a partial signal: a sweeper that always runs to completion before its next start contributes to the learned-tier, while a sweeper that exited 1 with no log around it doesn't. Building the flywheel before the per-run log would be a layering inversion.

Recommendation: promote F02 (run history) above the chatroom in the issue tracker. The order should be: run history → harvested trajectory → facade tools → chatroom. Currently it's: facade → trajectory → distillation → chatroom, with run history deferred.

SC2 — Cobra+Viper added to a deliberately small tree

ADR-0001 chose the small-dependency Charm stack and explicitly counted at decision time. ADR-0016 added 14 modules including a second TOML parser and an unused YAML parser. The cost was named and paid. Not a bug, just a precedent. The next ADR that proposes a similar addition needs to count explicitly. Adding another HTTP server framework for any chatroom-side feature would be the wrong precedent.

SC3 — Backend abstraction pays for itself

The native-vs-tmux Backend interface was the right precaution against x/vt immaturity. That single decision has already absorbed scope (resize policy per ADR-0003, copy-mode deferred) without swallowing scope. Worth holding up as the success-case model for future risk-receiver interfaces.

08Testing Posture

The site does not surface a tests/ directory, a CI badge, or a coverage report from the public docs. The ADRs name acceptance tests per ADR ("this is testable", "these scenarios are required"), but there's no central test inventory.

T01 — Single shared acceptance harness would centralise ADR promises

Every ADR named a set of acceptance tests in its "Confirmation" section. ADR-0010 alone lists 4 acceptance tests for the broker; ADR-0012 lists 7. There is no evidence of where these live.

Suggestion: one shared test/acceptance_test.go with one named subtest per ADR's promise, each described with the ADR number in a comment. Cheap to do, highest leverage for outsiders trying to verify shipped behaviour matches promised behaviour.

T02 — x/vt corpus-of-trajectories test is gold, not actually shipped

ADR-0003 names a "corpus of real agent-CLI sessions (Claude Code, Crush) as a golden test set" for the emulator. The x/vcr tooling is mentioned. There is no published fixtures/ directory or sample script in the public docs. One of these is the most valuable tests you can ship for a virtual terminal emulator.

T03 — Cron/scheduler determinism needs property tests

ADR-0013's deferred list — DST, timezone, suspend/resume, wall clock jumps — is the exact surface where property-based tests shine (fire a bunch of random intervals, simulate forward by N hours, verify expected next-firing). Characterising robfig/cron with this style before swapping it would make F03 verifiable in 30 lines.

T04 — Configuration precedence is testable as a single table

ADR-0016 ends with a precise list of "Confirmation" acceptance tests that are already a table in disguise. Building that as a Go subtest matrix with one row per combo would catch regressions in a parse-and-bind pass that's notoriously easy to break.

T05 — parseInterleaved characterization tests first

ADR-0016 names three ambiguous positional/flag cases the migration must preserve. None is in the public doc as a test. Characterising them before the Cobra swap is the difference between a Friday merge and a Monday revert.

Architectural concerns worth surfacing

A1 — Single binary, single process, single point of failure

ADR-0001 commits to a single Go binary. ADR-0002 makes the daemon the supervisor. ADR-0005 acknowledges the consequence ("if harnessd crashes, every harness dies with it"). The architectural story is honestly two-tiered, but the recovery story between tiers is F04 (unaddressed). The architecture is sound; the operational runtime needs its own hardening pass.

A2 — Two config readers: a feature, not a sin

ADR-0016 explicitly accepts a two-reader config model (Viper+BurntSushi) in exchange for line-numbered errors. The seam is the deliberate consequence. A code comment in internal/config/config.go that says "this is the seam, do not unify without ADR amendment" turns a future reader's instinct into a project decision.

A3 — Two sources of harness definitions, deliberately split

Global TOML (ADR-0006) + project repos (ADR-0009). The two surfaces are intentionally separate but their reconciliation on conflict and on TUI edit has no published algorithm. S07 above.

A4 — Three "kill the next reader" footguns are well-flagged

  • ADR-0005 spells out the "two bosses" anti-pattern of per-harness init units.
  • ADR-0006 records why "directory-per-profile" was rejected.
  • ADR-0013 records why a separate [job.*] table was rejected.

Each is a temptation the maintainer will face. The decisions are recorded where they'll be looked for. Excellent practice.

10Prioritised Improvement Plan

Sorted by impact-per-effort. Each step is sized to be a single PR or a single issue thread.

01

Ship run history + per-run logs (F02, largest)

A bounded ring of { run_id, started_at, ended_at, exit_code, outcome, trigger } persisted in state.json; one log file per run pruned by keep_runs. Surface in harness list as a column and in harness describe as the canonical last-5-runs pill. Implement the deferred schema from ADR-0013. Largest impact — the cockpit-without-history is the advertisement-vs-reality gap.

02

Resolve enabled × schedule persistence (F01)

Add Manager.fire(harnessID) distinct from Manager.Start; persist last_fired_at in state.json; on boot, detect the missed window and skip (or queue, with a config flag). Closes issue #159 referenced in ADR-0013.

03

Suspend-safe scheduler + acceptance test (F03)

Add the property-based test "schedule survives overnight suspend" that ADR-0013 names in its Confirmation list. If robfig/cron fails the test, swap to a per-tick evaluator. Use Now().Add(8h).Sub(LastTick) rather than armed long timers.

04

Daemon-crash blast-radius banner (F04, partial)

Until the per-harness reaper lands, surface a TUI banner on every reattach that started within 60s of daemon uptime: "all harnesses were restarted by daemon crash; scrollback is fresh." Cheap, honest, documents the limitation.

05

Trajectory-gating default (F05)

In the TUI's harvest_trajectory flow: default false when the harness has an env_file; default false for any harness created via the new flow; require an explicit confirmation phrase for true. Closes the silent opt-in flagged in ADR-0011 + ADR-0012.
