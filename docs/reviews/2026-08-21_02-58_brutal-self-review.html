The headline

Root sat at 96% full while the system's only automated space-recovery tool (nix-gc) had been aborting every night since 2026-08-17 — blocked by our own btrfs-gc-guard because device-unallocated was "only" 3%… which is 21.7 GiB of idle headroom. The guard demanded 10% of a 723 GiB device (72 GiB) — a level garbage collection can never restore, because deleting files frees extents within allocated chunks; only balance returns chunks. We built a deadlock, deployed it as protection, and then wrote four days of feature reports while it strangled the machine. The system alerted the whole time (nightly OnFailure notifications + a live Gatus BTRFS CRITICAL alert). Nobody acted. That is the finding everything else orbits: we generate alerts and reports faster than we generate remediation.

01The Eleven Questions

1. What did we forget?

The P0 that stopped being interesting. "Free root below 95%" has been the top TODO since 2026-08-17. Since then: hermes hardening, qmd reintegration, PapDashboard, session-boot guards — four days of P1/P2 work while the P0 worsened to 96% and its primary lever (GC) quietly died on night one. We also forgot the review-follow-through items our own 2026-08-20 report promised as "immediately actionable": workspace-usage metric, deploy.sh concurrent-activation check (done this session), gotchas entries (done this session), CHANGELOG/FEATURES hermes entries (CHANGELOG done this session; FEATURES not).

2. What is stupid that we do anyway?

Gating a recovery action on a threshold the action cannot satisfy. The GC guard is the flagship example (now fixed), but the pattern matters: a guard must be gated on the resource it actually consumes (a few GiB of metadata churn room), or it locks the door and swallows the key. Runner-up: alerts without remediation paths — nix-gc's OnFailure has fired 5 nights into a desktop notification void; the Gatus CRITICAL alert repeats a runbook nobody ran.

3. What could we have done better?

Monitoring is our least-tested layer. gatus-config.nix (1,525 lines), system-health.nix (863), the SigNoz provisioner stack (~1,100 across three files), dnsblockd (714), pocket-id (684), homepage (674), buildcache recovery (553), btrfs-health guard/collector — zero tests. Every phantom-green incident we've documented (buildcache zombie mount, gatus sqlite self-check, BTRFS chunk check) lived in exactly this untested stratum. The thing that watches everything is watched by nothing.

4. What could we still improve?

See the prioritized plan — 14 steps ranked by effort × impact, split into user-sudo actions, my no-gate actions, and backlog. The theme: convert review findings into closed loops (tests, auto-remediation, or explicitly-dropped items) instead of new reports.

5. Did I lie to you?

Not in this report — everything here was verified live this session (journal greps, re-measured directories, built-and-executed scripts). But honesty requires noting two lies I caught myself almost telling: (a) I initially blamed the forgejo mirror errors on a PrivateTmp change from commit 26beaf0c — checking showed that comment belongs to the backup oneshot, not the main unit; the hypothesis is dead and the report says "cause unknown". (b) I almost reported "5 nightly GC failures" from a since-clause that only covered Aug 14+ — the count and first-failure date were re-verified from the journal directly. Prior reports in this repo have contained unverified claims (see Stale Truths below); the only defense is measuring before writing.

6. How can we be less stupid?

Three rules: (1) Every guard on a recovery action must use a threshold the action itself can re-satisfy — or it deadlocks at the moment of need (now in AGENTS.md + gotchas-archive). (2) Every alert ships with a runbook and an owner; alerts without either get muted after a week — an unacted alert is training us to ignore alerts. (3) Point-in-time claims in TODO/reports get re-measured before anyone acts on them — the global AGENTS.md has said this all along; today it caught two of our own (the 58G hermes claim, the "stranded" monitor365 change).

7. Ghost systems — integrated or dead?

visionreviewd: a module that flake-check evaluates on every run, enabled on no host anywhere — dead code costing eval time and carrying bitrot risk. Either wire it or delete it (decision item in the plan). minecraft/voice-agents/monitor365 are deliberate disabled options with documented blockers — not ghosts. Filesystem ghosts found: ~/.cache.pre-subvol (2.1G, migration leftover), ~/backups/activitywatch-sqlite-preDecimation-13GB.db (13G, "delete after settling" — it settled), ~/tmp (12G, unexamined). Darwin is the biggest ghost of all: its registry fix is written but undeployed, flake check skips aarch64-darwin, and the macOS half of this repo drifts untested by design — a conscious decision nobody has consciously made recently.

8. Are we in the scope-creep trap?

Yes, by recency bias. TODO priorities 2.5 and 3 contain SigNoz log-pipeline polish, dashboard generators, and Caddy access-log ingestion — all added while a P0 disk deadlock ran. AGENTS.md itself is 791 lines against a charter of "concise, enduring context"; incident narratives keep accreting there instead of gotchas-archive. The documentation machine has outrun the doing machine: 8 status reports in 3 days, TODO items "carried ×4".

9. Did we remove something that was useful?

No harmful removals found. The major retirements (Waybar, rofi, awww, cliphist, the qmd HTTP daemon, the @go/@npm/@cargo subvolumes) all have documented successors and were re-verified in their sessions.

10. Did we create any split brains?

Known-and-documented: the manual ossWebsites list vs terraform, AUTH_VHOSTS vs caddy.nix. Found this session: AGENTS.md claimed flake.nix at "~680 lines" (reality: 943 — fixed); TODO_LIST's "stranded monitor365 change" vs a clean tree (it had landed and deployed — fixed); TODO_LIST's "hermes 58G" vs a 3.2M reality (closed). The oldest standing one: master is 6+ commits ahead with the push held since 2026-08-18 pending a history-purge decision that key rotation already made moot — the repo lives in don't-push limbo while the auto-commit daemon keeps advancing the divergence.

11. How are we doing on tests?

The eval-guard layer is world-class; the runtime-monitoring layer is untested. 18 test files cover: port-uniqueness, exec-start-paths, session-boot-audit (eval), hermes, paperless, attic, browser-history, searxng, caddy-auth, oauth2-proxy, ksm, mkFilesystem, pma-identity (VM), scripts, gatus patterns (lint). Nothing covers the collectors, provisioners, or the guard logic — the exact code where this session found a 5-day-old deadlock. Start where it hurts: synthetic btrfs-chunk-check fixtures for the guard, /proc//sys fixtures for system-health, jq-projection tests for the SigNoz provisioner.

The btrfs-gc-guard deadlock (2026-08-17 → 08-21)

platforms/nixos/system/btrfs-health.nix · nix-gc.service ExecStartPre

Evidence: journal shows nix-gc.service: status=1/FAILURE at 00:00 every night since Aug 17 ("BTRFS GUARD: ABORT — device-unallocated at 3%" — 3% of 723 GiB = 21.7 GiB idle); 44 system generations accumulated Aug 16→21 (exactly the failure window — the oldest kept gen dates to the last successful GC); nix-build-cleanup blocked by the same guard; root at 96%; forgejo slow-SQL (23–42s mirror-table UPDATEs) as IO-pressure collateral.

Fix (verified): guard now gates on UNALLOC_BYTES < 5 GiB (the same floor this module's balance jobs use) + META_PCT > 90 hard block, with a runbook-bearing abort message. The shipped script was built and executed against four synthetic chunk-check outputs (live→OK rc0, 3GiB→ABORT, META 95%→ABORT, META 87%→WARN) and against the real filesystem: current state (2% unalloc = 20.4 GiB, META 82%) passes → after the next deploy, GC runs and auto-prunes generations >3d. Generation retention needs no separate fix — it was a symptom.

Deploy needed: the fix is in the tree, not yet activated (this session has no sudo). Until deployed, nightly GC keeps aborting. User: nix run .#deploy.
