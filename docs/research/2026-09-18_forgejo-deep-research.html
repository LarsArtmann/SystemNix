Deep Research Report · Snapshot 2026-09-18

Forgejo, Maxed Out

Everything the Forgejo project and its community shipped up to v16 — mapped against the SystemNix instance on evo-x2: what is already excellent, which features are sitting idle, what the ecosystem can add, and a prioritized roadmap to push the forge to its limits.

Local: forgejo-lts (v15.0.x) · SQLite · OIDC-only Upstream stable: v16.0.5 · LTS: v15.0.9 134 pull mirrors · Actions + runner enabled All claims sourced · see §10

01Summary

Forgejo is a community-governed, self-hosted software forge (a hard fork of Gitea, stewarded by the German non-profit Codeberg e.V.) that has shipped 119 releases and moved to a fast 3-month major cadence. The current stable line is v16.0.5 (2026-09-17) and the current LTS is v15.0.9 — which is the branch this instance runs (pkgs.forgejo-lts), supported until 2027-07-15. v17.0 lands 2026-10-15.

The SystemNix deployment is already in the top tier of self-hosted forges on the axes most people get wrong: SSO-only login via Pocket ID (no password surface at all), a monitored GitHub pull-mirror fleet (~134 mirrors) with staleness/failure metrics that caught a real 14-day silent outage, daily full dumps to the RAID1 pool, hardened systemd units, and a wired Actions runner. The gaps are almost all unused capability, not misconfiguration: Actions is live on exactly three repos — a Rust CI matrix, a fmt/config-guard, and a nightly Nix+attic cache warmer — out of ~260, the runner still needs its v13 compatibility pass, the 23 package registries are idle, and the community ecosystem (MCP server, Renovate, Pages servers, theming, IaC providers) is untapped.

The single biggest unlock: Forgejo is not just a GitHub mirror cabinet — with ~15 lines of config plus a handful of workflow files it becomes the CI/CD, artifact registry, and API surface for the whole LarsArtmann portfolio, with the mirror fleet as its outage-immune backup layer.

03The Forgejo Project

Forgejo was forged in late 2022 as a community hard fork of Gitea, after the for-profit Gitea Ltd takeover triggered a broad open letter from the community (including many distros and Codeberg). It is developed in the open on codeberg.org/forgejo/forgejo (5.5k stars, 955 forks, 119 releases at snapshot time), governed by Codeberg e.V. teams with transparent funding, and is what powers Codeberg itself — which means Codeberg-scale load problems (crawlers, mirror storms, DB deadlocks) get fixed upstream and flow into every instance.

Release cadence (verified)

A major every ~3 months; the April release each year is LTS. Daily *-test builds and a public next-instance (v16.next.forgejo.org) let you validate upgrades before patch day.

Support windows are short for non-LTS

v16.0 dies 2026-10-29 when v17 lands. Running the LTS line (as this instance does) is the right call for a homelab: v15.0.9 is patched until 2027-07-15.

Known pain points (documented, monitored, partially upstream)

  • The mirror unique-queue can wedge after a hard freeze — cron pushes then dedup-skip silently. Detected via mirror_sync_stalled; fix is a forgejo.service restart.
  • Three upstream gaps are fully drafted and source-verified (docs/services/forgejo-upstream-issues.md, re-verified 2026-09-18): failed syncs still advance mirror_updated; queue dedup-skips log at Trace only; credential-helper temp-file failures abort syncs with no repository notice.   • SQLite + Actions is fine at this scale, but this host’s IO-storm history (the pocket-id SQLITE_BUSY class) applies here too — keep DB maintenance tasks off-storm-hours.

5.3 The 23 package registries (all idle right now)

Forgejo ships registries for Alpine, ALT, Arch, Cargo, Chef, Composer, Conan, Conda, Container (OCI/ Docker), CRAN, Debian, Generic, Go, Helm, Maven, npm, NuGet, Pub, PyPI, RPM, RubyGems, Swift, Vagrant — each backed by tokens and per-owner quotas. The three most interesting for this portfolio:

  • Container (OCI) — since v15 uploaded containers auto-link to their repo when the image carries org.opencontainers.image.source or is named {owner}/{repo}. Roadmap item R16 uses this as a Docker-Hub-outage-immune mirror of the pinned images in lib/images.nix.
  • Cargo — private registry for the Rust collector crates without publishing to crates.io. Caveat: Nix’s buildRustPackage cargo-fetch flow needs registry config + token plumbing; treat as exploratory.
  • Generic — the escape hatch: Nix closure tars, release binaries, benchmark artifacts. Dead simple PUT /api/packages/{owner}/generic/{name}/{version}/{file}.

06Forgejo Actions — The Complete Picture

Actions is enabled and already carrying production weight on exactly three repos — wireguard-collector (Rust CI matrix), collector-utils (fmt + config-guard), and monitor365 (nightly Nix+attic cache warmer with secrets and a cron schedule) — all on the native label. That is 3 of ~260 repos, and all three workflow files say they are kept in sync with their GitHub twins manually. Meanwhile upstream has turned Actions into a serious CI system. What is available on your v15 LTS, plus what v16 adds when you eventually move:

Workflow language (v15 baseline)

  • Reusable workflow expansion v15 — uses: another repo’s workflow; jobs expand with separate logs and independent runner labels. This is the building block for a portfolio-wide workflow-library repo.
  • Concurrency groups + dynamic matrices (matrix and runs-on computed by earlier jobs) v14.
  • OIDC identity tokens v15 — workflows get short-lived signed JWTs instead of static secrets for third-party systems (runner > v12.5).
  • Failure email notifications via enable-email-notifications: true v12 — lands in your inbox through the mail relay once Resend domain verification completes.
  • Scheduled workflows (cron, with CRON_TZ timezones in v16) — cron-as-code for the things currently living in systemd timers.

Control plane & APIs

  • PR trust management v14 — approve-once / approve-always / deny for workflows from untrusted branches, with revocation.
  • Run attempt viewer v13 and manual run prioritization v16.
  • Static workflow validation in the UI v13 — typos like ruins-on: are caught before dispatch.
  • Full Actions APIs v16 — list/download/delete artifacts, fetch workflow/job logs, cancel runs, /actions/run introspection; admin-managed user tokens v16.
  • Authorized Integrations v16 — external systems (or workflows) authenticate to Forgejo’s API/Git with JWTs; no static tokens, no permission-escalation surface.

6.2 Forgejo Runner v13 — the compatibility pass you must not skip

The runner line moved to v13.1.0 (2026-08-31) and v13.0.0 shipped deliberate breaking changes (security & predictability). nixpkgs updates forgejo-runner independently of the forge server, so one of these days a routine bump will land it on your runner unit. Before that happens, audit every workflow you own for:

Removed in v13 Replacement
::set-output name=X::v echo "X=v" >> "$FORGEJO_OUTPUT"
::set-env name=X::v echo "X=v" >> "$FORGEJO_ENV"
::add-path:: /dir echo "/dir" >> "$FORGEJO_PATH"
DOCKER_USERNAME/DOCKER_PASSWORD secrets for registry pulls explicit jobs.<id>.container.credentials
container.network_mode setting container.network (already set here)
GITEA_* env vars, ${{ gitea.* }} context FORGEJO_* / ${{ forgejo.* }}
Also in v13: expression-evaluation failures now fail the job (no more warn-and-continue), invalid matrices are hard errors, Docker ≥ 25 required (IPv6 network parsing bug fixed in Docker 28.0.1 — this host runs Docker 29.x, fine), Git subprocesses run in a process group, and a refs/replace/* commit-impersonation path during action checkout was closed. New and notable: an experimental gRPC plugin backend for custom executors and EnableNamespaces for matrix reusable workflows.

6.3 Runner security posture (read before adding workflows)

The runner is, by design, a remote-code-execution service. Yours is single-user and the repositories are mirrors of your own code, which is the low-risk end of the spectrum — but two of its current settings deserve a conscious decision:

  • container.network = "host" gives containers your host network namespace. Convenient for hitting 127.0.0.1 services (attic, flm), but workflows can reach every loopback service. Keep it only while the workflow set is 100% yours.
  • The native label (registered as native:host) executes jobs directly on the host. All three live workflows already use it; never let it pick up workflows from anything you did not write.

7.1 The headline find: an official MCP server

gitea-mcp — your forge as an AI-agent tool surface

gitea.com/gitea/gitea-mcp · official Gitea project, active (commits Sept 2026) · Go

Speaks the Gitea API — which Forgejo implements — and exposes 60+ MCP tools: repos, issues, PRs (read/diff/merge), reviews, Actions (dispatch/cancel/rerun, logs, artifacts, secrets), releases, wiki, packages, labels, milestones, notifications, time tracking, file/branch/tag operations. Caveat: it is built and tested against Gitea. Forgejo’s API compatibility is high but not contractual — probe the tool set you need (issues, repos, actions) before wiring it into daily-driver agents.

08The Max-Out Roadmap

Ordered by impact-per-effort. P0 = config-only, safe, do this week. P1 = real unlocks. P2 = ecosystem adoption. P3 = frontier/watchlist.

P0 — config-only quick wins

R1
P0

Point DEFAULT_ACTIONS_URL at data.forgejo.org

Today it is "github", so uses: actions/checkout@v4 silently clones from GitHub — making your “local” CI GitHub-dependent at exactly the moment you wanted independence. https://data.forgejo.org hosts known-good, FSF-licensed actions (actions, docker orgs) curated for Forgejo Actions — including actions/checkout, a maintained mirror of the GitHub action (verified via its API 2026-09-18), so the three live workflows keep working after the flip. 

services.forgejo.settings.actions.DEFAULT_ACTIONS_URL = "https://data.forgejo.org";
R2
P0

Cap Actions log & artifact retention

Defaults are 365 days of job logs and 90 days of artifacts on the QLC NVMe — the exact write-churn profile this host fights. 30 days is generous for a personal forge. 

services.forgejo.settings.actions.LOG_RETENTION_DAYS = 30;
services.forgejo.settings.actions.ARTIFACT_RETENTION_DAYS = 30;
R3
P0

Lock the mirror fleet’s network scope ([migrations] allowlist)

134 mirrors all point at GitHub; nothing else should ever be fetched. The allowlist turns any mirror-URL surprise (pastied URL, hijacked upstream redirect) into a loud fetch failure instead of an outbound request. 

services.forgejo.settings.migrations = {
  ALLOWED_DOMAINS = "github.com,api.github.com,codeload.github.com,objects.githubusercontent.com,raw.githubusercontent.com";
  ALLOW_LOCALNETWORKS = false;
};

Verify by forcing one mirror sync afterwards (system_forgejo_mirror_erroring must stay 0). Note the full redirect-following fix lands in v16; on v15 this is defense in depth, not completeness.

R4
P0

Dry-run the commit-status doctor

If Actions has ever run here, the commit_status table may carry the historical duplicate-row bug Forgejo fixed in v14 — on their own instance 97% of rows were redundant. Measure before Actions adoption makes it worse. 

sudo -u forgejo forgejo doctor cleanup-commit-status --dry-run
# On SQLite: run with a small --delete-chunk-size, ideally while the
# service is quiet (two writers on one SQLite file lock each other).
R5
P0

Adopt the Catppuccin Mocha theme

The instance ships forgejo-auto/arc-green while every other surface in the homelab is Catppuccin Mocha. The community theme installs as CSS into Forgejo’s custom dir and its catppuccin-*-auto variants follow system light/dark. 

# 1. fetch the catppuccin/gitea release CSS into
#    ${stateDir}/custom/public/assets/css/
# 2. extend the theme list:
services.forgejo.settings.ui.THEMES =
  "forgejo-auto,forgejo-light,forgejo-dark,arc-green,catppuccin-mocha-auto";

Manage the CSS via a small derivation symlinked into custom/ so deploys stay declarative.

P1 — real unlocks

R7
P1

Scale the existing workflow pattern (3 repos → the active set)

The pattern already exists — monitor365 runs a nightly Nix build that logs into attic with ATTIC_ENDPOINT/ATTIC_TOKEN secrets on a cron, and the two collector crates run Rust CI on native. What is missing is reach: port that shape to the actively-developed Go repos and to SystemNix itself, and use the v15 reusable-workflow expansion so every repo inherits one library workflow instead of hand-synced copies. 

# .forgejo/workflows/ci.yml  (target shape for a Nix-exposed Go repo)
jobs:
  nix-build:
    runs-on: native
    steps:
      - uses: actions/checkout@v4
      - run: |
          nix build .#default --accept-flake-config \
            --option extra-substituters https://cache.home.lan/monitor365
          nix flake check --no-build

Auth for private inputs rides the deploy-key pattern from nix-check.yml; add the key as an Actions secret (repo or org scope), not a literal. Host-mode jobs run inside your nix environment — keep the §6.3 trust boundary in mind.

R8
P1

Runner v13 compatibility pass — before nixpkgs forces it

Check the deployed runner version, then sweep any workflow for the v13 removals (§6.2). Your container.network = "host" setting is already the post-v13 name. The three existing workflows are clean on a spot-check (no removed commands, no GITEA_* usage); run the sweep to confirm before the next nixpkgs bump lands v13. Pin/hold the bump if any workflow still uses ::set-output until it is migrated. 

forgejo-runner --version
rg -n "::set-output|::set-env|::add-path|DOCKER_USERNAME|GITEA_" ~/projects/*/.forgejo 2>/dev/null
R9
P1

Scheduled workflows with failure emails

Anything currently a hand-rolled timer against a repo (nightly benchmarks, doc regeneration) can become a scheduled workflow; the enable-email-notifications: true flag mails you on failure through the relay. Prereq: finish the Resend domain verification so non-owner delivery works.

R10
P1

File the three drafted upstream issues

docs/services/forgejo-upstream-issues.md holds three source-verified drafts (failed-sync TouchMirror masking, Trace-level queue dedup-skips, credential-helper aborts). They are blocked only on the Codeberg-account decision. Filing them converts your worst mirror-pipeline blind spots into upstream fixes that reach every v15.0.x patch.

R11
P1

Plan the v15 → v16 (or v17) upgrade on your terms

Stay on the LTS until at least the first v16.x patches prove out — then read the breaking changes that actually touch you: (1) mirrors of renamed/transferred upstream repos will hard-fail on redirects (inventory renamed repos first), (2) container-only REVERSE_PROXY_TRUSTED_PROXIES change does not apply (you run the binary), (3) EXIF removal is a no-op for you, (4) cookie rename logs everyone out once. v16’s Authorized Integrations + Actions APIs are the carrot.

R12
P1

Re-issue long-lived tokens as repo-scoped (v15)

The sync, hermes, and future MCP/MCP-adjacent tokens are instance-wide today. v15 repository-scoped tokens shrink each of them to the repos they touch — the same least-privilege move the deploy keys got in CI.

P2 — ecosystem adoption

R13
P2

Wire gitea-mcp into crushrc (read-only first)

stdio MCP server + GITEA_HOST=https://forgejo.home.lan + repo-scoped token + GITEA_READONLY=1. Agents gain mirror triage, issue filing, and CI dispatch. Remember: Crush loads MCP changes only at session start, and probe the tool set against Forgejo before trusting it daily.

R14
P2

Self-hosted Renovate on native repos

Run the Renovate container/CLI as a scheduled workflow (platform=forgejo, PAT with repo/user/issue/org scopes, explicit repository allowlist — autodiscovery would skip your mirrors anyway, which is exactly right). Dependency PRs then appear on the forge instead of only in GitHub.

R15
P2

A nightly skopeo copy timer mirrors the pinned images from lib/images.nix into the Forgejo container registry (tag + digest preserved). Anti-recommendations (considered and rejected)

  • Woodpecker/Crow alongside Actions — two CI systems, one user, zero marginal value.
  • Terraform provider — your Nix oneshots are already declarative, idempotent, and reviewed; adding Terraform forks the source of truth.
  • PostgreSQL migration “because scale” — SQLite is the right engine for a single-writer forge; revisit only if Actions jobs + mirrors start contending visibly (then it joins the shared PG instance with peer auth).
  • Global 2FA enforcement — meaningless under SSO-only; Pocket ID owns the passkeys.
  • Opening registration / public exposure — the forge is LAN-first behind SSO; moderation, quota, and guardian tooling only matter if you ever change that.

09Risks & Gotchas (instance-specific)

Known class

SQLite on a storm-prone filesystem

cf. pocket-id SQLITE_BUSY storms, 2026-08-22 / 2026-09-06 incidents

The forge DB shares the QLC-NVMe write profile that produced documented lock storms on sibling services. Keep doctor/cleanup jobs off storm hours, keep the mirror queue healthy (restart on mirror_sync_stalled 1), and don’t stack heavy Actions windows with btrbk sends.

Design fact

The runner is RCE by contract

forgejo.org/docs/latest/admin/actions/security/

Fine for your own workflows; the guardrails are the two settings called out in §6.3 (host networking, native label). If anyone else ever gets commit access, those settings are the first thing to revoke.

Upgrade trap

v16 mirror redirect strictness

http.followRedirects=false means mirrors of repos that were renamed or transferred upstream stop syncing with a redirect error until their mirror URL is updated. Inventory renames before any v16+ move — the fleet’s own erroring metric will name the victims.

Rate discipline

GitHub API budget

260+ repos enumerated every 6h plus per-repo mirror creation through the API + gh. Watch for secondary rate limits when adding bulk operations (mass re-mirror, issue import) — stagger them, the way the auto-assign service staggers its edits.

Note

Actions on mirrored repos

Workflows live in repo content and Actions is built around native repo events. Treat the mirror fleet as the archival/backup tier and run CI on native repos (or push-mirrored originals) — that is the designed pattern, and it keeps the runner’s trust boundary equal to “code you wrote.”
