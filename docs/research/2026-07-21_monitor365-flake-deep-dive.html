00Summary

SystemNix consumes the Monitor365 flake exactly the way a downstream consumer should. The wrapper module at modules/nixos/services/monitor365.nix (164 lines) opens with imports = [ inputs.monitor365.nixosModules.monitor365 inputs.monitor365.nixosModules.monitor365-server ] and then layers only SystemNix-specific defaults — ports, sops secret paths, runtime deps, Pocket ID SSO — every one annotated with lib.mkDefault so the operator can still override. There is zero option duplication: every option the upstream modules declare (listenAddr, jwtSecretFile, bootstrap, sso, healthCheck, backup, tlsCertFile, displayUser, …) flows in through the import. This is the pattern the DiscordSync deep dive (same date) recommends adopting.

The overlay is consumed correctly too: overlays/linux.nix:197 registers monitor365.overlays.default, then layers a build-fix overlay (monitor365SwaggerUiFixOverlay) on top for two genuine upstream build bugs (utoipa-swagger-ui PermissionDenied + libspa SPA_ID_INVALID bindgen failure). Both fixes are necessary and correctly isolated. The surface integration is comprehensive: 8 Gatus checks with Discord alerts, Caddy vHost with conditional SSO, Homepage tile, Pocket ID OIDC client, sops templates, and restartTriggers on the shared auth-token secret.

The bottom line This is exemplary flake consumption. Three minor gaps remain: (1) the upstream backup option is unused — the DuckDB is the sole store of all monitoring data and BTRFS snapshots are local-only, so this is a real data-loss exposure; (2) eight desktop collectors are enabled but neither display-discovery mechanism (displayUser or the graphical-helper module) is wired, so they likely skip gracefully as silent no-ops; (3) a load-bearing CORS workaround comment documents an upstream env-var-vs-TOML-sequence bug that should be fixed upstream. Fixing all three lifts the score to ~96.

01Findings

Ordered by impact. None of these are consumption anti-patterns — they are capabilities the upstream flake exposes that SystemNix has not yet wired. The pattern itself is exemplary.

Missed Opportunity · Medium-high impact (data-loss exposure)

Scheduled backup unused — DuckDB is the sole store, BTRFS is local-only

SystemNix monitor365.nix + configuration.nix:428-434 (no backup attr); upstream server-module.nix:200-217 exposes backup.enable / backup.schedule / backup.keep; timer at server-module.nix:502-533

The upstream server module ships a complete scheduled-backup subsystem: a oneshot service that runs monitor365-server … backup --output-dir <stateDir>, plus a systemd timer (default daily at 03:00, Persistent = true), with configurable retention (keep = 7 default, oldest pruned). SystemNix sets none of these — the option defaults to enable = false.

The risk is real and documented. Per AGENTS.md: “All snapshots are LOCAL-ONLY. If the NVMe fails, everything is lost. This is the #1 data loss risk (flagged since 2026-06-25).” The DuckDB at /var/lib/monitor365-server/monitor365.duckdb is the sole store of every captured event — system telemetry, app usage, screenshots metadata, keystroke counts, location. BTRFS snapshots of @ cover it, but only locally. A daily *.backup_*.db export is a prerequisite for any future offsite sync (rsync/rclone/borg) of those files — you cannot safely rsync a live DuckDB.

Recommendation Three lines in configuration.nix under services.monitor365-server. The timer, retention, and backup script all arrive free via the upstream import. 
# configuration.nix — services.monitor365-server
monitor365-server = {
  enable = lib.mkDefault true;
  bootstrap = { /* unchanged */ };
  sso.enable = lib.mkDefault true;
  backup = {
    enable = lib.mkDefault true;
    schedule = lib.mkDefault "*-*-* 03:00:00"; # daily, before btrbk at 23:00 next day
    keep = lib.mkDefault 7;
  };
};
Missed Opportunity · Medium impact (silent no-op)

Eight desktop collectors enabled but no display-discovery path wired

SystemNix configuration.nix:412-424 (enables screenshots, keystrokes, mouse, clipboard, camera, notifications, app_usage, afk_status); monitor365.nix sets neither displayUser nor imports nixosModules.monitor365-graphical-helper; upstream module.nix:101-112 (displayUser) and flake.nix:566 + graphical-helper-module.nix

The agent runs as a dedicated system user (monitor365) with linger = true, so it survives logout — correct for headless collectors. But graphical collectors (screenshots, window titles, keystrokes, mouse, clipboard, AFK) need DISPLAY/WAYLAND_DISPLAY/ XAUTHORITY/XDG_RUNTIME_DIR, which are session-scoped environment variables on the logged-in user. The upstream module offers two discovery paths:

  • displayUser (module.nix:101-112) — the agent discovers display env from this user's active login session at startup via /proc/<pid>/environ. SystemNix does not set it.
  • monitor365-graphical-helper (flake.nix:566 → graphical-helper-module.nix) — a separate systemd.user service in graphical-session.target that forwards graphical events to the agent over the IPC socket at /run/monitor365/agent.sock. SystemNix does not import this module (confirmed: grep for graphical.helper in modules/, platforms/ returns only the comment at monitor365.nix:18).

The SystemNix wrapper comment (monitor365.nix:17-20) says “Display env discovered from active sessions via the graphical helper” — but neither mechanism is actually wired. The upstream module docstring says collectors “check availability at startup and skip gracefully if unavailable.” The likely runtime state: the eight desktop collectors are enabled in TOML, pass validation, and then silently emit zero events because the agent has no DISPLAY. No crash, no error — just an empty dashboard for those categories. This needs runtime verification (see Recommendation).

Recommendation (verify first, then pick one path) Step 1 — verify the current state: journalctl -u monitor365 -b | grep -iE "display|wayland|skip|graphical|screenshot|keystroke" and check the dashboard for any non-headless events since the last reboot. Step 2 — if confirmed empty, wire one of the two paths. The graphical-helper module is the upstream-recommended design (it runs inside the user's graphical session, so display env is natural); displayUser is the lighter single-line option but depends on /proc discovery surviving the hardening profile. AGENTS.md has a note that displayUser “does NOT exist in the current upstream module” — that note is stale; the option is present at module.nix:101-112 as of the pinned rev. 
# Option A — graphical-helper module (upstream-recommended)
# monitor365.nix — add to imports list
imports = [
  inputs.monitor365.nixosModules.monitor365
  inputs.monitor365.nixosModules.monitor365-server
  inputs.monitor365.nixosModules.monitor365-graphical-helper # ADD

# then enable it (deviceId is required, derive from settings.device)

Partially Used · Low impact (upstream debt)

CORS workaround is load-bearing knowledge — fix should go upstream

SystemNix monitor365.nix:120-126 (the comment); upstream server-module.nix:441-443 emits MONITOR365_SERVER__CORS_ORIGINS as a comma-separated string

SystemNix correctly works around an upstream bug: the upstream module emits MONITOR365_SERVER__CORS_ORIGINS=https://a,https://b (a single string), but the server's Rust figment config parser expects a TOML sequence (["https://a", "https://b"]), so startup crashes with a parse error. SystemNix's workaround is to simply not set corsOrigins — valid because the WASM dashboard and API are same-origin behind Caddy (monitor.${domain}), so CORS is unnecessary.

The workaround is correct for this deployment, but the comment at monitor365.nix:120-126 is the only place this knowledge lives. If the comment is ever deleted, or a future contributor adds corsOrigins thinking it will work, the server will crash-loop. The root fix belongs upstream: the module should write a TOML config file for sequence-typed values (as the comment itself suggests).

Recommendation File an upstream issue/PR in github:LarsArtmann/monitor365 describing the env-var-vs-TOML-sequence mismatch, with the fix sketch from the SystemNix comment. Until then, the SystemNix comment is doing essential work — do not remove it.
