00Summary

SystemNix consumes only inputs.discordsync.packages.${system}.default — the compiled binary — from the DiscordSync flake. The flake's two other outputs, nixosModules.default and overlays.default, are ignored entirely. In their place, modules/nixos/services/discordsync.nix hand-writes a 160-line NixOS module that re-declares every option the upstream module already provides.

This is not careless duplication. SystemNix's module adds real host integration the upstream cannot: sops templates, the shared harden {} / serviceDefaults helpers, onFailure Discord alerts, a DNS-readiness wait gate, and correct ordering after dnsblockd.service. That layering is genuinely superb. The cost is silent drift: upstream commit ced0431b (“extract NixOS module to standalone file + add user/group options”) already changed the option surface, and SystemNix's copy has not followed. Three binary-supported capabilities are dark as a direct consequence.

The bottom line Strong integration layer, weak consumption. The single highest-leverage change is to consume flake.nixosModules.default as the base and layer the SystemNix-specifics on top — eliminating 160 lines of drift-prone duplication while keeping every hardening and sops integration. In parallel, wire three one-line environment variables that turn on OTel tracing, SIGHUP hot-reload, and self-alerting webhook notifications — all of which the binary already supports and SystemNix already has the infrastructure for.

◆What's already excellent

SystemNix's integration is not a subset of upstream — it adds host-specific hardening and dependency wiring that a portable upstream module cannot. These are done superbly and should be preserved in any refactor.

+
Rev-pinned with nixpkgs.follows flake.nix:393-402 — pinned to 9c640075, all five sub-inputs follow the SystemNix nixpkgs. Reproducible, no double instantiation.
+
Shared harden {} hardening — stronger than upstream discordsync.nix:152 uses the SystemNix harden helper, which is broader than upstream's hand-rolled NoNewPrivileges/ProtectSystem list. MemoryMax=2G + ReadWritePaths scope writes.
+
Structured sops secret management sops.nix:178-200 — Discord token, Turso URL+token, and GCS credentials flow through a sops template (discordsync-env) with svcEnabled guards. One missing service cannot block atomic secret decryption.
+
DNS-readiness gate (defends a documented boot race) discordsync.nix:23-33 — waitDnsReady blocks ExecStart until discord.com resolves. Necessary because dnsblockd owns :53 and the embedded sdns resolver must finish cache warm-up. A documented SystemNix gotcha.
+
Correct dependency ordering on dnsblockd discordsync.nix:107-116 — after = [ ... "dnsblockd.service" ]. Upstream only orders after network-online.target, which does NOT guarantee :53 has a listener. SystemNix is correct here; upstream is not.
+
Full surface integration onFailure → Discord alert; Gatus health check + Discord alert (gatus-config.nix:639); Homepage tile (homepage.nix:187); Caddy protectedVHost with SSO (caddy.nix:204). GCS backup wired (gcsBucket = "discordsync-backup") with sops-managed credentials.
+
Intentional backfillOnStartup = true default SystemNix flips upstream's default (false → true) for backup completeness. A deliberate divergence, documented at the option site.

Missed Opportunity · High impact (drift risk)

Upstream flake.nixosModules.default ignored — 160-line module duplicated

SystemNix modules/nixos/services/discordsync.nix:1-160 vs upstream nixos-module.nix:1-220; upstream flake export at flake.nix:554

DiscordSync's flake.nix line 554 exports flake.nixosModules.default = import ./nixos-module.nix; — a complete NixOS module declaring enable, package, user, group, discordTokenFile, backend, databasePath, tursoUrl, tursoAuthTokenFile, backfillOnStartup, apiAddr, apiKeyFile, and a healthCheck ExecStartPost. SystemNix re-declares a parallel set from scratch and does not reference the upstream module anywhere (confirmed: grep for discordsync.nixosModules in modules/, platforms/, flake.nix returns nothing).

The duplication is already drifting. Upstream commit ced0431b (“extract NixOS module to standalone file + add user/group options”) is recent, and SystemNix's copy diverges in defaults (backfillOnStartup), option shape (gcsBucket is first-class in SystemNix, env-var-only upstream), and missing options (apiKeyFile, healthCheck, package). Every future upstream option addition will require a manual port that nobody will remember to do.

Recommendation Import the upstream module as the base, then layer SystemNix-specifics on top via lib.mkMerge / disabledModules only where needed. The custom harden, sops, onFailure, and DNS-gate logic stays — it merges cleanly onto the upstream module's systemd.services.discordsync. See the Proposal section for the concrete pattern. 
# Before: 160-line re-implementation (modules/nixos/services/discordsync.nix)
{ inputs, ... }: {
  flake.nixosModules.discordsync = { config, pkgs, lib, ... }: let
    # ... re-declares every option upstream already declares ...
    # ... drifts silently on every upstream release ...
  in { ... };
}

# After: consume upstream, layer the SystemNix-specifics
{ inputs, ... }: {
  flake.nixosModules.discordsync = { config, pkgs, lib, ... }: {
    imports = [ inputs.discordsync.nixosModules.default ];

    # Override only the defaults that differ
    services.discordsync = {
      backfillOnStartup = lib.mkDefault true; # SystemNix wants full backfill
      apiAddr = "127.0.0.1:${toString ports.discordsync-api}";
    };

    # Layer SystemNix-specific hardening + secrets on top of the upstream unit
    systemd.services.discordsync =
      let waitDnsReady = pkgs.writeShellApplication { ... };
      in {
        after = [ "dnsblockd.service" "sops-nix.service" ];
        wants = [ "dnsblockd.service" "sops-nix.service" ];
        inherit onFailure;
        serviceConfig = lib.mkMerge [
          (harden { MemoryMax = "2G"; ReadWritePaths = [ cfg.stateDir ]; })
          { ExecStartPre = "+${lib.getExe waitDnsReady}"; }
        ];
      };
  };
}
Missed Opportunity · Medium-high impact

OTel tracing unused — SigNoz runs on 127.0.0.1:4318, tracer is a no-op

SystemNix discordsync.nix:129-139 (Environment list — no OTEL_EXPORTER_OTLP_ENDPOINT); upstream cmd/discordsync/init.go:356-367 reads it; SigNoz collector at signoz.nix:827 binds 127.0.0.1:4318

DiscordSync's initObservability() reads OTEL_EXPORTER_OTLP_ENDPOINT. When unset, it installs a noop tracer and every span is dropped. SigNoz is enabled on evo-x2, its OTLP/HTTP receiver binds 127.0.0.1:4318, and DiscordSync supports the otlptracehttp exporter with WithInsecure() (plaintext localhost). The infrastructure is fully in place; only one env var is missing.

DiscordSync is exactly the service where traces pay off: long-lived gateway connection, backfill workers with crash-resume checkpoints, projection workers, attachment downloads with retry, and GCS reconciliation. Today, incident diagnosis relies on journalctl log greps. With traces, a stuck backfill or a projection-lag spike would be a click in SigNoz.

Recommendation Add one line to the Environment list. The harden {} RestrictAddressFamilies = [ AF_INET AF_INET6 ] permits localhost sockets, so no capability change is needed. 
Environment = [
  "DB_BACKEND=turso-sync"
  "DATABASE_PATH=${cfg.databasePath}"
  "API_ADDR=${cfg.apiAddr}"
  # ... existing ...
  "OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:${toString ports.signoz-otlp-http}"
];
Missed Opportunity · Medium impact

SIGHUP hot-reload not wired — config tweaks force a full gateway reconnect

SystemNix discordsync.nix (no ExecReload); upstream nixos-module.nix:139 wires ExecReload = kill -HUP $MAINPID; binary cmd/discordsync/shutdown.go:32-51 handles SIGHUP

The binary implements waitForSignalOrReload: on SIGHUP it hot-reloads COMPRESSION_ALGO, CAPTURE_BOT_MESSAGES, CAPTURE_WEBHOOK_MESSAGES, DISCORDSYNC_WEBHOOK_URL, and BOT_HEALTH_GRACE_PERIOD — with a storm-guard against rapid repeats. Upstream's module wires this as ExecReload, so systemctl reload discordsync applies the change instantly.

SystemNix's module omits ExecReload. The consequence: toggling capture policy (e.g. systemctl reload would not work) requires systemctl restart, which drops the Discord gateway connection, re-runs waitDnsReady, and re-triggers backfill resume bookkeeping. A 50 ms config refresh becomes a multi-second reconnect cycle.

Recommendation One line in serviceConfig. If SystemNix adopts the upstream module (Issue 1), this comes for free. 
serviceConfig = lib.mkMerge [
  # ... existing ...
  { ExecReload = "${pkgs.coreutils}/bin/kill -HUP $MAINPID"; }
];
Partially Used · Medium impact (silent data loss risk)

Health monitoring hits shallow /healthz, not deep /readyz

SystemNix gatus-config.nix:643 polls /healthz; upstream nixos-module.nix:217 ExecStartPost polls /readyz; binary distinction documented in internal/api/server_test.go:135-158

DiscordSync exposes two health endpoints with deliberately different semantics: /healthz is pure liveness — it returns 200 even when the database is closed (verified by TestHealthz_DatabaseClosed). /readyz is deep readiness — it aggregates database, projection, and content-store health, with a configurable grace window that tolerates transient gateway disconnects (BOT_HEALTH_GRACE_PERIOD, default 30s).

SystemNix's Gatus check and Homepage site-monitor both hit /healthz. This means the “DiscordSync backup bot down” Discord alert only fires on process death. A broken projection worker, a closed DB handle, or a stuck content store all return 200 on /healthz — the bot appears healthy while silently dropping events. There is also no ExecStartPost health gate, so systemd considers the service started the moment execve succeeds, before any subsystem is verified.

Recommendation Switch the Gatus URL to /readyz, loosen the status condition to [STATUS] < 400 (to tolerate grace-period 503s), and add the upstream ExecStartPost curl gate so systemd restarts on degraded subsystem state. 
# gatus-config.nix — Before
url = "http://localhost:${toString ports.discordsync-api}/healthz";
conditions = [ "[STATUS] == 200" "[RESPONSE_TIME] < 500" ];

# After — deep health, tolerates grace 503
url = "http://localhost:${toString ports.discordsync-api}/readyz";
conditions = [ "[STATUS] < 400" "[RESPONSE_TIME] < 500" ];

# discordsync.nix — add the systemd readiness gate
serviceConfig.ExecStartPost =
  "+${pkgs.curl}/bin/curl --fail --silent --retry 5 --retry-delay 2"
  + " --max-time 10 http://localhost:${cfg.apiAddr}/readyz";
Missed Opportunity · Low impact, high ease

DISCORDSYNC_WEBHOOK_URL unused — instant disconnect alerts already possible

SystemNix discordsync.nix (not set); upstream internal/config/config.go:121-124 (WebhookURL); SystemNix already holds discord_alert_webhook_url in sops (sops.nix:176)

The binary posts a JSON payload to a Discord/Slack-compatible webhook on every gateway disconnect and reconnect. SystemNix already has a Discord webhook URL in sops (used by Gatus). Today, a gateway disconnect is only noticed via the 60-second Gatus poll — and only if Issue 4 is fixed so the check uses /readyz. With the webhook wired, the bot self-pushes an alert within seconds of the event.

Recommendation Add DISCORDSYNC_WEBHOOK_URL to the sops template (sops.nix discordsync-env) sourced from the existing discord_alert_webhook_url. Zero new infrastructure.
Partially Used · Low impact

flake.overlays.default unused — package referenced by raw input path

SystemNix discordsync.nix:20 (inputs.discordsync.packages.${system}.default); upstream flake.nix:550-552 exposes overlays.default

Upstream exports an overlay that injects pkgs.discordsync. SystemNix reaches across the input boundary directly. Both work, but the overlay is the idiomatic consumption pattern: it lets any module reference pkgs.discordsync without threading inputs through, and it composes with mkLarsPackages. Low impact on its own; becomes relevant if Issue 1 is addressed (the upstream module uses lib.mkPackageOption pkgs "discordsync", which resolves through the overlay).

Recommendation Register inputs.discordsync.overlays.default in overlays/linux.nix, then drop the inputs.discordsync.packages reference.

02Target state — consume upstream, layer SystemNix

The refactor below preserves every SystemNix-specific strength from the Strengths section while eliminating the 160-line duplication. The upstream module becomes the base; SystemNix merges its hardening, secret, dependency-ordering, and DNS-gate logic on top. Issues 2, 3, and 5 are addressed inline (tracing, reload, webhook) because they are each a one-line addition. 

# modules/nixos/services/discordsync.nix — target shape
{ inputs, ... }:
{
  flake.nixosModules.discordsync =
    { config, pkgs, lib, ... }:
    let
      inherit (import ../../../lib/default.nix lib)
        harden serviceDefaults onFailure ports;
      cfg = config.services.discordsync;

      waitDnsReady = pkgs.writeShellApplication { /* unchanged */ };
    in {
      # 1. Consume the upstream module as the base
      imports = [ inputs.discordsync.nixosModules.default ];

      # 2. Override only the defaults that differ
      services.discordsync = {
        backfillOnStartup = lib.mkDefault true;          # Issue: intentional
        apiAddr = "127.0.0.1:${toString ports.discordsync-api}";
      };

      # 3. Layer SystemNix-specific unit config
      systemd.services.discordsync = {
        after  = [ "network-online.target" "sops-nix.service" "dnsblockd.service" ];
        wants  = [ "network-online.target" "sops-nix.service" "dnsblockd.service" ];
        inherit onFailure;
        startLimitIntervalSec = 300;
        startLimitBurst = 10;

        serviceConfig = lib.mkMerge [
          (harden { MemoryMax = "2G"; ReadWritePaths = [ cfg.stateDir or cfg.dataDir ]; })
          (serviceDefaults { Restart = "on-failure"; RestartSec = "10"; })
          {
            ExecStartPre = "+${lib.getExe waitDnsReady}";
            ExecReload   = "${pkgs.coreutils}/bin/kill -HUP $MAINPID";   # Issue 3
            Environment  = [
              "OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:${toString ports.signoz-otlp-http}" # Issue 2
            ];
          }
        ];
      };

      # 4. Reuse the existing sops template (unchanged) — adds DISCORDSYNC_WEBHOOK_URL (Issue 5)
      # sops.secrets & sops.templates stay in modules/nixos/services/sops.nix
    };
}
Why this is strictly better ‐ Eliminates ~160 lines of option re-declaration that drift on every upstream release. ‐ Keeps every hardening, sops, and DNS-gate strength. ‐ Wires three binary-supported capabilities (tracing, reload, webhook) that were dark. ‐ Future upstream option additions arrive automatically via imports.
