00Summary

SystemNix runs Paperless-ngx 3.1.x on evo-x2 with an unusually good non-AI foundation: PostgreSQL backend, Tika + Gotenberg consume path, barcode ASN + splitting, duplicate rejection, SSO-only login, declarative dashboards, nightly PG dumps. The native AI layer (v3 "Paperless AI") is correctly wired to the local FastFlowLM NPU LLM (qwen3.6-moe:35b-a3b) and the llama-rag GPU embeddings instance (bge-m3) — on paper a textbook fully-local setup.

In practice, the audit found the AI layer is mostly idle: LLM suggestions run per-document and manual-only (observed flm traffic from paperless-ai: zero), the RAG/semantic layer is dark (llama-rag config-disabled since the 2026-09-18 llama.cpp regression, so the embedding endpoint, the sqlite-vec index, chat grounding, and semantic search never went live), the automation lever that makes AI metadata automatic — the "Apply AI suggestions" workflow action shipped in 3.1.0 — is not wired anywhere, structured data extraction (custom fields) is not a native capability at all and has no local substitute deployed, and the bge-reranker instance on :8849 is served, monitored, and smoke-checked with zero consumers because upstream paperless has no rerank support.

The bottom line The single highest-leverage move is not adding anything new — it is finishing what is wired: (1) re-enable llama-rag via the already-shipped soak harness so RAG, chat, and semantic search go live, (2) wire an "Apply AI suggestions" workflow so every consumed document gets LLM title/tags automatically, and (3) deploy paperless-gpt as a small NixOS module to get the one capability paperless will never have natively — structured custom-field extraction from statements and receipts, plus local vision OCR via the already-served Qwen3-VL model.

01Capability assessment

Feature-by-feature, ordered by impact. "Native" = capability of paperless-ngx v3.2.1 upstream; grading compares deployed 3.1.x behavior against that surface.

Missed opportunity · Highest impact

"Apply AI suggestions" workflow never wired — every suggestion is a manual click, and observed AI traffic is zero

modules/nixos/services/paperless.nix:490-499 (AI env wired, no workflow anywhere) · docs/services/fastflowlm.md:19 ("paperless-ai wired but zero observed traffic")

Native v3 can suggest title, tags, correspondent, document type, storage path, and created date per document (opt-in "Suggest" button), and since 3.1.0 (#13639) the same suggestions can be applied automatically in bulk via the Apply AI suggestions workflow action — triggered on consumption finish, scoped by filters, with create-missing and overwrite options. SystemNix wires the LLM but has zero workflows, so the "AI to the max" automation that makes metadata free never engages: documents land raw and the model sits idle (zero observed traffic, Aug 18–21 baseline).

Recommendation Add a Consumption-finished workflow: filter = all non-empty docs (or a pilot tag first), action = Apply AI suggestions with fields title + tags + correspondent, "create missing" ON for tags, "overwrite existing" ON for title only. Documented caveats: empty-text docs are skipped (3.2.0 hardens this), storage paths are never auto-created, each matching doc = one LLM query (scope the filter; the NPU socket-activation + 480 s timeout already absorb cold loads). Provision it declaratively via the DRF API using the paperless-dashboard-provision pattern so it survives DB restores and lands in the VM test.
Missed opportunity · High impact

The entire RAG layer is dark: embeddings endpoint dead → no sqlite-vec index → no semantic search, no grounded chat

modules/nixos/services/llama-rag.nix (config-disabled since 2026-09-18) · paperless.nix:506-509 points PAPERLESS_AI_LLM_EMBEDDING_* at the dead :8848 · docs/todo/ai-stack.md:22 (soak harness shipped, execution owner-gated)

Native v3's semantic index (sqlite-vec vector store, document_llmindex CLI, daily PAPERLESS_LLM_INDEX_TASK_CRON) powers: AI chat with source-document links (single-doc AND corpus-wide from the toolbar), similarity-grounded suggestions, and semantic search. All of it silently no-ops without an embedding backend. The deployment chose the RIGHT backend (GPU bge-m3 via llama-server, OpenAI-compatible) — it is simply down, gated on the llama.cpp mid-load spin regression. The 2026-09-18 re-enable attempt also proved the config ships correctly; only the underlying runtime gate remains.

Recommendation Execute the already-shipped soak gate: sudo ./scripts/llama-rag-soak.sh --server <candidate> --model /data/ai/models/gguf/bge-m3.gguf --minutes 10 (systemd-run sandbox mirroring the deployed units; a PASS verdict is the re-enable gate per docs/todo/ai-stack.md). Then: re-enable module → document_llmindex rebuild → verify end-to-end (the open [watch] item "Verify Paperless AI actually USES the llama-rag embeddings"): chat answers cite source docs, index task green at 02:10, flm/llama traffic observable in SigNoz. Fallback while gated: the native huggingface embedding backend runs fully in-process (CPU, default all-MiniLM-L6-v2; bge-m3 selectable) — but decide ONCE, because switching embedding model later forces a full index rebuild.
Missed opportunity · High impact (the "smart extraction" ask)

Structured data extraction (custom fields) is not native — and no local substitute is deployed

Upstream docs (usage/advanced_usage/configuration + wiki, checked 2026-10-02): custom fields are NOT an AI suggestion target in any v3 release · no extraction sidecar in modules/nixos/services/

The core request — "smart document data extraction" (IBAN, amount, statement period from Polish bank statements; totals and merchants from receipts) — maps to paperless custom fields, which native AI does not populate: the suggestion surface stops at title/tags/correspondent/type/path/ date. The ecosystem answer is icereed/paperless-gpt (active Go project, ~2.7k stars): automatic custom-field generation with editable custom_field_prompt.tmpl, write modes Append/Update/Replace, tag-driven auto-processing (paperless-gpt-auto), and any OpenAI-compatible backend — i.e., it rides FastFlowLM as-is. clusterzx/paperless-ai was evaluated and rejected (unmaintained; author cites the native integration as superseding it).

Recommendation Package paperless-gpt as a NixOS module (pkgs/ buildGoModule from a pinned flake input, the house pattern): bind loopback only (it has NO built-in auth — visionreviewd precedent: no vHost, unit-state monitoring only), PAPERLESS_API_TOKEN via sops (runtime-mint like bank-sync-paperless-token, never pasted), OPENAI_BASE_URL=http://127.0.0.1:52625/v1. Define custom fields for statements (IBAN, amount, period, account) and receipts (merchant, total); start in Append mode (only fills missing fields — cannot clobber) with a dedicated auto tag + retries. Define fields declaratively via the DRF API in the same provisioning oneshot.
Missed opportunity · Medium-high impact

Local vision OCR is one wire away: llama-vlm already serves Qwen3-VL-8B, but nothing consumes it and the model has never had a verified inference

modules/nixos/services/llama-vlm.nix (live since system-796, 2026-09-22) · docs/todo/ai-stack.md:24 ("verify a real inference through each socket … before relying on them") · native remote OCR = Azure-only (cloud)

Upstream's "remote OCR" is Azure Document Intelligence only — a paid cloud dependency on the most sensitive documents in the archive; correctly not adopted. The local alternative already runs: paperless-gpt does LLM-enhanced OCR through VISION_LLM_PROVIDER=openai against any OpenAI-compatible vision endpoint, and llama-vlm's captioner (Qwen3-VL-8B Q8_0 + mmproj, :8128) is exactly that. Two gates: the llama-vlm instances have never been soak-verified (queued [watch] item), and they are CPU-inference — fine for occasional bad scans, not bulk retro-OCR; the GPU llama.cpp path stays blocked by the same spin regression as llama-rag.

Recommendation Sequence: (1) run the llama-vlm live verification item (real inference + cold-load timing through :8128/:8127), (2) evaluate captioner-vs-stock: the NSFWCaption-v3 fine-tune may degrade document OCR — llama-vlm's mapAttrs' design makes a third instance (stock Qwen3-VL GGUF) a config row, (3) point paperless-gpt's VISION_LLM_* at it, tag-gated (paperless-gpt-ocr-auto + retries) so only scans the tesseract layer fails on pay the CPU cost.
Partially used · Medium impact

Suggestion layer left at defaults: output language unset, DB-over-env precedence unverified, no post-wiring traffic assertion

paperless.nix:490-514 (no PAPERLESS_AI_LLM_OUTPUT_LANGUAGE) · paperless.md "Known traps": "UI-saved values override env" · docs/todo/services.md:26 [watch] (embeddings end-to-end verify)

Three small gaps compound: PAPERLESS_AI_LLM_OUTPUT_LANGUAGE (3.0.4+) is unset so suggestion language follows the UI account (the archive is German/English/Polish — an explicit value makes tag/correspondent suggestions consistent); the known app_config.x or settings.X precedence trap means a single UI save in Application Configuration would silently override the env wiring (never audited); and after wiring the workflow, nobody asserted WHICH entity served the traffic — the house rule from the glm-5.3-flash incident applies verbatim.

Recommendation Set PAPERLESS_AI_LLM_OUTPUT_LANGUAGE explicitly; probe paperless-manage shell for app_config AI rows once (a five-minute check that converts the trap from "known" to "ruled out"); after the workflow lands, verify flm's journal/SigNoz traffic comes from paperless-web/celery, not another consumer.
Split-brain wiring · Medium impact

bge-reranker-v2-m3 on :8849 is served, monitored, and smoke-checked — with zero consumers, because upstream has no rerank support

modules/nixos/services/llama-rag.nix (reranker instance + Gatus + smoke) · paperless.nix:512-514 ("No PAPERLESS_AI_LLM_RERANKER_* exists … zero rerank support upstream — do not attempt") · docs/todo/ai-stack.md:19 (decision queued, source-verified)

The reranker is a research artifact that outlived its hypothesis: paperless retrieves by plain vector KNN against sqlite-vec (no rerank anywhere upstream, Sourcegraph-verified), paperless-gpt doesn't rerank either, and a query-time proxy sidecar is not semantically valid. Every deploy carries the instance, its health checks, its smoke assertions, and its wedge surface for nothing. This is already a queued [decision] — this audit adds the missing input: no consumer exists in the entire candidate ecosystem today.

Recommendation Resolve the decision as: drop the :8849 leg at re-enable (instance + Gatus + smoke rows), keep the bge-m3 embeddings leg. Revisit only if a reranker consumer lands (e.g., a future custom RAG tool over the paperless corpus) — the module resurrects from git history in minutes. Keeping a monitored-dead hardware path contradicts the "no phantom greens" doctrine.
Fully leveraged · consciously excluded

What was evaluated and correctly rejected (keep it that way)

ecosystem research, 2026-10-02

clusterzx/paperless-ai: unmaintained (author publicly unsure the rewrite will finish, citing the native integration) — its tagging/RAG features are now native; adopting it would add a Docker sidecar that duplicates v3.0. DO NOT adopt. Azure remote OCR (PAPERLESS_REMOTE_OCR_*): sends documents to Microsoft cloud; the whole stack here exists to keep documents local; llama-vlm covers the bad-scan case offline. DO NOT enable. The classic ML classifier + native AI coexist by design — never "replace" the classifier with LLM suggestions; they answer different latency/cost budgets.

04Target architecture

Where the pipeline lands if items 1, 2, 6, and 7 execute. Every box is local (NPU/GPU/CPU on evo-x2); no new hardware, no cloud.

Ingest → OCR (tesseract) ⇢ vision OCR (paperless-gpt → Qwen3-VL, tag-gated) → classifier (auto-match ML) → AI suggestions (flm NPU, workflow-driven) → custom-field extraction (paperless-gpt) → bge-m3 index (GPU) → chat + semantic search

services.paperless-gpt = {
  enable = true;
  bind = "127.0.0.1";                // no auth upstream → loopback only
  paperless.url = "http://127.0.0.1:${toString ports.paperless}";
  paperless.tokenFile = "/run/secrets/rendered/paperless-gpt-token";
  llm.baseUrl = "http://127.0.0.1:52625/v1";   // FastFlowLM NPU
  vision.baseUrl = "http://127.0.0.1:8128/v1"; // llama-vlm captioner
  customFields = [ "iban" "amount" "period" ];
};

services.paperless-provision.workflows = [ {
  name = "AI metadata on consume";
  trigger = "consumption-finished";
  filter = { hasContent = true; };        // 3.2.0 also skips empties server-side
  action = { type = "apply-ai-suggestions";
             fields = [ "title" "tags" "correspondent" ];
             createMissingTags = true; overwriteTitle = true; };
} ];
Sequencing constraint (do not reorder) The workflow (item 2) works today but floods flm with cold-load cycles until the model warms; run it AFTER item 1 so the daily index task and chat share the warm endpoints, and AFTER the 3.2.x bump so empty-content docs skip server-side. paperless-gpt (item 6) is independent — it can land in any window.

05Conclusion

SystemNix's Paperless AI posture is "wired but not alive": a correctly-architected fully-local stack (NPU LLM, GPU embeddings, CPU vision) where the semantic layer is down behind a known runtime gate, the automation that makes LLM metadata free is unwired, the one capability native paperless will never ship (structured custom fields) has an active, fit-for-purpose ecosystem answer, and a reranker serves an API that does not exist. None of the gaps require new infrastructure — they require finishing gates that are already built and adopting one small sidecar. Items 1+2 alone move the adoption score from 42 to roughly 70; adding paperless-gpt closes the extraction gap that motivated this audit.
