# Projects Management Automation (PMA) — Agent Notes

> Module: `modules/nixos/services/projects-management-automation.nix`. Bullets migrated verbatim from AGENTS.md on 2026-10-01 (restructure). Full crash narrative: `docs/crash-analysis-2026-08-09.md`.

## Gotchas

- **PMA commit blackout (2026-08-22..09-02: 11 days, ~3,800 failed commits — fixed)** — every auto-commit failed on `429 rate_limit_error (2056)` while service liveness stayed GREEN the whole time. Four stacked causes: (1) minimax's Token Plan exhausted (billing state — the same dead key class as the crush minimax disable); (2) the daemon's go-commit flake input was pinned at `7321133`, which PREDATES `22f0e4c` (v0.8.0) where `DefaultChainFromEnv` learned `OPENAI_BASE_URL` — the SystemNix env vars sat in the daemon's environment pointing at FastFlowLM while the BUILT binary ignored them and sent OpenAI requests to api.openai.com with key `local` (eternal 401); (3) NO fallback — go-commit fails the whole commit when message generation fails (its retry middleware exists but is never wired in), and PMA's flat 5-min/project cooldown retried every dirty project for 11 days straight; (4) NOTHING monitored commit OUTCOMES. Fixes: PMA input → `22f0e4c` (the flake-lock pin can LAG the go.mod requirement — the prepared-source replace wins at build time; always check `jq '.nodes.go-commit.locked.rev'`), committer heuristic fallback on `errorfamily.Code(err)=="commit.generate"` (generation runs BEFORE staging → side-effect-free retry with `chore: auto-commit N changed file(s) (heuristic) on <branch>`, `Result.Fallback` + WARN journal line `committed via heuristic fallback`), escalating failure cooldown (5m doubling → 4h cap, resets on success), `MINIMAX_API_KEY` dropped from `pma-env` (empty template kept — never re-add an external provider key without a fallback plan), and `system_pma_commit_{scrape_errors,failures_1h,failures_over_threshold,heuristic_fallbacks_24h,fallbacks_over_threshold}` textfile metrics + the "PMA Commit Health" Gatus check (failures ≥3/h pages = blackout class; fallbacks ≥20/24h = LLM path dead while commits keep landing). **flm crash-trigger composite (2026-10-23)**: `system_pma_generate_timeouts_24h` (journal `commit.generate` deadline-exceeded lines — with OPENAI_TIMEOUT=10m wired, ANY occurrence means a consumer carries a wrong budget), `system_flm_coredumps_24h` (`code=dumped` on fastflowlm, the SIGABRT/SEGV class), and `system_flm_crash_trigger_pair_24h` (1 when BOTH in the same 24h — the 2026-10-07 crash-trigger signature, asserted 0 by the same Gatus check; fail-closed anchored pattern; regression-tested by `checks.flm-crash-trigger-pair`). First FastFlowLM-bound commits after a cold idle may ride the fallback once (30s HTTP timeout vs 2-5min cold load) — **that "self-heals" claim was WRONG (2026-10-07)**: the 30s disconnect fires while flm is mid-cold-load and the client-disconnect cancel path crashes flm's v1.0.2 heap (SIGABRT `corrupted double-linked list`, live 12:23:12 with a go-commit commit-message request in the flm echo). Durable fix: go-commit `DefaultChainFromEnv` now honors `OPENAI_TIMEOUT` (positive Go duration; malformed/non-positive fail loud; implemented 2026-10-07 in the go-commit local tree, pending push + PMA re-vendor) and SystemNix wires `OPENAI_TIMEOUT=10m` in the PMA module's extraEnvironment (covers the flm socket bridge's 480s deadline with margin); sustained fallbacks alert instead

- **PMA LLM-commit REGRESSION RECURRENCE (2026-09-07, fixed same day — the blackout's cause #2 came back through lock churn)** — PMA commit `6d4cb619` ("chore: auto-commit 313 changed file(s) (heuristic)") flipped PMA's own flake.lock go-commit pin BACK from `22f0e4c` to `7321133`, silently un-applying the 2026-09-02 fix: the deployed daemon ignored `OPENAI_BASE_URL`, sent every request to api.openai.com with key `local`, and 401-fell-back on 100% of commits. Diagnostic signatures that separate the failure classes: INSTANT fallbacks (`duration=170-900ms` = an HTTPS RTT to api.openai.com, ZERO connections to :52625) = env-chain dead / stale vendored rev; `duration=30s` fallbacks = real HTTP attempts timing out against flm (cold load or the v1.0.2 crash-loop window). Diagnostic chain that pinned it in ~30 min: (1) `go version -m <deployed-binary>` shows the go.mod REQUIREMENT (`v0.8.0`) but the `=> ./_local_deps/go-commit (devel)` REPLACE wins at build time — the requirement version LIES about the vendored code; (2) the vendored rev is decided by PMA's OWN flake.lock, not SystemNix's — SystemNix's root `go-commit` node was healthy at `9dfbf1e` while PMA's lock subtree carried the stale pin (consumer-subtree-drift class); (3) the regression mechanism: the PMA lock node's `original.url` had a hard `?rev=7321133` baked in from an old flake.nix edit, so any lock re-run re-pinned BACKWARD (same class as the rev-pin silent-no-op trap). Fixes deployed: PMA `1c144c8d` (re-lock to go-commit `9dfbf1e`, which also carries the SSRF `withTrustedBaseURL` bypass REQUIRED for loopback `OPENAI_BASE_URL` — post-v0.8.0 go-commit rejects 127.0.0.1 without it, the next trap in that direction) + PMA `9bbc7dfb` (vendorHash refresh — go-commit 9dfbf1e's dep refresh invalidates the FOD hash even with zero PMA go.mod changes). **Rule: after ANY projects-management-automation input bump, check the PMA lock's go-commit rev ≥ `22f0e4c` AND that `DefaultChainFromEnv` still reads `OPENAI_BASE_URL` in the vendored tree before deploying** (docs/todo/upstream.md carries the upstream CI guard). Verify with `journalctl -u projects-management-automation | grep "committed changes"` — LLM commits log `duration=10-20s` with NO `heuristic fallback` tag
- **Pre-commit build gate ACTIVATED (2026-10-31, `requireCleanBuild = true; requireCleanVet = true;`)** — upstream gate (PMA TODO J3, hold-not-discard semantics): a Go tree that does not `go build`/`go vet` clean is HELD, not snapshotted — the commit lands on the next daemon event after the tree is fixed, so a red intermediate state can never become HEAD. Motivated by emeet-pixyd's red-at-HEAD auto-commits (TODO #176 there). The gate runs `GOWORK=off` with a writable GOCACHE under the unit HOME. **Toolchain trap:** the module puts `pkgs.go` (1.26.x at this lock) on the gate's PATH — any repo whose go.mod needs a newer toolchain (emeet-pixyd ≥ 1.27.1) would fail the gate on the TOOLCHAIN, not the tree, freezing that repo's auto-commits as held WARN loops; the module sets `systemd.services.projects-management-automation.path = lib.mkBefore [ pkgs.go_1_27 ]` so the gate always measures the tree. Config is NOT hot-reloaded (`/etc/projects-management-automation/service.yaml` is written by the activation) — the gate is INERT until the next NixOS switch. Held commits surface as `journalctl -u projects-management-automation` WARN lines with the failing repo + build/vet error. **gcc gate hole (found + fixed 2026-11-03):** the unit PATH carried no C compiler, so the gate false-held every CGO-containing tree (`cgo: C compiler "gcc" not found`) — 1148 holds in 4h across ~110 repos (first hit 2026-11-02 14:34); fix = `pkgs.gcc` beside `go_1_27` in the module's `path` mkBefore (dev-shell parity), inert until the next switch like all gate config.
- **2026-11-03 fleet-wide commit gridlock (RESOLVED LIVE 2026-11-04, gen-977)** — the daemon stayed `active/running` while commits fell minutes-to-hours behind across 260+ repos (the mass staged-uncommitted state in that evening's `mr status`). Three stacked causes: (1) **flm SIGABRT crash-loop** — `double free or corruption (!prev)` at 22:10:47, restart counter 4, ESCALATING to `status=11/SEGV` with restart counter 10 by 23:16 (demand-driven: each client attempt after the cache-clear path double-frees the heap): the KNOWN go-commit-30s-timeout < flm-cold-load disconnect class; every message generation burned a 30s `context deadline exceeded` then fell back → `heuristic fallback ratio crossed alert threshold ratio=1` (22:10:11). (2) **gate gcc hole** — see the build-gate bullet above. (3) **batch-queue saturation** — 2 committer workers at 30s LLM timeouts + 20-200s gate builds cannot drain a 260-repo event flood; signature is the `batch queue full, will retry on next stale sweep` WARN loop (215/4h) plus `deletion guard` (38) and `conflicts detected` (11) deferrals. Separate debris class the same evening: the daemon's go.work backup-restore cycle left STAGED `go.work → go.work.pdg-bak` renames in ~12 repos and rode inside project-discovery-sdk's release commit `f95a37d` (repaired `2fba043`/`5e4b24a`) — cleanup + upstream fix row in `docs/todo/upstream.md`. **Resolution (full narrative: docs/status/2026-11-03_23-18_pma-commit-daemon-gridlock-diagnosis-gcc-gate-fix.md §12):** flm held STOPPED by owner order through the incident — fallbacks went 30s→0.4s on the connection-refused fast path, so stopping the provider RAISED commit throughput; gen-977 shipped the gcc PATH fix AND the PMA@4053b2ed rebuild whose vendored go-commit `4081b55` activates `OPENAI_TIMEOUT=10m` (the env var had sat inert since 2026-10-07 behind a stale deployed binary — row 43's real blocker was never the push, both legs had landed upstream by 21:13 the same evening). Post-switch verification: 0 gcc holds in the first 10 minutes, commits landing at 65-265ms, flm restart-safe whenever wanted (crash trigger structurally fixed). Diagnostic of record: `duration=30s` fallbacks = live HTTP timeouts against a hung/cold flm; `duration<1s` fallbacks = provider connection-refused (stopped or dead).
- **PMA page-cache death-loop containment** — PMA reads 260+ git repos during discovery, charging ~16 GB of page cache to its cgroup. Without `MemoryHigh`, reclaim loops at 91% CPU (`memory.events max` climbing, `oom_kill = 0` — page cache is reclaimable) until system-wide PSI freezes the kernel. Contained by: `MemoryHigh=12G`, `MemoryMax=16G`, `CPUQuota=200%`, `MemorySwapMax=0`, `PMA_COMMITTER_WORKERS=2`, `PMA_DISCOVERY_WORKERS=2`, `ManagedOOMPreference=omit`. **Ceiling retuned 2026-08-14:** the 6G/8G ceiling from the 2026-08-09 analysis fell below the scan's grown working set — every restart pinned memory at ~6.3G in permanent direct reclaim and the discovery daemon goroutine starved (unix socket accepted connections, never answered; 3 hangs in one day, incl. a 21h one that 503'd Overview the whole time). 12G high restores scan headroom (pre-incident scans completed under a 16G max); 16G max keeps the freeze-proof hard bound. **`pma-daemon-watchdog`** (every 5 min) probes the daemon socket liveness and restarts PMA after 2 failed probes 30s apart — the hang class is "hung but active", invisible to systemd. Note: Overview has `partOf` PMA, so every PMA restart bounces Overview (it re-discovers on start). The `system-health` collector emits `system_service_memory_events_{max,high}` metrics with a Gatus "Memory Events Thrash" alert (collector runs as root with `ProtectSystem=full` — `/sys/fs/cgroup` unaffected).
