# journal (accounting kernel CLI)

**Deployed as journal-serve + protected vHost (owner g-2 answer, 2026-10-26).** `journal` is an interactive CLI plus the Hauptbuch web dashboard (`journal serve`, unit live since 2026-10-26): `services.journal-serve` binds **127.0.0.1:8484 only** (upstream refuses non-loopback until passkey auth — their T16), fronted by the registry vHost **journal.home.lan** (`vHost.layer = "protected"` — oauth2-proxy forward-auth for external, LAN bypass; the g-2 answer also fixes the T16 WebAuthn RP ID). Double-entry bookkeeping kernel: chart of accounts, immutable journal, bank reconciliation against invoices, period close with gates, VAT determination. Upstream: `github:LarsArtmann/journal` (**PRIVATE** — CI deploy key `NIX_DEPLOY_KEY_JOURNAL`, read-only key id 166885168, wired in all four workflows' auth blocks). Consumes bank-sync's `transactions.v1` exports; feeds `postings.v1` to future reporting.

## Ops

- **Books home: `~/books/` (evo-x2, live 2026-10-23).** `journal.yaml` (the two real entities + all 7 in-scope Wise balance mappings + matcher settings + `export.account_map: skr04-technologies.yaml`), `journal.db` (initialized: both charts imported — technologies 18 accounts, holding 9 with the expected VAT role-gap warnings), `chart-*.yaml`, `skr04-technologies.yaml`, `entries/`, `exports/`, `out/`, `backups/`. Still USER data: nothing under `/var/lib`, no backup-coordination row. The config's `database: journal.db` is CWD-relative (`config.AbsoluteDatabase` → `filepath.Abs`) — always run the CLI with CWD = `~/books` (the month-end runbook's `$J` alias assumes exactly that).
    - **Web dashboard (Hauptbuch, tier 0, unit live 2026-10-26)**: the `journal-serve` unit serves it at **http://127.0.0.1:8484** (status / exceptions+waive / reconcile); from the LAN/VPN open **https://journal.home.lan** (oauth2-proxy protected; LAN bypass per Layer 2). **Loopback-ONLY bind by upstream design** — the CLI refuses non-loopback binds until passkey auth (upstream T16) lands, and the proxy must never be pointed anywhere else. From the MacBook without LAN DNS: `ssh -L 8484:127.0.0.1:8484 evo-x2` still works against the unit. Port 8484 = `lib/ports.nix` `journalServe`. The g-2 answer (shared reverse proxy) also fixes the T16 WebAuthn RP ID: `journal.home.lan`.
    - **ALL-ZERO dashboard = empty books, not a bug (live-verified 2026-11-10)**: the dashboard renders kernel truth; until the first month-end import runs (`bank-sync export` → `import bank-sync` → `reconcile`), entries/postings/facts are legitimately 0 (books initialized 2026-10-23 hold only the 2 entity registrations — the event journal's only 2 rows). Cross-check kernel truth with `journal status` from `~/books` before suspecting the serve unit. **The pipeline is proven end-to-end (2026-11-10, agent-executed via `sudo -u bank-sync` — works under the current crush unblock rc, verify per-session) but imports 0 facts because bank-sync holds NO in-scope transactions**: all 7 mapped Wise balances have never had a statement synced (sync windows were fresh-start-reset to 2026-11-09; `bank_sync_sca_approval_pending 1` gates statement syncs — owner flow in docs/todo/services.md "re-arm Wise SCA" row), and bank-sync's only Wise data (116 tx, 2021→2025-04) sits on Helpless.AI LLC balances that `journal.yaml` deliberately leaves unmapped (facts reject loudly). Export mechanics that cost a probe each: `--schema v1` REQUIRES `--format json` (`[Rejection:export.schema_format]` otherwise), export is PER-BALANCE (`--balance`), the live DB is `data.db` (NOT `bank-sync.db` — that name is the quarantined side-db-trap artifact): `sudo -u bank-sync bank-sync export --schema v1 --format json --provider wise --balance <id> --database-path /mnt/pool/services/bank-sync/data.db --output - > ~/books/exports/transactions-<YYYY-MM>-<id>.json`. A 0-fact import is still useful: it lands per-balance COVERAGE records, upgrading the dashboard's close-gate verdicts from "no coverage record" to explicit "statements never synced" + last-sync (all 7 done 2026-11-10).
- **Real-time sync is ON (2026-11-13, ADR-0009)**: bank-sync publishes each completed sync cycle's `transactions.v1` envelopes onto NATS JetStream, and `journal-mesh` ingests them immediately (no timer, no staging files, no shell glue). The 15-min file pipeline remains available as break-glass (`services.journal-import.enable = true`) and replays cleanly because both paths are idempotent. What automation covers: bank-fact import, tier-1/2 auto-book via reconcile, coverage-record self-updates. What stays human: tier-3 confirm/reject/waive + `book`/`waive` decisions (Exceptions queue). Until Wise SCA is re-approved (services.md [blocked:user] row) in-scope facts stay zero — after approval + bank-sync's window-widening backfill the next cycle publishes automatically. Inspect with `journalctl -u journal-mesh -u nats -n 100`; break-glass publish of any envelope: `journal mesh publish --file <envelope.json>`.
- **Nightly backup is deploy-owned** (`journal-backup.timer`, see table). Pre-close and ad-hoc backups stay manual: `journal backup --out backups/journal-<name>.db --verify`. Health: `journal doctor` (SQLite integrity, event journal, read models) + `journal status` (queue depths, AR residual, closed periods). The month-end rhythm lives upstream: `~/projects/journal/docs/runbooks/month-end.md` (bank-sync exports → import → reconcile → close → DATEV).
- **vendorHash drift class**: NON-FOLLOWER — root nixpkgs bumps CANNOT re-hash journal's FOD (its own nixpkgs pin governs the go toolchain). It re-stales only when journal's own lock moves; upstream pushes genuinely fix it (crm class), so re-lock + probe, never a consumer-side shim: `nix build github:LarsArtmann/journal/<rev>#default` first (probe-before-lock), then `nix flake lock --update-input journal`.
