# immich (photo/video management)

**Service:** nixpkgs `services.immich` — `modules/nixos/services/immich.nix` (wrapper: pool storage, OIDC, hardware transcode, backup). Port 2283 (`lib/ports.nix`), loopback. URL: `immich.<domain>` — **Layer 2 protected** vHost via the registry, combined with **native OIDC in-app** (password login disabled): a deliberate hybrid, see below. DNS `immich` in `platforms/common/dns-local.nix`.

Media lives on the HDD pool (`/mnt/pool/services/immich`) — immich-server, immich-machine-learning, and immich-db-backup all carry `RequiresMountsFor` on it: a detached DAS fails the units loudly instead of writing to a root-fs shadow (bank-sync precedent).

## What it serves

| Route                           | Auth                                 | What                                                        |
| ------------------------------- | ------------------------------------ | ----------------------------------------------------------- |
| `/`                             | forward-auth (external) / open (LAN) | Web UI                                                      |
| `/api/*`                        | immich session (OIDC)                | App + mobile API                                            |
| `/auth/login`, `/user-settings` | immich session (OIDC)                | OAuth callback redirect targets (registered in Pocket ID)   |
| `app.immich:///oauth-callback`  | immich session (OIDC)                | Mobile app callback scheme (LAN path — forward-auth exempt) |
| `/api/system_config`            | 401 unauthenticated                  | Gatus probe target — 401 PROVES API up + auth enforced      |

## Ops

- **Auth is a LAYER HYBRID** — in-app: native OIDC via Pocket ID (`oauth.enabled`, issuer `https://auth.<domain>`, clientId `immich`, secret via upstream `clientSecret._secret` from the provisioner path, `autoLaunch` + `autoRegister`, button "Login with Pocket ID"; `passwordLogin.enabled = false` — NO local password fallback). Routing: the registry renders the **protected** vHost — external browsers pass oauth2-proxy forward-auth first, then immich's auto-launch redirect reuses the live `auth.<domain>` session (no second prompt in practice); LAN traffic and the mobile app (a native OIDC flow that cannot carry forward-auth cookies) bypass forward-auth entirely. This is the ONE deliberate exception to "native OIDC ⇒ plain reverse_proxy" — do not "fix" either side without the other.
- **OIDC client registration** — via the registry entry's `oidc` field (fans into `pocket-id-config.provision.extraOidcClients`): callbacks `…/auth/login`, `…/user-settings`, `app.immich:///oauth-callback`; logout callback `https://immich.<domain>`; PKCE enabled. Secret lands in `/var/lib/pocket-id/client-secrets/immich`.
- **Transcoding** — VAAPI on the iGPU: `accelerationDevices = ["/dev/dri/renderD128"]`, `LIBVA_DRIVER_NAME=radeonsi`, user in `video` + `render` groups. ML enabled (face detection / CLIP): MemoryMax 4G, CPUQuota 300%, `HOME=/var/lib/immich`.
- **Redis dual transport** — the app talks to redis over the (faster) unix socket, but `immich.redis.port` opens a loopback-only TCP listener too, because the Gatus `tcp://127.0.0.1:6379` health check cannot reach a socket-only redis.
- **Job queues are BullMQ-on-Redis — not pg_boss, not in-memory; the "frozen pendings" mode is a DRAINED queue, not a stuck one (diagnosed 2026-11-17, supersedes the 15:36 report's "in-memory queue loss" verdict)** — v3.3.6 keeps all job state in the immich redis under `immich_bull:<queue>:*` (faceDetection, ocr, duplicateDetection, thumbnailGeneration, metadataExtraction, smartSearch, …; per-job opts `removeOnComplete:true, removeOnFail:false, attempts:1`; queue state survives server restarts and immich upgrades — keys from the 3.3.3 era were intact after the event). Per-asset ML jobs are enqueued by the import pipeline; the catch-all is the per-queue **QueueAll sweep**: admin Jobs START → `queue.service.start()` → e.g. `AssetDetectFacesQueueAll {force}` → `asset-job.repository` streams NULL-job-status assets (force=false adds `assetsWithPreviews()` + `visibility != hidden` + not-deleted filters; force=true sweeps everything, reaching preview-less assets too). A server restart NEVER re-seeds — only a sweep or new imports feed the queues. Signature of the 2026-11-16 00:00 CET event: `asset_job_status` NULL counts frozen for days, ZERO ML-job error lines, zero jobs added to any ML queue, last event per queue `completed` → `drained` at 00:00:30-35 — the pending backlog was NEVER ENQUEUED (upstream gates: preview-less assets break the chain at thumbnail generation, so ML never fires for them), nothing was lost from a live queue. Remedy: the 30-second admin-UI START per ML queue (staging OWNER-STEPS.md); the force variant also reaches the preview-less population (which will then fail ML on the same broken files — that population's fix is deletion, a separate owner decision).
- **Queue/ML probe set (verified live 2026-11-17)** — psql as the shared-PG postgres user: pending counts + global max timestamps off `asset_job_status` (camelCase QUOTED columns `"facesRecognizedAt"`/`"ocrAt"`/`"duplicatesDetectedAt"`; the asset table is `asset` SINGULAR and `deviceId` no longer exists — discriminate import sources by `originalPath`/`libraryId`; `asset_job_status` rows can lag asset inserts, so JOIN-based counts read ~1 low on fresh imports). redis-cli on 127.0.0.1:6379 (no auth; the Gatus TCP listener serves probes too): `--scan --pattern 'immich_bull:*'`, `XREVRANGE immich_bull:<q>:events + - COUNT 2` (last events — epoch-ms stream ids date exactly; `drained` as the tail = queue ran empty, the definitive stuck-vs-empty discriminator), `GET immich_bull:<q>:id` (job-id counters — no movement = nothing enqueued), `ZRANGE immich_bull:<q>:failed` (permanent failures persist there). Journals: date-qualified `--since`/`--until` on `immich-server`/`immich-machine-learning` (midnight windows!), error histogram `rg -o 'Unable to run job handler \([A-Za-z]+\)' | sort | uniq -c`, `{"id":"…"}` in Microservices error lines = asset UUID (joinable). Noise baselines so probes are not over-read: the nightly 00:00 CET external-library scan re-queues thumbnail retries (a burst of `AssetGenerateThumbnails` "Input file contains unsupported image format" errors per broken file is EXPECTED while such files exist), and ML gunicorn workers SIGINT-recycle ~00:05 after midnight bursts — routine (Nov 10/14/16 pattern), never outage evidence by itself. Queue COMMANDS are admin-UI-only by design: `/api/jobs` 401s the takeout-import key and 403s the media-atlas key; no admin API key exists on box (an owner decision would change that).
- **PostgreSQL** — `database.enable = true` on the host's shared local PG, tuned for the immich workload (`shared_buffers 512MB`, `effective_cache_size 2GB`, …) — the settings apply to the shared cluster; keep that in mind when other services join it.
- **DB backup** — `immich-db-backup` daily 01:00 (`Persistent`): `pg_dump --clean --if-exists` as user immich → `<mediaLocation>/database-backup/immich-<ts>.sql`, 7d retention, mount-gated, registered in backup-coordination (maxAge 25h). The media tree itself is covered by the pool's btrbk snapshot set, not a dump.
- **SMTP notifications are DECLARATIVE (2026-11-15)** — `services.immich.settings.notifications.smtp` in immich.nix, relay-gated: 127.0.0.1:25 (postfix null client, no auth), from `immich@larsartmann.cloud`, relayed to Resend on the nix-email-verified domain. Sender identity only — no immich@ mailbox exists on Stalwart, replies land nowhere.
- **Settings precedence: the config FILE replaces the DB** — `IMMICH_CONFIG_FILE` is set, so `services.immich.settings.*` overrides everything; admin-UI config saves throw "Cannot update configuration while IMMICH_CONFIG_FILE is in use" and UI-era DB values are ignored. Any admin surface the host wants (user delete delay, trash days, image preview progressive, SMTP, …) must be declared in the Nix settings block; defaults fill the rest. Settings changes deploy via the regenerated pre-start script (jq render of `/run/immich/config.json`) which restarts the unit on switch.
- **API-key lifecycle — Nix-owned, never pasted** — every machine consumer's key is DECLARED in Nix as `services.immich.apiKeys.<name>` (`permissions` = Immich `Permission` enum strings, `keyFile`, `owner`/`group`, `url`, `restartUnits`) and minted by the root converger `immich-api-key-provision` (`lib/immich-api-key-provision.nix`). Because auth is OIDC-only there is no API-level bootstrap: the converger inserts straight into `api_key` over peer-auth postgres (`runuser -u postgres`, `key` = raw sha256 of a 32-byte random token as `bytea`, `userId` = the admin row) and renders the token 0400 — env format (`IMMICH_URL` + `IMMICH_API_KEY`) when `url` is set, bare token otherwise. Convergence: file + row consistent ⇒ no-op; file present but row gone (DB restore) ⇒ re-insert from the file plaintext; file absent ⇒ mint + insert + render + `try-restart` the declared `restartUnits`. **Rotation: `rm <keyFile>` + `sudo systemctl restart immich-api-key-provision`.** A UI-side revoke is resurrected by the re-insert path BY DESIGN — rotate, don't revoke. A daily timer (`Persistent`, 6h jitter) covers DB-restore healing and `scripts/deploy.sh`'s provisioner loop re-converges on every deploy. The converger fails loudly if `api_key.key` stops being `bytea` (Immich schema drift) — that guard is the reason the INSERT can be trusted. The unit's `StateDirectory=immich-api-keys` is what lets `ReadWritePaths=/var/lib/immich-api-keys` survive namespace setup (2026-11-14: without it every start died 226/NAMESPACE — the google-sync class; a custom `keyFile` outside that dir still needs its parent dir to pre-exist).
- **Consumer: `takeout-import` (2026-11-14)** — Google Takeout → Immich via immich-go (`scripts/takeout-ingest-photos.sh`), read from `/var/lib/immich-api-keys/takeout-import.env` (override `TAKEOUT_IMMICH_ENV`; `IMMICH_API_KEY` in the environment wins). Scope = immich-go's documented set MINUS `asset.delete`: an archive import must never carry delete authority. Nothing about the key lives in the staging directory.
- **Gatus** — "Immich" (`/api/system-config` expecting **401**, 1s budget) in the Media group + redis TCP check; `monitored = true` in the registry (system-health unit watch).
- **Incoming: Drive images (2026-10-19, dormant)** — `services.drive-paperless` with `ingestImages = true` uploads Google-Drive-mirrored raster images via `POST /api/assets` (multipart `assetData` + ISO `fileCreatedAt`/`fileModifiedAt` + `filename`, `x-api-key` from the machine-minted key `services.immich.apiKeys.drive-paperless` — scope **asset.read + asset.upload**, env file `/var/lib/immich-api-keys/drive-paperless.env`; 2026-11-16: the `drive_paperless_immich_api_key` sops paste path and its placeholder scaffold are deleted, no human transports an Immich key anymore). v3 API notes (verified against the deployed 3.3.3 dist): no `deviceAssetId`/`deviceId` anymore — idempotence is the ingest journal + server-side checksum dedup (duplicates answer 200 `status=duplicate`). Rides the same google-sync OAuth go-live flip; runbook + sub-checklist: [google-sync.md](./google-sync.md). DiscordSync's `/lookup` cross-archive key left the sops world 2026-10-25 (direct-DB provisioner, consolidated onto the shared converger as `apiKeys.discordsync-lookup` 2026-11-16; runbook: discordsync.md "Key lifecycle").
