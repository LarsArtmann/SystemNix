## InboxClean (Gmail AI assistant, inbox.home.lan)

Event-sourced Gmail assistant (go-cqrs-lite + SQLite WAL + templ/HTMX dashboard). Upstream flake `github:LarsArtmann/InboxClean` exports `packages.default` (hermetic buildGoModule) + `nixosModules.default`; the SystemNix wrapper (`modules/nixos/services/inboxclean.nix`, discordsync pattern) layers only sops/port/hardening/GOMEMLIMIT. Port 8099 (`lib/ports.nix`), Caddy `protectedVHost "inbox"`, DNS `inbox` in `platforms/common/dns-local.nix`, Gatus liveness (`/health`) + functional (`/` renders HTML) checks, Homepage tile in Sync & Backup.

- **Hermetic build quirks (upstream flake)**: go.mod floor 1.26.6 > nixpkgs go → go.dev tarball override (drop when nixpkgs ≥ 1.26.6). `go.sum` is deliberately gitignored upstream (commit 47e62d6) → the package regenerates it via `preBuild = "go mod download all"` (bare `go mod download` misses graph edges like go-error-family/diagnose) and the FOD sets `GOSUMDB=off` because go-cqrs-lite tags 404 on sum.golang.org while still being served by the Go proxy. License is PROPRIETARY → `licenses.unfree`; local builds need `NIXPKGS_ALLOW_UNFREE=1 --impure` (evo-x2 config already allows unfree). `doCheck = false` — tests bind loopback listeners which the Nix sandbox forbids.
- **Secrets**: `platforms/nixos/secrets/inboxclean.yaml` holds `inboxclean_gmail_credentials` (raw Google OAuth client credentials.json, block scalar; owner `inboxclean`). The upstream module seeds `<dataDir>/credentials.json` on every start but copies `token.json` ONLY when absent (runtime oauth2 refreshes persist).
- **Multi-account (Gmail + Workspace)**: the module sets `extraAccounts = [{ name = "work"; credentialsFile = <same sops credentials>; }]` — one OAuth client, the Workspace mailbox shares the personal account's credentials.json; its token lands at `<dataDir>/token-work.json`. Event streams are namespaced `work:<messageID>` in the shared SQLite DB; the dashboard (`/inbox`, `/labels`) has account tabs, `/sync` shows a cursor card per account, and `/health` reports `services.gmail.<name>` per account.
- **OAuth runbook (one-time per Google account)**: `sudo -u inboxclean GMAIL_CREDENTIALS_FILE=/var/lib/inboxclean/credentials.json GMAIL_TOKEN_FILE=/var/lib/inboxclean/token.json DB_PATH=/var/lib/inboxclean/inboxclean.db inboxclean auth` on the evo-x2 desktop (opens browser; the CLI is on system PATH). For the Workspace account, run the same with `inboxclean auth --account work` and log in AS the Workspace identity (the CLI only loops accounts whose token file is missing) — the env MUST add `INBOXCLEAN_CONFIG="$(grep -oP 'INBOXCLEAN_CONFIG=\K\S+' /etc/systemd/system/inboxclean-web.service | head -1)"`: extra accounts are defined in the generated accounts TOML, and without it the CLI sees only the env-default main account and fails `no account matched --account "work"` (exit 75, hit 2026-08-29). If Google answers `access_denied`, add that Google user under "Test users" on the OAuth consent screen (Cloud Console) and retry. Verify with `curl -s http://127.0.0.1:8099/health | jq .services.gmail` — every account must say `connected`. Then flip `services.inboxclean.sync.enable = true` (default false until the token exists — without it every sync run fails exit 69 and would spam onFailure alerts).
- **`inboxclean auth` "already authenticated!" was a PHANTOM GREEN (fixed upstream 2026-09-30, InboxClean `1540a56`, deploy pending):** the CLI treated token-FILE PRESENCE as a working grant — main sat dead 26 days (2026-09-04 → 09-30: `invalid_grant`/`gmail.token_revoked` on every 30-min sync, cursor frozen at 5152620, OnFailure every tick) while repeated `inboxclean auth --account main` runs printed "✓ already authenticated!" WITHOUT ever re-consenting. auth now probes the stored grant with the same `VerifyAuth` primitive the web `/health` endpoint uses (that endpoint reported `services.gmail.main: "auth_expired"` the whole time — trust IT over the old CLI verdict): verified grants keep the fast path, revoked grants (`gmail.AuthRevoked`) fall through to a fresh consent (the flow truncates the dead token.json via `saveToken` O_TRUNC — no manual mv needed), transient verification failures (network/Google 5xx) fail the run loudly instead of guessing. Regression-tested in `cmd/inboxclean/auth_command_test.go` (5 cases incl. the mutation-proven dead-grant fall-through). PRE-DEPLOY unblock for a dead account (the deployed binary still carries the bug): `sudo mv /var/lib/inboxclean/token.json /var/lib/inboxclean/token.json.expired-$(date +%Y%m%d)` then run the auth command above — the missing file sends the OLD binary into the consent flow.
- **Testing-mode 7-day token expiry CONFIRMED LIVE (2026-09-04 incident)**: the InboxClean OAuth client sat in "Testing" publishing status, so Google expired BOTH refresh tokens exactly 7d after issuance — main (issued Aug 28 04:54) died Sep 04 between 07:34 (last good sync) and 08:04 (first `invalid_grant`), cursor frozen at 5152620 while work kept advancing; work (issued Aug 29 ~19:00) would have died Sep 05 evening. **CORRECTION (2026-09-12 live check): `work` is ALIVE 14 days past its recorded grant** (cursor advancing, `token-work.json` refreshing, zero `token_revoked` since Sep 04) — either it was silently re-consented, the production flip predated its grant, or testing-mode expiry is not a clean 7 days; unresolved. `main`'s on-schedule death is unaffected — the flip-then-re-consent fix order still stands. This is the google-sync lesson ("OAuth client MUST be In production") confirmed for InboxClean. **Fix order matters: switch the consent screen to "In production" FIRST, then re-auth both accounts** — tokens issued under Testing carry the 7-day bomb even after the flip. Re-auth = re-run the OAuth runbook commands above (the auth CLI overwrites the existing token files). Two monitoring lies to remember: `/health` reports `connected` from token PRESENCE, not refresh validity — main showed `connected` for 8+ h while every API call failed (phantom green; the real signal is `inboxclean-sync` exit 75 + OnFailure every 30 min), and the UI classifies `invalid_grant` as `transient`/"wait and try again" — it NEVER self-heals, only re-consent fixes it. Upstream status (2026-09-30): the health probe validates the refresh (`VerifyAuth` → `auth_expired`, live); the auth command's dead-grant detection (`1540a56`) AND the dashboard re-auth banner + `/health` `services.gmail_aggregate` word (`d23c48a`) are LANDED but UNPUSHED — deploy chain: push → `nix flake lock --update-input inboxclean` → deploy. **2026-10-04 addendum: the /health self-heal after a re-consent is BROKEN on deployed 01d2c5e** — the lazy reconnect matches the brand-prefixed id form (`"Account:main"`) against the prod closure's plain config names (`"main"`), fails Debug-silently, and the status stays `auth_expired` even with a live grant (hit during the 2026-10-04 main re-consent: corpus resumed indexing while /health stayed red); upstream fix `e9735c7` joined the unpushed deploy chain, interim remedy after ANY re-auth = `sudo systemctl restart inboxclean-web`. `gmail_aggregate` (`ok`/`degraded`/`not_configured`) is the machine-readable paging signal; HTTP stays 200 on grant death by design (grant health ≠ process liveness, bring-up must not look down) — per-account paging stays the open decision below.
- **Units**: `inboxclean-web.service` (dashboard, 512M/GOMEMLIMIT 384MiB) + `inboxclean-sync.service/.timer` (oneshot Gmail History-API sync, 1G/768MiB, 30min default once enabled). Both share `/var/lib/inboxclean/inboxclean.db` (WAL + busy_timeout handles concurrency).
- **Paperless attachment archiving (LIVE 2026-09-02)**: the upstream papersync integration uploads Gmail attachments (16-format allowlist) + opt-in `.eml` bodies to Paperless after every sync; a local SQLite ledger + Paperless checksum dedup make runs idempotent, and failures are warnings that never break the sync. Wiring: sops `inboxclean-paperless.yaml` `paperless_api_token` (provisioned via `paperless-manage drf_create_token admin`; NOTE sops edits run as your USER with the SOPS_AGE_KEY one-liner from the Sops + Age section, FROM the repo root — `.sops.yaml` discovery is CWD-based, and plain `sudo sops` FAILS because root carries no age identity, live-verified 2026-09-06) → `inboxclean-paperless-env` template (root-owned — systemd reads EnvironmentFile as PID 1; rotation restarts both units) + `PAPERLESS_URL=http://127.0.0.1:2892` / `PAPERLESS_TAGS=gmail` via `extraEnvironment`; `services.inboxclean.paperless.enable = true` (configuration.nix). **Keep the sops value and the flag in sync: PAPERLESS_URL without a token is a config Rejection at EVERY inboxclean process start (web + sync both crash — validate.go); a PLACEHOLDER token 401-warns per sync tick.** Monitoring: Gatus "InboxClean Paperless Archive Auth" (`Authorization: Token $PAPERLESS_TOKEN` — the only check that sees token death; the unauthenticated paperless login-page check cannot; green within 5 min of a deploy = token valid) + post-deploy smoke (401-unauth proves route + auth enforcement). Native Paperless mail rules stay reserved for a future scanner/forwarding mailbox (the Gmail archiving job rides InboxClean: OAuth, no app passwords, both accounts). Regression: `tests/test-inboxclean-paperless.nix` (minimal-nixosSystem eval — NOT evo-x2: the full config's assertions list carries the null-owner poison, so negative tests must use a bare eval).
- **Encrypted-statement decryption (2026-09-06, empty-vocabulary incident follow-up)**: Polish bank statements arrive as PASSWORD-PROTECTED PDFs; paperless archives them with EMPTY content (pdftotext exit 1, ocrmypdf refuses). Upstream papersync (InboxClean ≥ 2026-09-06) detects them (trailer `/Encrypt` heuristic), decrypts via `qpdf` when `PAPERLESS_DECRYPT_PASSWORD` is set (SystemNix: sops `inboxclean-decrypt.yaml` `paperless_decrypt_password`, PLACEHOLDER-inert by design — same line rides the `inboxclean-paperless-env` template), and otherwise uploads as-is with an `encrypted` tag so the gap is VISIBLE. `qpdf` rides the sync unit's systemd `path` (only when archiving is on). The ledger records the DECRYPTED checksum — the same statement via the second mailbox decrypts to identical bytes and dedups (belt: `PAPERLESS_CONSUMER_DELETE_DUPLICATES`). Go-live: sops-edit `platforms/nixos/secrets/inboxclean-decrypt.yaml` with the SOPS_AGE_KEY one-liner (Sops + Age section; plain `sudo sops` fails — root has no age identity) + paste the bank PDF password. Papersync tags are created with matching NONE (legacy AUTO tags self-heal via PATCH on next EnsureTag — the 2026-09-03 `gmail` AUTO tag was the classifier incident's trigger); correspondents deliberately keep AUTO. **Retro-decrypt repair (upstream 2026-09-12, NOT yet deployed — needs upstream push + flake bump):** `inboxclean paperless --backfill --decrypt-repair` replaces already-archived encrypted originals in place (re-fetch source attachment, ledger-checksum integrity gate, qpdf decrypt, upload with old metadata, settle, delete original, repoint ledger row; duplicate-refusal converges, dry-run read-only). A manual run NEEDS the deployed unit's env — `INBOXCLEAN_CONFIG` (accounts TOML, else work-account rows resolve no source email), `LLM_PROVIDER` (the CLI's global config gate exits `config.api_key_required` BEFORE dispatch without it — default provider is openai, the unit runs ollama; live-verified 2026-09-12), `GMAIL_CREDENTIALS_FILE`/`GMAIL_TOKEN_FILE` (the main account's source re-fetch client; there is NO `INBOXCLEAN_TOKEN_FILE` knob), and the unit `PATH` (carries qpdf); corrected reconstruction + flow: `docs/services/paperless.md`.
- **Monitoring**: the "InboxClean Projections Ready" Gatus check asserts `[BODY] == pat(*email_state*)` — the LIVE projection is named `email_state` (SINGULAR). Upstream's `projection_status_test.go` fixture says `email_states` (plural); fixture ≠ prod truth — the check's first live run (2026-08-30, binary 716c1fd) would have sat permanently red on the fixture-derived pattern. `pre-deploy-check.sh` §10 excludes `email_state(s)` as a lowercase JSON-field body pattern (same slot as the `connected` /health field), and `post-deploy-check.sh`'s convergence guard compares the 7-char `shortRev` store-path prefix against the lock rev at the DEPLOYED length (a `case "$deployed" in "$lock"*` glob can never match a string shorter than its pattern).
- **Paperless' `/api/` root is browsable HTML only — never probe or ping it as an API** (2026-09-03, broke InboxClean's ping for ~12h): the root answers `Accept: application/json` (with or without a version parameter) with **406 regardless of token validity**, curl's default `Accept: */*` with a **302 login redirect**, and 200 even UNAUTHENTICATED without an Accept header — so it simultaneously breaks JSON clients, defeats route/auth probes, and can look green while proving nothing. Valid-token probes must hit an auth-required JSON view: `/api/documents/` is the contract (valid token → 200, dead token → 401, no content-negotiation traps). Fixed upstream in InboxClean (`0f6ff43` ping → `GET /api/documents/?page=1&page_size=1`, flake bump) + SystemNix's Gatus "InboxClean Paperless Archive Auth" URL and post-deploy smoke probe moved to `/api/documents/`. Symptom of the old bug: inboxclean-sync warning `cannot reach http://127.0.0.1:2892 ... [rejection:paperless.client_error]` every tick while the token was valid.
