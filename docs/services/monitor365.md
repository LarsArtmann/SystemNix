## Buffer segment integrity + auto-quarantine (2026-11-17)

A crash under the agent's `Throughput` durability policy can leave a truncated AEAD segment; before 2026-11-02 the upload pipeline retried that head segment forever (recurring "encrypted payload too small for AEAD nonce" WARNs — the freeze-38 class, and the 2026-11-02 incident that dead-stopped uploads for five days behind one truncated segment). Live state 2026-11-17: zero AEAD WARNs in all retained journal, zero quarantine events, backlog 14 events, stall cycles 0. If the quarantine counter ever appears in `:9421/metrics`, expect a matching gap in uploaded event sequences (the lost range is dropped, not healed).

## Event volume + retention (2026-10-23)

**Diagnosis** (docs/status/2026-10-23_01-09_monitor365-db-io-diagnosis-self-review.md + planning/2026-10-23_01-42_SUPERB-monitor365-event-volume-fix.md): the DB grew <1 GB → 25.1 GB in 4 days when the 597M-event backlog drained (Oct 18–21); `system_monitor365_buffer_pressure` has been 1 since ~Oct 19 (25.1 GB file vs MemoryMax 4G). **Fixes (live at the next `nix run .#deploy`):**

0. **fs_event interval semantics — VERIFIED AGAINST SOURCE (2026-11-20, task 000001a1f6b5, pinned lock rev `d293d3f4`)**: the collector (`crates/collectors/common/src/fs_event.rs`) is notify-crate `RecommendedWatcher`-driven — events arrive on the OS file-watch callback, and `interval_seconds` ONLY controls how often `collect_batch` drains the internal channel (capped at 500/burst; the single-event `collect()` path it replaced lost burst events on the 100-slot channel). There is NO filesystem polling and NO debounce tied to the interval. With the current `watch_paths = []` zero watches register and the collector emits nothing at ANY interval. The 1s→60s change is detection-NEUTRAL: it alters only the drain cadence of a channel that receives nothing. If paths are ever added, detection stays immediate (event-driven) with ≤interval delivery latency — no adjustment needed.
1. **Volume-engine cuts** — configuration.nix `settings.collectors`: `keystrokes.enabled = false`, `mouse.enabled = false` (afk_status already covers idle detection), `fs_event.interval_seconds = 60` (future-proofing only — currently zero events, see the corrected diagnosis above). EFFECTIVE ONLY AT THE NEXT AGENT START — the agent unit is owner-stopped since 2026-10-21 03:10; the collector cut does nothing until then.
2. **Nightly retention** — the quiesced backup script (monitor365.nix `monitor365BackupScript`) now runs, INSIDE the server-stopped window and AFTER the export: `DELETE FROM events WHERE try_cast(timestamp AS TIMESTAMP) < TIMESTAMP '<now-90d>'` (validated on DuckDB 1.5.5 against both TIMESTAMP and VARCHAR columns + malformed rows — try_cast skips them). The export that precedes it each night is the rollback copy; the 2026-10-22 owner NVMe safety copy above is the belt-and-suspenders pre-retention snapshot. Window = `retentionDays` in monitor365.nix; raise/lower there. **CONFIRMED 90d 2026-11-20 (task 000001a1f6b5): live since the 2026-11-12 converged fire, ratified as the standing window** — **raised to 100d 2026-11-21 (see the mic/audio section below): 90d stays the HOT window, the extra 10d is the archive-before-delete grace**
3. **Weekly VACUUM** — DuckDB never truncates the file after deletes; a stamp-gated (`$STATE_DIR/.retention-vacuum-stamp`, 7 d) `VACUUM;` reclaims the ~15 GB bloat. Headroom-guarded: skipped with a loud WARN if free space on the state dir < DB size + 5 GiB (never ENOSPC the root at 03:00). First fire after deploy VACUUMs immediately (no stamp) — expect the 03:00 window to run long ONCE (~10-20 min on the QLC root), then ~6 min/night.
4. **Backup unit hardening** — MemoryHigh 8G / MemoryMax 12G (observed peaks 7.4–20.8 GB uncapped), ioTier.background, TimeoutStartSec 30min.

**First-fire expectations** (first calm night post-deploy): journal shows `monitor365-retention:` lines (deleted-boundary count ≈ Apr–Jul era events, likely 400M+), rows-remaining, and a VACUUM line with the 25.1 GB → ~7-10 GB shrink. If DELETE or VACUUM fails, the script WARNs and leaves the DB as-is (that night's export is intact); the server still comes back via the EXIT trap. Rollback ladder: prior night's `*.backup_*.db` (heal-script restore path) → the NVMe safety copy.

**Retention DELETE was silently failing every fire (2026-11-11 diagnosis + fix):** every fire since ≥Nov 6 logged "DELETE failed (DB left as-is)" while the script's `2>/dev/null` hid duckdb's error (VACUUM "succeeded" but reclaimed 0 bytes — nothing was ever deleted; DB grew 25.1 GB → 39 GB/133.4M rows). Root cause (proven live on a reflink copy of the nightly export — yolo-session sudo reaches the 0700 state dir): a single-transaction DELETE over the ~127M-row backlog era is unbounded — OOM "failed to pin block" at 5.5 GiB (6G limit), still OOM with threads=2 + preserve_insertion_order=false, SIGABRT at 9.3 GiB (10GB limit); the working set scales WITH the limit because the whole delete set lives in one txn's undo structures. Fix (scripts/monitor365-retention.sh): rowid-batched deletes — `DELETE … WHERE rowid IN (SELECT rowid … LIMIT $RETENTION_BATCH_SIZE)` — 5M rows/batch fits at 6G (~4.5 min/batch, full-scale-verified), 8 batches/fire (`RETENTION_MAX_BATCHES`, bounds the quiesce window ~40 min), next fire continues, one fresh duckdb process per batch (allocator never high-waters across batches — the index-rebuild lesson). Boundary count at fix time: **126,932,708 deletable rows** → converges in ~4 nights; the 7d VACUUM stamp (expires 2026-11-18) then reclaims the file bloat (expect 39 GB → single-digit GB per the 10-23 projection). duckdb stderr now logged on DELETE and VACUUM failure. Note (updated 2026-11-21): the 03:25 `monitor365-pool-copy` fire no longer re-fires the backup — the `wants` edge was dropped 2026-11-20 because it re-STARTED the finished oneshot nightly (double export+retention). Since After= orders only same-transaction units, the now-independent timer fire instead carries a fail-closed ExecStartPre guard (scripts/monitor365-pool-copy-guard.sh, checks.monitor365-pool-copy-guard-selftest): if the backup is still active/activating, pool-copy refuses (onFailure alert) and the next nightly fire catches up; if the backup timed out to "failed", the copy of whatever export landed still proceeds.
**Live execution 2026-11-11 evening (two quiesce windows, orchestrators in ~/.cache/monitor365-cleanup/):** window 1 deleted 95M rows (19x5M batches) before batch cost DEGRADED (each batch's scan crosses accumulated free-block masks; batch 20 OOM'd — smaller 2.5M batches degraded immediately after, same OOM signature); window 2 deleted 2.5M more, then shrank the file via the only path that actually shrinks DuckDB: rebuild-copy (`ATTACH src; ATTACH dst; COPY FROM DATABASE src TO dst` at a 16G session cap — **plain VACUUM is proven live to reclaim 0 bytes**: it reuses freed blocks internally, the file never shrinks; the 10-23 "25.1 GB -> 7-10 GB" projection was theory). Remaining ~34M deletable rows converge post-deploy on the compact file (fresh file = no degradation masks: ~7x5M batches = 1 night). ## Microphone monitoring + pool audio archives (2026-11-21, corrected 2026-11-27)

Owner directive: "mic-monitor installed on evo-x2, store the audio on the HDD pool." mic-monitor is the extracted **library crate** (LarsArtmann/mic-monitor). There is no standalone daemon: it ships as two monitor365 agent collectors, enabled in `platforms/nixos/system/configuration.nix` `settings.collectors`. The agent unit is **`monitor365.service`** (there is no `monitor365-agent.service`; only the watchdog is named `monitor365-agent-watchdog.timer`).

- **`mic_monitor`** (10s): change detection via `pactl` against the displayUser's pipewire-pulse socket. `RecordingStarted`/`RecordingStopped` per `(device, process_name, pid)`. `capture_snippets` is on since the 2026-11-27 second wave; a snippet rides microphone recordings only (see State).
- **`audio_stream`** (300s): ambient capture via `parecord` from the default source, 10s per fire; captures below -60 dBFS RMS are skipped as silence. `capture_system_output = false` (mic; flip for the sink-monitor source).
- Requires `pkgs.pulseaudio` in `runtimeDeps` (pactl + parecord client binaries, PulseAudio 17.0) and a live graphical session (headless = probe-once skip; the `monitor365-graphical-restart` path unit re-arms at login).
- **Pulse bridge (load-bearing):** the agent is a SYSTEM user; `/run/user/1000` is 0700 lars:lars, so the socket is bound into `/run/monitor365/pulse/native` (BindPaths, `-`-prefixed = skipped pre-login) + `PULSE_SERVER=unix:/run/monitor365/pulse/native` points pactl/parecord at it. Without this the mic collectors EACCES silently (row in docs/todo/services.md).
- **Hotplug:** mic-monitor emits `DeviceConnected`/`DeviceDisconnected` since its commit `b9c8a8a` (2026-11-21), but monitor365's adapter maps no device event, so none reaches the DB in any deployed state. The lock at `259d2df2` predates that code anyway.

**What was wrong until 2026-11-27 (reproduced on the agent's own binary):** PulseAudio 17's `parecord` has no `--duration` option. Both collectors passed it; `parecord` printed `unrecognized option '--duration=2'`, exited in about 3 ms with empty stdout, and both collectors swallowed that without a log line at any level. mic-monitor also sent stderr to `/dev/null` and returned `None`; monitor365's `audio_stream` provider returned `Ok(None)`. Result: 0 of 76 `audio.recording` started events carried a snippet and `audio_stream` produced 0 events in its first 5 days, while the stack read as healthy because `collector_events_collected` also counts empty cycles (fixed in monitor365 with the same wave) and a collector that never produced an event gets no silence warning. Five earlier "audio verified" claims rested on that counter: see the corrections in the 2026-11-21 17:08, 2026-11-21 23:12 and 2026-11-22 14:54 reports.

**What the 151 events of 2026-11-21..26 were:** not microphone recordings. Every row had `process_name: "unknown"`, no pid and `device_name: "source #<n>"`. The watcher caught the stream on 2026-11-27 01:15 CET: `cava -p /tmp/dms-cava-*.conf`, child of `.dms-wrapped` (DankMaterialShell's audio visualizer), tapping the sink monitor (`alsa_output.pci-0000_c6_00.1.hdmi-stereo-extra2.monitor`, system audio). PipeWire lists that server-side stream with `Client: n/a`, no `application.*` property, `node.virtual = "true"`; its only names are `node.name` and `media.name` (`cava`). DMS restarts it often: 61 stream starts on 2026-11-25 alone, durations in multiples of 10 s. `Source:` is a numeric index on PipeWire-pulse too, which is why the device read `source #<n>`.

**State (2026-11-27, second wave):**

- The `parecord` compatibility shim is gone from `modules/nixos/services/monitor365.nix`. Both repos bound the recorder themselves now: mic-monitor's public `mic_monitor::parecord::capture_pcm` kills `parecord` at the end of its window and passes `--latency-msec=100` (PipeWire delivers 2 s fragments otherwise, so the first byte would land about 2 s late). mic-monitor is floated to its 2026-11-27 capture fix; monitor365's audio_stream collector captures through the same function, a failed capture is an error (no longer a silent `no data`), and the mic adapter reports the source NAME and the process behind each recording instead of `source #<n>` / `unknown`. The `RUST_LOG` directives stay: each capture leaves a journal line.

## Data governance: cadence + the tenant-cap governor (2026-10-23)

Owner directive (2026-10-23): store the right kind of data at the right intervals INSTEAD of leaning on retention windows; the metric that matters is IO/s, not total storage. Design (source-verified):

- **The tenant daily event cap is the IO/s governor.** Upstream default 10,000 events/day (`max_events_per_day`, api-types/src/tenant.rs:32); the 2026-10-18..21 backlog drain lifted it to 1B and the live value is unverified (admin-JWT/sudo-gated — `/health` is the ONLY unauthenticated route, live-probed 2026-10-23). **Restore before any agent restart — owner action via admin API/sudo, never agent-side. Recommendation: 250,000/day** (~3 ev/s ceiling, ~2.5× a worst build-day's process churn, 30× below the storm class).
- **A cap without volume-correct collectors = balloon**: the agent's offline queue is UNBOUNDED, so a binding cap buffers silently on disk (the 113-day/597M backlog mechanism). The cadence set is what makes the cap safe; the bounded-queue fix is queued upstream.
- **Cadence set (configuration.nix, inert until the owner restarts the agent):** explicit `interval_seconds` only where module defaults were realtime/unbounded — process 5s (SAMPLING not debouncing: sub-5s processes vanish unseen; accepted trade for the cmdline+environ stream), network/battery 300s, location 900s. Already-bounded defaults untouched (system_info 60s, screenshots 300s, camera 3600s, fs_event 60s). clipboard/notifications/afk_status realtime BY DECISION (event-driven, human-paced — the event is the right granularity). mouse/keystrokes OFF (volume-engine cuts). Upload batching verified rendering correctly in the live TOML (`[cloud] sync_interval_seconds=60, batch_size=100`) — deliberately not re-pinned.
- **Endgame (upstream, queued):** bounded offline queue (drop-oldest + dropped-counter), environ opt-in/once-per-app (bulk + secrets-in-DB smell), rollup tables (raw expires in days, aggregates forever — makes DELETE+VACUUM churn structurally unnecessary in DuckDB single-file, which has no cheap partition drop).
- **Server binary env overrides follow the figment pattern `MONITOR365_SERVER__<FIELD>` (2026-10-25)** — but the memory_limit value MUST match `<digits>(KB|MB|GB|TB)` (crates/db memory_limit.rs): a "6G"-shaped value is SILENTLY REJECTED (WARN log only) and falls back to the config default `"2GB"` (decimal 2e9 = 1.86 GiB — the "1.8 GiB/1.8 GiB used" in every OOM). The backup wrapper shipped exactly this typo 2026-10-25 (the 03:01 OOM "fix" never worked); corrected to `6GB`. The server unit now sets `MONITOR365_SERVER__MEMORY_LIMIT=4GB` with MemoryHigh 6G/MemoryMax 8G (schema-init index rebuilds over the 25 GB events table need > 1.86 GiB — the 2026-10-25 14:57-15:00 crash-loop class, monitor365.nix server block).
