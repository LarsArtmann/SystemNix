## Event volume + retention (2026-10-23)

**Diagnosis** (docs/status/2026-10-23_01-09_monitor365-db-io-diagnosis-self-review.md + planning/2026-10-23_01-42_SUPERB-monitor365-event-volume-fix.md): the DB grew <1 GB → 25.1 GB in 4 days when the 597M-event backlog drained (Oct 18–21); `system_monitor365_buffer_pressure` has been 1 since ~Oct 19 (25.1 GB file vs MemoryMax 4G). The 597M came from the Apr 21 → Aug 12 collection era: the integrity-hash serialization bug rejected ~every upload (fixed upstream 2026-07-18), so the agent buffered everything (~61 events/sec average). **Volume engines (CORRECTED 2026-10-23 02:3x after reading upstream source): mouse (realtime, per-movement), keystrokes (realtime, per-keypress), process (one event per start AND exit, cmdline+environ payloads — kept: core dashboard feature). fs_event was a PHANTOM engine — `watch_paths = []` means the notify watcher registers zero watches and emits ZERO events (its interval is only the drain cadence); the 60s interval stays as future-proofing for when paths get added.**

**Fixes (live at the next `nix run .#deploy`):**

1. **Volume-engine cuts** — configuration.nix `settings.collectors`: `keystrokes.enabled = false`, `mouse.enabled = false` (afk_status already covers idle detection), `fs_event.interval_seconds = 60` (future-proofing only — currently zero events, see the corrected diagnosis above). EFFECTIVE ONLY AT THE NEXT AGENT START — the agent unit is owner-stopped since 2026-10-21 03:10; the collector cut does nothing until then.
2. **Nightly retention** — the quiesced backup script (monitor365.nix `monitor365BackupScript`) now runs, INSIDE the server-stopped window and AFTER the export: `DELETE FROM events WHERE try_cast(timestamp AS TIMESTAMP) < TIMESTAMP '<now-90d>'` (validated on DuckDB 1.5.5 against both TIMESTAMP and VARCHAR columns + malformed rows — try_cast skips them). The export that precedes it each night is the rollback copy; the 2026-10-22 owner NVMe safety copy above is the belt-and-suspenders pre-retention snapshot. Window = `retentionDays` (90) in monitor365.nix; raise/lower there.
3. **Weekly VACUUM** — DuckDB never truncates the file after deletes; a stamp-gated (`$STATE_DIR/.retention-vacuum-stamp`, 7 d) `VACUUM;` reclaims the ~15 GB bloat. Headroom-guarded: skipped with a loud WARN if free space on the state dir < DB size + 5 GiB (never ENOSPC the root at 03:00). First fire after deploy VACUUMs immediately (no stamp) — expect the 03:00 window to run long ONCE (~10-20 min on the QLC root), then ~6 min/night.
4. **Backup unit hardening** — MemoryHigh 8G / MemoryMax 12G (observed peaks 7.4–20.8 GB uncapped), ioTier.background, TimeoutStartSec 30min.

**First-fire expectations** (first calm night post-deploy): journal shows `monitor365-retention:` lines (deleted-boundary count ≈ Apr–Jul era events, likely 400M+), rows-remaining, and a VACUUM line with the 25.1 GB → ~7-10 GB shrink. If DELETE or VACUUM fails, the script WARNs and leaves the DB as-is (that night's export is intact); the server still comes back via the EXIT trap. Rollback ladder: prior night's `*.backup_*.db` (heal-script restore path) → the NVMe safety copy.

**Successors deliberately not done here:** upstream archive-to-Parquet-then-delete (the `archival` crate exists), server-native retention, DuckDB hot-tier move, agent restart decision (owner) — queued in docs/todo/{services,upstream}.md.

## Data governance: cadence + the tenant-cap governor (2026-10-23)

Owner directive (2026-10-23): store the right kind of data at the right intervals INSTEAD of leaning on retention windows; the metric that matters is IO/s, not total storage. Design (source-verified):

- **The tenant daily event cap is the IO/s governor.** Upstream default 10,000 events/day (`max_events_per_day`, api-types/src/tenant.rs:32); the 2026-10-18..21 backlog drain lifted it to 1B and the live value is unverified (admin-JWT/sudo-gated — `/health` is the ONLY unauthenticated route, live-probed 2026-10-23). **Restore before any agent restart — owner action via admin API/sudo, never agent-side. Recommendation: 250,000/day** (~3 ev/s ceiling, ~2.5× a worst build-day's process churn, 30× below the storm class).
- **A cap without volume-correct collectors = balloon**: the agent's offline queue is UNBOUNDED, so a binding cap buffers silently on disk (the 113-day/597M backlog mechanism). The cadence set is what makes the cap safe; the bounded-queue fix is queued upstream.
- **Cadence set (configuration.nix, inert until the owner restarts the agent):** explicit `interval_seconds` only where module defaults were realtime/unbounded — process 5s (SAMPLING not debouncing: sub-5s processes vanish unseen; accepted trade for the cmdline+environ stream), network/battery 300s, location 900s. Already-bounded defaults untouched (system_info 60s, screenshots 300s, camera 3600s, fs_event 60s). clipboard/notifications/afk_status realtime BY DECISION (event-driven, human-paced — the event is the right granularity). mouse/keystrokes OFF (volume-engine cuts). Upload batching verified rendering correctly in the live TOML (`[cloud] sync_interval_seconds=60, batch_size=100`) — deliberately not re-pinned.
- **Endgame (upstream, queued):** bounded offline queue (drop-oldest + dropped-counter), environ opt-in/once-per-app (bulk + secrets-in-DB smell), rollup tables (raw expires in days, aggregates forever — makes DELETE+VACUUM churn structurally unnecessary in DuckDB single-file, which has no cheap partition drop).
- **Server binary env overrides follow the figment pattern `MONITOR365_SERVER__<FIELD>` (2026-10-25)** — but the memory_limit value MUST match `<digits>(KB|MB|GB|TB)` (crates/db memory_limit.rs): a "6G"-shaped value is SILENTLY REJECTED (WARN log only) and falls back to the config default `"2GB"` (decimal 2e9 = 1.86 GiB — the "1.8 GiB/1.8 GiB used" in every OOM). The backup wrapper shipped exactly this typo 2026-10-25 (the 03:01 OOM "fix" never worked); corrected to `6GB`. The server unit now sets `MONITOR365_SERVER__MEMORY_LIMIT=4GB` with MemoryHigh 6G/MemoryMax 8G (schema-init index rebuilds over the 25 GB events table need > 1.86 GiB — the 2026-10-25 14:57-15:00 crash-loop class, monitor365.nix server block). The retention script's duckdb sessions carry their own caps (`DUCK_SESSION`: memory_limit 6G, threads 4) for the same cgroup reason.

## Index desync + boot-rebuild OOM incident (2026-10-25)

Chain: the 13:27 deploy-restart left the DuckDB WAL unclean → the unit's heal script DELETED the WAL → multiple indexes desynced from table data (every bootstrap died `Duplicate key "api_key: …"` — DuckDB UPDATE = delete+re-insert self-collides with stale index entries; even the indexes' own delete paths failed). Repaired live in two moves:

1. **`scripts/monitor365-apikey-desync-repair.sh`** — drops EVERY droppable index (constraint-owned PK/UNIQUE are not droppable, reported as skipped) + CHECKPOINT; the server's schema.sql (`CREATE … IF NOT EXISTS`) re-creates them at boot. Zero row-data loss; tenants/devices/domain_events verified intact throughout.
2. **`scripts/monitor365-index-rebuild.sh`** — the boot rebuild itself OOM'd at the 1.86 GiB default (schema init runs INSIDE the server), crash-looping the unit. The script quiesces server+watchdog and runs the schema.sql index DDL through the duckdb CLI, **one invocation per statement**: a single connection high-waters ACROSS statements (the 61-statement batch OOM'd even at 6GB while single fresh-process builds fit at 1.8 GiB). Verified live: 65/65 indexes, 0 failed, server healthy after.

Operational DuckDB facts learned live: single-writer lock (query only when the server is stopped — the scripts lock-wait); DROP INDEX + DDL live in WAL until CHECKPOINT (a clean service stop checkpoints); DDL autocommits per statement (the crash loop was slowly converging, one index per ~40s attempt, at brutal IO cost — don't wait it out, run the rebuild script).

## Backup export redesign: CHECKPOINT + reflink (2026-10-25)

Upstream's `monitor365-server backup` (DuckDB ATTACH + `COPY FROM DATABASE`) cannot export this ~30 GB DB under any sane cgroup: it pins target blocks until commit and OOM-aborts regardless of memory_limit — 1.86 GiB default at the 03:01 run, then a shape-VALID 6GB limit (5.5 GiB applied) still died "failed to pin block" ~3 min in at ~8 GB written (forced fire 16:12). The Oct 24/25 ~7-8 GB "backups" are partial corpses of that class; last FULL export before the redesign = Oct 23.

The wrapper (`monitor365-server-backup.service`, quiesced slot) now does: stop watchdog timer → stop server → `duckdb … CHECKPOINT` → `cp --reflink=always` (same BTRFS subvol = instant CoW snapshot; plain-copy fallback) → chown → retention + weekly vacuum (`scripts/monitor365-retention.sh`) → restore server (EXIT trap). The export IS a consistent backup because the single writer is stopped and the file checkpointed. Reflink extents are shared with the live DB — app-level rollback insurance, not filesystem-level damage insurance (owner NVMe copy + pool-side layers cover that).

Sandbox lesson (first fire 17:13): `runuser -u monitor365-server` from the hardened root unit fails `cannot set user id: Operation not permitted` — CAP_SETUID present, @setuid inside the @system-service filter, still EPERM. The CHECKPOINT therefore runs as ROOT with a `chown -R monitor365-server:monitor365-server "$STATE_DIR"` net right after (root-owned WAL/tmp residue is the hazard; a clean checkpoint deletes the WAL anyway — root-run duckdb is the pattern the index rebuild already proved live-safe).

Forced-fire evidence tool: `scripts/monitor365-backup-fire.sh` (self-elevates; pre/post state, journal excerpts). Prune warning: partial corpses (`*.backup_2026102[45]*`, ~7-8 GB) sit NEWER than several good rungs — count-based retention (KEEP=7) will NOT select them out; remove deliberately.
