## Gotchas

- **Wise SCA (Strong Customer Authentication) gates bank-sync balance statements (~every 90 days, UK/EEA profiles)** — Wise answers `GET /v1/profiles/{id}/balance-statements/{id}/statement.json` with **403 + EMPTY body**; verdict + one-time token (OTT) live in the `x-2fa-approval-result`/`x-2fa-approval` RESPONSE HEADERS, which wise-go < v0.6.1 discarded (a bare unexplained 403 → zero transactions synced). Since bank-sync 2026-09-16 the OTT VALUE is never logged (bool `approval_token_issued` only). Renewal, in order: **the dashboard approval flow** (bank-sync ≥ 2026-09-16, `run` mode — Sync State card → "Wise approval needed" → Approve now: probe → channel → OTP → verify → auto-sync, riding the daemon's own Wise creds; OTT held in a server-side session, never rendered), then the CLI `bank-sync sca status` / `sca approve` (same Wise env as the daemon; `sca status` is the ONLY sanctioned token-value surface), then break-glass env drop-in `BANK_SYNC_WISE_SCA_APPROVAL_TOKEN=<ott>` for exactly one cycle (the service still carries `EnvironmentFile = ["-/var/lib/bank-sync-sca/token.env"]` — root-owned 0400, `-` makes absence a no-op). Full runbook: `docs/services/bank-sync-sca.md`. A plain 403 WITHOUT 2FA headers = personal-token regional restriction instead (statements unsupported outside US/CA/AU/NZ/SG/MY) — different fix. **Re-armed again 2026-09-30** (618 cumulative challenges; `bank_sync_sync_errors_total 3` kept the deploy smoke red — the counter is restart-cumulative, so only a post-approval restart clears it); approval pending the user's OTP via the dashboard flow.
- **Wise API rejects non-UTC timestamps with 422 `wrong.date.format` (fixed 2026-08-21, wise-go v0.8.1)** — Wise demands `YYYY-MM-DDTHH:mm:ssZ`; a numeric zone offset (`+02:00`) is refused. wise-go < v0.8.1 formatted caller-local `time.Time` as-is, and bank-sync's sync window `to` bound is host-local `time.Now()` — EVERY `/v1/transfers` call 422'd for ~2.5 days (2026-08-19..21), including the SCA transfers fallback that exists to ride out statement challenges (silent partial degradation: balances synced, transfers didn't; only per-run "15 sync failure(s)" journal lines revealed it). wise-go's `formatWiseTimestamp` now normalizes all outgoing query timestamps (`createdDateStart/End`, `intervalStart/End`, rates `time`) to UTC; callers may pass any zone. Symptom signature: `wise: api error (422): wrong.date.format` with `createdDateEnd=…%2B02%3A00` in the URL
- **bank-sync SQLite migration v5 MUST be idempotent + record its version (fixed 2026-08-21)** — the original v5 ran a bare `ALTER TABLE … ADD COLUMN last_error_code` and never wrote version 5 to `schema_migrations` (only v4 recorded itself; the fresh path seeds 1-5). On the pool DB (v4-era) the first start applied the column, and the FIRST RESTART crash-looped with `duplicate column name: last_error_code` → exit 69 → start-limit-hit (bank-sync down until the heal). migrateToV5 now checks `PRAGMA table_info`, skips an existing column, and records version 5 in the same transaction. General rule for this schema: every incremental migration must (a) record its version atomically with its changes and (b) tolerate re-execution — SQLite `ALTER TABLE ADD COLUMN` has no `IF NOT EXISTS`
- **bank-sync statement_coverage RFC3339 corruption — tolerant read + V10 canonicalization (fix committed locally 2026-09-06, UNPUSHED; writer never identified)** — `[corruption] db.scan: unparseable sync_states.statement_coverage` fired on every 5-min sync per balance because the mapper parsed the column with a single canonical layout while the stored values were bare RFC3339 (`2026-09-06T13:36:24Z`). Fix (bank-sync `a9b0b8e..60015cc`): `parseStoredTimestamp` tolerant multi-layout read (canonical + RFC3339 variants, static sentinel for err113) + migration V10 canonicalizing existing rows (V4 discipline: raw-BLOB read, Go rewrite, one tx incl. version record; `''` sentinel untouched) + 3 Ginkgo specs. **Forensics that did NOT add up (2026-09-06, exhaustive):** NO bank-sync binary can write that format — proven three ways: the only writer (SyncStateProjection `internal/cqrs/projections.go:~206`) binds `time.Time` (born that way in 5a66473); modernc v1.53–v1.57 defaults to `t.String()` (`… +0000 UTC`) and `_time_format=sqlite` (in every V8-era binary via `ensureSQLiteDriverOptions`, Aug 19) writes canonical `2006-01-02 15:04:05.999999999-07:00` (driver source + live probe both verified); and the DEPLOYED binary run end-to-end (`bank-sync demo` against a scratch DB) wrote canonical `2026-09-06 14:20:28+00:00`. No triggers, no schema defaults, no sqlc writes (read layer is pure SELECT), no second process (full /proc cmdline+fd scans), no timers/cron/user units. Yet the values ADVANCED every ~15:04 min from 2026-08-31 12:30 until 2026-09-06 13:51:49 — exactly when SCA paused the last statement-backed syncs — tracking statement-sync successes (the reads' "falling back to initial window" then re-trigger). The fix is correct regardless: tolerant reads stop the error loop, V10 heals history, and if the phantom RFC3339 writer returns post-SCA-approval, tolerant reads keep working (mixed formats are harmless; the corruption ERROR was the only failure). Watch after SCA approval: if new RFC3339 values appear, the writer is statement-sync-coupled and INSIDE the daemon despite the proofs — dump goroutines then. Counter resets + corruption lines stop only after push + `nix flake lock --update-input bank-sync` + deploy (vendorHash likely stable: go.mod untouched)

## Sync sentinels + rev-drift tripwire (module 2026-10-07)

**Daemon-side gauges** (exported on `/metrics` by bank-sync master after the 2026-10-07 sentinel commits): `bank_sync_sca_approval_pending` (1 while any balance waits on a Wise SCA approval), `bank_sync_sync_consecutive_failures{provider}` (streak; success resets), `bank_sync_sync_sustained_failure` (1 once any streak reaches 4 cycles ≈ 1h at the 15m default; streaks re-seed after daemon restarts so the sentinel survives them).

**Gatus checks** (registry `services.integration.bank-sync.checks`): `Bank-Sync SCA Approval` and `Bank-Sync Sync Sustained` probe `/metrics` every 5m and require the anchored value line `pat(*\n<metric> 0\n*)` — HELP/TYPE comments can never satisfy the pattern (phantom-green guard). Gatus default failure-threshold adds ~15m debounce before the Discord push. Alerting on these replaces the "ratio > 0.9 over 1h" PromQL idea — the daemon owns the windowing, gatus only reads the text.

**Deploy order is load-bearing**: the checks reference gauges only the post-2026-10-07 bank-sync binary exports. The switch that adds these checks MUST also carry the flake.lock bank-sync input bump to that rev (push bank-sync master → update input → one switch). Switching with a stale lock turns both checks red the moment gatus reloads and fires a spurious SCA-pending push.

**Rev-drift tripwire** (`bank-sync-rev-drift.service` + hourly Persistent timer): compares `readlink /proc/<MainPID>/exe` of the running daemon against `${package}/bin/bank-sync` for the current generation; mismatch (failed restart, manual start from an old generation, GC'd store path surfacing as `(deleted)`) exits 1 → `notify-failure@` desktop push. Runs as root (reading another unit's /proc exe needs it; harden{} sets no Proc* keys by design). Ordering-only `after` — never `wants`: a tripwire must not start the service it monitors. **Root is not enough (2026-10-08, 40/40 false-positive class):** harden{}'s default `CapabilityBoundingSet = ""` strips ALL capabilities from root too — the readlink got EACCES, and the NixOS script wrapper's implicit `#!/bin/bash -e` then killed the unit SILENTLY before the diagnostic echoes (mirrors the nix-build-cleanup CAP_DAC_OVERRIDE precedent; same mechanism as the service-health-check d4 bug fixed the same day). Fix: `harden { CapabilityBoundingSet = "CAP_SYS_PTRACE"; }` + `readlink … || true`; first green tick 2026-10-08 19:02:45 — the running binary had matched all along.

## Paperless archival (weekly, AUTOMATED — zero-secret go-live 2026-10-01)

Weekly Sunday 03:00 oneshot (`bank-sync-paperless.service` + Persistent timer) archives statements + transfer receipts into the local Paperless-ngx via `bank-sync paperless --receipts`. NO manual token step exists: the DRF token is minted at archival time by the `bank-sync-paperless-token` oneshot — `drf_create_token admin` is `get_or_create` (same token every run), runs as the paperless user against the PG socket, and writes `/run/bank-sync-paperless/env` (tmpfs only, 0400 bank-sync via root ExecStartPost handover). The URL derives from `lib/ports.nix` (paperless 2892). Enabled 2026-10-01 in configuration.nix; Persistent catches up the missed Sunday run on the first post-deploy boot. Rotation: `drf_create_token -r admin` (reset) once, then any subsequent archival run re-materializes the NEW token into the env file — the old one dies with the next mint. Eval regression: `tests/test-bank-sync-paperless.nix` (mint + archival + coupling assertion: archival on requires `services.paperless.enable`). History: the 2026-09-13 wiring (`50ddba86`) shipped enable-gated on a paste-the-DRF-token-into-sops step that never happened (the sops file held PLACEHOLDERs from creation until its removal).
