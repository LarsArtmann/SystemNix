## FastFlowLM (AMD XDNA NPU LLM)

Background LLM server (Qwen3.6-35B-A3B MoE, ~3B active, 21.6 GB mmap'd since v1.0.2) on the AMD XDNA NPU of evo-x2. OpenAI-compatible at `http://127.0.0.1:52625/v1`. Replaces the hand-patchelf'd `~/.local/share/fastflowlm/` install with a Nix-managed package + socket-activated systemd service.

- **Package**: `pkgs/fastflowlm.nix` — `fetchurl` tarball + `autoPatchelfHook` + `protobuf_32` (XRT swemu/hwemu libs link against libprotobuf.so.32; resolved via `autoPatchelfIgnoreMissingDeps` because the swemu/hwemu libs are never loaded on real NPU). Wrapper replaces the upstream bash wrapper with a deterministic `$out`-pinned XILINX_XRT. **v1.0.3 went LIVE with the weekend gens (774, nixpkgs 20260911.eaad089) and FAILED at the 2026-09-14 10:34 boot — REVERTED to v1.0.2 same day (system-775, `793ac3d2`)**: with kernel 7.2.5 and `/dev/accel/accel0` present, every start still died `No such device with index '0'` in <2s — BOTH theories dead (kernel premise: amdxdna byte-identical v7.2→v7.2.3; loader path: the dual-lib-dir LD_LIBRARY_PATH wrapper did NOT fix flm-real's hardcoded `/nix/store/lib/…` prefix probe — the WARNING persists in the journal). Post-revert live proof: v1.0.2 enumerates the NPU and model-loads (24.3G peak, no device error) — then the NEW guard Zone 6 (IO-PSI trip #69, crush-session QLC churn saturating io PSI ~50-80%) stopped it mid-cold-load BY DESIGN; flm returns when IO drains (`systemctl start fastflowlm.socket` in a quiet window works). Upstream issue now ELIGIBLE per the staged-bump gate (fails post-fix) — optional. No weight re-pull ever happened (v1.0.3 dies pre-model-load), so the v1.0.2 weights on /data are intact. **v1.0.1 → v1.0.2 (2026-08-21)**: +13% decoding/+20% prefill on qwen3.6-moe:35b-a3b; FLM re-quantized the weights (13.6 GB → 21.6 GB `model.q4nx`) so the upgrade REQUIRED a re-pull — old files hash-mismatch the new manifest (`flm pull` treats them as missing and overwrites in place; tokenizer/vision files verified fine and were kept) — snapshot-pinning caveat: the in-place overwrite pins old AND new weights through the ~4-5w /data window (the snapshot-pinning doctrine table in docs/agents/storage.md). Memory ceilings re-sized 32G/26G → 40G/32G (the 13.6 G model already peaked at 26G), proxy deadline 300s → 480s, smoke timeout 240s → 480s.
- **Module**: `modules/nixos/services/fastflowlm.nix` — `fastflowlm.socket` on `127.0.0.1:52625` with **`Accept=true`** (inetd-style): systemd itself accepts each connection and spawns one per-connection `fastflowlm@.service` instance (`StandardInput/Output=socket`) whose bridge script (`fastflowlm-proxy-conn`) `/dev/tcp`-probes the backend until it accepts, then `exec socat - TCP:127.0.0.1:52626`. Backend `fastflowlm.service` (flm serve) is pulled up per-connection via the template's after/wants. `MaxConnections = 8` (flm enforces a hard 10-connection limit — never exceed or even approach it; probing it with HTTP during cold load churned slots and reset genuine clients, live incident 2026-08-18). The kernel TCP backlog is the cold-load hold: flm binds :52626 ~55 s before its accept loop goes live; clients queue in-socket with zero userspace polling. 1h idle TTL via `fastflowlm-idle.timer` (every 5 min, stops `fastflowlm@*.service` + backend when the backend journal has no "TCP connection established" entries for ≥ keepAlive AND the backend has been active for ≥ 10 min). `ioTier.background` (BE/6, 13.6 GB cold read must not starve boot/SSHD on QLC NAND).
- **WHY no systemd-socket-proxyd**: nixpkgs does not build that binary at all (verified 2026-08-18 against every systemd 261.1 store output). A proxy unit ExecStart'ing it dies exit 127 → start-limit-hit → **systemd deactivates the socket itself** → :52625 refused connections for ~5 h while every liveness check stayed green (Gatus must not probe the port by design — nothing else watched it). The Accept=true + socat bridge replaced it with zero resident daemons.
- **Accept=true NAMING RULE (systemd 261, socket.c)**: the per-connection template MUST be named `<socket-prefix>@.service` (`fastflowlm@.service`). `Service=` overrides on accepting sockets are unsupported: when the value resolves, `socket_verify()` refuses to load; when it's a bare template name it is silently IGNORED ("missing the instance name") and connections then fail `Failed to load connection service unit: No such file or directory` → socket result `resources`. Never reintroduce `Service=` here.
- **Deploy-time E2E smoke** (`scripts/post-deploy-check.sh`): `curl --max-time 480 http://127.0.0.1:52625/v1/models` through the public socket, enable-gated. It is the ONLY functional gate for this endpoint (Gatus cannot probe :52625) — it would have caught the dead-endpoint class within one deploy. Note it cold-pins the 21.6 GB model on every deploy (connection restarts the idle clock). Pre-deploy check #12 (ExecStart existence) catches the phantom-binary class before switch.
- **WHY socket activation**: the model is 21.6 GB mmap'd from `/data/ai/models/fastflowlm`. Pinned 24/7 it would reserve ~30+ GB of the 94 GB CPU-visible pool at idle. Cold load is 2-5 min (acceptable for a background LLM); idle unload frees the RAM.
- **WHY Gatus MUST NOT probe :52625**: every TCP probe is a permanent keepalive. The `system-health` textfile collector emits `system_service_state_failed` / `system_service_start_limit_hit` for `fastflowlm` so Gatus can alert on actual failure without pinning the model. Wired in `gatus-config.nix`.
- **NPU access**: service user needs `video` group (`/dev/accel0` is `root:video 0660`) + `LimitMEMLOCK=infinity` (NPU DMA requirement). Existing `hardware.amd-npu` module wires the XRT runtime + udev rules.
- **`--embed 1` removed (was BROKEN, now obsolete)**: Co-loading embed-gemma with the Qwen 13.6 GB model failed (`DRM_IOCTL_AMDXDNA_CREATE_HWCTX` / `xrt::ext::bo` ENOMEM). The `loadEmbed` option has been removed from the module. Embeddings are now served by the `llama-rag` module (bge-m3 on GPU). See the llama-rag section below.
- **OOM resilience (2026-08-18 storm)**: flm's 22.5 GB cold load colliding with a full machine (user llama-server + PMA + deploy restart churn) caused repeated global OOM kills — 4 rapid restart retries pile-drove 22 GB reads each, and the kernel slaughtered user-session services (pipewire, dbus-broker, dconf, oom_score_adj=200) instead of flm. Backend now carries `OOMScoreAdjust=300` (flm is the BEST global-OOM victim: stateless, socket-activated, self-heals on next connection — protect the desktop, sacrifice the model) + exponential restart backoff (`RestartSec=60` + `RestartSteps=5` + `RestartMaxDelaySec=15min`, 2026-08-21). Flat 60s was measured insufficient: under sustained oomd slice-pressure kills (systemd-oomd marks flm whenever `/system.slice` PSI >60%/30s — 13 kills over 4 days), the backend re-paid the 22.5 GB cold load every 2-3 min (2026-08-21 18:09-18:25: 8 kills, ~180 GB QLC reads in 20 min; 742 GB total read across 61 lifecycles in 4 days) until start-limit wedged activation. Backoff doubles the delay up to 15 min, letting pressure storms drain; flm being the oomd kill target is BY DESIGN (26G peak = biggest candidate) — the backoff only stops the reload I/O bomb. Post-OOM NPU driver state self-recovers once system memory frees (the `CREATE_HWCTX ENOMEM` after the storm was transient driver-level exhaustion, not a wedge — 6th attempt loaded fine).
- **Known crash (2026-08-21, 4 days of journal)**: 4× SIGABRT `double free or corruption (fasttop)` + 1 SEGV at 26G peak under memory pressure — flm v1.0.1 heap bug, self-heals via restart. **UPGRADED to v1.0.2 on 2026-08-21** (weights re-pulled, hash-verified) — the bug SURVIVED: the 2026-08-31 boot saw 4 more core-dumps (segfault `libqwen2_npu.so` at prefill, same offset every time), each restart re-paying a 21.6 GB cold load stretched from 2-5 min to 27-43 min under IO contention — the amplifier of the 16:34 freeze (incident #3). **v1.0.3 bump REVERTED — held at v1.0.2 (2026-08-31 evening, 49ac851e "flm v1.0.2 held")**: the freeze-incident-3 calibration commit rolled the package back to v1.0.2, so repo pin AND deployed ExecStart are 1.0.2 (flm self-reports "current v1.0.2, latest v1.0.4" as of 2026-09-04); any future bump still needs the live-serve validation + one-time re-pull discipline (Q4_K weights hash-mismatch the v1.0.2 manifest). Release notes do NOT claim a crash fix — the guard's Zone 4 is the structural containment, treat any bump as accuracy + best-effort. Usage baseline (Aug 18-21): ~87 conns/day, ~40 chat completions/day; consumers = PMA go-commit (heaviest) + papdashboard enricher; paperless-ai wired but zero observed traffic. flm echoes full LLM request/response bodies to journald (→ SigNoz, `all=true`) — prompts are in the logs. **OWNER DECISION 2026-10-02: journald + SigNoz are TRUSTED — the echo is accepted as-is (no journald filter, no SigNoz `all=false`).** Do not re-flag this as a privacy gap; it was the gate on the paperless AI-workflow go-live and is resolved (see docs/status/2026-10-02_12-50_paperless-ai-deep-dive-status.md)
- **idle-check bugs fixed (2026-08-18)**: the idle timer killed a backend 2.5 min into a cold load. Two causes: (1) `ActiveEnterTimestampMonotonic` is an ABSOLUTE monotonic timestamp, not an age — the `[ "$active_us" -lt 600000000 ]` guard never fired on any host with >10 min uptime; correct form subtracts it from `/proc/uptime` µs. (2) During cold load the backend hasn't run its accept loop, so backlog-queued connections leave NO "TCP connection established" journal lines — the journal grep alone sees "idle". The check now exits early if ANY `fastflowlm@*.service` instance is active (a live instance = live connection, queued or served — the only reliable cold-load guard).
- **Combine with PMA auto-commit**: `modules/nixos/services/projects-management-automation.nix` sets `OPENAI_BASE_URL=http://127.0.0.1:52625/v1` + `OPENAI_MODEL=qwen3.6-moe:35b-a3b` via `extraEnvironment`. The OpenAI provider chain reads these env vars ONLY in go-commit v0.8.0+. The pinned go-commit follows our `go-commit` input — `nix flake update go-commit` activates the wire-up once the Go proxy has propagated v0.8.0 (typically 15-60 min after `git tag` push). Until then, the env vars are ignored and the daemon falls back to heuristic commit messages.
- **Crates runtime**: `XILINX_XRT` is set to `$out` (the package's store path) so XRT can find `./lib/x86_64-linux-gnu/`. The wrapper creates the multiarch symlinks on first run if absent.
- **Hand-started process is now obsolete**: delete `~/.local/share/fastflowlm/`, `~/.local/bin/flm`, and the LD_LIBRARY_PATH exports in `~/.bashrc` after the deploy proves stable.
- **Manual install**: `~/projects/anime-comic-pipeline/docs/npu-fastflowlm-llm-server.md` has the measured resource usage (24.9 GB RSS at idle, 14 t/s decode, ~3 s TTFT) and full operational guide.
