## llama-rag (Embeddings + Reranking on GPU)

**Module:** `modules/nixos/services/llama-rag.nix` (`services.llama-rag`) — two lightweight `llama-server` instances on the GPU (ROCm) for retrieval-augmented generation. Completes the three-tier AI stack:

| Role       | Engine                                      | Port                     | Hardware   | Module           |
| ---------- | ------------------------------------------- | ------------------------ | ---------- | ---------------- |
| Chat LLM   | FastFlowLM                                  | 52625 (socket-activated) | NPU        | `fastflowlm.nix` |
| Embeddings | llama-server (`--embedding`)                | 8848                     | GPU (ROCm) | `llama-rag.nix`  |
| Reranking  | llama-server (`--reranking --pooling rank`) | 8849                     | GPU (ROCm) | `llama-rag.nix`  |

- **Why llama-server, not Ollama or TEI:** Ollama does NOT support reranking (issue #3368, open since Mar 2024 — no `/rerank` endpoint, zero rerank code). TEI is Docker-only with no gfx1150 ROCm support. `llama.cpp` has had native reranking since PR #9510 (Sept 2024): `--reranking` enables the `/v1/rerank` endpoint, `--pooling rank` selects cross-encoder pooling. Both engines are already packaged as `llama-cpp-rocwmma` in `ai-stack.nix` — zero new packages, zero Docker
- **Why two instances:** `--embedding` and `--reranking` are independent server modes (verified via `llama-server --help` on nixpkgs build). One instance serves `/v1/embeddings` (bge-m3), the other serves `/v1/rerank` (bge-reranker-v2-m3). Both are ~568M params: cold load ~1s, VRAM ~1-2 GB each
- **Model download:** The `llama-rag-model-fetch` oneshot downloads GGUFs from HuggingFace (`gpustack/bge-m3-GGUF`, `gpustack/bge-reranker-v2-m3-GGUF`) into `/data/ai/models/gguf/`. Verifies GGUF magic bytes, stamps source URL for staleness detection, atomic rename from `.part`. `ConditionPathIsDirectory` on modelDir skips if `/data` isn't mounted. Both server services `requires` the fetch — they won't start without models
- **Flags verified** (llama-cpp-10408 in nixpkgs): `--embedding`, `--reranking`, `--pooling {none,mean,cls,last,rank}`, `--alias STRING` all present. No `--rerank-bge-v2-m3-default` preset in this version — explicit `--reranking --pooling rank` is used instead
- **Paperless AI integration:** `PAPERLESS_AI_LLM_EMBEDDING_*` env vars in `paperless.nix` point to `:8848/v1` with model alias `bge-m3`. Dummy API key `llama-server-no-auth` (llama-server ignores Authorization). Replaces the previous "NO embedding settings" caveat — RAG semantic search is active when both `paperless` and `llama-rag` are enabled. **(DARK since 2026-09-18 — the module is config-disabled pending the upstream soak gate; see the CPU-spin regression bullet below. Reranker leg dropped 2026-10-02, plan A13.)**
- **FastFlowLM `--embed 1` removed:** The `loadEmbed` option has been removed from `fastflowlm.nix`. Co-loading embed-gemma with the Qwen model was broken (xrt ENOMEM). Embeddings are now permanently served by llama-rag.
- **Causal-LM rerankers (Qwen3-Reranker) have a near-zero score bug** in llama.cpp (PR #25448 unmerged). Must use BERT/XLM-RoBERTa-family rerankers like `bge-reranker-v2-m3`
- **Monitoring:** Gatus health checks on `:8848/health` and `:8849/health` (60s interval, <1s response time, Discord-alerting). SigNoz alerts on `node_systemd_unit_state` (active < 1). Post-deploy smoke: 4 checks (2 liveness `/health` + 2 functional `/v1/embeddings` 1024-dim vector + `/v1/rerank` correct ranking). Homepage tile in the AI group
- **`Requires=` the fetch unit:** if HuggingFace is unreachable at boot, the servers do NOT start (no crash-loop) — Gatus alerts on the dead `/health` endpoints instead
- **Verified functional semantics:** `/v1/embeddings` returns 1024-dim vectors; `/v1/rerank` ranks correctly (both probed in post-deploy-check). bge-m3 dims are 1024 — if the model is ever swapped, update the smoke check's dimension assertion
- **Why this exists (2026-08-19 incident):** the module originally shipped with "place GGUFs manually before starting" — nobody did, both services crash-looped to `start-limit-hit` on `failed to open GGUF` at every deploy (silent partial degradation: Paperless AI just disables RAG when the embedding endpoint is down). Declarative provisioning beats manual runbook steps
- **2026-09-04 incident — 20 llama-servers, RAG dark ~2 days:** an flm crash wedged the amdxdna NPU driver so every `open("/dev/accel/accel0")` blocks FOREVER inside `amdxdna_drm_open`. ROCm's libdrm enumeration opens ALL DRM nodes (incl. the NPU accel node — reachable because the service user sits in `video`), so every llama-server start hung in D-state before binding its port. D-state ignores SIGKILL (pending, undeliverable), systemd's stop-timeouts gave up (`Unit process ... remains running after unit stopped`), and EVERY unit restart — i.e. every deploy — stranded another unkillable corpse pair: 10 pairs by 2026-09-04, `llama-server --help` hangs too, load avg ~50 from D-state. Fix: `rocm.deviceCgroup` in `lib/rocm.nix` (`DevicePolicy=strict` + `DeviceAllow` dri/kfd only) — the cgroup BPF rejects the accel open with EPERM BEFORE it reaches the driver. Applied to `llama-embeddings`, `llama-reranker`, and `ollama.service` (ai-stack, same enumeration path; whisper is Docker-device-scoped already). Corpses clear only on REBOOT. Detection: `system_stuck_dstate_processes` (system-health, D-state >1h) + Gatus "Stuck D-State Processes" — fires on the class, not just the endpoints. **Recurrence 2026-09-05 (same 2026-08-31 boot, still no reboot):** a deploy-restart of `llama-embeddings` hung MID-LOAD (972 MB model read, 1.9s CPU over 5m53s — flaky driver state, not IO) and hit the GLOBAL `DefaultTimeoutStartSec=3min` → `Failed with result 'timeout'` → the stop wedged on the unkillable corpses ("remains running after unit stopped") — then the unit SELF-HEALED via auto-restart 9 min later (4s cold load). A start-timeout on these units is usually transient wedgedness: check whether a later restart succeeded before intervening. Also: the permanent D-state corpse pile inflates node IO PSI some to ~73-75% with ALL disks idle (5s diskstats delta ≈0) — a "storm is building" pre-deploy WARN on an idle-disk box is the corpse-pile signature, not real IO; only the owed reboot reclaims both
- **flm's own corpse pins :52626 (EADDRINUSE forever, seen 2026-09-04..05)**: the same wedged-driver incident left the backend's `flm-real` thread group dead MID-EXIT — leader = unreapable zombie (parent PID 1, `Zsl`) + one X-state sibling — and the group's shared fd table keeps the :52626 LISTEN socket pinned after the process is "gone" (1,771 CLOSE_WAITs piled up in its backlog from the proxy probes; there is NO live flm process to kill). Every backend start then dies in <1s with `Error: bind: Address already in use` (mem peak ~78M — never reaches model load) → restart loop → start-limit-hit, and each :52625 client connection re-requests a start ("immediately on client request"). Rootless diagnosis: `/proc/net/tcp` shows the 52626 LISTEN uid=1000; `ls /proc/<zombie-pid>/task/` shows >1 task; `ps -eLo pid,tid,stat,comm | grep flm` shows the Z+X pair (plain `ps aux` cannot see non-leader threads, so the wedge looks like "no process at all"). SIGKILL is meaningless — ONLY a reboot releases the socket. **RECURRED on the 2026-09-07 boot (kernel 7.2.3, post-Samsung-flip)** — the v1.0.2 prefill crash class struck again; the new corpse (PPid 1, 2 tasks) still holds :52626 as of 2026-09-11 (journal: `bind: Address already in use` → start-limit-hit at 07:53; llama :8848/:8849 UP — only flm consumers dark). The reboot is NOT owed anymore — **corpse RESOLVED without one (2026-09-30, verified live)**: zero flm processes, zero listeners on :52625/:52626, bind test green on both ports (PID 1 reaping eventually released the fd table). The empirical check before any flm start is the BIND TEST on both loopback ports, not journal inference; the socket itself stays stopped until `sudo systemctl start fastflowlm.socket`. No module fix exists; do not "fix" the unit for this. **SUPERSEDED IN PART (2026-09-30): a reboot is NOT the only release path** — that morning's pin had a NON-corpse variant: an orphaned ESTABLISHED loopback pair `127.0.0.1:52626 ↔ 127.0.0.1:1411` held by LIVE foreign services (gatus uid 63216 ↔ pocket-id uid 970; no flm process, no zombie, no LISTEN) blocked every bind. Restarting the HOLDER service (gatus) closed the pair; after the 60s TIME_WAIT expired, the backend started clean and served `/v1/models` — no reboot. Distinguisher: corpse = dead flm threads present (reboot-class); orphan pair = no flm process + established pair with foreign uids (restart-the-holder class). Diagnosis is HEX: grep `:CD92` (52626) in `/proc/net/tcp` — a decimal grep false-negatives, and a WRONG hex (`:CDB2` = 52658) false-greens the check forever (a 2026-09-30 stability-row closure carried exactly that bug). Red-herring rule: `curl: (1) Received HTTP/0.9` on the flm port right after a start = usually a memory-emergency-guard Zone-6 kill mid-cold-load, not a bridge bug — check `journalctl -u memory-emergency-guard` for the same minute before debugging the proxy chain. Full narrative: `docs/status/2026-09-30_04-51_fastflowlm-eaddrinuse-orphan-pair-recovery.md`.
- **Two servers is the FLOOR, not waste:** llama-server `--pooling` is a single GLOBAL flag — bge-m3 needs cls/mean pooling for embeddings, bge-reranker-v2-m3 needs `rank` for correct scores. One process — even via the new router mode (`--models-dir`/`--models-max`, present in llama-cpp 0.3.0) — cannot serve both correctly with one pooling value; wrong pooling = silently wrong rerank scores. Revisit single-process consolidation ONLY if per-model pooling config is verified upstream
