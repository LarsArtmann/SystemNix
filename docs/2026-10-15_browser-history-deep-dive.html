00Summary

SystemNix is one of the best-wired consumers in the LarsArtmann fleet: the wrapper module stays thin, upstream owns hardening, and every operational scar since 2026-08 (WDT crash loop, SQLITE_READONLY uid-drift, agent timer races, quiet-day freshness 503) is encoded as gates, heals, or VM-test steps. Version currency is healthy — the deployed binary is the locked rev (fff6034, verified live in /etc/systemd/system/browser-history.service this session), tracking unreleased master deliberately. What keeps this from "perfect": the 2026-10-14 re-attribution was done with manual SQL where upstream ships a replay-consistent claim-orphaned CLI, leaving the event journal un-rewritten and 217 behavioural rows unclaimed; the entire AI suite (llm.* options — summaries, per-user cron digests, themes, and the brand-new chat-with-history) is dark; and three module options are bypassed by unit-level duplicates.

The bottom line No — not "perfectly." The operational layer is superb (9 of 13 capability groups fully leveraged), but one anti-pattern has live residue (journal-inconsistent re-attribution; 217 zero-user rows), the AI feature suite is entirely unconfigured, and upstream moved 86 commits past the lock today carrying chat-with-history and a provider swap. Highest-value action: run the already-dry-run-verified claim-orphaned (+ compact-visit-journal) in one stop-window, then flip the LLM options on.

Anti-pattern · High impact · live residue

Manual SQL re-attribution bypassed the replay-consistent claim-orphaned CLI

docs/status/2026-10-14 re-attribution op · residue: docs/todo/services.md:492 (217 rows), :483 (runbook polish) · tool: api/claim_orphaned_cli.go, cmd/browser-history-server/main.go:29 (in deployed fff6034 since 2026-10-07)

Upstream ships claim-orphaned: rewrites CBOR event payloads so projection replay stays consistent, then claims read-model rows (behavioural tables via UPDATE OR REPLACE), with a replay-consistency proof test. It was dry-run-verified on a backup copy on 2026-10-07 and the live run was queued as Critical (S05, "assert 3179 visits / 135,035 payloads"). The 2026-10-14 owner-authorized op instead did a manual tx UPDATE on the visits table: 3,179 rows moved, but the event journal stayed zero-user (the op report's own "replay caveat"), and 217 zero-user behavioural rows remain (searches 125, downloads 58, forms 20, bookmarks 7, permissions 5, omnibox 2). A future full replay (wipe + rebuild — exactly the recovery path the backups exist for) would resurrect zero-user ownership. The CLI was built for precisely this job and was in the deployed binary at op time. 

# What ran (manual, journal-inconsistent):
#   stop-window tx UPDATE visits SET user_id=<owner> WHERE user_id IS NULL/zero
# What was available and verified on a backup copy:
sudo systemctl stop browser-history.service
browser-history-server claim-orphaned \
  -db /var/lib/private/browser-history/data.db \
  -user-email lars@larsartmann.cloud -yes   # rewrites events + claims rows
browser-history-server compact-visit-journal -yes -vacuum
Recommendation Fold the 217-row cleanup into one stop-window: pool backup → claim-orphaned (dry-run first, assert 217 + 3179-consistent) → compact-visit-journal -vacuum → health-poll-until-200. This closes blocked:user row 492 AND heals the replay caveat the manual op left behind. The already-queued runbook-polish row (:483) should reference the CLI, not a hand-rolled tx template.

modules/nixos/services/browser-history.nix:261-271 (option block sets no llm.*) · upstream: nix/server-module.nix:296-313 (llm.model/baseUrl/timeout), :437 (searchThemeKeywords), LLM_API_KEY via environmentFile

Partially Used · Medium impact

Three module options bypassed by unit-level duplicates

browser-history.nix:286 (LOG_LEVEL=debug env) vs upstream logLevel option (server-module.nix:275) · :481 (User = primaryUser) vs upstream agent user option (agent-module.nix:40) · :283 (EnvironmentFile unit-level) vs upstream environmentFile option (server-module.nix:458)

The wrapper sets Environment = "LOG_LEVEL=debug" at unit level while the upstream module also renders LOG_LEVEL = cfg.logLevel (default "info") — two sources of the same variable, resolved only by systemd's last-assignment-wins plus Nix list-merge order. It works today because the wrapper's definitions concatenate after the imported module's, but that is implicit ordering, not configuration. Same pattern for the agent's User (upstream grew a proper user option on 2026-10-06, after this wiring was written) and for environmentFile. 

# Fragile: unit-level duplicate (last-wins by merge order)
Environment = [ "GOMEMLIMIT=384MiB" "LOG_LEVEL=debug" "MAX_USERS=1" ];
# Explicit: the option the upstream module owns
services.browser-history.logLevel = "debug";
Recommendation One tidy-up commit: logLevel via option, agent User via services.browser-history-agent.user, sops file via the environmentFile option. GOMEMLIMIT and MAX_USERS stay unit-level — upstream exposes no options for them.

Partially Used · Low impact

Two freshness clocks, 30m vs 60m, with a known quiet-day wart

upstream agentFreshness default 30m (server-module.nix:444, unset) · SystemNix agentActivity.maxAgeMinutes=60 (browser-history.nix:188-214) · open [ready] docs/todo/services.md:71

The server's /health freshness gate uses the upstream default 30m while SystemNix's own zero-agent alert allows 60m — two clocks for one concept, so gatus can be red on agent-data while /health already 503-degrades (or vice versa on a quiet browsing day, the known empty-batch heartbeat bug — fix belongs upstream).

Recommendation Set agentFreshness explicitly to match maxAgeMinutes (or derive both from one let-binding) until the upstream heartbeat fix lands.
