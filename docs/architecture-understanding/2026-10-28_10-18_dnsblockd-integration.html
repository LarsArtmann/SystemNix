Architecture Review

Is the dnsblockd integration superb?

Deepest per-service operational surface in the tree — runbook, discriminator, measured readiness budget, OOM immunity, five-layer monitoring. Capped at good, not superb, by one structural decision: it re-implements the upstream NixOS module instead of consuming it.

The one-sentence verdict

This is operator-grade integration — the runbook alone records five distinct incident classes with journal-measured budgets — but it is architecturally capped: modules/nixos/services/dns-blocker.nix (1,494 lines) hand-rolls a config renderer for a service that ships its own 2,224-line NixOS module (options split by theme, renderer, assertions, two VM tests) at the exact rev already locked. Every upstream capability added since 2026-10 is invisible to Nix until someone edits a Nix attrset by hand.

01Findings

What is genuinely superb (and rare)

Failure-class memory. docs/services/dnsblockd.md carries a 5-phase startup discriminator, the journal-measured readiness budget (300s poll inside a 330s envelope, sized against a measured 255.5s healthy tail — the two previous guesses, 60s and 150s, both sat inside the healthy distribution), the oomd kill-loop history (730 kills/day), the block-page phantom-200 diagnosis, the NetBird tunnel-IP hijack proof matrix, and the gatus-watches-itself-with-the-watched caveat. That is a runbook written from incidents, not from documentation.

Guard depth. 22 eval assertions mirror upstream caps (256 devices / 16 IPs, 64 policies / 512 domains / 16 windows, dup ids, dangling refs, single ownership, schedule shape, ECS prefix range, h3-requires-tls, filter-needs-address). tests/test-dns-blocker-render.nix (446 lines) both pins the real rendered YAML and negative-tests every assertion by forcing the failing variant and requiring the message.

What keeps it from superb

Split schema. The upstream module is the schema of record; the wrapper is a second, smaller schema. Live config proves the gap: gateway_* (ADR-0011 interception gateway, shipped 2026-10-17), cluster_* (HA fabric), dns_doq_enabled, dns_doh3_*, dns_qname_minimization_level, dns_circuit_breaker_*, retention_*, tracking_batch_*, dashboard_sse_*, dhcp_lease_file, pprof_enabled, allow_sibling_domains — all present at the locked rev, none reachable from services.dns-blocker.

Re-implemented readiness. The deployed binary already calls sdnotify.Ready() after srv.Startup() — listeners bound, probe gate passed. The wrapper overrides Type = "simple" and substitutes a 300s ss -ltn poll for the block-page port (80), never the DNS contract (:53 TCP/UDP).

02Issue Cards

Structural

Upstream module not consumed — documented doctrine, broken in the largest service

modules/nixos/services/dns-blocker.nix:1-1494 · ~/projects/dnsblockd/nix/modules/nixos/{config,options/*,assertions}.nix

docs/agents/integration-registry.md states the rule plainly: when an upstream LarsArtmann flake exports nixosModules, always consume the upstream module — never hand-roll a parallel one, with monitor365.nix named as the gold standard. dnsblockd exports nixosModules.default and .dnsblockd. The wrapper still re-declares the schema in camelCase (blockIP vs upstream block_ip), so a migration is now a 53-option rename plus a user-identity decision — the longer it waits, the wider the gap.

Fix Migrate to inputs.dnsblockd.nixosModules.dnsblockd and delete the render block; keep only SystemNix-owned layers (sops env, gates, ioTier, onFailureP0, ports, registry entry). Re-tag the queue row: its stated blocker is falsified (see Evidence E7).
Availability

The readiness gate proves port 80, not DNS

modules/nixos/services/dns-blocker.nix:1346-1367 (listenerWait) · :1383 Type = "simple"

ss -ltn | grep ":${cfg.blockPort} " polls the block-page listener. The service contract is resolution on :53 (UDP and TCP). Two blind spots follow: (a) ss -ltn is TCP-only, so a UDP-only :53 failure is invisible to the gate; (b) nothing in the gate names port 53 at all. The 2026-10-12 wedge is caught only incidentally — that wedge bound no listeners whatsoever.

Fix Adopt upstream Type = "notify" (add AF_UNIX to RestrictAddressFamilies, drop the poll) — or, as a one-line interim, extend the poll to ss -ltnu and match :53.
Security

The sole resolver and its L7 proxy run as root

live unit: no User= · upstream config.nix:256-259 (cfg.user/group, CAP_NET_BIND_SERVICE)

The deployed unit has a strong sandbox (ProtectSystem=strict, syscall arch native, three address families, NoNewPrivileges) but no User=: the process that parses untrusted DNS, TLS SNI, and HTTP is root. Upstream creates an unprivileged dnsblockd user and relies on CAP_NET_BIND_SERVICE, which the wrapper already grants — so the privilege is not needed.

Fix Owner decision (already recorded in the queue row): adopt upstream's user with a one-time chown -R dnsblockd:dnsblockd /var/lib/dnsblockd heal, or override user = "root" explicitly so the choice is visible.
Observability

The OTel leg is dead and self-blinding

/health: otelInternalErrors=40667 · journal: 903 × “Post http://localhost:4318/v1/…: connection refused” this boot

signoz-collector.service is the known 2026-10-27 outage (fix in tree, undeployed), so :4318 is dark. The integration-level lesson is separate: services.signoz-coverage.expected.dnsblockd.wiring = "config" still asserts the leg works, and the only signal that it does not — dnsblockd_otel_internal_errors — travels through the same broken exporter. The watcher dies with the watched, again.

Fix Deploy the collector fix; then add a collector-independent assertion: a textfile metric (or gatus check) on otelInternalErrors sampled from 127.0.0.1:9090/metrics — the stats API survives exporter failure, which is exactly why it is the right vantage point.
Durability

The one owner-curated dataset has no backup

allowlist_path=/var/lib/dnsblockd/allowlist · snapshots.nix:393-413 (only hot/forgejo is btrbk-covered)

The permanent allowlist (dashboard “Always allow”, POST /api/allowlist, Likely-Broken-Sites bulk flow) is the fix for the daily data-loss bug documented as max-adoption finding #1. It now persists — onto hot/dnsblockd, a Samsung subvolume that is deliberately outside every snapshot set (doctrine C). tracking/journal loss is acceptable analytics loss; the allowlist is a few hundred bytes of human judgement that cannot be regenerated.

Fix Add a tiny oneshot (or a btrbk subvolume entry) that copies allowlist into /var/backup/ — snapshot-covered, pool-shipped.
Correctness of the record

Runbook drift: two claims falsified by live state

docs/services/dnsblockd.md:140-145

(1) “Open anomaly: TWO tracking DBs coexist” — the live data dir holds one tracking.db (2.55G); the 724M dnsblockd_tracking.db is gone. (2) “Both retention surfaces bounded (30d)” — actual upstream defaults (no keys rendered) are tracks 30d / metrics 90d / block-rate 365d, correctly stated in dnsblockd-tracking-dial.md but not here. Also undocumented: trust-anchor.db / trust-anchor-tombstones.db (0600 root) now live in the data dir.

Future-proofing

Split-brain CA trust with no parity guard

platforms/nixos/system/dns-blocker-config.nix:244-278 (inline PEM) vs sops dnsblockd_ca_cert

The same CA exists twice: a PEM literal in the repo and a sops secret. Parity holds today (verified this session: identical SHA-256 fingerprint), but nothing enforces it. The first CA rotation silently breaks browser trust and the filter-proxy “scoped lie”, which needs devices to trust that CA.

Fix One line in scripts/post-deploy-check.sh: compare openssl x509 -fingerprint -sha256 of the PKI cert against /run/secrets/dnsblockd_ca_cert.
Freshness

Blocklists are eval-pinned with no staleness signal

platforms/common/dns-blocklists.nix (SRI over mutable gitlab main) · scripts/dns-update.sh

SRI pinning is the right call (content drift fails the build loudly), but it makes freshness a manual act: scripts/dns-update.sh has no timer and no telemetry. Upstream's native runtime fetcher (dns_blocklist_urls + dns_blocklist_cache_dir) is unreachable from the wrapper, which wires the cache dir only for trial URLs. Every other artifact in this integration reports its age; the blocking data itself does not.

04Roadmap

P0

Make the readiness gate test the contract

Interim: ss -ltnu and match :53 in dnsblockd-wait-listener. Proper: Type = "notify" + AF_UNIX, delete the poll. One deploy, one render-test line.

P0

Give the OTel failure a collector-independent observer

Deploy the signoz project_id fix (already in tree), then sample dnsblockd_otel_internal_errors from :9090/metrics into a textfile metric + gatus check. Extend the existing “4318 refused journal spam” queue row to carry this second half.

P1

Migrate to nixosModules.dnsblockd

Unblock a queue row that is already unblocked: csrf_enabled and blocklist_files exist at the locked rev. Sequence: owner decides user identity → map 53 options → adopt upstream VM test → FOD probe → deploy → verify 110-key parity. Subsumes P0 #2 and unlocks gateway/cluster/DoQ/retention for free.

P1

Back up the allowlist

Copy /var/lib/dnsblockd/allowlist into a snapshot-covered path on a timer. Smallest irreversible-data fix in the whole integration.

P2

Add the two cheap parity/freshness guards

CA fingerprint parity in post-deploy-check.sh; a blocklist-age metric (max mtime across dns_blocklists) with a gatus threshold, and a calendar reminder to run scripts/dns-update.sh.

P3

Finish the registry inversion

Move the three DNS gatus checks into services.integration.dnsblockd.checks and document the vHost exception where the registry can see it.
