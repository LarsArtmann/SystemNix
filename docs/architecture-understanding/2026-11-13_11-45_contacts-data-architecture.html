Deep Review · Contacts Data Architecture

Seven surfaces, one declared owner, zero runs.

The Mesh B doctrine (Stalwart owns contacts, Google is an edge, Kith is a relation store) is sound. What exists on disk is different: the owner is unprovisioned, a second live address book sits inside webphone, and the glue that was supposed to connect everything has never executed on evo-x2.

Verdict

The architecture you are asking for already exists on paper: one DAV hub (Stalwart), one glue service per external edge (pim-sync for Google People and Calendar), and read-only consumers (Kith, webphone, InboxClean, devices). The failure is execution and inventory, not design. Stalwart's address books are declared but not provisioned; pim-sync is flip-ready but disabled; webphone quietly runs an independent contacts store with a write API, a deploy-time shared list, and no phone normalization; InboxClean is a writer of people observations, not just a reader. Adding Radicale would make this worse, not better.

Recommendation in one paragraph

Keep Stalwart as the only contact truth. Do not deploy a second DAV server (Radicale, Baïkal, DAViCal). Make pim-sync stay exactly what it is, glue, and give it the two things it lacks: an append-only run receipt per execution and a doctor command. Then classify every other surface in one registry as truth, edge, projection, consumer, or cache, and retire the write authority that does not belong (webphone's local book) or declare it explicitly as device-local.

01Do we have a log of what it did?

No. There is nothing to log yet.

pim-sync has never run on evo-x2. The enable flag is false (platforms/nixos/system/configuration.nix:917), no unit exists in the running system, and no state directory, metrics file, token or receipt exists on the host. Upstream is also explicit that an enabled unit without tokens would fail every five minutes, which is why the disable is deliberate (docs/services/pim-sync.md).

What will be the log after the flip

Three sources, none of them a change ledger: per-leg counters in a Prometheus textfile (changes, conflicts, quarantined, quarantine_depth, last_success_unix); per-account atomic 0600 JSON state holding sync tokens, quarantines and provenance; and journalctl -u pim-sync for run output (pim-sync/docs/CONTRACT.md §Observability, docs/CONTRACT.md:75).

That answers “did it run and how much”, not “who changed which card at 10:42”. Mesh B deliberately traded the Kith journal's actor-attributed provenance for a cleaner storage boundary; the lineage has to be rebuilt somewhere, or the first disputed contact has no evidence behind it.

Two details make the gap sharper than it looks. Dry-run is the default and --live is the only write switch, so a dry-run writes nothing at all — no state, no receipt, no journal entry beyond stdout. The per-account report is printed to stdout and never persisted (cmd/pim-sync/report.go:10-45), so yesterday's run is gone. Logging is operator-facing slog text on stderr, not a change record; the durable evidence is the textfile gauges plus whatever systemd captured.

Fix Emit one append-only JSON receipt per run (leg, account, counts, UIDs touched, cap/quarantine decisions, actor) and either ship it to the CRM journal as audit events (bot:pim-sync:<acct>) or keep it as a rotated file with a Gatus freshness check. Truth stays in Stalwart; lineage comes back.

04Findings

Blocking

F1 · webphone is a second, live address book

webphone/internal/cqrs/contacts.go:1-40,197-228 · internal/server/contacts_api_test.go · package/options.nix:22

Contacts are a real aggregate in webphone's event store: per-owner streams, an upsert keyed by (owner, phone), delete by ID, a 500-contact cap, and a rename that keeps identity. The projection lives in /var/lib/webphone/system.db (webphone/internal/app/cqrs.go:83-90), and a second, deploy-time shared list lives in config.contacts[] (pbx-artmann/hosts/pbx/default.nix:934-948). Import and export are vCard 3.0, deliberately lossy: first TEL only, no emails, and the full name is written into the family-name slot (internal/vcard/vcard.go:16-19,78-97). Nothing syncs either copy anywhere. The CRM lane is separate and read-only: a memoized GET /api/contacts/by-phone lookup (6 h positive / 5 min negative cache, no invalidation) plus a fail-open context resolver (internal/crm/resolver.go:18-22,120-170, internal/crm/context.go:84-88); webphone logs calls onto existing CRM contacts but never mints them (internal/crm/client.go:276-311).

This is the single largest architectural fact in this review, and it is not in the mesh document. A naive sync between this book and Stalwart would create a feedback loop: two writable stores, two ID spaces, one human.

Fix Decide explicitly: either (a) device-local/private book, never synced, with the UI saying so, or (b) a retired writer whose tab reads the canonical store. Do not build a bidirectional spoke between two writable books.
Blocking

F2 · The declared truth is not provisioned

pbx-artmann/docs/architecture/data-ownership.md:118 · docs/agents/data-ownership.md:34

Stalwart owns contacts by decision, but the mail host's declarative plan carries no address-book object family. The collections exist, if at all, as runtime state inside the store and are pinned by no gate. The nightly archive exists; the PII restore drill does not.

Fix Provision address books declaratively (demo VM first, then the host), then run the restore drill and stamp the receipt into the data-ownership row. A truth you cannot restore is a second copy of Google with extra steps.
Blocking

F2b · “One book per source” is load-bearing, not a preference

pim-sync/internal/contactsin/quarantine.go:45,65,124 · cmd/pim-sync/account.go:169-172 · internal/guard/guard.go:80-100 · cmd/pim-sync/sync.go:30

The IN leg treats the whitelisted book as its book: a full Google listing quarantines every card present in the book but absent from that listing. A card that belongs to another source, or one the owner typed by hand, becomes a deletion hold — and clearing it deletes the card. The --book override applies to every Google account at once, so two accounts can be collapsed onto one book and both then claim the whole collection. In addition, the change cap is enforced in dry-run too, and it defaults to 50: a fresh book projecting more than 50 creates aborts with exit 3 even without --live (internal/guard/guard.go:80-100, cmd/pim-sync/sync.go:30).

This is the structural reason not to merge several sources into one address book, and the reason a multi-source DAV server looks attractive and is a trap: it invites exactly the shared-collection model this glue cannot safely own.

Fix Keep one book per source (personal, work, twenty, imports), never share a book across accounts, and set the first run's cap above the card count so an import cannot block the flip. Record the rule in the runbook before anyone “tidies” the books together.
Blocking

F3 · Zero runtime evidence for the whole mesh

platforms/nixos/system/configuration.nix:917 · pim-sync/docs/CONTRACT.md:75

Not one leg has executed against a live Google account or a live Stalwart book. The code is tested against fakes and a demo VM, and the 139-person rehearsal ran against an in-memory fake CardDAV server, not the production book. pim-sync doctor now exists (read-only pre-flight: token shapes, state dir, caps; cmd/pim-sync/doctor.go:16-45, registered at cmd/pim-sync/main.go:44) but it deliberately makes no Google API call and has never run with real credentials, so the first live failure still lands in a oneshot's stdout.

Fix Ship the receiver before the sender: receipts + metrics + doctor, then a dry-run timer, then one live leg with a change cap.
Important

F4 · InboxClean writes people, and keeps side identities

InboxClean/internal/crmsync/people.go · internal/crmfeed/feed.go:34-50 · internal/papersync/pipeline_upload.go:65

InboxClean owns no contact store, but it is not passive either: it aggregates senders and recipients, optionally enriches them with an LLM, and pushes 500-observation batches to the CRM. It also keeps a shadow list of already-extracted addresses in cqrs_kv and creates Paperless correspondents from sender display names. The matching ladder lives in the CRM, which is the right place, but the side lists are unowned identity data.

Fix Classify it as a hint source with a cap and an actor, delete the per-sender shadow list once the canonical store can answer “known person?”, and treat Paperless correspondents as presentation labels, never as the booking of a person.
Important

F5 · Two Google accounts produce duplicate humans, by construction

pim-sync/docs/CONTRACT.md:35-40 · crm/docs/DATA-MESH.md:47

UID = a stable hash of google:<account>/resourceName, scoped per account. That is correct for collision safety and wrong for identity: the same person in personal and work Google becomes two vCards, two projections and two phone owners. Nothing in the mesh defines a cross-account link rule. Underneath it, webphone has no phone canonicalization either: the store key is the sanitized string, so +4930… and 030… are two different contacts (webphone/internal/domain/ids.go:63-101, exact-string server lookup at internal/server/crm.go:62-68).

Fix Adopt an explicit identity rule at the projection layer: one person per normalized email/phone, cards linked not merged (RELATED/external IDs), with a duplicate report the owner can review. Do not merge cards inside Stalwart: pim-sync has no merge and never invents data, duplicates are reported only, and conflicting values are counted, not queued for review (pim-sync/README.md:138, docs/CONTRACT.md:63-65).
Important

F6 · Consumers read a projection of a projection, with no freshness bound

webphone/internal/crm/context.go:165-191 · crm/docs/ops/CARDDAV-PROJECTION.md:57

Caller-ID in webphone resolves through the CRM by phone number, cached for 6 hours with no invalidation hook; the CRM's people are a read-only projection of Stalwart. That is three stores between a phone number and a name, with no staleness SLO. It fails open, which is good for calls and bad for trust: a missing name looks like an unknown caller. The surfaces also disagree with each other — call history prefers the PBX-supplied caller name, list views try personal contacts before the CRM, the in-call panel reads the CRM only, and the mobile ring push carries no name at all (internal/pbx/client.go:96-107, internal/server/crm.go:46-101, internal/server/livecontext.go:40-75, internal/push/push.go:86-88).

Fix Declare the chain and its bound: projection runs after each pim-sync window, a freshness metric per hop, and a UI hint when the projection is older than N minutes.
Important

F7 · Identity exists in four places in the PBX deployment alone

pbx-artmann/hosts/pbx/default.nix:934-948,977-988 · webphone/internal/store/db.go:218-225

The deployed host defines people three times before any contact store is involved: the shared contact list, the passkey-user map, and the Pocket ID / Stalwart account roster. webphone adds a fourth (the CQRS projection) plus a dead legacy SQL contacts table that is still created on every fresh database and has no production reader. Its ROADMAP also declares contact depth to be Ledger's domain while the surface people actually edit keeps writing locally, with no write path into the CRM.

Fix One identity map per deployment, referenced by all four surfaces; a deterministic link key (normalized E.164 + email); and a scheduled DROP for the dead legacy table so nobody reintroduces it as a “migration”.
Security

F8 · The shared contact list is served before authentication

webphone/internal/server/server.go:683,870 · internal/server/platform/configjs.go:86

/config.js is mounted on the unauthenticated mux and embeds the operator's shared directory (names and numbers). That is personal data with no session gate, and it is also a second copy of identity that no contact review would find unless it looks at the deploy config rather than the database.

Fix Serve the shared directory only to authenticated sessions, or move it behind the CRM/directory read path entirely.
Nice to have

F9 · OpenCloud is not a contact surface, and Radicale is not the missing app

docs/services/opencloud.md:1-10 · radicale.org v3 documentation

OpenCloud is deployed as a file platform. Radicale is a CalDAV/CardDAV server with filesystem storage, htpasswd / LDAP / IMAP / OAuth2-relay authentication, sharing and Git-versioned collections. It has no contacts application; its documentation delegates the UI to clients (DAVx5, GNOME, Evolution, KDE PIM, Thunderbird, InfCloud). Deploying it would add a fourth DAV endpoint, a fourth auth path and a fourth backup leg to solve a UI problem.

Fix Keep OpenCloud files-only. If a web contact UI is the actual need, pick a client (the already-deployed Stalwart webmail reads JMAP contacts; InfCloud or CardDavMATE can front CardDAV) and never a second store.

On “a dedicated service where pim-sync is only glue”

That is exactly the current design, and it is correct. The dedicated service is Stalwart; pim-sync is the adapter. What is missing is not another daemon but the operational layer around the existing pair: provisioning, receipts, a duplicate report, and a declared consumer contract. Adding Radicale would invert the pattern, giving you two dedicated services and no single truth.

06Target architecture

Stalwart CardDAV/CalDAV (pbx) — the ONLY contact writer
  ├── pim-sync glue → Google personal (People API, in + field-scoped out, caps, quarantine)
  ├── pim-sync glue → Google work (same contract, separate state)
  ├── Kith projection (read-only links; relations, deals, calls stay in the journal)
  │    ├── webphone caller context (read-only, memoized, freshness-bounded)
  │    └── InboxClean routing (roster read; people hints flow the other way, capped)
  ├── Devices: phone / desktop via CardDAV (DAVx5, GNOME, Thunderbird)
  ├── Webmail (JMAP contacts: agenda, birthdays)
  └── Audit spine: run receipts → journal events (bot:pim-sync:<acct>)

webphone local book — decide: device-local, or retire writes
Radicale / second DAV server — not deployed
Paperless correspondents — display labels, never person identity

Four rules that make the diagram enforceable

1. Exactly one write authority per entity type, named in the registry before the first line of client code.
2. Every edge has a direction, an actor, a change cap and a deletion quarantine — no exceptions for “small” accounts.
3. Every consumer is read-only and declares its maximum staleness. A consumer that needs to write becomes a spoke or it does not write.
4. Every run leaves a receipt. Aggregated counters are not evidence of what changed.

07Roadmap

P0

Stop the bleeding: classify and freeze surfaces

Add all seven rows to docs/agents/data-ownership.md with class (truth / edge / projection / consumer / cache), direction, actor and kill switch. Decide webphone's book in the same change. This is documentation only, and it is the highest leverage hour in the project.

P0

Provision the truth and prove the restore

Declare the address books (and calendars) in the mail host plan, demo VM first; then run the PII restore drill and record the receipt. Until this lands, “Stalwart owns contacts” is a sentence, not a fact.

P0

Give pim-sync a memory

Ship per-run JSON receipts (leg, account, counts, UIDs, caps, quarantines, actor), the quarantine-depth gauge, and pim-sync doctor before the first enabled timer. Then flip it dry-run only.

P1

Define person identity across accounts

Normalized email/phone as the link key; one person, many cards; duplicates reported, never silently merged. Run the report against the 139 staged people and both Google accounts before enabling outbound writes.

P1

Fix the consumer chain

Webphone: local book becomes device-local or is retired; E.164 normalization lands before any sync; the shared config list moves behind authentication; caller context keeps its read-only path with a freshness bound. InboxClean: hint source with a cap; delete the shadow extracted list once the hub can answer by email.

P2

One Google account, outbound, behind a canary

Field-scoped writes, per-run cap, deletion quarantine, dry-run diff reviewed by the owner. Second account only after the first has run clean through one full sync cycle.

P3

Re-evaluate Radicale only against a written requirement

If a device or client cannot speak Stalwart's DAV dialect, write the failing requirement down first. If Stalwart satisfies it, there is nothing to deploy.
