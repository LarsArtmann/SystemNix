Architecture Review · Service Orientation

Thin Platform, Fat Services

The repo already has module-per-service and registry options — but every integration is still a row in a horizontal god file. One logical service scatters across 8–22 files. The fix is inverting integration ownership, not restructuring the tree.

The one-sentence diagnosis. Service modules own their daemons but not their wiring: vHosts, health checks, dashboard tiles, DNS names, secrets, backups and OIDC clients are all declared inside six shared "layer" files that every service must edit — the exact coupling the registries were built to remove, left unadopted.

01Findings

1 · Integration inversion — the core structural debt

The natural owner of "forgejo's vHost is plain on port X" is forgejo.nix. Instead it lives in caddy.nix; its health checks live in gatus-config.nix; its tile in homepage.nix; its OIDC client in pocket-id.nix; its sqlite staleness logic (70+ lines) in system-health.nix; its secret template in sops.nix; its mirror list and backup entry in configuration.nix. Adding a service in AGENTS.md is an 11-step tour across horizontal files. Change ripple: a service question like "which files does forgejo touch?" (asked today) needs a repo-wide grep to answer — 18 files.

2 · Registries exist but have zero adoption

services.caddy.extraVHosts (caddy.nix:110) and services.gatus-config.extraEndpoints (gatus-config.nix:151) were built exactly for service-owned contributions. Grep across all service modules: 0 files use either. Every vHost and endpoint is still hardcoded inside the god files, and no service module writes into services.caddy.* at all. The architecture is half-migrated and the new direction is unproven.

3 · homepage.nix has no registry — it is the worst offender

28 hand-maintained fooEnabled = config.services.foo.enable or false bindings, one per service, then lib.optional gates per tile. Every new service edits this file forever. The groups single-source-of-truth pattern inside it is good — but the tiles themselves can only be added centrally.

4 · God files concentrate unrelated churn

gatus-config.nix 2,479 lines (every service's checks), system-health.nix 1,616 (per-service sqlite/journal readers inline), configuration.nix 1,038 (enables + backup-coordination + guards), pocket-id.nix 785 (every OIDC client), homepage.nix 773, sops.nix 753. These are merge-conflict and parallel-session hotspots by construction (the repo runs concurrent agent sessions — AGENTS.md documents the race rules).

5 · Flat namespace with unique-filename constraint

Auto-discovery maps filename → module name, so names must be globally unique across services/ and desktop/. Helper files hide behind _: forgejo's 723-line script file is _forgejo-scripts.nix — invisible ownership, name does not say "forgejo" in discovery terms. At 85 files this is friction, not breakage — but it caps discoverability ("where does X live?" relies on grep, and the answer is: everywhere).

The fix: policy stays central, data becomes service-owned

Keep the horizontal files as thin platform renderers: caddy.nix still owns TLS headers, proxyTo, the protected/plain policy, and renders extraVHosts into real vHosts. gatus-config.nix still applies withPapIngest, alert defaults, and the pat() lint — but endpoints arrive as contributions. homepage.nix gains the one registry it lacks. The NixOS module system merges attrsets for free; every service module already sits in the same flake-parts module set, so a service module can write services.caddy.extraVHosts with no new plumbing. "Add a service" collapses from ~9–11 files to 2–3.

today ├── service module ── daemon only ┐ god files own vHost/tile/checks/dns/secrets ← every service edits them
target ├── service module ─ daemon + all its rows in registries ┐ thin renderers apply POLICY (TLS, alert pass, lint) to contributed DATA
Constraint to respect: the gatus pat()-lint in flake.nix greps gatus-config.nix's source text directly (flake.nix:942–987). Migrating endpoints into service modules must extend that lint to every contributing module (or the rendered settings) in the same change, or the phantom-green trap class loses its guard. Same check applies to the CI/eval audits that read file paths: audits reading config are migration-safe; audits reading source files are not.

04Roadmap

1

P0 · Give homepage the registry it lacks effort S

Add services.homepage.tiles (list of tile attrsets; groups derived as today). Migrate 3 tiles as proof. This is the only integration surface with NO escape hatch today.

2

P0 · Pilot inversion on the NEXT new service zero risk

No migration required: the next service added wires itself entirely through the existing registries (caddy extraVHosts, gatus extraEndpoints, backup-coordination from its own module). Proves the pattern on a real service and deletes the "edit 9 files" procedure for all future services. Add dns-local.subdomains + pocket-id.oidcClients contributions if not yet options.

3

P1 · Migrate highest-churn rows out of the god files impact

Move per-service gatus endpoints (biggest file, 2,479 lines) into owning modules, batch per service. Land the lint-coverage change (flake.nix:942–987) with the FIRST batch. Then homepage tiles, caddy vHosts, and system-health's per-service readers (forgejo mirror block, 70+ lines, belongs in forgejo's module).

4

P1 · configuration.nix → pure enable manifest

backup-coordination entries, monitoredServices, sops owner guards move into owning modules with mkDefault (host overrides still win). Target: ~1 line per service, host-specific deltas only.

5

P2 · Optional: per-service directories mechanical

modules/nixos/services/forgejo/{default,scripts}.nix — kills the global filename-uniqueness rule and the _-prefix hiding (the 723-line _forgejo-scripts.nix). Requires flake.nix discovery change (one module per dir) and relative-import fixes across moved files. Do it opportunistically per service, or not at all if flat+grep is preferred — it is the least important item.

6

P3 · pkgs/ co-location for single-consumer packages

pkgs/ is flat and fine for cross-cutting tools; but single-consumer packages (fastflowlm.nix, openseo.nix) could live beside their service module. mkLarsPackages (lib/lars-packages.nix) is already the right single source of truth for the Go ecosystem — leave it.

05Strengths to keep

+
Module-per-service + auto-discovery. Daemons are genuinely isolated, one file each, upstream-module consumption pattern (discordsync/monitor365) is textbook.
+
Composable platform primitives. harden, protectedVHost, proxyTo, mkHttpCheck, ioTier, mkOidcGate/mkDnsGate, mkDockerService — policy as reusable functions, exactly right.
+
Registries + eval-time guard layer. ports.nix, the audits, the VM tests — prevention reads config, so most guards survive the proposed inversion unchanged.
+
Single-source-of-truth derivations. homepage groups→layout, backup-coordination→gatus — derive, never hand-write the derived artifact.
